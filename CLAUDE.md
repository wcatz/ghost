# Ghost — MCP Memory Server

## Stack
- Go 1.26+ CLI application
- SQLite with FTS5 for memory persistence (modernc.org/sqlite — pure Go, no CGO)
- CLI harness callers (claude/opencode/codex/goose subprocesses) — used by reflection, resolve, and supersede. Each harness owns its authentication and billing; Ghost does not add a direct API client. The prompt is written to the child's stdin and no positional message is passed: the kernel caps one argv element at 32 pages (128 KiB on a 4 KiB-page x86, 512 KiB on a 16 KiB-page one) and a reflect prompt reaches megabytes, so an argv prompt failed the spawn with E2BIG instead of answering. `claude -p` and `opencode run` read the message from a pipe when none is given; codex gets `exec -` and goose `run -i -`. `claude --system-prompt` stays an argument — small, fixed, and never confusable with user content. `cli.model_reflect` / `model_resolve` / `model_supersede` pin the opencode harness model per phase (each phase is its own process; ignored by claude/codex/goose which have no model flag). Empty = any inherited `GHOST_OPENCODE_MODEL`, else Ghost's explicit `opencode/big-pickle` default; a configured pin overrides an inherited env pin for that phase.
- MCP server via modelcontextprotocol/go-sdk (stdio transport)

## Architecture
- `cmd/ghost/main.go` — CLI entrypoint; subcommands: mcp, hook, reflect, resolve, supersede, project, obsidian, bench, backup, export, import, upgrade, version, context. `runCLI` answers `-h`/`--help` (`cmd/ghost/help.go`, one usage table) before the dispatch, so a help request has no side effect. A command line the dispatch cannot route — an unknown command, a missing or unknown subcommand, no command at all — is `usageError` on stderr (the diagnostic, then that level's own usage) and exit `2`, the conventional usage-error code, kept distinct from the `1` every command uses for a run that started and failed (#691; bare `ghost mcp` still starts the server, the one group with a default action). Only the groups in `commandGroups` dispatch on a subcommand word: a word after a command that takes an OPERAND (`ghost history <memory-id>`, `ghost reflect <project>`) is data and its parser's business, and an unknown FLAG is that parser's too — exit `1` where it rejects one (`ghost reflect` still ignores it, as it always has)
- `internal/adversarial/` — Test-only support: the shared hostile-input corpus (prompt injection, secret shapes, invisible-character tricks, path shapes) and the shared inert-content invariant the three untrusted parse surfaces assert against (#585). Nothing under `cmd/` may import it; it exists to be called from `_test.go` files. The invariant in one sentence: a value parsed from an untrusted surface is data — stored exactly as parsed, naming at most one path component inside the directory its surface owns, and never deciding the parse. `internal/mcpserver/adversarial_test.go` (#538) proves the same invariant one layer out, over the wire
- `internal/ai/` — CLI-harness providers (`CLIClient`/`OpenCodeClient`/`SourceProvider`) used by reflection + resolve + supersede — no Anthropic HTTP API client. Every child is spawned through the one `harnessCommand` funnel, which applies the `harnessEnv` allowlist and confines the working directory and temp variables to an invocation-owned scratch dir. The backend is part of the policy, so each harness keeps only its own auth/config root (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, the safe `GOOSE_*` set, `OPENCODE_API_KEY`). Two harnesses additionally get an isolated config tree because their plugin/MCP discovery would otherwise find Ghost's own registration: opencode gets a fresh home plus an `mcp: {}`/`plugin: []` config, and goose gets an empty invocation-owned `HOME` (its plugin root is home-relative by specification, so `XDG_CONFIG_HOME` alone cannot move it). The goose home carries the config rather than restating where it lives — the inherited `XDG_CONFIG_HOME` when set, otherwise reproducing each home-relative root goose may resolve (`.config/goose`, `Library/Application Support/goose`; Windows uses `%APPDATA%`, which the allowlist already passes through) — so goose's own per-platform resolution is untouched and authentication still works. `GOOSE_PATH_ROOT` is the exception: goose consults it before any home variable (plugins resolve to `$GOOSE_PATH_ROOT/.agents/plugins`), so it is repointed at a root inside the isolated tree with the real `config/` carried into it, and a relative value is left alone because goose ignores one. Where a symlink is refused (Windows without Developer Mode) the files are copied instead. If the home cannot be established, the call fails rather than running with the real home. Codex needs no tree — `--ignore-user-config` already covers it. OpenCode's tree also owns a DATA root (`XDG_DATA_HOME`), which is what keeps a lifecycle run out of the user's session list (#588): `opencode run` has no flag to skip saving a session, so the store's location is the only control, and OpenCode resolves its session database from that variable (verified on v2.0.15 with `opencode debug paths`). V2 needs `--standalone` for this to hold — without it `run` attaches to the user's shared background service, and the server holding the user's data dir is what creates the session. No `session delete` follows a run: the store sits in the invocation-owned directory whose deferred cleanup removes it, so a session cannot outlive its call, and a delete would cost a second OpenCode process per harness call (hundreds per lifecycle) to erase a row from a directory about to be deleted. The pre-isolation backlog is `ghost opencode cleanup-sessions`.
- `internal/memory/` — SQLite CRUD, FTS5 search, vector search, time-decay scoring, and the retriever contract behind the assembler (`Store.Candidates`: one read snapshot, widened untrimmed rows with their scoring facts, leg/edge statuses)
- `internal/assemble/` — context assembly: `assemble.Run` is the one entry point (one `[]stage` in `pipeline.go`), owning selection, validity, category/scope predicates before window closure, provenance (pinned at 1.0), budget closure, the outcome, the always-recorded trace and the shared `Item.Line()` renderer. Depends on one method, `Candidates`; `internal/memory` never imports it. `ScopeLabel` is the scope label `Item.Line()` embeds and the session-start block prints, so no surface re-derives it; `ScopeContradicts` is the named negation of `memory.ScopeMatches` rather than a second copy of the rule. The session-start loaders are callers of those two but not yet of `Run` — passive retrieval is not served by the seam
- `internal/mcpserver/` — MCP server: 20 tools + 4 resources + 2 prompts (`recall_project`, `record_decision`)
- `internal/hostevent/` — Normalized host-event contract (v1) and the transcript scanners; every parse or validation failure is an error the caller turns into "allow the stop", and a payload past `maxPayloadBytes` is one of them (nothing else on the path bounded it — the hook read stdin with an unbounded `io.ReadAll`, and `Parse` retains the payload decoded and again verbatim in `Raw`). The hook now reads through `hostevent.ReadPayload`, which stops one byte past the ceiling, so the bound limits the allocation and not only the parse. Field values are text the host did not write, so only the contract's own fields decide the envelope: an unknown field cannot become a known one, an instruction-shaped `hook_event_name` normalizes to nothing, and the goose native aliases (`event`, `working_dir`) bind only for `--source goose` and only per field where the dialect field is absent. `GhostSaves` counts STRUCTURE, never prose — a save tool named inside a text part, a shell command or an opencode Code Mode `execute` body is not a save, because that count is the save-nudge's evidence
- `internal/mcpinit/` — `ghost mcp init`, `ghost mcp status`, `ghost hook <event> --source <host>` (contract-v1 lifecycle dispatch; installers: claude-code, opencode plugin, codex TOML+hooks.json, goose Agent-Plugins package; goose field aliasing lives in hostevent.Parse). Every write to a file the user owns — settings.json, codex config.toml and hooks.json, the opencode plugin, the goose package, the MEMORY.md redirect — goes through `writeFileAtomic`/`writeFileAtomicPrivate` in settings.go, never a bare os.WriteFile: temp file in the same dir, flushed (data and mode) with `f.Sync()`, then rename, then the parent directory flushed, so an interrupted write cannot truncate a config, a reader holding it open still sees a whole document, and a power cut can leave neither an empty config nor a missing one. A temp-file flush failure stops the write and is reported; a directory-flush failure is not (the rename already landed, and Windows has no directory flush at all). The rename carries the permission bits across and nothing else — not the owner, POSIX ACLs, xattrs or hardlinks, so a hardlinked config in a dotfiles repo silently diverges from its repo copy. `writeFileAtomicPrivate` additionally clamps the mode to 0600 and is used only by settings.json, because that is the ceiling every pre-refactor save enforced; the other files keep whatever mode the user chose, even where a codex `[mcp_servers.ghost.env]` sub-table can hold a credential. Ghost's own marker/scratch files are exempt. Two files get a one-time `.bak` through `writeBackupOnce`: settings.json on its first save, and codex `config.toml` the first time a repair rewrites a ghost table that was already present. Neither is ever rolled forward, so the `.bak` stays the pre-ghost file instead of becoming Ghost's own previous output.
- `internal/claudeimport/` — One-time import of Claude Code auto-memory on first contact. The files are written by a session that read a checkout Ghost never chose, so the parse layer is an untrusted surface: a front-matter line gets its own bound (`maxFrontmatterLine`) because `bufio.Scanner`'s 64 KiB default stops the scan on a long description and the block's loss is silent (the type, and with it the category, went with it), a block that could not be read whole is imported as body text rather than half-parsed, and a file past `maxMemoryFileBytes` is skipped. The import writes nothing to disk at all — a fixture asserts the tree is byte-identical afterwards — and it never promotes: `categoryMap` is the only thing that picks a category, so a planted `source: manual`, `pinned: true` or `type: _global` reaches none of the fields consolidation filters on
- `internal/embedding/` — Ollama async vectorization worker; every vector is stamped with the identity of the space that produced it (`<model>[:<dimensions>][+prefix]`, `embedding.VectorIdentity`) and nomic-embed-text is embedded with its `search_document: `/`search_query: ` task prefixes
- `internal/linking/` — Background worker linking similar memories into a graph
- `internal/resolve/` — `ghost resolve`: LLM-classified de-weighting of resolved-evidence memories (drops from ranked injection, stays searchable); classifies via CLI harness (see Classifier backend below)
- `internal/supersede/` — `ghost supersede`: LLM-classified 'supersedes'/'causes' link creation over live memories, batched 8 candidate pairs per harness call with a content-keyed NEITHER cache (`supersede_checked`, schema v8, cascading FKs) so a converged project's fresh candidates make zero calls — except reversed ones, which are never cached and are re-asked every pass (live-link pairs are still validated each pass). A classify call that FAILS is re-issued ONCE, after `classifyRetryDelay` (2s, injectable through `SetRetryDelay`) and counted by `Retries()` — it is on both reports and the reassess summary log — because a real `opencode run` that exited 1 once cost a whole `ghost supersede` pass in #699's rehearsal, and the rerun a minute later answered normally. ONE retry, not a schedule, and it decides nothing: the second failure is returned unchanged so a genuinely dead harness is exactly as fatal as before, `Run` still aborts and writes nothing, an UNPARSEABLE reply is not a transport failure and is not retried, and the wait is context-bounded so a cancelled run does not spend a second spawn to be told the same thing. Pairs are oriented by `updated_at`, so the prompt also carries each note's `created_at` and offers a fourth verdict, `reversed`: a supersedes link only points newer→older, so a verdict saying the OLDER note is the current one is refused (never written, never cached) rather than written backwards (#641). The pass is KEEP-biased because the edge is not an annotation: the ranking guards demote its target and `ghost resolve`'s piggyback stamps `resolved_at` on it, so a wrong edge removes a live memory from every later session. Two rules decide that, both from #686's 43%-precision measurement (every wrong edge joined two notes that were BOTH still true). The rubric asks the falsity question — after the newer note, is the older note's claim false or no longer applicable, and two notes both still true are NEITHER even on the same topic — and a `supersedes` answer must name the claim in a `replaced:` field; missing/empty/placeholder reads NEITHER, which is a decision and therefore cacheable, and the NEITHER cache key prefix moves v2→v3 for it (a cache hit is a permanent skip for the life of that text). `replaced:` is the twin of resolve's `closed-by:` and is read by the SAME helpers (`resolve.ReasonedField`/`resolve.ReasonlessValue`), so a value that keeps a note in one pass's injection cannot bury it in the other's ranking; a synonym verdict is no way around the field. `VetoSupersede` is the free half, before any call: an older note stating an imperative that the newer note never names as retired or changed is settled as no-edge, and the imperative vocabulary is resolve's own (`VetoKeepImperative`, which `VetoKeep` also calls) rather than a copy, so one list protects a memory from being buried and from being demoted. Its error is in resolve's direction — a false veto leaves a stale note ranked, and #641's own "status-report-fix" fixture is what that costs, which the labeled regression set pins by name. A pair whose endpoints' scopes conflict is never classified: the scope reaches `SearchVectorScoped` so the neighbour budget counts only linkable rows, and `Run` re-checks the rule over every pair it is about to spend a call on — the reclassify path included, which is the only way a link written before the rule existed is reached at all. The classifier is handed note text only, so it cannot see a `memories.scope` column; the guard is structural, not a rubric line. The reclassify half saves one call per endpoint edit rather than one per pass, because skip-if-unchanged already holds an untouched pair quiet. The scope refusal is not counted in `Result`: against the shipped store the query drops the conflicting rows before `SelectCandidates` sees them, so a count there would read as zero for work declined, while the veto IS counted (`Result.Vetoed`, printed) because a run that declined work it did not do must not report the same totals as one that found nothing to. An existing scope-conflicting edge is left in the graph and exempted at read time by `SupersedePenalties`, by `ghost resolve`'s supersedes piggyback, and by the two fold-target liveness checks — the piggyback is the one that would have been persistent, stamping `resolved_at` on the older endpoint. A vetoed pair's existing edge is left alone there — the creation pass is not where graph history is deleted — and `ghost supersede <project> --reassess [--apply]` (`internal/supersede/reassess.go`) is the repair path: it re-judges every live 'supersedes'/'llm' edge under the current rules and withdraws the ones that come back NEITHER, vetoed, CAUSES or REVERSED through `InvalidateLink` (which writes the `unsupersede` history row), printing each withdrawn edge with the rule that withdrew it, which half decided it (`veto, no harness call` vs `classifier`) and — because a withdrawal sweeps the pair's 'causes' edge as `Run` does on the same self-contradicting verdicts — how many `causes` rows that took (`WithdrawnEdge.CausesSwept` is the PREDICTION in a dry run and the OBSERVED count under `--apply` — a row never claims a deletion that did not happen, and a sweep that ERRORED sets `SweepFailed` and prints "unknown" instead of a count (`ReassessResult.CausesSweepFailed` counts those rows, separately from the swept ones, because "swept 0" and "could not tell" are different sentences); a `causes` VERDICT sweeps nothing, because it affirms that relation). The prediction is read through each pair's OWN endpoints (`GetLinks` on the older id), NOT through `LinksByRelationSource`: the sweep deletes by id with no project predicate, so a pair whose older note has been promoted to `_global` or moved by `ghost project merge` is still swept, and a project-scoped read (which joins on the edge's source, and a 'causes' edge's source is the OLDER note) cannot see it. A dry run reports the count it is about to print, not `Result.Withdrawn` (which is 0 by construction in a dry run — the same rule `reassessSummaryLine` follows on the resolve side), and a failed invalidation returns the edges that DID land with the error, because each is its own transaction and a later pass will not see them again. That 'causes' sweep is predicted by a read that ONLY a dry run makes: under `--apply` every row's count comes from the sweep itself, so the prediction is not read at all and a discarded read can never be the reason a repair failed (`TestReassessUnderApplyNeverReadsThePrediction`). A dry run whose prediction read fails marks the row's second deletion unknown (`WithdrawnEdge.PredictionUnknown`, counted as `CausesPredictionFailed`) instead of printing a count nobody looked for, and `SweepFailed` stays false — no write ran. A classify call that FAILED is not fatal to those rows either, and that is the direction of the fix (#699: one dead `opencode run` cost a real rehearsal every withdrawal, 76 of 87 edges waiting on a rerun, including the ones the veto had settled for free): the settled withdrawals apply, the pairs the classifier never answered move to `ReassessResult.Unjudged` with their edges LEFT ALIVE, and the pass still returns an error so the exit says "rerun me". Every open pair is unjudged, not the subset the harness named last — a call that failed answers nothing about anything it carried, and a verdict-count mismatch is the same state, so both take this path. Withdrawing is the safe direction and settling the veto needs no harness, which is what makes it the one case where a partial repair is still a repair. The withdrawal sweeps the other relation's edge too, as `Run` does on the same self-contradicting verdicts, but NOT under a CAUSES verdict: there the existing 'causes' edge may be saying something true. THIS IS THE ONE PLACE THE VETO'S ERROR ARGUMENT DOES NOT CARRY OVER: on the creation pass a false veto costs recall, here it deletes a correct edge, and since the veto is deterministic on the same two note bodies the ordinary pass re-fires it forever, so the pair cannot be re-linked until a note changes — which is why the report marks those rows. Withdrawing is only half the repair: the memory is still stamped `resolved_at`, and only `ghost resolve --reassess` can clear it, so the chain is pinned end to end in `TestReassessResolvesAChainIntoResolveReassess`
- `internal/bench/` — `ghost bench`: retrieval-quality benchmark harness (graded dataset + sweep + staleness/recency/maintenance-state suites + the no-answer false-positive report)
- `internal/obsidian/` — One-way Markdown vault mirror (`ghost obsidian export|sync`). The store can hold ids, project names, tags and bodies Ghost never generated (`ghost import` writes an artifact's ids verbatim), so every name it builds is a name somebody else chose: `idToken` keeps the first 8 bytes of an id only when they name a single path component a person could type and hashes the id otherwise (a separator put the note outside the `Memories/` subtree prune manages and had it deleted; a tab or line break is a legal name nobody can open; a NUL failed the whole export with `EINVAL` on every run), `folderNames` replaces a folder over `maxFolderName` the same way it replaces one that would escape because `ENAMETOOLONG` failed the export just as permanently, and `hasGhostID` unquotes exactly what `yamlScalar` emits. What prune keys its RETENTION on is the note's vault-relative PATH (`keepSet`, keyed by `keepKey`), not the id read back out of the note and not the bare basename — the front matter still decides whether a file is Ghost's to touch at all, so the block is prune's ownership test, but the id inside it is not its key: `yamlScalar` flattens tab/CR/LF to a space so every key stays on one line, and that is lossy — three records can render one `ghost_id` line, and keyed on that line they would collide on it and two of the three would be deleted. A basename is not safe either, and for a different reason: the same slug occurs in two project folders, and a memory and a task with the same title produce the same name and can share an id fragment, so one live note anywhere in the vault would keep a stale copy alive everywhere. A key that decides what to keep should be one the system holds, not one parsed back out of a file written for a human Every front-matter value still has to occupy exactly one line — that is what makes the note valid YAML and the ownership test's answer well-defined (it reads to the first `---` and takes the one `ghost_id:` line there) — but no value read out of front matter, forged or merely flattened, can now make prune drop a note it wrote
- `internal/portable/` — The portable JSONL artifact (`ghost export` / `ghost import`): one typed record per line behind a schema-version header, written projects-then-memories-then-tasks-then-decisions in id order so two exports of an unchanged store are byte-identical. It is a wire format, not a backup — `memory.Store.Backup` is the restorable copy. Import never overwrites an id that already exists, so re-running is always safe; a record it cannot import is rejected individually and the run continues, so one hand-edited line does not abandon the file. A dry run opens the store read-only, so the preview cannot migrate or seed what it previews — which means openReadOnlyTransferStore must also refuse a store whose PRAGMA user_version is behind or ahead (memory.DBUserVersion / memory.SchemaVersion), or the first query fails with SQLite's "no such column" instead of a version mismatch. The artifact deliberately omits Ghost's own _global builtin seeds: they are written per-install under hex(randomblob(16)), so every importer's id-only dedup would duplicate them permanently, and the destination already re-creates them by content. Imported memories are stamped `source = "onboarding"` and unpinned unless `ImportOptions.TrustProvenance` is set: an artifact is a file that arrived from somewhere, and on its own authority it must not be able to plant rows the store exempts from consolidation by name (`manual`, `builtin`) or by pin. Embeddings, memory links and the resolve KEEP cache are not in the artifact: all three are derived and rebuilt by their workers
- `internal/reflection/` — Memory consolidation: LlmConsolidator + SQLiteConsolidator. The LLM tier speaks per-id operations, not free text (see "Reflection operation contract")
- `internal/secret/` — Credential-shape detection for stored text (`Detect`); shape-based, never keyword-based
- `internal/provider/` — Interface contracts: LLMProvider, MemoryStore
- `internal/config/` — Layered YAML + env config (koanf). `Load` returns an error for a config file that exists but does not parse, for a `GHOST_*` value that is not readable as its key's type, and warns on file keys no `Config` field binds (env names are not key-checked — most `GHOST_*` variables are not config keys); CLI subcommands call it and fail. `LoadForHook` is the host-session path (SessionStart/Stop hooks, obsidian auto-sync, routing, the scratch budget): it reports the same problem on stderr and returns `FallbackConfig` — the compiled defaults plus the `GHOST_*` environment, i.e. every layer that does not read a file — so a typo cannot fail someone's session and cannot undo an environment opt-out. `envOverrides` lists the `GHOST_*` names the generic `GHOST_` prefix + `_`→`.` transformer cannot map, each with the parser for its key's type. `SetWarningWriter` redirects the warning sink, which `runMCP` points at its log channel; the sink is atomic because harness spawns warn from goroutines.
- `internal/selfupdate/` — `ghost upgrade` self-update from GitHub Releases

## Key Patterns
- Memory categories: architecture, decision, pattern, convention, gotcha, dependency, preference, fact
- Untrusted parse surfaces (`claudeimport`, `hostevent`, `obsidian`): a value somebody else wrote is DATA. It is stored exactly as parsed, it names at most one path component inside the directory its surface owns, and it never decides the parse — the parser's own vocabulary does, and a payload that does not fit is rejected or mapped to the documented fallback, never obeyed. `internal/adversarial` states the invariant once and holds the corpus all three suites drive (#585). Two rules that look like filters and are not: a planted payload stays retrievable (hiding the tampering is worse than showing it; quoting into the data block happens on the way out), and every `hostevent` refusal fails open, because "allow the stop" is the only response the hook contract emits. Defects here were silent rather than loud — a front-matter line past `bufio.Scanner`'s default cost a memory its category, a separator in a record id cost it its note, a quoted `ghost_id` cost it a second prune pass — which is why each is a fixture and not a line of prose
- Backup and portable transfer: `ghost backup` is `Store.Backup` → `memory.vacuumInto` (SQLite `VACUUM INTO`, the same one implementation the pre-migration copy uses), so both claim the destination with `reserveBackupPath` (a `0600` `O_EXCL` create, before any byte is written) and both refuse an existing path. `VACUUM INTO` names no mode, so creating the file first is what keeps a full copy of the memory database out of a group-readable window on an `--out` outside the `0700` data directory. The write lock is held for the vacuum and nothing longer. It counts the snapshot by opening the written file read-only, never the live one — the counts a restore is checked against have to describe the file that was written. The portable artifact (`internal/portable`) is the other half: `memory.PortableProjects` / `PortableMemories` are separate reads because `ListProjects` has no `repo_remote` and an artifact needs the columns in an order it owns. (The other reason this line used to give — that the ordinary list readers drop the validity triple — stopped being true when `memory.Memory` gained `valid_from`/`valid_until`/`verified_at`: retrieval hydrates all three, and `PortableMemories` selects them for itself.), and `Import*` are separate writes because no existing writer can preserve an imported id, `created_at` or pin. Every `Import*` takes an `apply` flag, so a dry run runs the same validation as the run it previews
- Time-decay scoring: convention/preference/fact never decay; architecture/pattern 45-day; decision/gotcha/dependency 30-day
- Empty-set guard: never replace all memories with empty reflection output, and a reflection response carrying no operations fails the LLM tier rather than relying on that guard alone
- The gate lives in `TieredConsolidator`, NOT in the LLM tier — so naming a backend bypasses it unless the tier is wrapped. `ghost reflect --tier cli` and `--tier opencode` used to hand the bare `LlmConsolidator` to the apply path and had no floor at all, while the default `auto` tier and the unattended path were bounded; `eval/cycle` measures with `--tier opencode --apply`, so the suite was grading an ungated consolidator against a gated production one. Both branches now go through `gatedLLMTier` (`cmd/ghost/lifecycle.go`), which calls `reflection.NewGatedConsolidator` — one tier, no fallback added, so "exactly this backend" still means that and a too-small answer is a failed run rather than a quiet drop to Jaccard. It is a named function because `runReflect` calls `os.Exit`, so the tier switch is unreachable from a test and the behaviour has to be pinned at the seam. The wrapper reports the tier's OWN name, not the `tiered:` prefix (`TieredConsolidator.gated`): `Consolidator: cli` must keep printing `cli`, because a script or saved log-grep keyed on that label breaks silently otherwise, and wrapping a tier changes how it is bounded, not which one runs. The prefix marks WHICH CONSTRUCTOR ran, not how many tiers were in the list — `auto --require-llm` is a one-tier list and still prints it, so do not read the prefix as a claim about fall-through
- Reflection reduction warning counts survivors, not one scope: `reportReductionWarning` (`cmd/ghost/lifecycle.go`) measures `reflectRetained`, which adds the cross-project candidates back in when promotion is off because `applyReflection` folds them into the project. Reading `len(projectMems)` understates retention by the whole candidate set and fired `>50% reduction` on rounds that lost nothing — a warning that cries wolf on the one path where nobody reads it is worse than none. The input side is `len(consolidatable)`, not a re-count of non-`manual` sources: `consolidatable` already dropped `manual`/`builtin`/`pinned`/resolved, so every row left is one `ReplaceNonManual` would delete. It fires on a dry run too (the call is above the `if !apply` return), which is deliberate — the preview reports the compression it would apply — and only from `reductionWarnMinInput` (6) up, which is where the quality gate stops judging and this becomes the only signal
- Save-time consolidation opt-out: `ghost_memory_save`'s `pin` maps to `UpsertOptions.Pin` and pins inside `Upsert`'s existing `BEGIN IMMEDIATE` transaction, so a memory can opt out of `ghost reflect` in the call that stores it rather than in a second `ghost_memory_pin` call — nothing an agent writes is excluded by `source`. A fold pins BOTH rows (the copy just stored and the existing row the text merged into, which is the one a later consolidation is most likely to absorb), so the save result says so rather than letting the caller infer the pin from the id it returned; `FoldOnly` stores no row, so the target is the only thing the request can mean. `pinMemoryTx` deliberately leaves `updated_at` alone: the row's age and timestamp are load-bearing for decay and the `--skip-unchanged` fingerprint
- Upsert dedup is one write transaction: `UpsertWithOptions` opens its `BEGIN IMMEDIATE` transaction BEFORE the FTS duplicate probe and commits the writes the probe decides on, because a probe outside it leaves a window another ghost process can use — a save that strengthened the same row in that window had its increment overwritten by arithmetic on a value read before the fact, and a row committed in that window was invisible to the probe, so two saves of one fact became two unlinked rows (both are cross-process; the per-`Store` `s.mu` cannot close either). The strengthen is therefore `SET importance = MIN(1.0, importance + ?)`: the value it adds to is the one the row holds when the statement runs. Never query the pool inside an open transaction on the same handle — `OpenDB` pins one connection, so it deadlocks; go through the `sql.Tx`. `FoldOnly`'s re-verify of its target happens in that same transaction, which makes it a statement about the probed row, not a race guard

It is not the `manual` source that covers this: seeds are written `builtin`, agent saves `mcp` and reflection writes `reflection`, so nothing an agent writes is ever excluded from consolidation by that filter. With the per-id pass-through the guard no longer rescues omissions, and what it still covers is narrow: a MERGE's sources (`ReflectionResult.Merges`, carrying the ids it folded in AND the text it produced, scored against the text of THAT merge), an explicit `obsolete` drop, and the SQLite tier's absorbed duplicates (it names no ids, so all of its inputs are measured the strict way). The merge's own text is the whole witness available, because a merge source is consumed by its merge (its own text is never in the result) and the parser rejects an id claimed twice (so a sibling cannot be there either); scoring against the siblings could only LOWER the bar. A merge that is not in the result has no witness and its sources fall back to the strict per-output test. THERE IS NO EXEMPTION. Not for a rewrite and not for a supersession: **an unattended reflect never deletes a memory on the model's say-so alone.** A `rewrite <id> -> <text>` or a `drop <id> reason: superseded by <id>` is audited exactly like an `obsolete` drop — the corpus has to be able to SHOW the row is gone. `ReflectionResult.Replacements` still RECORDS the ids a response disposed of and the text it says took their place, because that is the only place the response's own account of a disposal is visible to a reader of a result, but nothing acts on it. The carve-out this replaced was the hole: a supersession disposed of a row whenever the named successor's text was in the result, and the parser's only rule is that the target survives the response — so naming a neighbour was a valid operation and two ordinary deployment notes in the same project, paired because they sat adjacent in the prompt, was a silent deletion with no warning, no `--allow-drops` and a zero exit status. Requiring the witness to be RELATED closed that, and then turned out to be redundant: the witness text is itself an output, so a row at 45% containment against it also passes the per-output scan. The whole branch was dead code. The rule is KEEP-biased on purpose, and the reason is repairability: a stale row that is KEPT can be demoted, because the lifecycle runs `resolve` and `supersede` immediately after `reflect` and demoting a genuinely stale row is their job, while a deleted row is gone. So the failure direction is a duplicate — the old text back beside its replacement — never a silent deletion. The cost, named: the "three issues are still open" class comes back as a kept stale row whenever the successor is reworded below the containment bar (measured: this repo's own superseded note about the Anthropic API client scores 0.429 against its replacement), and stays visible until resolve or supersede demote it, so a corpus of those grows the input each pass has to read. That is the right way round for a command that rewrites a memory store with no human in the loop. Because a re-added verbatim memory reaches `ReplaceNonManual` through the exact-content reuse path, retention must not be treated as consolidation: `reusePreservesAge` (`internal/memory/store.go`) keeps the stored `created_at` and `source` when the re-emission matches the row's content and category — for every verbatim re-emission, not only retention: a `keep`, a pass-through and the SQLite tier's unmerged (always verbatim) output keep their age too, so decaying categories now age out of injection instead of being refreshed by each applied reflect — and omitting a stale memory cannot restart its decay or relabel its source, while a genuine rewrite (new text, or the same text in another category) still gets `created_at = now` and `source = 'reflection'`. That decision is only as good as the row it is made against, so the pick is deliberate too: `takeReusableRow` prefers the candidate whose category matches the emission (a project can hold one text under several categories, since Upsert keeps the incoming category on a linked copy) and falls back to the first, and the candidate query is `ORDER BY created_at, id` so a duplicate keeps the oldest age deterministically rather than whichever row the planner happened to return
- Reflection operation contract: the LLM tier returns `{"learned_context", "ops"}` where each op is `keep <id>` / `merge <id>,<id> -> <text>` / `rewrite <id> -> <text>` / `drop <id> reason: obsolete|superseded by <id>` on the ids the prompt renders (`internal/reflection/ops.go`), because the retired free-text contract had no vocabulary for "this row is fine": only a byte-identical re-emission kept an identity, so retyping — including retyping to improve — reset the id, and with it the embedding, the link graph (both ON DELETE CASCADE) and the age (measured: 12 of 13 new ids in one project, 15 of 17 in another). A memory leaves the corpus only when its id is named as a merge source, named for a rewrite, or named in a drop with a reason — AND a surviving output accounts for it (the drop guard's 45% token containment, with a merge source measured against its OWN merge) or `--allow-drops` accepts the deletion. Naming an id is NECESSARY BUT NOT SUFFICIENT: a rewrite whose replacement does not carry the old row's substance leaves that row in the corpus verbatim, so a rewrite is not a free change of wording on the unattended path (#549). EVERY OTHER INPUT IS CARRIED THROUGH VERBATIM by `executeOps` — the pass-through that makes the tier zero-loss, and the reason the token guard is not load-bearing for omissions: an unnamed memory was emitted by nobody, so it survived only if the guard FAILED to recognise a survivor, which made a false positive in the "absorbed" direction a silent deletion with no warning and no `--allow-drops` (measured: "SSH to the bastion goes through port 2222, not 22" gone, because an unrelated survivor shared 45% of its tokens). A guard can only re-add what it flags, so an id the harness never mentioned needs no inference at all. `keep` and the pass-through emit the stored row's own content, category, importance and tags so the exact-content reuse updates it in place; a merge or rewrite derives its category from the first id, its importance from the strongest source, its tags from the union, and its scope from `inferGlobalScope` — the model states none of them, and an unattended model choosing `global` moves knowledge into every project's injected context. An operation id may echo the prompt's own `id:` label, which is stripped rather than failing the pass. Everything else is strict, because a partially-understood operation list is a corpus rewritten as if the model had said something else: an unreadable line, an id Ghost did not feed the model (compared case-insensitively, never by prefix), an id claimed twice, a supersession whose target the same response does not carry forward, or a response with no `ops` array at all each fail the whole response so the tiered consolidator falls through to SQLite. The grounding check (`internal/reflection/grounding.go`) is the other half: a merge or rewrite that introduces a path, hash, version, hostname or number found in none of its source ids is REJECTED and its sources are emitted unchanged — the output is never repaired, because Ghost cannot know which side of a corrupted identifier (`2.BeXIAhbj.js` vs `2.BeXIAhbq.js`) is true, and a wrong specific is stored as fact forever. That is also why a `rewrite` fixes a CLAIM and never a specific: the corrected value would be an identifier the source does not contain, so the prompt asks for `keep` (or `drop`) instead and the check is never asked a question it must refuse. Ordinary prose is not an identifier: a merge that needs a new connective word is a legitimate merge, and a bare proper noun the model misspells is outside these classes
- Reflection input accounting: `ghost reflect` prints a section after the result list that accounts for EVERY input id (#684), identical for a dry run and for `--apply` and printed BEFORE the write so a dry run previews it exactly. The invariant is a partition: each input id appears in exactly one line or one count and EVERY count is a count of ids — a merge names any number of sources, so `Merges (3)` over one three-source merge is right and the count of operations is not — so an operator (or an independent judge) can add the numbers up to the input total, and the test asserts the quoted ids plus the two counts ARE the input set with no id twice AND that the section's own headers sum to the input total. The one place a line quotes an id it does not account for is a `superseded by` reason, which names the successor that replaced the row: that successor is accounted for by its own bucket, so the accounting is per input id and not per mention. It exists because the report used to list only what the corpus BECAME — an input a merge consumed vanished from it, so a merge and a loss printed identically, and the applied run recorded the answer in `memory_history` while the preview showed none of it. The truth lives in `reflection.AccountInputs` (`internal/reflection/accounting.go`), a PURE function of the result, because the records about a round belong beside the round; `reportInputAccounting` (`cmd/ghost/reflect_accounting.go`) only formats, and is a named function because `runReflect` calls `os.Exit`. A merge prints `new <- <ids> (<bytes> B from <bytes> B)` and NOT a successor id: the row does not exist until the apply writes it, and `memory_history`'s `related_id` is where the identity becomes visible, so the section cannot name an id that is not knowable yet and a dry run is still an exact preview. The buckets are the result's OWN records, which is why three of them had to be added: `Kept` (an explicit `keep`, otherwise indistinguishable from the pass-through), `Drops` (every explicit drop with its reason — an `obsolete` drop names no successor, so before this the result said NOTHING about the id it disposed of) and `Refusals` (a grounding-check rejection with the ids it kept and the identifiers that caused it, which used to be a log line inside the tier). Like `Replacements`, all three are RECORDS: nothing acts on them, and the drop guard still audits every disposed row on its own evidence. The sixth bucket, **deleted**, is the set of rows an apply REMOVES, one line each with its reason, and it is counted by the replace's own reuse pass rather than by whether the row's text is still in the result. `ReplaceNonManual` reuses stored rows by byte-identical content and claims ONE per emission — the row in the same category, else the oldest, which is why the claim is re-implemented in `claimedRows` over `(created_at, id)` — and deletes every candidate left in the bucket, so two inputs holding the same bytes both have their text in the result and only one is still there afterwards. Keying on the text called BOTH of them carried, which is this report's own defect pointed the other way (#684 review, a blocker). The two reasons are different outcomes: a row nothing carries is a loss, a row whose identical twin was reused is a deduplication whose knowledge is still in the project, and collapsing them is the confusion the section exists to remove. Every id a line prints is the STORED spelling, resolved through the input map rather than echoed from the record: `memIDKey` compares case-insensitively so a response may spell an id any way, and the parser normalises only a drop's successor target (a stored id is `hex(randomblob(16))`, which SQLite renders UPPER-case — measured on a real store, not read off the schema). A guard verdict annotates the line that named the id, by COUNT rather than by id (the line already names them, and a second mention would break the one-account contract), and says `re-added` or `--allow-drops accepts the deletion` so a drop line cannot be read as a deletion that did not happen. `--full` removes the 120-byte preview everywhere in the report through one `reflectTextLimit` seam, is display-only, and is deliberately not on the unattended lifecycle path whose stdout is an append-only log
- Hybrid search: 70% vector (cosine, Ollama) + 30% FTS5, RRF fusion — window selection is `Store.fuseAndRank` delegating to `selectWindow` (scope narrowing, keyword reservation, final cut), which every production search reaches including the FTS-only degenerate path; `FuseAndSelectWindow` is the exported entry point over the same seam, called only from the fusion tests; explain mode reuses the same scoped membership. Status demotion (`statusDemotionFactor` and the `resolvedDemotionFactor`/`globalDemotionFactor` constants in `internal/memory/demotion.go`) multiplies a resolved row's fused score — and a `_global` row's when a specific project is searched — by 0.5 inside `fuseCandidatePool`, before the cut, so it owns membership as well as order; it scales the score rather than dropping the row, so both stay searchable, and explain reports the same number as `status_factor`. With k=60 the factor effectively ranks a demoted row below every live candidate the legs fetched (a halved rank-1 two-leg score of ≈0.0082 sits under the 0.7/80≈0.0088 floor of the deepest vector row in a default window), but it only reorders what the legs fetched — each leg pulls limit*2 rows from the project plus `_global`, which counts against that budget, so a short project result set still fills with demoted `_global` rows. The keyword reservation skips rows whose status factor is below 1 (raw rank and the demoted score would otherwise disagree), and injection never reaches fusion on either path — `loadSessionContext` (`internal/mcpinit/hook.go`) builds the session-start digest, `Store.GetTopMemories` backs the MCP tool surface, both filter `resolved_at IS NULL` — so no factor reaches injection. What the digest does share with the tool surface is the scope rule and its label: the two loaders select `memories.scope`, print it with `assemble.ScopeLabel`, and narrow their own fetch by `injection.session_scope` using `memory.ScopeMatchesSQL`, the SQL statement of `memory.ScopeMatches` that the assembler applies in Go — they need it in SQL because their `LIMIT` chooses which rows are read at all, the same reason `scopesConflictSQL` exists for the fold targets, and a test runs both forms over the same rows to hold them together. Unset, the clause is absent and the block is byte-identical to the one that shipped. The formatted `ghost_memory_search` path does not read that window directly: it asks `Store.Candidates` for a widened untrimmed set and hands it to `assemble.Run`, so the caller's category and scope are applied before the window closes (the window itself is still chosen inside fusion, unchanged) — `internal/assemble` owns every decision after retrieval, and `internal/memory` never imports it
- Vector scan: both legs are brute force over the project's embeddings, and they run in two phases (`internal/memory/vector_scan.go`, #556). `snapshotVectors` copies every candidate row out of SQLite and returns, holding the store's read lock and its single connection for the copy only; `vectorRows.search` scores the copy afterwards, so the O(corpus × dims) cosine pass — which `ghost supersede` runs once per memory — no longer blocks writers for the length of the corpus. The copy keeps the stored bytes rather than decoding them and the score loop reads the little-endian float32s back out in place (`cosineFromBytes`, bit-identical to `cosineSimilarity` on a decoded vector), and the scope column is parsed only for a row that wins a slot; a `scopeProbe` decides per-row eligibility by checking whether the stored text can mention a requested key at all, which can only save a `json.Unmarshal` and never decides membership, since `ScopeMatches` only excludes a row that names a requested key and disagrees. Ranking keeps a bounded window instead of the corpus — a min-heap whose root is the worst row held, ordered once at the end over at most `limit` rows — and the order is total (cosine descending, exact ties broken by scan position) so the answer is a function of the stored data AND the order the scan yielded it in, not of the heap's internals; that is not independence from the scan order (the query has no ORDER BY, so a VACUUM or index rebuild can reorder a tie), and it does not claim to be — what it buys is that two searches over the same rows in the same order agree, which the unstable `sort.Slice` it replaced did not promise. `TestSearchVectorRankingMatchesTheCollectAndSortBaseline` pins the whole result against a transcription of the pre-#556 collect-and-sort search, and `TestVectorSearchCopiesTheCorpusUnderTheStoreReadLock` / `TestVectorSearchScoresWithTheStoreLockReleased` pin that the copy takes the read lock and the scoring pass does not. A writer is still kept out during the copy, and that is the connection rather than the mutex: OpenDB pins the pool at one, so no amount of lock work lets a write start while a query is streaming. The scratch is recycled through a `sync.Pool` on the store, and an oversized embedding buffer is dropped on return rather than retained. What a query still allocates is the driver: `modernc.org/sqlite` copies every BLOB and TEXT column into a fresh allocation per row, which is why the remaining cost is a decoded-vector cache keyed on `PRAGMA data_version` (and then an ANN index), not more work on the scoring loop
- Vector-space identity: a stored vector is only scored when `memory_embeddings.model` equals the identity this process embeds into (`Store.SetEmbeddingIdentity`, fed from `embedding.VectorIdentity`). A model, dimension or task-prefix change therefore retires the old vectors instead of comparing them with queries from the new space. The rule is read in four places, one per caller: `loadVectorRows` (may a vector enter a search), `GetEmbedding` returning nil (may a stored vector act as a QUERY vector — the link worker and `ghost supersede` both do), `UnscannedEmbeddedMemoryIDs` (may the linker compare this memory yet), `EmbeddingStats` (is it covered, which `ghost mcp status` and `ghost_health` report). A retired vector never hides its memory: the keyword leg still finds it. Two side effects of a rewrite ride along: `StoreEmbedding` clears the row's `link_scans` slot when the identity changes (so the linker re-scans it in the new space — the re-scan ADDs current-space `related` edges alongside the ones the retired space produced; nothing invalidates those old rows, and `CreateLink`'s `MAX(strength, excluded.strength)` upsert means an edge whose new-space similarity is lower keeps its old strength), and the foreign-vector warning in `loadVectorRows` is emitted once per retired identity (a second reconfiguration in the same process warns again). `EmbeddingStats` reports stale and unembedded rows separately so `ghost mcp status` can show both. The identity is opaque (compared, never parsed) and empty means "no model configured", which keeps the bench harness and tests unfiltered
- Memory history: `memory_history` (schema v17, #578) is the append-only CHANGE LOG of how a memory reached its current state — one row per write. The name `memory_provenance` went to a different and later concept (evidence records, several per memory, answering "who or what supports this memory" — see "Evidence provenance" below), so never rename this table to it, and do not treat the two as the same thing; and every writer appends one row in the SAME transaction as the write — `Create`, `Upsert` (insert and the fold's `merge`), `UpdateMemory`, `ReplaceNonManual` (rewrite, reuse, bulk delete), `SetResolved`/`ClearResolved`, `CreateLink` for a `supersedes` edge and `InvalidateLink` for its withdrawal (`unsupersede` — a memory can be superseded, withdrawn and superseded again, and only the sequence says which claim is live), `RestoreSnapshot`, `ImportMemory`, `Delete`, the decision companion memory and the shipped seeds. Each row is a VERSION, not a diff: the state the memory held once that write landed, so "what did Ghost know at T" is the newest row at or before T (#647) and the prior content is the previous row. `agent`/`session_id` are the PERFORMER (the save/merge/import paths carry a Provenance; the lifecycle passes do not, and an empty field is an admission, not a claim) — which is what makes the issue's "a row changed by two different agents" answerable. `memory_id` deliberately has NO foreign key so a hard delete leaves a tombstone carrying the text the row held; `project_id` does cascade. Growth is bounded in the appending transaction: newest 50 versions per memory, newest 20 000 rows per store (rowid window, since an implicit rowid is max(rowid)+1 and never reused). A write that changes none of a memory's own recorded columns appends nothing (`Touch`, `TogglePin`, the KEEP cache), and a write that moves a memory BETWEEN projects must also move its history rows' project_id or the project-delete cascade takes the past of a memory that survived: `MergeProject` and `PromoteToGlobal` both do (the merge list exists twice on main). TWO writers deliberately repeat the state instead, and neither is a licence to repeat: a consolidation that re-emits a memory verbatim appends a byte-identical `reflect` row (retention is not consolidation — the row records which run touched it), and a `supersedes` edge appends a `supersede` row when it BECOMES active, recording a claim about the target's standing rather than a state change. Both spend a slot under the cap, which is what bounds them. Two columns carry the event's other end: `related_id` (the id that replaced a deleted row, or the memory whose edge claims it) and `merged_content` (the text a FoldOnly fold dropped, which no row keeps). `ghost history purge <id>` and `ghost_memory_delete`'s `purge_history` delete a row AND its history in one transaction — the redaction path, because a plain delete keeps the text a memory used to hold — and `ghost_history_content` is the SQL seam where #656's `secret.Detect` will redact content on the way in. A purge reaches a memory that is ALREADY deleted through `Store.PurgeMemoryHistory` (history only, never the row), because the tombstone is the feature and a delete-time purge cannot cover it; the same operation is what frees an id for `ghost import`, which REFUSES an id that still has history rather than splicing two memories' records under it (ids are not reused by Ghost, but a portable artifact carries them verbatim). `migrateV17` backfills nothing, so a pre-v17 memory's first edit files a `baseline` row before it overwrites the text. Read it with `Store.MemoryHistory` (oldest first, rowid order) or `ghost history <memory-id>` `as_of` (RFC 3339) on `ghost_memory_search` / `ghost_project_context` and `--as-of` on `ghost context` is the OTHER reader, and it is the reason the rows are versions rather than diffs: `Store.MemoriesAsOf` takes each memory's newest row at or before T, drops the ones whose newest row is a `delete` tombstone or whose first row is after T, and returns the version's own `content`/`category`/`importance`/`resolved_at`/`source`/`project_id` — one statement, driven by `memory_history` rather than by `memories` (a deleted memory's tombstone is the only surviving record of it, so a read that started from the live tables would report "Ghost never knew this" for a memory it held for months), ranked `ROW_NUMBER() OVER (PARTITION BY memory_id ORDER BY recorded_at DESC, rowid DESC)` with `rowid` as the second key because `recorded_at` is second-precision. A pre-v17 memory with no row at or before T is UNKNOWN, never guessed: it is left out of the set and counted in `AsOfSet.Unknown`, because a shorter set that says nothing about the gap reads as the whole truth — and that "no row at or before T" is TWO time-bounded tests, not one, because an unbounded `NOT EXISTS` asks "does this memory have history at all" and a pre-v17 memory the lifecycle touched after the upgrade does (only `UpdateMemory` files a baseline; every other first write appends a row read out of the memories row in the same transaction, so its text is recorded anyway, and that is why no writer needs a baseline there). The gap half also reaches the TOMBSTONES, because a pre-v17 memory deleted after T has no live row either and its gap is otherwise invisible — and that half must do TWO things, or a memory is counted twice: exclude ids that are LIVE again (because `RestoreSnapshot` reinstates a row under the id it recorded, so "tombstoned" does not imply "not live"), AND rank per memory keeping its newest tombstone (a delete → restore → delete memory holds two delete rows, and `UNION ALL` does not dedup). `CreatedAt` — the field the decay measures an age from — is the row's own when that column can answer and the version's `recorded_at` when it cannot: the row is gone (every column NULL, and an empty `created_at` reads as ~56,000 days, so a memory deleted yesterday sat at the decay floor in every listing covering the past year), or the column is LATER than T (no writer produces that, and it is refused because `ageDays` clamps a negative age at 0, making a future-dated column the most favourable value a row could carry into a ranking of the past). Everything else in `AsOfRow` is the current row, including the validity triple: `valid_from`/`valid_until` in particular are the present's until #575's writers land, as are tags, scope, pin, access count and provenance, which were never versioned. A promotion REWRITES the history rows' `project_id` (it has to, or the project-delete cascade takes a memory's past with it), so a pre-promotion instant reports a promoted memory under `_global`; that imprecision is pinned by a test rather than worked around. Nothing in the as_of path reads `memory_provenance` (v18, the EVIDENCE table): an evidence record is one OBSERVATION of a memory, not a version of it, so nothing there can be placed at an instant — a count taken now would be a present-day claim about a past memory. The counts therefore stay zero, and since a zero renders as "no recorded evidence", the as_of DISCLOSURE says they were not read rather than leaving that phrase to stand as a claim. Every statement in the read names `memory_history` or `memories` and nothing else, so a pre-v18 store answers an as_of read in full (`TestCandidatesAsOfDoesNotDependOnMemoryProvenance` drops the table and reads on). In the assembler `as_of` is a BINDING, not a filter: `Run` moves `Now` to it, so age, validity and the trace are all decided against T, and the store treats `AsOf` as authoritative over `Now` for the same reason. The retrieval is keyword-ONLY and says so in the answer, the trace and the leg status: `memories_fts` and every embedding describe CURRENT content, so an as_of search matches the query's terms against the versions' own text (through the same `ftsQueryTerms` extraction the FTS leg uses, phrase- and prefix-aware), ranks by matched terms then the same decay composite at T — not bm25, so not comparable with a current order — reports the vector leg as `not applicable` and REFUSES `vector_only` rather than downgrading it, and does not read `memory_links` at all (it records when an edge was invalidated, never the graph at T) so the supersede demotion comes from the recorded `supersede`/`unsupersede` sequence and the edge status is a fifth value, `not_applicable`, because "no edge joins two of these candidates" is a claim a retrieval that read no graph must not render. Those disclosures are `Result.Qualifiers`, not `Result.Notes`: a note list is bounded from the end and shown for the empty answer, where a qualifier is the first thing to go, and a block that is silently a past reading is read as a present one. `ghost context --as-of` runs NONE of that path's startup side effects (the Obsidian mirror, the session-count bump) — they exist because the command backs a session start, and counting a replay would move the present's session number to answer a question about the past. Restoring the store to a past state is not this; that is export/import (#586)
- Evidence provenance: `memory_provenance` (schema v18, #673) is the EVIDENCE table — SEVERAL rows per memory, one per observation, answering "who or what supports this memory", which the change log above cannot: a fact claude-code reported in one session, codex in another, and a human verified is three rows here and one row of mutable columns on `memories`, which can only remember the last. Three concepts stay distinct and are not interchangeable: SOURCE is how Ghost received a memory (`memories.source`: mcp, reflection, import, manual), AGENT is which agent produced or observed it (`agent`), PROVENANCE is the evidence records themselves. `memory_id` CASCADES (unlike the change log's deliberately FK-free `memory_id`) because "3 observations support this" is a claim about a memory, and once the memory is gone the claim is about nothing; a purge deletes these rows explicitly as well, because `PurgeMemoryHistory` leaves the memory in place and no cascade fires for a row that stays — and it deletes the `memory_snapshot_evidence` rows too, since a snapshot is the rollback point for a whole PROJECT, so its evidence would otherwise outlive the purge by however many reflects prune that snapshot Every value except `kind` is NULL when the host did not report it — a guessed agent or session is a provenance claim nobody made, and `observed_at` is NULL for the migration's seed because the seed can say what the columns hold now and not when the fact was first seen. Writers, each in the SAME transaction as the write, each ONE statement: `Create` and `Upsert`'s insert append `observed`; a near-duplicate FOLD appends the second report to the SURVIVING memory (the point of the issue — the folding agent used to be discarded with the incoming wording, and `FoldOnly` stores no row of its own so without this the report would leave no trace); `RecordDecision` appends `observed` for its companion memory (an ordinary memory search returns and a later save folds against), empty of provenance because the decision tool reports none; `ReplaceNonManual`'s FRESH INSERT carries its sources' records onto the new id with `carried_from` naming each source — a rewrite or a merge mints an id whose evidence the cascade would otherwise have just deleted, which would make every consolidated memory read "no recorded evidence" forever, so the emissions loop runs BEFORE the delete and a test fails if the two swap; the REUSE branch appends nothing because the row never changed identity; `ImportMemory` appends `imported` plus whatever records the artifact carried (and NOT `carried_from`, which names a memory this store has never heard of); `RestoreSnapshot` restores a re-created row's records from `memory_snapshot_evidence` (a table, because a memory has several records, pruned with the snapshots) and touches NOTHING for a row it updates in place — the snapshot holds an older copy of that row's evidence, and restoring it would drop every corroboration recorded since. `AppendVerifiedEvidenceTx` is the exported seam for the validity writers (#677) that own the reserved `verified` kind. There is no growth prune, deliberately: it would be a second statement inside the write transaction, which is what took `TestMultiProcessSharedDatabase` to SQLITE_BUSY for the change log's prune, and the cascade keeps deleted memories from contributing. `migrateV18` REFUSES a database whose `memory_provenance` is not the EVIDENCE table (a pre-rename #664 dev build used the reserved name for the change log) rather than converting or dropping it, naming `sqlite3 <db> 'DROP TABLE memory_provenance'`, and `OpenDB` runs the same check BEFORE the pre-migration backup so a refusal costs no copy and its same-second retry reports the real error — the check tests for `id`/`memory_id`/`kind` ONLY, so it is an identity test and not a version test: a future column here must not make it refuse a legitimate store with a remedy that DROPs its evidence — initSQL's CREATE INDEX cannot catch that one, because the change log has a `memory_id` too, and a warning nobody sees leaves every writer failing on the same missing column. Otherwise it seeds one `legacy` row per memory that recorded at least one of agent/session_id/source_ref/confidence, and NONE for a memory that recorded nothing — an evidence row with nothing in it still says "this was observed", and a row per memory would make every store report one observation, the same fabrication as inventing a session id. Read it with `Store.MemoryProvenance` (oldest first, rowid) and `Store.MemoryEvidenceCounts`, whose `Label()` renders "supported by 2 observations, 1 verified"; the assembler records the counts in stage 4's trace (`Signals.Evidence`, carried on `memory.Candidate` because that is the only read the assembler has) and NOTHING RANKS ON THEM — the stage's multiplier stays 1.0 until a measured change justifies one. The portable artifact (v2) carries the records, nested under the memory they support because a bare evidence line cannot be attributed; the Obsidian mirror does not — it is a human-readable mirror, not a transfer format
- Memory links: `memory_links` edge table auto-populated by cosine similarity (internal/linking worker); links cascade-delete with memories and self-heal after reflection. A graph-expansion ranking bonus was evaluated and removed — dominated by a deeper vector-k (links and the vector leg are both cosine); the link graph is retained for Obsidian export and supersedes ranking (see `docs/superpowers/specs/2026-07-20-graph-expansion-stays-off-design.md`). No edge may join a scope-conflicting pair: every writer refuses one (`Upsert`'s dedup probes, the linker's `related` edge, `ghost supersede`'s candidates) and every reader ignores one already stored — the two ranking guards (`DemotionPenalties`, `SupersedePenalties`), `Store.SupersedesWithin`, `ghost resolve`'s supersedes piggyback and the repair pass's matching floor (`scopeCompatibleSupersedes`, which needed `GetByIDs` on `resolveStore`/`reassessStore`/`resolveCapableStore` for the link endpoints' scopes), and the two fold-target liveness checks (`foldTargetStillLive` + the cross-category probe). Scope exempts a pair from ranking and folding; it never deletes a `memory_links` row. Where the exemption is decided: inside the candidate query, always, because the same `LIMIT` picks the candidates — a scope check applied after the cut spends the budget on rows the caller may not use and misses a compatible one ranked just below (#665). So the two cosine writers narrow before their window (`SearchVectorScoped`, in Go over the scan, so its top-k is the limit and there is no statement to fold the rule into) so their neighbour budgets count only linkable rows, and `Upsert`'s two dedup probes carry the rule inside their own `LIMIT 15` for exactly that reason. `foldTargetStillLive` is the one statement that carries it without a window to protect (it names one row by id) and for a different reason: a scope-conflicting `supersedes` edge is not a verdict that row may be acted on. Both are one rule in two forms, `scopesConflictSQL` in `internal/memory/scope.go`, held to `ScopesConflict` by `TestScopesConflictSQLAgreesWithScopesConflict`
- Resolution classifier: `ghost resolve` runs a keyword prefilter, then a deterministic KEEP veto, then batches up to 8 notes per KEEP-biased CLI-harness classify call (`claude`/`opencode`/`codex`/`goose` subprocess, numbered `N: RESOLVED | closed-by: <fact>|KEEP` reply judged by a strict first-field line parser) to mark `resolved_at`, dropping resolved-evidence memories (changelogs, cost estimates, closed experiment notes) from ranked injection while keeping them searchable. KEEP-biased in code, not prose (#640: an independent judge found ~1 resolve in 3 on a real DB had buried durable knowledge): `resolve.VetoKeep` settles a candidate KEEP with no harness call when its text carries an imperative (`never|do not|don't|must|always|required`) or an open marker (`not yet|outstanding|still pending|still open|still stale|unresolved|todo`), all case-insensitive and word-bounded; the rubric asks the fresh-session question (would an agent starting fresh make a mistake, repeat work, or break a rule without this?) and says dates, PR numbers, commit hashes and "fixed in" do not resolve a note; a RESOLVED must carry a non-empty `closed-by:` or the parser reads it as KEEP. The veto guards the classifier only — the supersedes-edge piggyback and correction pairing still demote. Only explicit KEEP verdicts are cached by content hash in `memories.resolve_kept_hash` (schema v7; the v3 hash prefix invalidates the v1 implicit-KEEP and v2 explicit-KEEP caches, so #640's re-judged rules are re-asked); UNKNOWN parse failures remain uncached and are retried, so a converged project makes no calls only after explicit KEEPs. Dry-run writes nothing, `--apply` writes resolved_at and explicit KEEP cache entries; transport or verdict-count failures fail fatally rather than applying incomplete results, while UNKNOWN lines remain eligible for a later pass. `ghost resolve <project> --reassess` is the repair path for the resolutions the pass already got wrong: it re-runs the vetoes and the classifier (no keyword prefilter) over memories that are ALREADY resolved, prints the ones that now come back KEEP, and with `--apply` clears their `resolved_at` via `memory.ClearResolved` and caches the classifier's KEEP verdicts; a failed clear is fatal, a failed cache write only warns; `memory.ClearResolved` runs every batch in one transaction so "a failed clear repaired nothing" is literally true. It honours Run's two free demotions as a floor — a row a live `supersedes` edge still asserts, or an older row a NEWER *unresolved* correction pairs with (the same pool Run searches, via `correctionPairTargetsFrom`), is counted as `Demoted` and left resolved, because Run fires both before the veto and the KEEP cache, so clearing it would report a repair the next pass undoes. The pairing is re-checked after the re-KEEP set is known (`holdBack`), because a correction that is itself repaired leaves the resolved pool and would re-assert its pairing; both the floor and the hold-back pair only Run's keyword-prefiltered subset, since a keyword-free row is never a pairing target and holding it would be a permanent, mislabelled hold no later pass could undo. A reasonless `closed-by` is not a reason: a bare mention of the key without its colon ("no closed-by available") and a placeholder value (`none`, `n/a`, `tbd`, …) are both KEEP — and so is a value whose FIRST WORD declines to name one ("not applicable", "no decision", "cannot name it", "unclear"), because a refusal is a phrase far more often than it is one of the nine placeholder keywords. That grammar is `resolve.ReasonedField`/`resolve.ReasonlessValue` and it is NOT resolve's alone: internal/supersede's `replaced:` field is the same contract for a supersedes verdict (#686), so one list decides both and a value that keeps a note here cannot bury it there. `VetoKeep` is likewise split — `VetoKeepImperative` is the imperative half, exported because internal/supersede's `VetoSupersede` reads the same words for the opposite decision (a rule is not a fact that goes out of date), while the open markers stay resolve's. The repair pass treats a live 'supersedes' edge as a floor, which is why `ghost supersede <project> --reassess --apply` has to run FIRST: withdrawing the edge is what makes the `resolved_at` it justified clearable, and `TestReassessResolvesAChainIntoResolveReassess` runs that chain against a real store. That floor is counted per EDGE, not per note: a note two newer notes both supersede is held by either one, so withdrawing one of the two does NOT release it (`Demoted`, nothing cleared, no harness call) and only the last withdrawal does. A withdrawal wider than the edge it names would otherwise hand the note back to injection, where the very next ordinary pass re-stamps it from the surviving edge and no edge ever changes again (`TestReassessHoldsTheNoteWhileAnySupersedesEdgeSurvives`). Never invoked from the stop hook's synchronous path (that path forbids DB access); the stop hook's detached `ghost lifecycle` spawn (whose resolve phase runs `--apply`, never `--reassess`) and the standalone batch command are the only callers. See `docs/superpowers/specs/2026-07-26-resolution-classifier-design.md`.
- Classifier backend: `resolve`/`supersede` classify via the calling session's own CLI harness — the backend is picked from the MCP client's reported identity (an opencode session uses the opencode binary, claude uses claude, etc.) via `ai.SourceProvider`, or — on the headless CLI path — from `--source`, else `ai.DetectSource()` (env markers plus process ancestors); if no calling harness can be determined it fails fast with an actionable error. There is no claude-first cascade: `NewSourceProviderForSource("")` is unavailable, and `ai.CLIProvider` is an availability probe only. MCP sampling was retired from this path per SEP-2577 — see `docs/superpowers/specs/2026-08-24-resolve-sampling-path-design.md`.
- Lifecycle spawn guards: the stop hook spawns the reflect→resolve→supersede chain behind TWO independent per-project guards. `AcquireLifecycleLock`'s PID file says "a run is not already in progress"; `lifecycle.min_interval` (default 30m, `0` to disable) says "a run did not start too recently". The second is the mtime of `lifecycle-<project>.last` in the data dir — a file, not a row, because the stop hook's synchronous path forbids DB access. Only the `ghost lifecycle` process writes it (`mcpinit.TouchLifecycleStart`), and only once it has passed every precondition that can exit non-zero, so a run that dies before doing any work does not burn a window. Most unknowns read as "run" (no stamp, unreadable, non-regular) so that a bookkeeping problem cannot silently stop maintenance; a stamp dated in the FUTURE is the deliberate exception and reads as INSIDE the window, because a future date is not evidence the window expired. `config.LifecycleConfig.MinIntervalDuration` resolves an unreadable value to the default rather than `0`, because `0` means the cooldown is off.

## Critical Rules
- Always `go vet ./...` before committing
- Tests use `go test ./...`
- Never commit to main directly — feature branches + PRs
- SQLite schema is embedded as a Go string constant in `internal/memory/schema.go` (currently v18; `migrate.go` carries one frozen step per version)
- `ghost mcp init` is idempotent and non-destructive — safe to re-run
- A test that needs a real *program* builds it with `go build` into a temp dir rather than re-exec'ing its own binary: under `go test` the test binary is the suite, so a self-spawn re-runs every test in the package once per spawn and a bug in the barrier logic becomes a fork bomb. A `-test.run`-bounded child test is fine (`internal/ai/harness_policy_test.go` does exactly that)
- The end-to-end suite (`e2e/`, build tag `e2e`) runs the BUILT binary: `make test-e2e`, or `go test -tags e2e ./e2e/ -count=1`. The tag is what keeps `go test ./...` and CI unchanged — with it absent the `./...` pattern skips `e2e/` silently, so do not add a file there without `//go:build e2e` (and `e2e/doc.go` deliberately carries `!e2e` so `go test ./e2e/` is a clean "no test files" rather than a build-constraint error). Rules for writing into it: every test runs in a sandbox whose environment is BUILT from an allowlist (never filtered from `os.Environ()`), the LLM harnesses and the embedding endpoint are fakes, and a failing case is a finding — fix the product in its own commit with a regression test if it is small, otherwise `t.Skip("known: #NNN")` plus a filed issue. Coverage is enforced against the product's own `tools/list` and against `cmd/ghost/help.go`'s `usageByCommand`, both read at run time, so a new tool or subcommand fails the suite. See [architecture.md](docs/architecture.md#testing)
- The concurrency contract in `docs/architecture.md` is enforced by `TestMultiProcessSharedDatabase` (`internal/memory/multiproc_process_test.go`, helper in `internal/memory/testdata/multiproc`): MCP server, CLI child, read-only handle, lifecycle writer, pinned-snapshot reader and sampler processes against one database. It reads `memory.OpenDB`'s and `memory.readOnlyDSN`'s settings back from a live connection, so dropping WAL, `foreign_keys`, `busy_timeout`, the pool pin or `_txlock=immediate` fails it. `mcpinit`'s own DSNs are not covered. Skips under `-short`; makes no LLM call
