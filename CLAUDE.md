# Ghost — MCP Memory Server

## Stack
- Go 1.26+ CLI application
- SQLite with FTS5 for memory persistence (modernc.org/sqlite — pure Go, no CGO)
- CLI harness callers (claude/opencode/codex/goose subprocesses) — used by reflection, resolve, and supersede. Each harness owns its authentication and billing; Ghost does not add a direct API client. The prompt is written to the child's stdin and no positional message is passed: the kernel caps one argv element at 32 pages (128 KiB on a 4 KiB-page x86, 512 KiB on a 16 KiB-page one) and a reflect prompt reaches megabytes, so an argv prompt failed the spawn with E2BIG instead of answering. `claude -p` and `opencode run` read the message from a pipe when none is given; codex gets `exec -` and goose `run -i -`. `claude --system-prompt` stays an argument — small, fixed, and never confusable with user content. `cli.model_reflect` / `model_resolve` / `model_supersede` pin the opencode harness model per phase (each phase is its own process; ignored by claude/codex/goose which have no model flag). Empty = any inherited `GHOST_OPENCODE_MODEL`, else Ghost's explicit `opencode/big-pickle` default; a configured pin overrides an inherited env pin for that phase.
- MCP server via modelcontextprotocol/go-sdk (stdio transport)

## Architecture
- `cmd/ghost/main.go` — CLI entrypoint; subcommands: mcp, hook, reflect, resolve, supersede, project, obsidian, bench, backup, export, import, upgrade, version, context. `runCLI` answers `-h`/`--help` (`cmd/ghost/help.go`, one usage table) before the dispatch, so a help request has no side effect
- `internal/ai/` — CLI-harness providers (`CLIClient`/`OpenCodeClient`/`SourceProvider`) used by reflection + resolve + supersede — no Anthropic HTTP API client
- `internal/memory/` — SQLite CRUD, FTS5 search, vector search, time-decay scoring, and the retriever contract behind the assembler (`Store.Candidates`: one read snapshot, widened untrimmed rows with their scoring facts, leg/edge statuses)
- `internal/assemble/` — context assembly: `assemble.Run` is the one entry point (one `[]stage` in `pipeline.go`), owning selection, validity, category/scope predicates before window closure, provenance (pinned at 1.0), budget closure, the outcome, the always-recorded trace and the shared `Item.Line()` renderer. Depends on one method, `Candidates`; `internal/memory` never imports it. `ScopeLabel` is the scope label `Item.Line()` embeds and the session-start block prints, so no surface re-derives it; `ScopeContradicts` is the named negation of `memory.ScopeMatches` rather than a second copy of the rule. The session-start loaders are callers of those two but not yet of `Run` — passive retrieval is not served by the seam
- `internal/mcpserver/` — MCP server: 20 tools + 4 resources + 2 prompts (`recall_project`, `record_decision`)
- `internal/mcpinit/` — `ghost mcp init`, `ghost mcp status`, `ghost hook <event> --source <host>` (contract-v1 lifecycle dispatch; installers: claude-code, opencode plugin, codex TOML+hooks.json, goose Agent-Plugins package; goose field aliasing lives in hostevent.Parse). Every write to a file the user owns — settings.json, codex config.toml and hooks.json, the opencode plugin, the goose package, the MEMORY.md redirect — goes through `writeFileAtomic`/`writeFileAtomicPrivate` in settings.go, never a bare os.WriteFile: temp file in the same dir, flushed (data and mode) with `f.Sync()`, then rename, then the parent directory flushed, so an interrupted write cannot truncate a config, a reader holding it open still sees a whole document, and a power cut can leave neither an empty config nor a missing one. A temp-file flush failure stops the write and is reported; a directory-flush failure is not (the rename already landed, and Windows has no directory flush at all). The rename carries the permission bits across and nothing else — not the owner, POSIX ACLs, xattrs or hardlinks, so a hardlinked config in a dotfiles repo silently diverges from its repo copy. `writeFileAtomicPrivate` additionally clamps the mode to 0600 and is used only by settings.json, because that is the ceiling every pre-refactor save enforced; the other files keep whatever mode the user chose, even where a codex `[mcp_servers.ghost.env]` sub-table can hold a credential. Ghost's own marker/scratch files are exempt. Only settings.json gets a `.bak`, and only on the first save (`writeBackupOnce`).
- `internal/claudeimport/` — One-time import of Claude Code auto-memory on first contact
- `internal/embedding/` — Ollama async vectorization worker; every vector is stamped with the identity of the space that produced it (`<model>[:<dimensions>][+prefix]`, `embedding.VectorIdentity`) and nomic-embed-text is embedded with its `search_document: `/`search_query: ` task prefixes
- `internal/linking/` — Background worker linking similar memories into a graph
- `internal/resolve/` — `ghost resolve`: LLM-classified de-weighting of resolved-evidence memories (drops from ranked injection, stays searchable); classifies via CLI harness (see Classifier backend below)
- `internal/supersede/` — `ghost supersede`: LLM-classified 'supersedes'/'causes' link creation over live memories, batched 8 candidate pairs per harness call with a content-keyed NEITHER cache (`supersede_checked`, schema v8, cascading FKs) so a converged project's fresh candidates make zero calls — except reversed ones, which are never cached and are re-asked every pass (live-link pairs are still validated each pass). Pairs are oriented by `updated_at`, so the prompt also carries each note's `created_at` and offers a fourth verdict, `reversed`: a supersedes link only points newer→older, so a verdict saying the OLDER note is the current one is refused (never written, never cached) rather than written backwards (#641). A pair whose endpoints' scopes conflict is never classified: the scope reaches `SearchVectorScoped` so the neighbour budget counts only linkable rows, and `Run` re-checks the rule over every pair it is about to spend a call on — the reclassify path included, which is the only way a link written before the rule existed is reached at all. The classifier is handed note text only, so it cannot see a `memories.scope` column; the guard is structural, not a rubric line. The reclassify half saves one call per endpoint edit rather than one per pass, because skip-if-unchanged already holds an untouched pair quiet. Neither refusal is counted in `Result`: against the shipped store the query drops the conflicting rows before `SelectCandidates` sees them, so a count there would read as zero for work declined. An existing scope-conflicting edge is left in the graph and exempted at read time by `SupersedePenalties`, by `ghost resolve`'s supersedes piggyback, and by the two fold-target liveness checks — the piggyback is the one that would have been persistent, stamping `resolved_at` on the older endpoint
- `internal/bench/` — `ghost bench`: retrieval-quality benchmark harness (graded dataset + sweep + staleness/recency/maintenance-state suites + the no-answer false-positive report)
- `internal/obsidian/` — One-way Markdown vault mirror (`ghost obsidian export|sync`)
- `internal/portable/` — The portable JSONL artifact (`ghost export` / `ghost import`): one typed record per line behind a schema-version header, written projects-then-memories-then-tasks-then-decisions in id order so two exports of an unchanged store are byte-identical. It is a wire format, not a backup — `memory.Store.Backup` is the restorable copy. Import never overwrites an id that already exists, so re-running is always safe; a record it cannot import is rejected individually and the run continues, so one hand-edited line does not abandon the file. A dry run opens the store read-only, so the preview cannot migrate or seed what it previews — which means openReadOnlyTransferStore must also refuse a store whose PRAGMA user_version is behind or ahead (memory.DBUserVersion / memory.SchemaVersion), or the first query fails with SQLite's "no such column" instead of a version mismatch. The artifact deliberately omits Ghost's own _global builtin seeds: they are written per-install under hex(randomblob(16)), so every importer's id-only dedup would duplicate them permanently, and the destination already re-creates them by content. Imported memories are stamped `source = "onboarding"` and unpinned unless `ImportOptions.TrustProvenance` is set: an artifact is a file that arrived from somewhere, and on its own authority it must not be able to plant rows the store exempts from consolidation by name (`manual`, `builtin`) or by pin. Embeddings, memory links and the resolve KEEP cache are not in the artifact: all three are derived and rebuilt by their workers
- `internal/reflection/` — Memory consolidation: LlmConsolidator + SQLiteConsolidator. The LLM tier speaks per-id operations, not free text (see "Reflection operation contract")
- `internal/provider/` — Interface contracts: LLMProvider, MemoryStore
- `internal/config/` — Layered YAML + env config (koanf). `Load` returns an error for a config file that exists but does not parse, for a `GHOST_*` value that is not readable as its key's type, and warns on file keys no `Config` field binds (env names are not key-checked — most `GHOST_*` variables are not config keys); CLI subcommands call it and fail. `LoadForHook` is the host-session path (SessionStart/Stop hooks, obsidian auto-sync, routing, the scratch budget): it reports the same problem on stderr and returns `FallbackConfig` — the compiled defaults plus the `GHOST_*` environment, i.e. every layer that does not read a file — so a typo cannot fail someone's session and cannot undo an environment opt-out. `envOverrides` lists the `GHOST_*` names the generic `GHOST_` prefix + `_`→`.` transformer cannot map, each with the parser for its key's type. `SetWarningWriter` redirects the warning sink, which `runMCP` points at its log channel; the sink is atomic because harness spawns warn from goroutines.
- `internal/selfupdate/` — `ghost upgrade` self-update from GitHub Releases

## Key Patterns
- Memory categories: architecture, decision, pattern, convention, gotcha, dependency, preference, fact
- Backup and portable transfer: `ghost backup` is `Store.Backup` → `memory.vacuumInto` (SQLite `VACUUM INTO`, the same one implementation the pre-migration copy uses), so both claim the destination with `reserveBackupPath` (a `0600` `O_EXCL` create, before any byte is written) and both refuse an existing path. `VACUUM INTO` names no mode, so creating the file first is what keeps a full copy of the memory database out of a group-readable window on an `--out` outside the `0700` data directory. The write lock is held for the vacuum and nothing longer. It counts the snapshot by opening the written file read-only, never the live one — the counts a restore is checked against have to describe the file that was written. The portable artifact (`internal/portable`) is the other half: `memory.PortableProjects` / `PortableMemories` are separate reads because `ListProjects` has no `repo_remote` and an artifact needs the columns in an order it owns. (The other reason this line used to give — that the ordinary list readers drop the validity triple — stopped being true when `memory.Memory` gained `valid_from`/`valid_until`/`verified_at`: retrieval hydrates all three, and `PortableMemories` selects them for itself.), and `Import*` are separate writes because no existing writer can preserve an imported id, `created_at` or pin. Every `Import*` takes an `apply` flag, so a dry run runs the same validation as the run it previews
- Time-decay scoring: convention/preference/fact never decay; architecture/pattern 45-day; decision/gotcha/dependency 30-day
- Empty-set guard: never replace all memories with empty reflection output, and a reflection response carrying no operations fails the LLM tier rather than relying on that guard alone
- Upsert dedup is one write transaction: `UpsertWithOptions` opens its `BEGIN IMMEDIATE` transaction BEFORE the FTS duplicate probe and commits the writes the probe decides on, because a probe outside it leaves a window another ghost process can use — a save that strengthened the same row in that window had its increment overwritten by arithmetic on a value read before the fact, and a row committed in that window was invisible to the probe, so two saves of one fact became two unlinked rows (both are cross-process; the per-`Store` `s.mu` cannot close either). The strengthen is therefore `SET importance = MIN(1.0, importance + ?)`: the value it adds to is the one the row holds when the statement runs. Never query the pool inside an open transaction on the same handle — `OpenDB` pins one connection, so it deadlocks; go through the `sql.Tx`. `FoldOnly`'s re-verify of its target happens in that same transaction, which makes it a statement about the probed row, not a race guard
- A newer schema is refused before it is written to: `memory.OpenDB` reads `PRAGMA user_version` and rejects a store from a newer Ghost BEFORE `initSQL` runs. `initSQL` is `CREATE … IF NOT EXISTS`, so on a store that merely has more than this build knows it is nearly a no-op — which is what hid the ordering — but an object the newer build renamed, replaced or dropped is recreated there, in a store the same call then declares unreadable. A fresh store has no stamp to read and is initialized and stamped; a store behind is backed up (`memory.vacuumInto`) and then migrated
- Project lookup: canonical path-prefix match (longest wins) OR exact repository remote OR basename name fallback — a basename match needs exactly one surviving candidate, a recorded path containing the session's directory, and no remote conflict; ambiguous matches are errors, a name-shaped input skips location checks, and a project with no recorded location is reached by name only. A path-shaped MCP save detects the checkout's Git remote and may bind it to one uniquely named, unclaimed project, but a unique name is the weakest evidence available: a candidate that records a usable path binds only when that path contains the saving directory, so an unrelated clone named after the project cannot take over its remote. A refused binding is reported to the save caller — the store returns it beside the project the memory was written to, and the save result names what kept the name and where the memory went — because routing the save is right and losing the context of a same-named project silently is not. Only the recorded-checkout refusal is repairable and it takes `ghost project merge` then `ghost project bind`, in that order: the merge drops the repository with the row it came from and the bind is refused while the other project still records that directory, so a merge alone re-splits on the next save, and a bind alone loses the memory just saved. A path-prefix match routes a save from inside a checkout to the project that encloses it but may not identify the repository for it: a save identifies the enclosing project only when the saving directory IS its recorded root or reports the same remote, so a nested checkout — a submodule, a vendored repository — never lends its remote to the project around it, while an ordinary subdirectory of the same repository still does. The session's remote is derived at most once per resolve, and only by the steps that read it
- Global memories: `_global` project, included in every project's context
- Source provenance: `manual` marks direct user material; `builtin` marks Ghost-shipped pinned rules and is never presented as user-authored
- Reflection promotion: cross-project candidates stay project-scoped by default; `ghost reflect --promote-globals` opts into `_global`, and the project replacement plus global writes share one transaction
- Reflection drop guard: every one of the eight categories is audited for a surviving merge target, not just the operational ones — an input under 45% token containment in the output it is compared against is re-added verbatim (`internal/reflection/drops.go`, `AuditGuardedDrops` + `RetainGuardedDrops`), and `ghost reflect --allow-drops` accepts the deletions instead. It is not the `manual` source that covers this: seeds are written `builtin`, agent saves `mcp` and reflection writes `reflection`, so nothing an agent writes is ever excluded from consolidation by that filter. With the per-id pass-through the guard no longer rescues omissions, and what it still covers is narrow: a MERGE's sources (`ReflectionResult.Merges`, carrying the ids it folded in AND the text it produced, scored against the UNION of the outputs because a merge may carry one source's substance across a survivor plus its siblings), an explicit `obsolete` drop, and the SQLite tier's absorbed duplicates (it names no ids, so all of its inputs are measured the strict way). Every claim the guard makes on the response's behalf is witnessed by text that is still in the result, for the same reason: with the pass-through, the union of a result whose merge was removed is the rest of the project, so a source scored against it passes containment against a vocabulary that has nothing to do with it. There is ONE exemption, and it is witnessed rather than inferred: `ReflectionResult.Replacements` names the input ids a response disposed of together with the text that took their place — a rewrite's own new text, or the emitted text of the successor a supersession named. A rewrite and a supersession are the same claim about the same thing, so they share one list and one check: re-adding such a row would put it back beside the text that replaced it, which is a duplicate by construction, not a save, and re-adding it is how a memory reading "three issues are still open" survived beside "the three open issues have all been fixed". The witness has to be present: a filter that runs over the result after the operations are resolved can remove the replacing text — `dropForeignProjectMemories` deletes a memory naming a project the input corpus never mentioned, and a rewrite or a merge is exactly such a memory — so an exemption trusted on the id alone disposes of a row with nothing in its place, silently, with nothing left for `--allow-drops` to act on. A claim whose text is gone lapses and the input goes back under the audit. Because a re-added verbatim memory reaches `ReplaceNonManual` through the exact-content reuse path, retention must not be treated as consolidation: `reusePreservesAge` (`internal/memory/store.go`) keeps the stored `created_at` and `source` when the re-emission matches the row's content and category — for every verbatim re-emission, not only retention: a `keep`, a pass-through and the SQLite tier's unmerged (always verbatim) output keep their age too, so decaying categories now age out of injection instead of being refreshed by each applied reflect — and omitting a stale memory cannot restart its decay or relabel its source, while a genuine rewrite (new text, or the same text in another category) still gets `created_at = now` and `source = 'reflection'`. That decision is only as good as the row it is made against, so the pick is deliberate too: `takeReusableRow` prefers the candidate whose category matches the emission (a project can hold one text under several categories, since Upsert keeps the incoming category on a linked copy) and falls back to the first, and the candidate query is `ORDER BY created_at, id` so a duplicate keeps the oldest age deterministically rather than whichever row the planner happened to return
- Reflection operation contract: the LLM tier returns `{"learned_context", "ops"}` where each op is `keep <id>` / `merge <id>,<id> -> <text>` / `rewrite <id> -> <text>` / `drop <id> reason: obsolete|superseded by <id>` on the ids the prompt renders (`internal/reflection/ops.go`), because the retired free-text contract had no vocabulary for "this row is fine": only a byte-identical re-emission kept an identity, so retyping — including retyping to improve — reset the id, and with it the embedding, the link graph (both ON DELETE CASCADE) and the age (measured: 12 of 13 new ids in one project, 15 of 17 in another). A memory leaves the corpus through exactly three operations: its id named as a merge source, its id named for a rewrite, or its id named in a drop with a reason. EVERY OTHER INPUT IS CARRIED THROUGH VERBATIM by `executeOps` — the pass-through that makes the tier zero-loss, and the reason the token guard is not load-bearing for omissions: an unnamed memory was emitted by nobody, so it survived only if the guard FAILED to recognise a survivor, which made a false positive in the "absorbed" direction a silent deletion with no warning and no `--allow-drops` (measured: "SSH to the bastion goes through port 2222, not 22" gone, because an unrelated survivor shared 45% of its tokens). A guard can only re-add what it flags, so an id the harness never mentioned needs no inference at all. `keep` and the pass-through emit the stored row's own content, category, importance and tags so the exact-content reuse updates it in place; a merge or rewrite derives its category from the first id, its importance from the strongest source, its tags from the union, and its scope from `inferGlobalScope` — the model states none of them, and an unattended model choosing `global` moves knowledge into every project's injected context. An operation id may echo the prompt's own `id:` label, which is stripped rather than failing the pass. Everything else is strict, because a partially-understood operation list is a corpus rewritten as if the model had said something else: an unreadable line, an id Ghost did not feed the model (compared case-insensitively, never by prefix), an id claimed twice, a supersession whose target the same response does not carry forward, or a response with no `ops` array at all each fail the whole response so the tiered consolidator falls through to SQLite. The grounding check (`internal/reflection/grounding.go`) is the other half: a merge or rewrite that introduces a path, hash, version, hostname or number found in none of its source ids is REJECTED and its sources are emitted unchanged — the output is never repaired, because Ghost cannot know which side of a corrupted identifier (`2.BeXIAhbj.js` vs `2.BeXIAhbq.js`) is true, and a wrong specific is stored as fact forever. That is also why a `rewrite` fixes a CLAIM and never a specific: the corrected value would be an identifier the source does not contain, so the prompt asks for `keep` (or `drop`) instead and the check is never asked a question it must refuse. Ordinary prose is not an identifier: a merge that needs a new connective word is a legitimate merge, and a bare proper noun the model misspells is outside these classes
- Hybrid search: 70% vector (cosine, Ollama) + 30% FTS5, RRF fusion — window selection is `Store.fuseAndRank` delegating to `selectWindow` (scope narrowing, keyword reservation, final cut), which every production search reaches including the FTS-only degenerate path; `FuseAndSelectWindow` is the exported entry point over the same seam, called only from the fusion tests; explain mode reuses the same scoped membership. Status demotion (`statusDemotionFactor` and the `resolvedDemotionFactor`/`globalDemotionFactor` constants in `internal/memory/demotion.go`) multiplies a resolved row's fused score — and a `_global` row's when a specific project is searched — by 0.5 inside `fuseCandidatePool`, before the cut, so it owns membership as well as order; it scales the score rather than dropping the row, so both stay searchable, and explain reports the same number as `status_factor`. With k=60 the factor effectively ranks a demoted row below every live candidate the legs fetched (a halved rank-1 two-leg score of ≈0.0082 sits under the 0.7/80≈0.0088 floor of the deepest vector row in a default window), but it only reorders what the legs fetched — each leg pulls limit*2 rows from the project plus `_global`, which counts against that budget, so a short project result set still fills with demoted `_global` rows. The keyword reservation skips rows whose status factor is below 1 (raw rank and the demoted score would otherwise disagree), and injection never reaches fusion on either path — `loadSessionContext` (`internal/mcpinit/hook.go`) builds the session-start digest, `Store.GetTopMemories` backs the MCP tool surface, both filter `resolved_at IS NULL` — so no factor reaches injection. What the digest does share with the tool surface is the scope rule and its label: the two loaders select `memories.scope`, print it with `assemble.ScopeLabel`, and narrow their own fetch by `injection.session_scope` using `memory.ScopeMatchesSQL`, the SQL statement of `memory.ScopeMatches` that the assembler applies in Go — they need it in SQL because their `LIMIT` chooses which rows are read at all, the same reason `scopesConflictSQL` exists for the fold targets, and a test runs both forms over the same rows to hold them together. Unset, the clause is absent and the block is byte-identical to the one that shipped. The formatted `ghost_memory_search` path does not read that window directly: it asks `Store.Candidates` for a widened untrimmed set and hands it to `assemble.Run`, so the caller's category and scope are applied before the window closes (the window itself is still chosen inside fusion, unchanged) — `internal/assemble` owns every decision after retrieval, and `internal/memory` never imports it
- Vector scan: both legs are brute force over the project's embeddings, and they run in two phases (`internal/memory/vector_scan.go`, #556). `snapshotVectors` copies every candidate row out of SQLite and returns, holding the store's read lock and its single connection for the copy only; `vectorRows.search` scores the copy afterwards, so the O(corpus × dims) cosine pass — which `ghost supersede` runs once per memory — no longer blocks writers for the length of the corpus. The copy keeps the stored bytes rather than decoding them and the score loop reads the little-endian float32s back out in place (`cosineFromBytes`, bit-identical to `cosineSimilarity` on a decoded vector), and the scope column is parsed only for a row that wins a slot; a `scopeProbe` decides per-row eligibility by checking whether the stored text can mention a requested key at all, which can only save a `json.Unmarshal` and never decides membership, since `ScopeMatches` only excludes a row that names a requested key and disagrees. Ranking keeps a bounded window instead of the corpus — a min-heap whose root is the worst row held, ordered once at the end over at most `limit` rows — and the order is total (cosine descending, exact ties broken by scan position) so the answer is a function of the stored data AND the order the scan yielded it in, not of the heap's internals; that is not independence from the scan order (the query has no ORDER BY, so a VACUUM or index rebuild can reorder a tie), and it does not claim to be — what it buys is that two searches over the same rows in the same order agree, which the unstable `sort.Slice` it replaced did not promise. `TestSearchVectorRankingMatchesTheCollectAndSortBaseline` pins the whole result against a transcription of the pre-#556 collect-and-sort search, and `TestVectorSearchCopiesTheCorpusUnderTheStoreReadLock` / `TestVectorSearchScoresWithTheStoreLockReleased` pin that the copy takes the read lock and the scoring pass does not. A writer is still kept out during the copy, and that is the connection rather than the mutex: OpenDB pins the pool at one, so no amount of lock work lets a write start while a query is streaming. The scratch is recycled through a `sync.Pool` on the store, and an oversized embedding buffer is dropped on return rather than retained. What a query still allocates is the driver: `modernc.org/sqlite` copies every BLOB and TEXT column into a fresh allocation per row, which is why the remaining cost is a decoded-vector cache keyed on `PRAGMA data_version` (and then an ANN index), not more work on the scoring loop
- Vector-space identity: a stored vector is only scored when `memory_embeddings.model` equals the identity this process embeds into (`Store.SetEmbeddingIdentity`, fed from `embedding.VectorIdentity`). A model, dimension or task-prefix change therefore retires the old vectors instead of comparing them with queries from the new space. The rule is read in four places, one per caller: `loadVectorRows` (may a vector enter a search), `GetEmbedding` returning nil (may a stored vector act as a QUERY vector — the link worker and `ghost supersede` both do), `UnscannedEmbeddedMemoryIDs` (may the linker compare this memory yet), `EmbeddingStats` (is it covered, which `ghost mcp status` and `ghost_health` report). A retired vector never hides its memory: the keyword leg still finds it. Two side effects of a rewrite ride along: `StoreEmbedding` clears the row's `link_scans` slot when the identity changes (so the linker re-scans it in the new space — the re-scan ADDs current-space `related` edges alongside the ones the retired space produced; nothing invalidates those old rows, and `CreateLink`'s `MAX(strength, excluded.strength)` upsert means an edge whose new-space similarity is lower keeps its old strength), and the foreign-vector warning in `loadVectorRows` is emitted once per retired identity (a second reconfiguration in the same process warns again). `EmbeddingStats` reports stale and unembedded rows separately so `ghost mcp status` can show both. The identity is opaque (compared, never parsed) and empty means "no model configured", which keeps the bench harness and tests unfiltered
- Memory links: `memory_links` edge table auto-populated by cosine similarity (internal/linking worker); links cascade-delete with memories and self-heal after reflection. A graph-expansion ranking bonus was evaluated and removed — dominated by a deeper vector-k (links and the vector leg are both cosine); the link graph is retained for Obsidian export and supersedes ranking (see `docs/superpowers/specs/2026-07-20-graph-expansion-stays-off-design.md`). No edge may join a scope-conflicting pair: every writer refuses one (`Upsert`'s dedup probes, the linker's `related` edge, `ghost supersede`'s candidates) and every reader ignores one already stored — the two ranking guards (`DemotionPenalties`, `SupersedePenalties`), `Store.SupersedesWithin`, `ghost resolve`'s supersedes piggyback and the repair pass's matching floor (`scopeCompatibleSupersedes`, which needed `GetByIDs` on `resolveStore`/`reassessStore`/`resolveCapableStore` for the link endpoints' scopes), and the two fold-target liveness checks (`foldTargetStillLive` + the cross-category probe). Scope exempts a pair from ranking and folding; it never deletes a `memory_links` row. Where the exemption is decided: inside the candidate query, always, because the same `LIMIT` picks the candidates — a scope check applied after the cut spends the budget on rows the caller may not use and misses a compatible one ranked just below (#665). So the two cosine writers narrow before their window (`SearchVectorScoped`, in Go over the scan, so its top-k is the limit and there is no statement to fold the rule into) so their neighbour budgets count only linkable rows, and `Upsert`'s two dedup probes carry the rule inside their own `LIMIT 15` for exactly that reason. `foldTargetStillLive` is the one statement that carries it without a window to protect (it names one row by id) and for a different reason: a scope-conflicting `supersedes` edge is not a verdict that row may be acted on. Both are one rule in two forms, `scopesConflictSQL` in `internal/memory/scope.go`, held to `ScopesConflict` by `TestScopesConflictSQLAgreesWithScopesConflict`
- Resolution classifier: `ghost resolve` runs a keyword prefilter, then a deterministic KEEP veto, then batches up to 8 notes per KEEP-biased CLI-harness classify call (`claude`/`opencode`/`codex`/`goose` subprocess, numbered `N: RESOLVED | closed-by: <fact>|KEEP` reply judged by a strict first-field line parser) to mark `resolved_at`, dropping resolved-evidence memories (changelogs, cost estimates, closed experiment notes) from ranked injection while keeping them searchable. KEEP-biased in code, not prose (#640: an independent judge found ~1 resolve in 3 on a real DB had buried durable knowledge): `resolve.VetoKeep` settles a candidate KEEP with no harness call when its text carries an imperative (`never|do not|don't|must|always|required`) or an open marker (`not yet|outstanding|still pending|still open|still stale|unresolved|todo`), all case-insensitive and word-bounded; the rubric asks the fresh-session question (would an agent starting fresh make a mistake, repeat work, or break a rule without this?) and says dates, PR numbers, commit hashes and "fixed in" do not resolve a note; a RESOLVED must carry a non-empty `closed-by:` or the parser reads it as KEEP. The veto guards the classifier only — the supersedes-edge piggyback and correction pairing still demote. Only explicit KEEP verdicts are cached by content hash in `memories.resolve_kept_hash` (schema v7; the v3 hash prefix invalidates the v1 implicit-KEEP and v2 explicit-KEEP caches, so #640's re-judged rules are re-asked); UNKNOWN parse failures remain uncached and are retried, so a converged project makes no calls only after explicit KEEPs. Dry-run writes nothing, `--apply` writes resolved_at and explicit KEEP cache entries; transport or verdict-count failures fail fatally rather than applying incomplete results, while UNKNOWN lines remain eligible for a later pass. `ghost resolve <project> --reassess` is the repair path for the resolutions the pass already got wrong: it re-runs the vetoes and the classifier (no keyword prefilter) over memories that are ALREADY resolved, prints the ones that now come back KEEP, and with `--apply` clears their `resolved_at` via `memory.ClearResolved` and caches the classifier's KEEP verdicts; a failed clear is fatal, a failed cache write only warns; `memory.ClearResolved` runs every batch in one transaction so "a failed clear repaired nothing" is literally true. It honours Run's two free demotions as a floor — a row a live `supersedes` edge still asserts, or an older row a NEWER *unresolved* correction pairs with (the same pool Run searches, via `correctionPairTargetsFrom`), is counted as `Demoted` and left resolved, because Run fires both before the veto and the KEEP cache, so clearing it would report a repair the next pass undoes. The pairing is re-checked after the re-KEEP set is known (`holdBack`), because a correction that is itself repaired leaves the resolved pool and would re-assert its pairing; both the floor and the hold-back pair only Run's keyword-prefiltered subset, since a keyword-free row is never a pairing target and holding it would be a permanent, mislabelled hold no later pass could undo. A reasonless `closed-by` is not a reason: a bare mention of the key without its colon ("no closed-by available") and a placeholder value (`none`, `n/a`, `tbd`, …) are both KEEP. Never invoked from the stop hook's synchronous path (that path forbids DB access); the stop hook's detached `ghost lifecycle` spawn (whose resolve phase runs `--apply`, never `--reassess`) and the standalone batch command are the only callers. See `docs/superpowers/specs/2026-07-26-resolution-classifier-design.md`.
- Classifier backend: `resolve`/`supersede` classify via the calling session's own CLI harness — the backend is picked from the MCP client's reported identity (an opencode session uses the opencode binary, claude uses claude, etc.) via `ai.SourceProvider`, or — on the headless CLI path — from `--source`, else `ai.DetectSource()` (env markers plus process ancestors); if no calling harness can be determined it fails fast with an actionable error. There is no claude-first cascade: `NewSourceProviderForSource("")` is unavailable, and `ai.CLIProvider` is an availability probe only. MCP sampling was retired from this path per SEP-2577 — see `docs/superpowers/specs/2026-08-24-resolve-sampling-path-design.md`.
- Lifecycle spawn guards: the stop hook spawns the reflect→resolve→supersede chain behind TWO independent per-project guards. `AcquireLifecycleLock`'s PID file says "a run is not already in progress"; `lifecycle.min_interval` (default 30m, `0` to disable) says "a run did not start too recently". The second is the mtime of `lifecycle-<project>.last` in the data dir — a file, not a row, because the stop hook's synchronous path forbids DB access. Only the `ghost lifecycle` process writes it (`mcpinit.TouchLifecycleStart`), and only once it has passed every precondition that can exit non-zero, so a run that dies before doing any work does not burn a window. Most unknowns read as "run" (no stamp, unreadable, non-regular) so that a bookkeeping problem cannot silently stop maintenance; a stamp dated in the FUTURE is the deliberate exception and reads as INSIDE the window, because a future date is not evidence the window expired. `config.LifecycleConfig.MinIntervalDuration` resolves an unreadable value to the default rather than `0`, because `0` means the cooldown is off.

## Critical Rules
- Always `go vet ./...` before committing
- Tests use `go test ./...`
- Never commit to main directly — feature branches + PRs
- SQLite schema is embedded as a Go string constant in `internal/memory/schema.go` (currently v14; `migrate.go` carries one frozen step per version)
- `ghost mcp init` is idempotent and non-destructive — safe to re-run
- A test that needs a real *program* builds it with `go build` into a temp dir rather than re-exec'ing its own binary: under `go test` the test binary is the suite, so a self-spawn re-runs every test in the package once per spawn and a bug in the barrier logic becomes a fork bomb. A `-test.run`-bounded child test is fine (`internal/ai/harness_policy_test.go` does exactly that)
- The concurrency contract in `docs/architecture.md` is enforced by `TestMultiProcessSharedDatabase` (`internal/memory/multiproc_process_test.go`, helper in `internal/memory/testdata/multiproc`): MCP server, CLI child, read-only handle, lifecycle writer, pinned-snapshot reader and sampler processes against one database. It reads `memory.OpenDB`'s and `memory.readOnlyDSN`'s settings back from a live connection, so dropping WAL, `foreign_keys`, `busy_timeout`, the pool pin or `_txlock=immediate` fails it. `mcpinit`'s own DSNs are not covered. Skips under `-short`; makes no LLM call
