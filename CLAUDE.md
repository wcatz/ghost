# Ghost — MCP Memory Server

## Stack
- Go 1.26+ CLI application
- SQLite with FTS5 for memory persistence (modernc.org/sqlite — pure Go, no CGO)
- CLI harness callers (claude/opencode/codex/goose subprocesses) — used by reflection, resolve, and supersede. Each harness owns its authentication and billing; Ghost does not add a direct API client. The prompt is written to the child's stdin and no positional message is passed: the kernel caps one argv element at 32 pages (128 KiB on a 4 KiB-page x86, 512 KiB on a 16 KiB-page one) and a reflect prompt reaches megabytes, so an argv prompt failed the spawn with E2BIG instead of answering. `claude -p` and `opencode run` read the message from a pipe when none is given; codex gets `exec -` and goose `run -i -`. `claude --system-prompt` stays an argument — small, fixed, and never confusable with user content. `cli.model_reflect` / `model_resolve` / `model_supersede` pin the opencode harness model per phase (each phase is its own process; ignored by claude/codex/goose which have no model flag). Empty = any inherited `GHOST_OPENCODE_MODEL`, else Ghost's explicit `opencode/big-pickle` default; a configured pin overrides an inherited env pin for that phase.
- MCP server via modelcontextprotocol/go-sdk (stdio transport)

## Architecture
- `cmd/ghost/main.go` — CLI entrypoint; subcommands: mcp, hook, reflect, resolve, supersede, project, obsidian, bench, backup, export, import, upgrade, version, context. `runCLI` answers `-h`/`--help` (`cmd/ghost/help.go`, one usage table) before the dispatch, so a help request has no side effect
- `internal/adversarial/` — Test-only support: the shared hostile-input corpus (prompt injection, secret shapes, invisible-character tricks, path shapes) and the shared inert-content invariant the three untrusted parse surfaces assert against (#585). Nothing under `cmd/` may import it; it exists to be called from `_test.go` files. The invariant in one sentence: a value parsed from an untrusted surface is data — stored exactly as parsed, naming at most one path component inside the directory its surface owns, and never deciding the parse. `internal/mcpserver/adversarial_test.go` (#538) proves the same invariant one layer out, over the wire
- `internal/ai/` — CLI-harness providers (`CLIClient`/`OpenCodeClient`/`SourceProvider`) used by reflection + resolve + supersede — no Anthropic HTTP API client. Every child is spawned through the one `harnessCommand` funnel, which applies the `harnessEnv` allowlist and confines the working directory and temp variables to an invocation-owned scratch dir. The backend is part of the policy, so each harness keeps only its own auth/config root (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, the safe `GOOSE_*` set, `OPENCODE_API_KEY`). Two harnesses additionally get an isolated config tree because their plugin/MCP discovery would otherwise find Ghost's own registration: opencode gets a fresh home plus an `mcp: {}`/`plugin: []` config, and goose gets an empty invocation-owned `HOME` (its plugin root is home-relative by specification, so `XDG_CONFIG_HOME` alone cannot move it). The goose home carries the config rather than restating where it lives — the inherited `XDG_CONFIG_HOME` when set, otherwise reproducing each home-relative root goose may resolve (`.config/goose`, `Library/Application Support/goose`; Windows uses `%APPDATA%`, which the allowlist already passes through) — so goose's own per-platform resolution is untouched and authentication still works. `GOOSE_PATH_ROOT` is the exception: goose consults it before any home variable (plugins resolve to `$GOOSE_PATH_ROOT/.agents/plugins`), so it is repointed at a root inside the isolated tree with the real `config/` carried into it, and a relative value is left alone because goose ignores one. Where a symlink is refused (Windows without Developer Mode) the files are copied instead. If the home cannot be established, the call fails rather than running with the real home. Codex needs no tree — `--ignore-user-config` already covers it.
- `internal/memory/` — SQLite CRUD, FTS5 search, vector search, time-decay scoring, and the retriever contract behind the assembler (`Store.Candidates`: one read snapshot, widened untrimmed rows with their scoring facts, leg/edge statuses)
- `internal/assemble/` — context assembly: `assemble.Run` is the one entry point (one `[]stage` in `pipeline.go`), owning selection, validity, category/scope predicates before window closure, provenance (pinned at 1.0), budget closure, the outcome, the always-recorded trace and the shared `Item.Line()` renderer. Depends on one method, `Candidates`; `internal/memory` never imports it. `ScopeLabel` is the scope label `Item.Line()` embeds and the session-start block prints, so no surface re-derives it; `ScopeContradicts` is the named negation of `memory.ScopeMatches` rather than a second copy of the rule. The session-start loaders are callers of those two but not yet of `Run` — passive retrieval is not served by the seam
- `internal/mcpserver/` — MCP server: 20 tools + 4 resources + 2 prompts (`recall_project`, `record_decision`)
- `internal/hostevent/` — Normalized host-event contract (v1) and the transcript scanners; every parse or validation failure is an error the caller turns into "allow the stop", and a payload past `maxPayloadBytes` is one of them (nothing else on the path bounded it — the hook read stdin with an unbounded `io.ReadAll`, and `Parse` retains the payload decoded and again verbatim in `Raw`). The hook now reads through `hostevent.ReadPayload`, which stops one byte past the ceiling, so the bound limits the allocation and not only the parse. Field values are text the host did not write, so only the contract's own fields decide the envelope: an unknown field cannot become a known one, an instruction-shaped `hook_event_name` normalizes to nothing, and the goose native aliases (`event`, `working_dir`) bind only for `--source goose` and only per field where the dialect field is absent. `GhostSaves` counts STRUCTURE, never prose — a save tool named inside a text part, a shell command or an opencode Code Mode `execute` body is not a save, because that count is the save-nudge's evidence
- `internal/mcpinit/` — `ghost mcp init`, `ghost mcp status`, `ghost hook <event> --source <host>` (contract-v1 lifecycle dispatch; installers: claude-code, opencode plugin, codex TOML+hooks.json, goose Agent-Plugins package; goose field aliasing lives in hostevent.Parse). Every write to a file the user owns — settings.json, codex config.toml and hooks.json, the opencode plugin, the goose package, the MEMORY.md redirect — goes through `writeFileAtomic`/`writeFileAtomicPrivate` in settings.go, never a bare os.WriteFile: temp file in the same dir, flushed (data and mode) with `f.Sync()`, then rename, then the parent directory flushed, so an interrupted write cannot truncate a config, a reader holding it open still sees a whole document, and a power cut can leave neither an empty config nor a missing one. A temp-file flush failure stops the write and is reported; a directory-flush failure is not (the rename already landed, and Windows has no directory flush at all). The rename carries the permission bits across and nothing else — not the owner, POSIX ACLs, xattrs or hardlinks, so a hardlinked config in a dotfiles repo silently diverges from its repo copy. `writeFileAtomicPrivate` additionally clamps the mode to 0600 and is used only by settings.json, because that is the ceiling every pre-refactor save enforced; the other files keep whatever mode the user chose, even where a codex `[mcp_servers.ghost.env]` sub-table can hold a credential. Ghost's own marker/scratch files are exempt. Only settings.json gets a `.bak`, and only on the first save (`writeBackupOnce`).
- `internal/claudeimport/` — One-time import of Claude Code auto-memory on first contact. The files are written by a session that read a checkout Ghost never chose, so the parse layer is an untrusted surface: a front-matter line gets its own bound (`maxFrontmatterLine`) because `bufio.Scanner`'s 64 KiB default stops the scan on a long description and the block's loss is silent (the type, and with it the category, went with it), a block that could not be read whole is imported as body text rather than half-parsed, and a file past `maxMemoryFileBytes` is skipped. The import writes nothing to disk at all — a fixture asserts the tree is byte-identical afterwards — and it never promotes: `categoryMap` is the only thing that picks a category, so a planted `source: manual`, `pinned: true` or `type: _global` reaches none of the fields consolidation filters on
- `internal/embedding/` — Ollama async vectorization worker; every vector is stamped with the identity of the space that produced it (`<model>[:<dimensions>][+prefix]`, `embedding.VectorIdentity`) and nomic-embed-text is embedded with its `search_document: `/`search_query: ` task prefixes
- `internal/linking/` — Background worker linking similar memories into a graph
- `internal/resolve/` — `ghost resolve`: LLM-classified de-weighting of resolved-evidence memories (drops from ranked injection, stays searchable); classifies via CLI harness (see Classifier backend below)
- `internal/supersede/` — `ghost supersede`: LLM-classified 'supersedes'/'causes' link creation over live memories, batched 8 candidate pairs per harness call with a content-keyed NEITHER cache (`supersede_checked`, schema v8, cascading FKs) so a converged project's fresh candidates make zero calls — except reversed ones, which are never cached and are re-asked every pass (live-link pairs are still validated each pass). Pairs are oriented by `updated_at`, so the prompt also carries each note's `created_at` and offers a fourth verdict, `reversed`: a supersedes link only points newer→older, so a verdict saying the OLDER note is the current one is refused (never written, never cached) rather than written backwards (#641). A pair whose endpoints' scopes conflict is never classified: the scope reaches `SearchVectorScoped` so the neighbour budget counts only linkable rows, and `Run` re-checks the rule over every pair it is about to spend a call on — the reclassify path included, which is the only way a link written before the rule existed is reached at all. The classifier is handed note text only, so it cannot see a `memories.scope` column; the guard is structural, not a rubric line. The reclassify half saves one call per endpoint edit rather than one per pass, because skip-if-unchanged already holds an untouched pair quiet. Neither refusal is counted in `Result`: against the shipped store the query drops the conflicting rows before `SelectCandidates` sees them, so a count there would read as zero for work declined. An existing scope-conflicting edge is left in the graph and exempted at read time by `SupersedePenalties`, by `ghost resolve`'s supersedes piggyback, and by the two fold-target liveness checks — the piggyback is the one that would have been persistent, stamping `resolved_at` on the older endpoint
- `internal/bench/` — `ghost bench`: retrieval-quality benchmark harness (graded dataset + sweep + staleness/recency/maintenance-state suites + the no-answer false-positive report)
- `internal/obsidian/` — One-way Markdown vault mirror (`ghost obsidian export|sync`). The store can hold ids, project names, tags and bodies Ghost never generated (`ghost import` writes an artifact's ids verbatim), so every name it builds is a name somebody else chose: `idToken` keeps the first 8 bytes of an id only when they name a single path component a person could type and hashes the id otherwise (a separator put the note outside the `Memories/` subtree prune manages and had it deleted; a tab or line break is a legal name nobody can open; a NUL failed the whole export with `EINVAL` on every run), `folderNames` replaces a folder over `maxFolderName` the same way it replaces one that would escape because `ENAMETOOLONG` failed the export just as permanently, and `hasGhostID` unquotes exactly what `yamlScalar` emits. What prune keys its RETENTION on is the canonical FILENAME (`keepSet`), not the id read back out of the note — the front matter still decides whether a file is Ghost's to touch at all, so the block is prune's ownership test, but the id inside it is not its key: `yamlScalar` flattens tab/CR/LF to a space so every key stays on one line, and that is lossy — three records can render one `ghost_id` line, and keyed on that line they would collide on it and two of the three would be deleted. A key that decides what to keep should be one the system holds, not one parsed back out of a file written for a human. Every front-matter value still has to occupy exactly one line — that is what makes the note valid YAML and the ownership test's answer well-defined (it reads to the first `---` and takes the one `ghost_id:` line there) — but no value read out of front matter, forged or merely flattened, can now make prune drop a note it wrote
- `internal/portable/` — The portable JSONL artifact (`ghost export` / `ghost import`): one typed record per line behind a schema-version header, written projects-then-memories-then-tasks-then-decisions in id order so two exports of an unchanged store are byte-identical. It is a wire format, not a backup — `memory.Store.Backup` is the restorable copy. Import never overwrites an id that already exists, so re-running is always safe; a record it cannot import is rejected individually and the run continues, so one hand-edited line does not abandon the file. A dry run opens the store read-only, so the preview cannot migrate or seed what it previews — which means openReadOnlyTransferStore must also refuse a store whose PRAGMA user_version is behind or ahead (memory.DBUserVersion / memory.SchemaVersion), or the first query fails with SQLite's "no such column" instead of a version mismatch. The artifact deliberately omits Ghost's own _global builtin seeds: they are written per-install under hex(randomblob(16)), so every importer's id-only dedup would duplicate them permanently, and the destination already re-creates them by content. Imported memories are stamped `source = "onboarding"` and unpinned unless `ImportOptions.TrustProvenance` is set: an artifact is a file that arrived from somewhere, and on its own authority it must not be able to plant rows the store exempts from consolidation by name (`manual`, `builtin`) or by pin. Embeddings, memory links and the resolve KEEP cache are not in the artifact: all three are derived and rebuilt by their workers
- `internal/reflection/` — Memory consolidation: LlmConsolidator + SQLiteConsolidator. The LLM tier speaks per-id operations, not free text (see "Reflection operation contract")
- `internal/secret/` — Credential-shape detection for stored text (`Detect`); shape-based, never keyword-based
- `internal/provider/` — Interface contracts: LLMProvider, MemoryStore
- `internal/config/` — Layered YAML + env config (koanf). `Load` returns an error for a config file that exists but does not parse, for a `GHOST_*` value that is not readable as its key's type, and warns on file keys no `Config` field binds (env names are not key-checked — most `GHOST_*` variables are not config keys); CLI subcommands call it and fail. `LoadForHook` is the host-session path (SessionStart/Stop hooks, obsidian auto-sync, routing, the scratch budget): it reports the same problem on stderr and returns `FallbackConfig` — the compiled defaults plus the `GHOST_*` environment, i.e. every layer that does not read a file — so a typo cannot fail someone's session and cannot undo an environment opt-out. `envOverrides` lists the `GHOST_*` names the generic `GHOST_` prefix + `_`→`.` transformer cannot map, each with the parser for its key's type. `SetWarningWriter` redirects the warning sink, which `runMCP` points at its log channel; the sink is atomic because harness spawns warn from goroutines.
- `internal/selfupdate/` — `ghost upgrade` self-update from GitHub Releases

## Key Patterns
- Memory categories: architecture, decision, pattern, convention, gotcha, dependency, preference, fact
- Untrusted parse surfaces (`claudeimport`, `hostevent`, `obsidian`): a value somebody else wrote is DATA. It is stored exactly as parsed, it names at most one path component inside the directory its surface owns, and it never decides the parse — the parser's own vocabulary does, and a payload that does not fit is rejected or mapped to the documented fallback, never obeyed. `internal/adversarial` states the invariant once and holds the corpus all three suites drive (#585). Two rules that look like filters and are not: a planted payload stays retrievable (hiding the tampering is worse than showing it; quoting into the data block happens on the way out), and every `hostevent` refusal fails open, because "allow the stop" is the only response the hook contract emits. Defects here were silent rather than loud — a front-matter line past `bufio.Scanner`'s default cost a memory its category, a separator in a record id cost it its note, a quoted `ghost_id` cost it a second prune pass — which is why each is a fixture and not a line of prose
- Backup and portable transfer: `ghost backup` is `Store.Backup` → `memory.vacuumInto` (SQLite `VACUUM INTO`, the same one implementation the pre-migration copy uses), so both claim the destination with `reserveBackupPath` (a `0600` `O_EXCL` create, before any byte is written) and both refuse an existing path. `VACUUM INTO` names no mode, so creating the file first is what keeps a full copy of the memory database out of a group-readable window on an `--out` outside the `0700` data directory. The write lock is held for the vacuum and nothing longer. It counts the snapshot by opening the written file read-only, never the live one — the counts a restore is checked against have to describe the file that was written. The portable artifact (`internal/portable`) is the other half: `memory.PortableProjects` / `PortableMemories` are separate reads because `ListProjects` has no `repo_remote` and an artifact needs the columns in an order it owns. (The other reason this line used to give — that the ordinary list readers drop the validity triple — stopped being true when `memory.Memory` gained `valid_from`/`valid_until`/`verified_at`: retrieval hydrates all three, and `PortableMemories` selects them for itself.), and `Import*` are separate writes because no existing writer can preserve an imported id, `created_at` or pin. Every `Import*` takes an `apply` flag, so a dry run runs the same validation as the run it previews
- Time-decay scoring: convention/preference/fact never decay; architecture/pattern 45-day; decision/gotcha/dependency 30-day
- Empty-set guard: never replace all memories with empty reflection output, and a reflection response carrying no operations fails the LLM tier rather than relying on that guard alone
- The gate lives in `TieredConsolidator`, NOT in the LLM tier — so naming a backend bypasses it unless the tier is wrapped. `ghost reflect --tier cli` and `--tier opencode` used to hand the bare `LlmConsolidator` to the apply path and had no floor at all, while the default `auto` tier and the unattended path were bounded; `eval/cycle` measures with `--tier opencode --apply`, so the suite was grading an ungated consolidator against a gated production one. Both branches now go through `gatedLLMTier` (`cmd/ghost/lifecycle.go`), which calls `reflection.NewGatedConsolidator` — one tier, no fallback added, so "exactly this backend" still means that and a too-small answer is a failed run rather than a quiet drop to Jaccard. It is a named function because `runReflect` calls `os.Exit`, so the tier switch is unreachable from a test and the behaviour has to be pinned at the seam. The wrapper reports the tier's OWN name, not the `tiered:` prefix (`TieredConsolidator.gated`): `Consolidator: cli` must keep printing `cli`, because a script or saved log-grep keyed on that label breaks silently otherwise, and wrapping a tier changes how it is bounded, not which one runs. The prefix marks WHICH CONSTRUCTOR ran, not how many tiers were in the list — `auto --require-llm` is a one-tier list and still prints it, so do not read the prefix as a claim about fall-through
- Reflection reduction warning counts survivors, not one scope: `reportReductionWarning` (`cmd/ghost/lifecycle.go`) measures `reflectRetained`, which adds the cross-project candidates back in when promotion is off because `applyReflection` folds them into the project. Reading `len(projectMems)` understates retention by the whole candidate set and fired `>50% reduction` on rounds that lost nothing — a warning that cries wolf on the one path where nobody reads it is worse than none. The input side is `len(consolidatable)`, not a re-count of non-`manual` sources: `consolidatable` already dropped `manual`/`builtin`/`pinned`/resolved, so every row left is one `ReplaceNonManual` would delete. It fires on a dry run too (the call is above the `if !apply` return), which is deliberate — the preview reports the compression it would apply — and only from `reductionWarnMinInput` (6) up, which is where the quality gate stops judging and this becomes the only signal
- Validity and provenance are written by the tools, or by nothing: `ghost_memory_save`, `ghost_save_global` and `ghost_memory_update` share one `validityArgs` struct (`internal/mcpserver/validity.go`) and one resolver, so the six optional arguments mean the same thing in all three schemas. `valid_from`/`valid_until`/`verified_at` take RFC 3339 or a date and are stored in `memory.StoredStampLayout` (`verified: true` is the same field as "now", and `verified` together with `verified_at` is refused rather than resolved); a window that does not end after it starts, a `confidence` outside [0,1], an unreadable stamp and a `source_ref` over `MaxSourceRefLen` are tool errors, because stage 2 would otherwise read them as claims nobody meant. Nothing is invented: an omitted argument is absent, and absent is NULL, so a store can still tell "nobody said" from "said to be nothing" — which also means a stamp can be replaced but not removed. Only `ghost_memory_search` filters on a window: the browsing surfaces do not run the pipeline, so they render one marked `expired` instead (assemble.ValidityStateOf), while the session-start block renders its own rows and shows no marker at all. Saying otherwise in a tool description is a lie the next surface inherits — and a surface that renders its own rows does not get the shared renderer for free. `agent` comes from `provenanceFor` (client name, then process ancestry) and `session_id` from `req.Session.ID()`, which is "" on the stdio transport every Ghost host actually uses — NULL is the honest record there, and a made-up id would be indistinguishable from a real one. `memory.UpdateMemoryWithOptions` writes the columns with `COALESCE` (and `NULLIF` on the provenance strings) rather than a read-merge-write, so an omitted field is the stored value by construction and two concurrent edits cannot lose each other; `provider.MemoryStore` is not widened for it, so `mcpserver` reaches it through the `updateCapableStore` assertion. Stage 4's multiplier stays `1.0`: the renderer shows confidence and the writer records it, and nothing ranks on either
- Save-time consolidation opt-out: `ghost_memory_save`'s `pin` maps to `UpsertOptions.Pin` and pins inside `Upsert`'s existing `BEGIN IMMEDIATE` transaction, so a memory can opt out of `ghost reflect` in the call that stores it rather than in a second `ghost_memory_pin` call — nothing an agent writes is excluded by `source`. A fold pins BOTH rows (the copy just stored and the existing row the text merged into, which is the one a later consolidation is most likely to absorb), so the save result says so rather than letting the caller infer the pin from the id it returned; `FoldOnly` stores no row, so the target is the only thing the request can mean. `pinMemoryTx` deliberately leaves `updated_at` alone: the row's age and timestamp are load-bearing for decay and the `--skip-unchanged` fingerprint
- Upsert dedup is one write transaction: `UpsertWithOptions` opens its `BEGIN IMMEDIATE` transaction BEFORE the FTS duplicate probe and commits the writes the probe decides on, because a probe outside it leaves a window another ghost process can use — a save that strengthened the same row in that window had its increment overwritten by arithmetic on a value read before the fact, and a row committed in that window was invisible to the probe, so two saves of one fact became two unlinked rows (both are cross-process; the per-`Store` `s.mu` cannot close either). The strengthen is therefore `SET importance = MIN(1.0, importance + ?)`: the value it adds to is the one the row holds when the statement runs. Never query the pool inside an open transaction on the same handle — `OpenDB` pins one connection, so it deadlocks; go through the `sql.Tx`. `FoldOnly`'s re-verify of its target happens in that same transaction, which makes it a statement about the probed row, not a race guard
- A newer schema is refused before it is written to: `memory.OpenDB` reads `PRAGMA user_version` and rejects a store from a newer Ghost BEFORE `initSQL` runs. `initSQL` is `CREATE … IF NOT EXISTS`, so on a store that merely has more than this build knows it is nearly a no-op — which is what hid the ordering — but an object the newer build renamed, replaced or dropped is recreated there, in a store the same call then declares unreadable. A fresh store has no stamp to read and is initialized and stamped; a store behind is backed up (`memory.vacuumInto`) and then migrated
- Project lookup: canonical path-prefix match (longest wins) OR exact repository remote OR basename name fallback — a basename match needs exactly one surviving candidate, a recorded path containing the session's directory, and no remote conflict; ambiguous matches are errors, a name-shaped input skips location checks, and a project with no recorded location is reached by name only. A path-shaped MCP save detects the checkout's Git remote and may bind it to one uniquely named, unclaimed project, but a unique name is the weakest evidence available: a candidate that records a usable path binds only when that path contains the saving directory, so an unrelated clone named after the project cannot take over its remote. A refused binding is reported to the save caller — the store returns it beside the project the memory was written to, and the save result names what kept the name and where the memory went — because routing the save is right and losing the context of a same-named project silently is not. Only the recorded-checkout refusal is repairable and it takes `ghost project merge` then `ghost project bind`, in that order: the merge drops the repository with the row it came from and the bind is refused while the other project still records that directory, so a merge alone re-splits on the next save, and a bind alone loses the memory just saved. A path-prefix match routes a save from inside a checkout to the project that encloses it but may not identify the repository for it: a save identifies the enclosing project only when the saving directory IS its recorded root or reports the same remote, so a nested checkout — a submodule, a vendored repository — never lends its remote to the project around it, while an ordinary subdirectory of the same repository still does. The session's remote is derived at most once per resolve, and only by the steps that read it
- Global memories: `_global` project, included in every project's context
- Source provenance: `manual` marks direct user material; `builtin` marks Ghost-shipped pinned rules and is never presented as user-authored
- Credential guard: no write path stores a credential value. Stored content is embedded, replayed into every later session's context, mirrored to the Obsidian vault, and quoted into the next `reflect`/`resolve`/`supersede` prompt, so anything saved is already copied to a third-party model. `memory.rejectSecret` is the one seam (`internal/memory/secret_guard.go`), called before any statement by every path that writes caller-supplied text — `UpsertWithOptions` (so `Upsert`, `UpsertWithProvenance`, both save tools, the Claude import), `UpdateMemory`, `RecordDecision` (each `alternatives` entry too), the three task writers, `UpdateLearnedContext`, and the four portable importers (`ImportProject`'s name and path included — `repo_remote` is not guarded because `NormalizeRepoRemote` strips the userinfo) — and returns `*SecretContentError`/`ErrSecretContent` naming the field and the format, never the value. The importers place the guard in a narrow window: after the id-presence check, so a record already in the store stays a skip and the portable format's re-run-is-always-safe promise holds; before the `apply=false` early return, so a dry run classifies a record exactly as the apply run it previews would. `internal/secret` decides by value SHAPE, never by the words around it: a memory store's ordinary vocabulary is "rotate the password quarterly" and "the access token lives in the runner env", and a keyword heuristic refuses both, which is why `internal/reflection`'s `looksLikeSecret` (a scope decision — is this safe to replay into every project — never a save decision) stays separate. Its rules whose verdict needs the matched text walk every candidate, not the leftmost one, or a `${DB_PASSWORD}` placeholder early in the save shadows a real credential later in it. An assigned credential needs BOTH a key that names a secret (split on `_ - .` and camelCase, so `existingSecret`, `token_url` and `token_sha` are references, not fields) AND a value that is not a reference: no dotted identifier path (every credential encoding excludes `.`, so `opts.OAuthClientSecretFromVault` names a place), no template, no code expression, no single-case word segment, and a length/entropy bar AND a value that is credential material (not a template, not a URL, no single-case word segment, and a length/entropy bar) — a Helm chart, a Grafana provisioning file and a CI workflow are mostly about credentials and record the NAME of one, never the value. Reflection drops rather than refuses, and the drop sits at the WRITE BOUNDARY (`applyReflection`), not in the tier: `ApplyReflection` replaces a corpus in one transaction, so a refusal would roll back the whole round. It must also be after the drop guard's audit — the audit asks which inputs the output failed to account for, and executeOps emits every unclaimed input verbatim, so a memory the tier carried forward is byte-identical to the output that carried it; filtering earlier makes that input look unaccounted for, and it is then either re-added verbatim (the drop is a no-op, after the audit printed its content to stderr) or silently deleted by `ReplaceNonManual` with no `--allow-drops`. At the boundary it is still accounted for, so `RetainGuardedDrops` does not re-add it and the drop is not a no-op; it IS deleted from the store, because `ReplaceNonManual` removes every replaceable row the emitted set no longer accounts for — and the report describes the mechanism without claiming a count, only when a project replace actually ran, since a drop that empties the set writes nothing — in which case the round reports `Applied: nothing`, names the surviving row, and records NO skip fingerprint, so `--skip-unchanged` does not skip the project forever. `applyReflection` returns `applied` for that distinction, and `dropCredentialProposals` returns fresh slices and `applyReflection` returns those post-drop slices, because the caller lists and counts them. `previewContent` in `internal/reflection` withholds a credential from the three tier log lines, which run before `cmd/ghost` sees anything. `--allow-drops` does not gate it — that flag authorises what the MODEL dropped. Every print site in `ghost reflect` goes through `displayProposal`, so a proposal or a guarded drop that holds a credential is shown as `<withheld: format, category, bytes>` rather than as 120 characters of it.

- Four deliberate exclusions from this guard: `CreateFromCorpus`, `RestoreSnapshot`, `SeedGlobalMemories` and `ReplaceNonManual` are outside both it and `MaxContentLen`. `CreateFromCorpus` exists because a public benchmark corpus contains real leaked credentials (measured: three in longmemeval-s) and a retrieval benchmark cannot refuse to ingest them; it is off `provider.MemoryStore`, off the MCP surface, and reachable only from the three `bench/` dataset seeders. The first two write byte-exact data into a restored store, and dropping a row from a restore is worse than the leak. `ReplaceNonManual` is excluded because filtering there DELETES the stored row — an unattended nightly reflect would silently remove a credential from a pre-guard database with no report — and because `dropCredentialProposals` in `cmd/ghost/promotion.go` already drops a credential-shaped proposal at the write boundary, after the drop guard's audit — where the stored row goes with it, since the row is the value. Detecting what is ALREADY in a database is still a separate report-first job, not a side effect of consolidation. A new caller-supplied text writer MUST call `rejectSecret` first
- Reflection promotion: cross-project candidates stay project-scoped by default; `ghost reflect --promote-globals` opts into `_global`, and the project replacement plus global writes share one transaction
- Reflection drop guard: every one of the eight categories is audited for a surviving merge target, not just the operational ones — an input under 45% token containment in the output it is compared against is re-added verbatim (`internal/reflection/drops.go`, `AuditGuardedDrops` + `RetainGuardedDrops`), and `ghost reflect --allow-drops` accepts the deletions instead. It is not the `manual` source that covers this: seeds are written `builtin`, agent saves `mcp` and reflection writes `reflection`, so nothing an agent writes is ever excluded from consolidation by that filter. With the per-id pass-through the guard no longer rescues omissions, and what it still covers is narrow: a MERGE's sources (`ReflectionResult.Merges`, carrying the ids it folded in AND the text it produced, scored against the text of THAT merge), an explicit `obsolete` drop, and the SQLite tier's absorbed duplicates (it names no ids, so all of its inputs are measured the strict way). A merge source is scored against its own merge and not against the union of the outputs, which #659 chose when the union was a handful of survivors and which the pass-through made into the whole project's vocabulary: every id the response never named is emitted verbatim, so a source whose substance its merge discarded passed containment on the strength of an unrelated memory sharing its words — the same class of loss the pass-through exists to remove, reintroduced through the merge branch (#549). The merge's own text is the whole witness available, because a merge source is consumed by its merge (its own text is never in the result) and the parser rejects an id claimed twice (so a sibling cannot be there either); scoring against the siblings could only LOWER the bar. A merge that is not in the result has no witness and its sources fall back to the strict per-output test. THERE IS NO EXEMPTION. Not for a rewrite and not for a supersession: **an unattended reflect never deletes a memory on the model's say-so alone.** A `rewrite <id> -> <text>` or a `drop <id> reason: superseded by <id>` is audited exactly like an `obsolete` drop — the corpus has to be able to SHOW the row is gone. `ReflectionResult.Replacements` still RECORDS the ids a response disposed of and the text it says took their place, because that is the only place the response's own account of a disposal is visible to a reader of a result, but nothing acts on it. The carve-out this replaced was the hole: a supersession disposed of a row whenever the named successor's text was in the result, and the parser's only rule is that the target survives the response — so naming a neighbour was a valid operation and two ordinary deployment notes in the same project, paired because they sat adjacent in the prompt, was a silent deletion with no warning, no `--allow-drops` and a zero exit status. Requiring the witness to be RELATED closed that, and then turned out to be redundant: the witness text is itself an output, so a row at 45% containment against it also passes the per-output scan. The whole branch was dead code. The rule is KEEP-biased on purpose, and the reason is repairability: a stale row that is KEPT can be demoted, because the lifecycle runs `resolve` and `supersede` immediately after `reflect` and demoting a genuinely stale row is their job, while a deleted row is gone. So the failure direction is a duplicate — the old text back beside its replacement — never a silent deletion. The cost, named: the "three issues are still open" class comes back as a kept stale row whenever the successor is reworded below the containment bar (measured: this repo's own superseded note about the Anthropic API client scores 0.429 against its replacement), and stays visible until resolve or supersede demote it, so a corpus of those grows the input each pass has to read. That is the right way round for a command that rewrites a memory store with no human in the loop. Because a re-added verbatim memory reaches `ReplaceNonManual` through the exact-content reuse path, retention must not be treated as consolidation: `reusePreservesAge` (`internal/memory/store.go`) keeps the stored `created_at` and `source` when the re-emission matches the row's content and category — for every verbatim re-emission, not only retention: a `keep`, a pass-through and the SQLite tier's unmerged (always verbatim) output keep their age too, so decaying categories now age out of injection instead of being refreshed by each applied reflect — and omitting a stale memory cannot restart its decay or relabel its source, while a genuine rewrite (new text, or the same text in another category) still gets `created_at = now` and `source = 'reflection'`. That decision is only as good as the row it is made against, so the pick is deliberate too: `takeReusableRow` prefers the candidate whose category matches the emission (a project can hold one text under several categories, since Upsert keeps the incoming category on a linked copy) and falls back to the first, and the candidate query is `ORDER BY created_at, id` so a duplicate keeps the oldest age deterministically rather than whichever row the planner happened to return
- Reflection operation contract: the LLM tier returns `{"learned_context", "ops"}` where each op is `keep <id>` / `merge <id>,<id> -> <text>` / `rewrite <id> -> <text>` / `drop <id> reason: obsolete|superseded by <id>` on the ids the prompt renders (`internal/reflection/ops.go`), because the retired free-text contract had no vocabulary for "this row is fine": only a byte-identical re-emission kept an identity, so retyping — including retyping to improve — reset the id, and with it the embedding, the link graph (both ON DELETE CASCADE) and the age (measured: 12 of 13 new ids in one project, 15 of 17 in another). A memory leaves the corpus only when its id is named as a merge source, named for a rewrite, or named in a drop with a reason — AND a surviving output accounts for it (the drop guard's 45% token containment, with a merge source measured against its OWN merge) or `--allow-drops` accepts the deletion. Naming an id is NECESSARY BUT NOT SUFFICIENT: a rewrite whose replacement does not carry the old row's substance leaves that row in the corpus verbatim, so a rewrite is not a free change of wording on the unattended path (#549). EVERY OTHER INPUT IS CARRIED THROUGH VERBATIM by `executeOps` — the pass-through that makes the tier zero-loss, and the reason the token guard is not load-bearing for omissions: an unnamed memory was emitted by nobody, so it survived only if the guard FAILED to recognise a survivor, which made a false positive in the "absorbed" direction a silent deletion with no warning and no `--allow-drops` (measured: "SSH to the bastion goes through port 2222, not 22" gone, because an unrelated survivor shared 45% of its tokens). A guard can only re-add what it flags, so an id the harness never mentioned needs no inference at all. `keep` and the pass-through emit the stored row's own content, category, importance and tags so the exact-content reuse updates it in place; a merge or rewrite derives its category from the first id, its importance from the strongest source, its tags from the union, and its scope from `inferGlobalScope` — the model states none of them, and an unattended model choosing `global` moves knowledge into every project's injected context. An operation id may echo the prompt's own `id:` label, which is stripped rather than failing the pass. Everything else is strict, because a partially-understood operation list is a corpus rewritten as if the model had said something else: an unreadable line, an id Ghost did not feed the model (compared case-insensitively, never by prefix), an id claimed twice, a supersession whose target the same response does not carry forward, or a response with no `ops` array at all each fail the whole response so the tiered consolidator falls through to SQLite. The grounding check (`internal/reflection/grounding.go`) is the other half: a merge or rewrite that introduces a path, hash, version, hostname or number found in none of its source ids is REJECTED and its sources are emitted unchanged — the output is never repaired, because Ghost cannot know which side of a corrupted identifier (`2.BeXIAhbj.js` vs `2.BeXIAhbq.js`) is true, and a wrong specific is stored as fact forever. That is also why a `rewrite` fixes a CLAIM and never a specific: the corrected value would be an identifier the source does not contain, so the prompt asks for `keep` (or `drop`) instead and the check is never asked a question it must refuse. Ordinary prose is not an identifier: a merge that needs a new connective word is a legitimate merge, and a bare proper noun the model misspells is outside these classes
- Hybrid search: 70% vector (cosine, Ollama) + 30% FTS5, RRF fusion — window selection is `Store.fuseAndRank` delegating to `selectWindow` (scope narrowing, keyword reservation, final cut), which every production search reaches including the FTS-only degenerate path; `FuseAndSelectWindow` is the exported entry point over the same seam, called only from the fusion tests; explain mode reuses the same scoped membership. Status demotion (`statusDemotionFactor` and the `resolvedDemotionFactor`/`globalDemotionFactor` constants in `internal/memory/demotion.go`) multiplies a resolved row's fused score — and a `_global` row's when a specific project is searched — by 0.5 inside `fuseCandidatePool`, before the cut, so it owns membership as well as order; it scales the score rather than dropping the row, so both stay searchable, and explain reports the same number as `status_factor`. With k=60 the factor effectively ranks a demoted row below every live candidate the legs fetched (a halved rank-1 two-leg score of ≈0.0082 sits under the 0.7/80≈0.0088 floor of the deepest vector row in a default window), but it only reorders what the legs fetched — each leg pulls limit*2 rows from the project plus `_global`, which counts against that budget, so a short project result set still fills with demoted `_global` rows. The keyword reservation skips rows whose status factor is below 1 (raw rank and the demoted score would otherwise disagree), and injection never reaches fusion on either path — `loadSessionContext` (`internal/mcpinit/hook.go`) builds the session-start digest, `Store.GetTopMemories` backs the MCP tool surface, both filter `resolved_at IS NULL` — so no factor reaches injection. What the digest does share with the tool surface is the scope rule and its label: the two loaders select `memories.scope`, print it with `assemble.ScopeLabel`, and narrow their own fetch by `injection.session_scope` using `memory.ScopeMatchesSQL`, the SQL statement of `memory.ScopeMatches` that the assembler applies in Go — they need it in SQL because their `LIMIT` chooses which rows are read at all, the same reason `scopesConflictSQL` exists for the fold targets, and a test runs both forms over the same rows to hold them together. Unset, the clause is absent and the block is byte-identical to the one that shipped. The formatted `ghost_memory_search` path does not read that window directly: it asks `Store.Candidates` for a widened untrimmed set and hands it to `assemble.Run`, so the caller's category and scope are applied before the window closes (the window itself is still chosen inside fusion, unchanged) — `internal/assemble` owns every decision after retrieval, and `internal/memory` never imports it
- Vector scan: both legs are brute force over the project's embeddings, and they run in two phases (`internal/memory/vector_scan.go`, #556). `snapshotVectors` copies every candidate row out of SQLite and returns, holding the store's read lock and its single connection for the copy only; `vectorRows.search` scores the copy afterwards, so the O(corpus × dims) cosine pass — which `ghost supersede` runs once per memory — no longer blocks writers for the length of the corpus. The copy keeps the stored bytes rather than decoding them and the score loop reads the little-endian float32s back out in place (`cosineFromBytes`, bit-identical to `cosineSimilarity` on a decoded vector), and the scope column is parsed only for a row that wins a slot; a `scopeProbe` decides per-row eligibility by checking whether the stored text can mention a requested key at all, which can only save a `json.Unmarshal` and never decides membership, since `ScopeMatches` only excludes a row that names a requested key and disagrees. Ranking keeps a bounded window instead of the corpus — a min-heap whose root is the worst row held, ordered once at the end over at most `limit` rows — and the order is total (cosine descending, exact ties broken by scan position) so the answer is a function of the stored data AND the order the scan yielded it in, not of the heap's internals; that is not independence from the scan order (the query has no ORDER BY, so a VACUUM or index rebuild can reorder a tie), and it does not claim to be — what it buys is that two searches over the same rows in the same order agree, which the unstable `sort.Slice` it replaced did not promise. `TestSearchVectorRankingMatchesTheCollectAndSortBaseline` pins the whole result against a transcription of the pre-#556 collect-and-sort search, and `TestVectorSearchCopiesTheCorpusUnderTheStoreReadLock` / `TestVectorSearchScoresWithTheStoreLockReleased` pin that the copy takes the read lock and the scoring pass does not. A writer is still kept out during the copy, and that is the connection rather than the mutex: OpenDB pins the pool at one, so no amount of lock work lets a write start while a query is streaming. The scratch is recycled through a `sync.Pool` on the store, and an oversized embedding buffer is dropped on return rather than retained. What a query still allocates is the driver: `modernc.org/sqlite` copies every BLOB and TEXT column into a fresh allocation per row, which is why the remaining cost is a decoded-vector cache keyed on `PRAGMA data_version` (and then an ANN index), not more work on the scoring loop
- Vector-space identity: a stored vector is only scored when `memory_embeddings.model` equals the identity this process embeds into (`Store.SetEmbeddingIdentity`, fed from `embedding.VectorIdentity`). A model, dimension or task-prefix change therefore retires the old vectors instead of comparing them with queries from the new space. The rule is read in four places, one per caller: `loadVectorRows` (may a vector enter a search), `GetEmbedding` returning nil (may a stored vector act as a QUERY vector — the link worker and `ghost supersede` both do), `UnscannedEmbeddedMemoryIDs` (may the linker compare this memory yet), `EmbeddingStats` (is it covered, which `ghost mcp status` and `ghost_health` report). A retired vector never hides its memory: the keyword leg still finds it. Two side effects of a rewrite ride along: `StoreEmbedding` clears the row's `link_scans` slot when the identity changes (so the linker re-scans it in the new space — the re-scan ADDs current-space `related` edges alongside the ones the retired space produced; nothing invalidates those old rows, and `CreateLink`'s `MAX(strength, excluded.strength)` upsert means an edge whose new-space similarity is lower keeps its old strength), and the foreign-vector warning in `loadVectorRows` is emitted once per retired identity (a second reconfiguration in the same process warns again). `EmbeddingStats` reports stale and unembedded rows separately so `ghost mcp status` can show both. The identity is opaque (compared, never parsed) and empty means "no model configured", which keeps the bench harness and tests unfiltered
- Memory history: `memory_history` (schema v17, #578) is the append-only CHANGE LOG of how a memory reached its current state — one row per write. The name `memory_provenance` went to a different and later concept (evidence records, several per memory, answering "who or what supports this memory" — see "Evidence provenance" below), so never rename this table to it, and do not treat the two as the same thing; and every writer appends one row in the SAME transaction as the write — `Create`, `Upsert` (insert and the fold's `merge`), `UpdateMemory`, `ReplaceNonManual` (rewrite, reuse, bulk delete), `SetResolved`/`ClearResolved`, `CreateLink` for a `supersedes` edge and `InvalidateLink` for its withdrawal (`unsupersede` — a memory can be superseded, withdrawn and superseded again, and only the sequence says which claim is live), `RestoreSnapshot`, `ImportMemory`, `Delete`, the decision companion memory and the shipped seeds. Each row is a VERSION, not a diff: the state the memory held once that write landed, so "what did Ghost know at T" is the newest row at or before T (#647) and the prior content is the previous row. `agent`/`session_id` are the PERFORMER (the save/merge/import paths carry a Provenance; the lifecycle passes do not, and an empty field is an admission, not a claim) — which is what makes the issue's "a row changed by two different agents" answerable. `memory_id` deliberately has NO foreign key so a hard delete leaves a tombstone carrying the text the row held; `project_id` does cascade. Growth is bounded in the appending transaction: newest 50 versions per memory, newest 20 000 rows per store (rowid window, since an implicit rowid is max(rowid)+1 and never reused). A write that changes none of a memory's own recorded columns appends nothing (`Touch`, `TogglePin`, the KEEP cache), and a write that moves a memory BETWEEN projects must also move its history rows' project_id or the project-delete cascade takes the past of a memory that survived: `MergeProject` and `PromoteToGlobal` both do (the merge list exists twice on main). TWO writers deliberately repeat the state instead, and neither is a licence to repeat: a consolidation that re-emits a memory verbatim appends a byte-identical `reflect` row (retention is not consolidation — the row records which run touched it), and a `supersedes` edge appends a `supersede` row when it BECOMES active, recording a claim about the target's standing rather than a state change. Both spend a slot under the cap, which is what bounds them. Two columns carry the event's other end: `related_id` (the id that replaced a deleted row, or the memory whose edge claims it) and `merged_content` (the text a FoldOnly fold dropped, which no row keeps). `ghost history purge <id>` and `ghost_memory_delete`'s `purge_history` delete a row AND its history in one transaction — the redaction path, because a plain delete keeps the text a memory used to hold — and `ghost_history_content` is the SQL seam where #656's `secret.Detect` will redact content on the way in. A purge reaches a memory that is ALREADY deleted through `Store.PurgeMemoryHistory` (history only, never the row), because the tombstone is the feature and a delete-time purge cannot cover it; the same operation is what frees an id for `ghost import`, which REFUSES an id that still has history rather than splicing two memories' records under it (ids are not reused by Ghost, but a portable artifact carries them verbatim). `migrateV17` backfills nothing, so a pre-v17 memory's first edit files a `baseline` row before it overwrites the text. Read it with `Store.MemoryHistory` (oldest first, rowid order) or `ghost history <memory-id>`
- Evidence provenance: `memory_provenance` (schema v18, #673) is the EVIDENCE table — SEVERAL rows per memory, one per observation, answering "who or what supports this memory", which the change log above cannot: a fact claude-code reported in one session, codex in another, and a human verified is three rows here and one row of mutable columns on `memories`, which can only remember the last. Three concepts stay distinct and are not interchangeable: SOURCE is how Ghost received a memory (`memories.source`: mcp, reflection, import, manual), AGENT is which agent produced or observed it (`agent`), PROVENANCE is the evidence records themselves. `memory_id` CASCADES (unlike the change log's deliberately FK-free `memory_id`) because "3 observations support this" is a claim about a memory, and once the memory is gone the claim is about nothing; a purge deletes these rows explicitly as well, because `PurgeMemoryHistory` leaves the memory in place and no cascade fires for a row that stays — and it deletes the `memory_snapshot_evidence` rows too, since a snapshot is the rollback point for a whole PROJECT, so its evidence would otherwise outlive the purge by however many reflects prune that snapshot Every value except `kind` is NULL when the host did not report it — a guessed agent or session is a provenance claim nobody made, and `observed_at` is NULL for the migration's seed because the seed can say what the columns hold now and not when the fact was first seen. Writers, each in the SAME transaction as the write, each ONE statement: `Create` and `Upsert`'s insert append `observed`; a near-duplicate FOLD appends the second report to the SURVIVING memory (the point of the issue — the folding agent used to be discarded with the incoming wording, and `FoldOnly` stores no row of its own so without this the report would leave no trace); `RecordDecision` appends `observed` for its companion memory (an ordinary memory search returns and a later save folds against), empty of provenance because the decision tool reports none; `ReplaceNonManual`'s FRESH INSERT carries its sources' records onto the new id with `carried_from` naming each source — a rewrite or a merge mints an id whose evidence the cascade would otherwise have just deleted, which would make every consolidated memory read "no recorded evidence" forever, so the emissions loop runs BEFORE the delete and a test fails if the two swap; the REUSE branch appends nothing because the row never changed identity; `ImportMemory` appends `imported` plus whatever records the artifact carried (and NOT `carried_from`, which names a memory this store has never heard of); `RestoreSnapshot` restores a re-created row's records from `memory_snapshot_evidence` (a table, because a memory has several records, pruned with the snapshots) and touches NOTHING for a row it updates in place — the snapshot holds an older copy of that row's evidence, and restoring it would drop every corroboration recorded since. `AppendVerifiedEvidenceTx` is the exported seam the validity writers (#677) own the reserved `verified` kind through, and they now CALL it. State the contract as an OUTCOME, because the mechanisms differ on purpose and a reader filtering by `kind` sees three shapes for one rule: every writer that stores a `verified_at` leaves a record carrying a verification stamp in the same transaction, and `EvidenceCounts.Verified` counts any record carrying one whatever its kind. The live callers are `insertMemory` (behind `Create`) and all three of `UpsertWithOptions`' branches plus `UpdateMemoryWithOptions`; each goes through `appendVerificationIfStatedTx`, which gates on the caller stating a verification IN THIS CALL and never on the column, because a partial update COALESCEs a `verified_at` an earlier save wrote and appending for that would record a check nobody made. Their stamp is the STORE's clock, not the caller's (a verifier must not be able to date its own check), so the column carries what was claimed and the record carries when Ghost heard; the two are different facts and both are kept. `UpdateMemoryWithOptions` appends the `verified` leg but NOT an `observed` one — an edit is a change to a fact already reported, not a new report of it, and widening #673's design from inside #575 would inflate the report count on every content edit. THREE more writers store a `verified_at` and are deliberately not callers, each for its own reason. `ImportMemory` is IN the set and not among the callers: the artifact carries an OBSERVATION, so a check happened and is attested, and it rides the import's own `imported` record instead of adding a `verified` one — same store-clock stamp, same count, no second statement. `CreateFromCorpus` records NOTHING: a third-party dataset's `verified_at` is a value in a column with no observation behind it, so there is no event and the only stamp a record could carry would manufacture one; it opts out through `insertOptions.recordVerification` because it shares `insertMemory` with `Create`, which is why it needed a PARAMETER and not a comment — and the column keeps the dataset's value either way, since losing the dataset's own data would be the opposite defect. `RestoreSnapshot` writes it in pure SQL from the snapshot table, and a restore is a faithful copy of a corpus whose evidence rows travel with it, so appending per restored row would double-count every check the snapshot holds. That enumeration has been wrong twice because prose is not checkable, so it is ALSO a table: `TestEveryVerifiedAtWriterIsEnumerated` walks all four writers and asserts the outcome each leaves. There is no growth prune, deliberately: it would be a second statement inside the write transaction, which is what took `TestMultiProcessSharedDatabase` to SQLITE_BUSY for the change log's prune, and the cascade keeps deleted memories from contributing. `migrateV18` REFUSES a database whose `memory_provenance` is not the EVIDENCE table (a pre-rename #664 dev build used the reserved name for the change log) rather than converting or dropping it, naming `sqlite3 <db> 'DROP TABLE memory_provenance'`, and `OpenDB` runs the same check BEFORE the pre-migration backup so a refusal costs no copy and its same-second retry reports the real error — the check tests for `id`/`memory_id`/`kind` ONLY, so it is an identity test and not a version test: a future column here must not make it refuse a legitimate store with a remedy that DROPs its evidence — initSQL's CREATE INDEX cannot catch that one, because the change log has a `memory_id` too, and a warning nobody sees leaves every writer failing on the same missing column. Otherwise it seeds one `legacy` row per memory that recorded at least one of agent/session_id/source_ref/confidence, and NONE for a memory that recorded nothing — an evidence row with nothing in it still says "this was observed", and a row per memory would make every store report one observation, the same fabrication as inventing a session id. Read it with `Store.MemoryProvenance` (oldest first, rowid) and `Store.MemoryEvidenceCounts`, whose `Label()` renders "supported by 2 observations, 1 verified"; the assembler records the counts in stage 4's trace (`Signals.Evidence`, carried on `memory.Candidate` because that is the only read the assembler has) and NOTHING RANKS ON THEM — the stage's multiplier stays 1.0 until a measured change justifies one. The portable artifact (v2) carries the records, nested under the memory they support because a bare evidence line cannot be attributed; the Obsidian mirror does not — it is a human-readable mirror, not a transfer format
- Memory links: `memory_links` edge table auto-populated by cosine similarity (internal/linking worker); links cascade-delete with memories and self-heal after reflection. - Resolution classifier: `ghost resolve` runs a keyword prefilter, then a deterministic KEEP veto, then batches up to 8 notes per KEEP-biased CLI-harness classify call (`claude`/`opencode`/`codex`/`goose` subprocess, numbered `N: RESOLVED | closed-by: <fact>|KEEP` reply judged by a strict first-field line parser) to mark `resolved_at`, dropping resolved-evidence memories (changelogs, cost estimates, closed experiment notes) from ranked injection while keeping them searchable. KEEP-biased in code, not prose (#640: an independent judge found ~1 resolve in 3 on a real DB had buried durable knowledge): `resolve.VetoKeep` settles a candidate KEEP with no harness call when its text carries an imperative (`never|do not|don't|must|always|required`) or an open marker (`not yet|outstanding|still pending|still open|still stale|unresolved|todo`), all case-insensitive and word-bounded; the rubric asks the fresh-session question (would an agent starting fresh make a mistake, repeat work, or break a rule without this?) and says dates, PR numbers, commit hashes and "fixed in" do not resolve a note; a RESOLVED must carry a non-empty `closed-by:` or the parser reads it as KEEP. The veto guards the classifier only — the supersedes-edge piggyback and correction pairing still demote. Only explicit KEEP verdicts are cached by content hash in `memories.resolve_kept_hash` (schema v7; the v3 hash prefix invalidates the v1 implicit-KEEP and v2 explicit-KEEP caches, so #640's re-judged rules are re-asked); UNKNOWN parse failures remain uncached and are retried, so a converged project makes no calls only after explicit KEEPs. Dry-run writes nothing, `--apply` writes resolved_at and explicit KEEP cache entries; transport or verdict-count failures fail fatally rather than applying incomplete results, while UNKNOWN lines remain eligible for a later pass. `ghost resolve <project> --reassess` is the repair path for the resolutions the pass already got wrong: it re-runs the vetoes and the classifier (no keyword prefilter) over memories that are ALREADY resolved, prints the ones that now come back KEEP, and with `--apply` clears their `resolved_at` via `memory.ClearResolved` and caches the classifier's KEEP verdicts; a failed clear is fatal, a failed cache write only warns; `memory.ClearResolved` runs every batch in one transaction so "a failed clear repaired nothing" is literally true. It honours Run's two free demotions as a floor — a row a live `supersedes` edge still asserts, or an older row a NEWER *unresolved* correction pairs with (the same pool Run searches, via `correctionPairTargetsFrom`), is counted as `Demoted` and left resolved, because Run fires both before the veto and the KEEP cache, so clearing it would report a repair the next pass undoes. The pairing is re-checked after the re-KEEP set is known (`holdBack`), because a correction that is itself repaired leaves the resolved pool and would re-assert its pairing; both the floor and the hold-back pair only Run's keyword-prefiltered subset, since a keyword-free row is never a pairing target and holding it would be a permanent, mislabelled hold no later pass could undo. A reasonless `closed-by` is not a reason: a bare mention of the key without its colon ("no closed-by available") and a placeholder value (`none`, `n/a`, `tbd`, …) are both KEEP. Never invoked from the stop hook's synchronous path (that path forbids DB access); the stop hook's detached `ghost lifecycle` spawn (whose resolve phase runs `--apply`, never `--reassess`) and the standalone batch command are the only callers. See `docs/superpowers/specs/2026-07-26-resolution-classifier-design.md`.
- Classifier backend: `resolve`/`supersede` classify via the calling session's own CLI harness — the backend is picked from the MCP client's reported identity (an opencode session uses the opencode binary, claude uses claude, etc.) via `ai.SourceProvider`, or — on the headless CLI path — from `--source`, else `ai.DetectSource()` (env markers plus process ancestors); if no calling harness can be determined it fails fast with an actionable error. There is no claude-first cascade: `NewSourceProviderForSource("")` is unavailable, and `ai.CLIProvider` is an availability probe only. MCP sampling was retired from this path per SEP-2577 — see `docs/superpowers/specs/2026-08-24-resolve-sampling-path-design.md`.
- Lifecycle spawn guards: the stop hook spawns the reflect→resolve→supersede chain behind TWO independent per-project guards. `AcquireLifecycleLock`'s PID file says "a run is not already in progress"; `lifecycle.min_interval` (default 30m, `0` to disable) says "a run did not start too recently". The second is the mtime of `lifecycle-<project>.last` in the data dir — a file, not a row, because the stop hook's synchronous path forbids DB access. Only the `ghost lifecycle` process writes it (`mcpinit.TouchLifecycleStart`), and only once it has passed every precondition that can exit non-zero, so a run that dies before doing any work does not burn a window. Most unknowns read as "run" (no stamp, unreadable, non-regular) so that a bookkeeping problem cannot silently stop maintenance; a stamp dated in the FUTURE is the deliberate exception and reads as INSIDE the window, because a future date is not evidence the window expired. `config.LifecycleConfig.MinIntervalDuration` resolves an unreadable value to the default rather than `0`, because `0` means the cooldown is off.

## Critical Rules
- Always `go vet ./...` before committing
- Tests use `go test ./...`
- Never commit to main directly — feature branches + PRs
- SQLite schema is embedded as a Go string constant in `internal/memory/schema.go` (currently v18; `migrate.go` carries one frozen step per version)
- `ghost mcp init` is idempotent and non-destructive — safe to re-run
- A test that needs a real *program* builds it with `go build` into a temp dir rather than re-exec'ing its own binary: under `go test` the test binary is the suite, so a self-spawn re-runs every test in the package once per spawn and a bug in the barrier logic becomes a fork bomb. A `-test.run`-bounded child test is fine (`internal/ai/harness_policy_test.go` does exactly that)
- The concurrency contract in `docs/architecture.md` is enforced by `TestMultiProcessSharedDatabase` (`internal/memory/multiproc_process_test.go`, helper in `internal/memory/testdata/multiproc`): MCP server, CLI child, read-only handle, lifecycle writer, pinned-snapshot reader and sampler processes against one database. It reads `memory.OpenDB`'s and `memory.readOnlyDSN`'s settings back from a live connection, so dropping WAL, `foreign_keys`, `busy_timeout`, the pool pin or `_txlock=immediate` fails it. `mcpinit`'s own DSNs are not covered. Skips under `-short`; makes no LLM call
