Architecture

One binary between your agents and one file.

The same ghost binary is the MCP server, the hook handler for four hosts, and the maintenance CLI. Several of them can run at once against the same database: a live MCP server, a hook, a detached lifecycle run and your own ghost command. There is no daemon to route through, because SQLite itself is the synchronization layer. Architecture

Scroll sideways to see the whole diagram.

A normal MCP session Data flow

  1. The client spawns ghost mcp over stdio. There is nothing to start beforehand.
  2. Tools call the store. Save, search, list and update make no LLM call.
  3. Search runs FTS5 and vectors, fuses them, and hands the result to the assembler.
  4. Workers embed and link new rows in the background.

Session start Injection

  1. The host fires SessionStart, and the project is resolved from the longest matching path.
  2. The digest is assembled by the same stages search uses: validity, scope, dedup and budget.
  3. It is a bounded, printable block. Subagents, resumes and compactions get nothing.
  4. opencode reads the same block through ghost context.

Stop and maintenance Lifecycle

  1. The host fires Stop, and ghost checks a per-project cooldown.
  2. If the user opted in, a detached ghost lifecycle runs reflect, then resolve, then supersede.
  3. Each pass goes through the caller's own harness, never a silently chosen one.
  4. A failed phase is logged and the next phase still runs.
Features

Everything a memory system should do. Nothing you have to run.

Most memory products make you choose between a hosted silo and a self-hosted stack of Postgres plus a vector database. GhostMem packs the whole pipeline into one static binary. Each card links to the documentation behind it.

Search

Hybrid vector + full-text

SQLite FTS5 and local Ollama embeddings, fused by Reciprocal Rank Fusion (0.3 FTS / 0.7 vector, k=60), so a memory both legs find always outranks one found by a single leg. Without embeddings it falls back to FTS only, with no error and no setup step.

Fusion and window selection
Context

One context assembler

Search and session-start injection run the same staged pipeline (validity, scope, provenance, dedup, budget, render) and share one item renderer. When nothing is good enough, the result says so instead of returning the best of a bad set.

Context assembly
Structure

Eight memory categories

architecture, decision, pattern, convention, gotcha, dependency, preference and fact. They are enforced by a database constraint and weighted by importance, and a near-duplicate save folds into the row it restates instead of adding a copy.

The memory model
Freshness

Category-aware time decay

Conventions, preferences and facts never fade, and pinned rows are exempt. Patterns and architecture fade slowly, while gotchas and decisions fade faster. A superseded fact is demoted below its replacement, so agents stop acting on outdated state.

See the curves
Retention

Three retention tiers

session rows expire 24 hours after they are saved, and only ghost prune, which is a dry run by default, removes them. project is the default. persistent is keep-forever, and every automated pass leaves it alone. A restatement raises a tier and never lowers it.

Retention tiers
Validity

Validity windows and scope

A memory can state when it became true and when it stops being true, and search withholds one whose window has closed. Scope (environment=production) keeps a claim about one place away from queries about another.

Memory axes
History

Append-only history, and time travel

Every write that changes a memory appends a version in the same transaction, so history cannot drift from state. ghost history <id> shows how a memory got here, and ghost context --as-of renders the context as the store stood at any past instant.

Memory history
Evidence

Provenance you can inspect

Source, agent and evidence are kept as separate things. When claude-code, codex and a person each observe the same fact, that is three evidence rows, and none of them overwrites another. Search results show who wrote a memory, its confidence and where it came from.

Evidence provenance
Security

Credential guard

No write path stores a credential. Every save, update, task, decision and import passes one check that looks at the shape of the value, not keywords, so "rotate the password quarterly" still saves and an API key does not. Reflection output is filtered at the same boundary.

Credential guard
Consolidation

Reflect, resolve and supersede, with guardrails

Maintenance runs through the calling host's own CLI harness. Reflect answers with operations (keep, merge, rewrite, drop) so a kept memory keeps its id, and a drop guard re-adds any row whose substance didn't survive. Every pass is a dry run unless you pass --apply.

Memory lifecycle
Graph

Auto-linked memory graph

Similar memories link automatically (cosine ≥ 0.70). Supersede adds directed supersedes edges, and scope conflicts block a relation instead of deleting it. The store mirrors to an Obsidian vault, so you can browse a project's knowledge as a graph rather than a log.

Obsidian and links
Scope

Cross-project and global

One memory across every repository and every MCP client: project-scoped recall, cross-project search, and a _global project for preferences that follow you everywhere, labelled with who wrote each one. Tasks and decisions live beside the memories.

MCP surface
Portability

Backup, export, import

ghost backup takes a consistent snapshot of a live database, with a SHA-256 manifest that ghost backup verify checks. ghost export writes portable JSONL, and ghost import never overwrites an existing id. Every migration is preceded by a backup.

Backup and transfer
Operations

Zero-infrastructure, multi-process

One binary, one SQLite file, and no daemon: GhostMem runs only when a client spawns it. WAL, busy timeouts and immediate transactions let a live server, a hook and a maintenance run share the file safely, and a real multi-process test enforces that. An older binary refuses a newer store instead of damaging it.

Concurrency contract
Supply chain

Verified upgrades

Prebuilt binaries for linux, macOS and Windows on amd64 and arm64, a multi-arch Docker image, and a one-command Windows installer. ghost upgrade checks checksums, refuses downgrades and has timeouts, and new releases attest every asset with GitHub build provenance.

The life of a memory

From one save to years of trustworthy recall.

A memory is not a log line. Every stage below either protects it, ranks it, or lets it go on purpose, and a destructive stage only ever runs with an explicit flag. Using GhostMem

write path, in-process read path, every query maintenance, opt-in and dry-run first
1on save

Save

An agent calls ghost_memory_save with a category, an importance, and optionally a tier, a scope, a validity window and a source_ref.

2on save

Guard

The credential guard refuses a secret-shaped value before any SQL runs. The refusal tells the agent to record where the value lives instead.

3on save

Fold and strengthen

A near-duplicate folds into the row it restates. It raises that row's importance, and its tier if the save asked for a higher one, instead of adding a second copy.

4background

Embed and link

Workers embed the row through local Ollama and link it to similar memories (cosine ≥ 0.70), unless a scope conflict blocks the edge.

5every query

Rank

Hybrid search, category decay, supersede demotion and the retention factor order the candidates. The assembler then filters and budgets them.

6lifecycle

Resolve and supersede

Resolved evidence leaves injection but stays searchable. Directed supersedes edges demote the old version. Both are reversible with --reassess and --withdraw.

7lifecycle

Reflect

Consolidation merges and rewrites near-duplicates using ids, not free text. It takes a snapshot first, spares manual, pinned and persistent rows, and a drop guard re-adds anything it would lose.

8by hand

Prune or purge

ghost prune removes expired session rows. It is a dry run unless you pass --apply, and it never runs on a timer. ghost history purge erases a memory and every recorded version of it.

Category-aware decay

preference · convention · fact: never fade pattern · architecture: 1/(1+d/45) decision · gotcha · dependency: 1/(1+d/30)

Four independent axes

A row can be live, in date, contradicted and low-confidence all at once, and each fact is judged separately. Memory axes
LifecycleIs it current, and how long is it wanted? resolved, pinned, retention tier, expiry, snapshots, history
ValidityIs it true now, and when was it checked? valid_from, valid_until, verified_at. Stage 2 withholds a closed window.
RelationshipsWhat does it replace or contradict? directed links: duplicate, supersedes, contradicts, elaborates, causes
ConfidenceHow much should a caller trust it? confidence, agent, session, source_ref, evidence rows. Visible, not yet ranked.

For companies

Built for environments where "just trust us" isn't an answer.

Cloud memory services mean your codebase's context — architecture decisions, credentials-adjacent gotchas, internal hostnames — sits on someone else's servers, metered per request. GhostMem was designed so the security review ends quickly: GhostMem itself adds no remote memory service, while explicit LLM-harness calls remain a documented egress path.

Data residency by construction

All memories live in one SQLite file under your own home directory. There is no cloud tier, no sync, no account, and no telemetry. The GhostMem store stays on your machine; when you use an LLM harness, the prompt or context you explicitly send to that harness crosses your network boundary. That makes GDPR/CCPA data-mapping tractable: the store location is a path you own, and each external egress path is explicit.

Auditable, enumerable egress

The normal local memory path results in zero network calls made by GhostMem. The explicit runtime integrations are localhost Ollama for embeddings, the selected CLI harness for memory maintenance, and the GitHub API for self-upgrade. The harness may use a provider's API or subscription according to its own configuration; GhostMem does not add a direct Anthropic client.

Inspect what your agent sees

The exact context injected into every session is a bounded digest you can print with one command. No mystery blob in the system prompt — what enters your LLM vendor's logs is knowable in advance, which is precisely what AI-governance reviews ask for and cloud memory can't show.

Deterministic retention & deletion

Deletion is real: remove the data directory and the memory is gone — no provider-side replica, backup window, or retention policy to negotiate. Lifecycle operations (resolve, supersede, consolidation) are dry-run by default and apply only with an explicit flag, so every destructive action has an owner.

No lock-in, honest exit

Memories live in a plain SQLite file whose schema is a readable constant in the repo. Query it with sqlite3, back it up with cp, read it with anything. If GhostMem disappears tomorrow, the data outlives the tool — procurement calls this "acceptable," auditors call it "portable."

Least privilege by default

Subagent sessions receive nothing injected (they inherit context in-band from the parent), resume sessions skip injection, and compaction emits a pointer instead of re-dumping content. Memory exposure is scoped to the interactive sessions that asked for it.

Reproducible evaluation

Every published number ships with its harness, dataset, seeds, and per-question logs — deterministic, judge-free retrieval scoring included. When compliance asks "how was this measured," the answer is a command anyone can run, not a screenshot of a vendor dashboard.

Small supply chain

One static Go binary, pure-Go SQLite (no CGO), checksums and GitHub build-provenance attestations published per release, Apache-2.0 licensed. No containers to patch, no Postgres to harden, no sidecar services in your threat model — because there are no other services.

Own your data

The strongest compliance control is not having a vendor.

Cloud memory platforms earn trust the traditional way: audit reports, DPAs, subprocessor lists, and a trust center you review before signing. Mem0's, for example, shows SOC 2 Type I achieved with Type II and GDPR work in progress — a normal, credible posture for a SaaS vendor. But every one of those artifacts exists to manage their access to your data. Own the data, and most of that machinery is simply not needed: there is no processor relationship to paper over, because nobody else holds anything.

The trust-center model

  • They hold itData custodyYour agents' knowledge of your codebase, customers, and internals sits in their cloud, in regions they chose.
  • Their chainSubprocessorsHosting, logging, and support tooling each add a third party you didn't select and must track as they change.
  • On requestDeletion & retentionGDPR erasure means asking the processor and trusting their backup windows and replication lag.
  • Depends on themBreach responseYour incident timeline includes their detection time, their disclosure obligations, and their communication quality.
  • ContractualOngoing cost of trustDPA negotiation, security questionnaires, renewal-time re-review — plus enterprise pricing for audit logs and SSO.

The ownership model

GhostMem — memory on infrastructure you already control
  • Nothing to verifyNo vendor access to GhostMemThere is no account, token, or endpoint for GhostMem that could reach your memories. An explicitly selected LLM harness is a separate, user-configured egress path; the harness does not act as a memory vendor with access to GhostMem.
  • You hold itData custodyOne SQLite file on company-managed hardware. Residency equals wherever IT put it — office, laptop fleet, or private VPC.
  • Your chain onlyExplicit external pathsGhostMem has no remote memory subprocessors. Ollama, a selected CLI harness, and the upgrade endpoint are the documented runtime integrations; each uses its own network and billing policy.
  • ImmediateDeletion & retentionDelete the file (or a row) and it's gone. Erasure is provable in seconds without anyone's ticket queue.
  • Yours aloneBreach scopeA compromised laptop exposes that laptop's data — same as any other local file. There is no multi-tenant blast radius.
  • One-timeCost of trustSecurity review reads one small Go codebase with an embedded schema. There is no DPA involving GhostMem; any separately selected LLM provider remains subject to its own terms.
Fair reading: certifications transfer trust cheaply, and self-hosting shifts obligations onto you — endpoint management, backups, and access control become your job. That trade is exactly why the next section exists.
For teams

What GhostMem needs to win small and mid-sized businesses.

Today GhostMem is a superb single-player product, and SMBs don't buy single-player — they buy team workflows with governance attached. The architecture is the hard part and it's done: storage, search, decay, and lifecycle all live behind one store interface. What follows is the honest gap list, sized for a 10–200 person company, with what has shipped since marked.

Deploy & share

  • Shared-team mode: a small server flavor of the existing store (same SQLite schema, Litestream-style replication) so a team shares org/project memories while individuals keep private stores.
  • Managed rollout: MDM-friendly packages and an org config file so IT ships ghost mcp init pre-configured instead of per-desktop setup.
  • Backup story:shipped ghost backup takes a consistent snapshot of a live store with a SHA-256 manifest, and ghost backup verify checks it. Scheduling it is still yours.

Control

  • Per-project ACLs: who may read vs write which project's memories — maps directly onto the existing project model, no schema redesign.
  • Encryption at rest: SQLCipher option or documented OS-disk-encryption posture (FileVault/BitLocker), stated plainly for the security questionnaire.
  • Retention policy engine:partly session, project and persistent tiers plus a dry-run ghost prune have shipped. TTLs per category ("gotchas purge after 90 days") have not.

Prove

  • Append-only audit log:partly memory_history records every change and which agent made it, and ghost history prints it, with JSON output. An org-wide export for the compliance review is still to come.
  • Compliance pack: a self-assessment mapping GhostMem's properties onto SOC 2 CC-series and ISO 27001 Annex A controls, plus a signed SBOM for the single binary.
  • LTS releases + support tier: pinned long-support versions and a paid channel — the parts of "enterprise-ready" that are process, not code.

Build on GhostMem

One memory engine, many industries.

GhostMem is Apache-2.0: anyone may take the engine and ship a vertical product on it — closed source, commercial, no royalties. The compliance posture that serves developers (data stays put, egress is enumerable) is exactly what regulated industries are asking for.

Healthcare

PHI can remain on premises. A clinic-deployed GhostMem store keeps patient-workflow knowledge — referral quirks, prior-auth gotchas, payer-specific rules — local. If maintenance invokes an external LLM harness, the prompt/context sent to that harness is a separate egress and provider review.

Position as HIPAA-ready architecture, never "HIPAA certified": residency by construction, append-only audit log for access reviews, retention TTLs aligned to record policies.

Hotels & hospitality

Guest preferences without a central PII honeypot. Each property or region holds its own store: room preferences, allergies, VIP notes surface to front-desk agents instantly — and a breach at one property isn't a breach of the whole chain.

Retention is a feature: category TTLs can age guest data out automatically to match privacy rules instead of accumulating it forever in a vendor cloud.

Legal & finance

Matter-scoped silos map onto GhostMem's project model. Engagement-specific memory stays isolated per client matter — cross-project search stays an explicit, audited act rather than a background leak.

Freshness is defensibility: supersede-and-demote means an agent citing last year's filing deadline gets outranked by the current one, with the update chain preserved for review.

FAQ

The questions a security reviewer will ask anyway.

Short answers here; the code and documentation behind them live in the repo — start at the README and docs/benchmarks.md.

Where does my data actually go?
One SQLite file under ~/.local/share/ghost (or $XDG_DATA_HOME/ghost) — same path on every OS. The normal local memory path results in zero network calls made by GhostMem. The explicit runtime integrations are localhost Ollama for embeddings, the selected CLI harness for memory maintenance, and the GitHub API for self-upgrade; a harness may use its own API or subscription authentication.
What exactly gets injected into my agent's context?
A bounded digest — project name, top memories, learned context, open tasks, active decisions. You can print the exact bytes your agent will see with ghost context, or through the hook itself: echo '{"cwd":"'"$PWD"'"}' | ghost hook session-start. Subagent sessions get nothing (context flows in-band from the parent), resume skips injection, compact emits a one-line pointer.
How do I get my data out?
It's already out — that's the point. Plain SQLite: query it with sqlite3, copy it with cp, read the schema as a Go string constant in internal/memory/schema.go. No proprietary format, no export request form. Getting in is easy too: ghost mcp init imports existing Claude Code memories read-only.
Is there a real off switch?
Yes, at four levels: remove the MCP entry from your client config (GhostMem only runs when spawned over stdio — there's no daemon); set embedding.enabled: false; automatic lifecycle phases are opt-in, while manual ghost reflect is dry-run by default and applies nothing without --apply; delete the data directory and everything is gone. There is nothing else.
What does it cost to run?
$0/month for GhostMem itself. Search, save, decay, and injection are local. If you enable maintenance that invokes a CLI harness, that harness's own subscription or provider billing applies; the standalone Phase 4 benchmark can also call its selected generator/judge provider directly. Benchmark reproductions cost $3–24 per full run depending on generator+judge choice.
