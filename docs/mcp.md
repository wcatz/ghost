# MCP surface

Ghost exposes 23 tools, 4 resources, and 2 prompts over standard MCP. The server runs over stdio, so the client launches the `ghost mcp` process and communicates through JSON-RPC.

## Tools

| Group | Tool | Purpose |
|---|---|---|
| Memory | `ghost_memory_save` | Save a project memory; likely duplicates are linked and the existing row is strengthened. `pin: true` exempts it from consolidation and guarantees it a slot on every passive context surface in the same call, and `retention` sets its tier |
| Memory | `ghost_memory_search` | Search project memories with FTS5 and optional vectors (its `limit` defaults to 5); filterable by category, retention tier and scope. A category outside the eight is refused with the allowed list, and a project Ghost has never registered is refused as `project "…" not found` (as `ghost_task_list` refuses it) rather than searched as `_global` alone, on the `explain` and `as_of` paths too |
| Memory | `ghost_search_all` | Search across all projects |
| Memory | `ghost_memories_list` | Browse memories, optionally by category and retention tier; a category or tier outside the vocabulary is refused before the project is looked up |
| Memory | `ghost_memory_update` | Update memory content or metadata |
| Memory | `ghost_memory_delete` | Delete one memory by ID |
| Memory | `ghost_memory_flag` | Record that this memory is wrong or stale, with a short reason: an append-only objection that changes nothing by itself — resolve and reflect count it as negative evidence, and the reason stays in the store. Its `session_id` is the transport's only (`provenanceFor`), so under Claude Code a flag records no session while the `retrieval_record` beside it carries a session id whenever one can be named — the host's own under Claude Code, the same id the stop hook's payload carries — so the audit can match the call to the scan that judged it (#922) |
| Memory | `ghost_memory_pin` | Pin or unpin a memory; a pinned memory is guaranteed a slot on every passive surface (session start, `ghost_project_context`, the project and global resources) ahead of ranking, still subject to validity, scope and resolution, and a block says how many pinned rows it cut when they outnumber the cap; an `as_of` reading replays the past and reserves nothing |
| Memory | `ghost_memory_promote` | Promote a project memory to `_global`; the move carries the memory and its history, and a later project restore leaves the promoted row alone because the project no longer owns it |
| Memory | `ghost_save_global` | Save a memory that applies to all projects; takes the same `retention` argument |
| Memory | `ghost_resolve` | Mark resolved evidence after source-matched classification |
| Memory | `ghost_resolve_mark` | Stamp `resolved_at` on memories you name |
| Memory | `ghost_link_withdraw` | Withdraw one named wrong `supersedes` edge |
| Project | `ghost_project_delete` | Permanently delete a project and its child records; applying is allowed only with the exact project id the dry run printed |
| Context | `ghost_project_context` | Load top memories and the learned-context summary (assembled, so a memory whose validity window has closed is withheld; tasks and decisions are separate tools and resources) |
| Context | `ghost_list_projects` | List known projects and their IDs |
| Context | `ghost_health` | Report store, embedding, Ollama, link, `memory_history` growth, and per-source retrieval health |
| Tasks | `ghost_task_create` | Create a durable task; `priority` is 0-4 (default 2), and a value outside that range is refused by name rather than reset to the default |
| Tasks | `ghost_task_list` | List tasks, optionally filtered by status; a status outside pending, active, blocked, done is refused with the allowed list, and a project Ghost has never registered is refused as `project "…" not found` (as `ghost_task_create` refuses it) rather than answered "No tasks found." |
| Tasks | `ghost_task_update` | Change task status, priority, or description; a `priority` outside 0-4 is refused and the stored priority is left unchanged; `completed_at` is stamped when the status becomes `done` and cleared when it leaves `done`. The row is read and merged inside the write transaction that writes it, so two clients editing different fields of one task (two MCP servers on one store, for instance) both land, and a task deleted in that window is an error rather than a reported success |
| Tasks | `ghost_task_complete` | Mark a task done with optional notes. Idempotent: completing an already-done task keeps its original `completed_at`, an omitted or empty `notes` leaves the stored notes untouched, and a non-empty `notes` replaces them (it does not append). A `notes` over the 8,000-byte cap is cut at `MaxContentLen` with the store's marker and the answer says so, the same cap `ghost import` applies to a restored note. The check and the write are one statement |
| Decisions | `ghost_decision_record` | Record a decision, rationale, and alternatives; `supersedes` also retires the reversed decision's companion memory (withheld from session start and demoted in search, linked, recorded in history) unless it is pinned, retention-exempt or a convention/preference, ambiguous, or a merged memory that also holds another decision not yet superseded, which the answer reports as a partial failure (an `isError` result) — the same shape a `supersedes` id the project cannot mark takes — and a `supersedes` id already superseded by a DIFFERENT decision that is still live (active or revisit) is refused before anything is written, naming that successor and suggesting `supersedes=<successor>`, because repointing it would drop the only record that the successor replaced it and leave two live decisions (#1144; a target whose successor was itself superseded or no longer exists is repointed; the same-pair no-op holds at the store level, since through the tool every call records a new decision, so a repeated `supersedes` is a different successor and is refused) — and the retirement reaches the companion even after it was promoted to `_global`, because the `decision:<id>` link travels with it, so a reversed decision cannot keep ranking from every project; the description and the server instructions tell the agent to find a changed decision with `ghost_decisions_list` and pass `supersedes`, and a record without `supersedes` whose title matches a live decision in the same project (case-insensitive, trimmed) is answered with that decision's id and a note to pass it, advice only, never a refusal or an automatic link  |
| Decisions | `ghost_decisions_list` | List active, superseded, or revisit decisions; a status outside those three is refused with the allowed list before the project is looked up, and a project Ghost has never registered is refused as `project "…" not found` rather than answered "No decisions found." |

The **injected** decision surfaces — the `ghost://project/{id}/decisions` resource, `ghost_project_context`'s `## Recent Decisions` section (shared by the `ghost://project/{id}/context` resource) and the session-start block — read a project's **live** decisions instead of an active-only filter: `active` and `revisit`, active first, superseded excluded. This matches the rest of the decision code, where live means "not superseded" (`FindLiveDecisionByTitle`, `LiveDecisionSuccessor`, and the same-title advice `ghost_decision_record` answers). A `revisit` decision is shown and labelled `(revisit)` after its quoted title, rather than hidden, because a decision flagged for reconsideration is exactly the context a session should see; superseded ones remain readable through `ghost_decisions_list` with `status=superseded`. Each surface keeps its own row cap and the active-first order is applied before the cap closes, so a revisit row never displaces an active one. The decisions resource follows the contents it now carries: its heading is `## Decisions` (it was `## Active Decisions`) and its empty sentence is `No live decisions for this project.` (it was `No active decisions for this project.`), since "active" no longer describes the row set.

`ghost_resolve` is dry-run by default. `ghost_project_delete` is also dry-run by default and is irreversible when applied: the apply form accepts only the exact project id its own dry run printed, and refuses a name, path or basename with a message pointing back at the dry run — those identifiers resolve to a project, and an irreversible delete must not delete whichever one they happen to resolve to. Core memory CRUD and search do not call an LLM; maintenance-oriented tools may use the calling session's CLI harness. Such a call is bounded by its own deadline as a whole — the harness runs in its own process group, the deadline signals the whole group and force-kills whatever the grace period left, and a short backstop closes the harness's output pipes — so a `ghost_resolve` or `ghost_supersede` call cannot wedge on, or leave behind, a process the harness started. `ghost_resolve --apply` stamps only the rows that still hold the exact text the classifier judged (#1052): the pass spends a classify call between reading candidates and writing, so a row a concurrent save or edit rewrote in that window is not stamped and the result names it as skipped stale, because `resolved_at` is persistent and would otherwise hide the new text on a verdict about the old one. The resolved listing prints only the rows the write actually stamped — never a refused row, and never the pre-write text a verdict was reached on, which is no longer what the store holds. The match covers the project as well as the text, so a row `ghost_memory_promote` moved to `_global` mid-pass is refused the stamp and counted as stale: promotion changes `project_id` only, which a content-only match cannot see, and a pass over one project cannot decide for all of them. A tag- or importance-only edit changes no text and so validates a verdict as before.

Wiring itself has no MCP surface. `ghost mcp wiring` is the operator's read-only check that each client's configuration still matches the plugin sources embedded in the running binary, `ghost mcp init` installs or repairs that wiring — with `--dry-run` previewing each step in the `~ would …` form and writing nothing — and `ghost mcp status` reports one client's full health — all CLI commands, because the wiring lives in the client's own configuration files rather than in the store the server reads — with its Ollama line distinguishing a conclusive outage, which the embedding worker's down marker can carry a duration for, from a probe that merely missed its deadline, which is reported as an undetermined endpoint rather than as an outage, and its model line resolving the configured name the way Ollama does — a leading `registry.ollama.ai/` and then a leading `library/` dropped, every other qualifier kept so namespaces name distinct models, and an untagged spelling filled in as `:latest`, applied to each installed name too — so a fully qualified configuration is not reported missing while embedding works. Init validates each configuration file before it registers anything, so a file it cannot parse — Claude Code's `settings.json` with a null or wrong-typed `permissions` or `hooks`, or codex's `hooks.json` with a null or wrong-typed `hooks`, or a null on one of the events it manages — is refused with the file and the field named and left untouched, rather than half-wiring the client around it; a codex `hooks.json` that is 0 bytes or only whitespace carries nothing to merge and is written as the canonical document instead, the way a 0-byte `config.toml` is appended to. The `[mcp_servers.ghost]` table is merged into codex's `config.toml` line-wise, and one leading UTF-8 byte-order mark — what a Windows editor leaves in front of the first line, and what codex's own TOML parser strips — is removed before the file is scanned and written back at the start, so a BOM-prefixed ghost header is repaired in place instead of being read as absent and duplicated. A refused data directory — one `GHOST_DEV_FORBID_DATA_DIR` names and this build is not a release (see [Development builds refusing a real store](cli.md#development-builds-refusing-a-real-store)) — stops the Claude Code installer after that pre-flight and before its first step, so the client is not registered and no configuration file is written, and `ghost mcp init --client claude` exits non-zero instead of reporting a completed install; the codex, opencode and goose installers never resolve the data directory, so no refusal reaches them. An agent can neither see nor edit the configuration of the client hosting it, and [`ghost upgrade`](cli.md#ghost-upgrade) runs the wiring check in the binary it just installed rather than in the process that performed the upgrade, since the embedded-source comparisons judge only against the image running them. An existing hook counts as ghost's own when any of its tokens is a ghost binary — the one init writes under whatever name it carries, or a `ghost` basename under any path — immediately followed by the event's `hook …` tail, so a hand-edited wrapper that runs ghost is recognised and not duplicated, while a hook another tool installed is never rewritten and is never read as ghost's: ghost's is added beside it, which is the only reading of an `already configured` line that describes a hook that will actually run. The same is true of a wrapper that hands the whole invocation over inside a quoted argument (`sh -c "ghost hook stop …"`, `bash -lc "…"`): its interior is read, behind the gate that the word before it is a shell's own command-list flag — a single-dash flag ending in `c`, directly after a shell name, so another tool's `-c` or `--sync` never opens its argument — or a shell name taking the script positionally, and only where the ghost binary is in command position there — a first token, or after a connective, an `X=1` assignment, or a word that runs what follows unchanged (`sudo`, `env -i`, `nice`, `command`, `exec`, `nohup`, `time`, `doas`, `stdbuf`, `ionice`, `chrt`, `taskset`, `timeout 5`) — so an argument that merely mentions ghost stays another tool's. That walk reads the other separators and group openers a wrapper can use too: a newline ends a command as `;` does, a `;` or `&&` glued to a word still ends the list it is in (an UNQUOTED operator is cut into its own token), and `(` or `{` opens a command list whose first word is in command position; a `;`, `&` or `|` inside a QUOTED argument (`--note "a;b"`, a URL with `&`) is the user's text and opens nothing; and a prefix command that takes a plain word of its own before the command it runs — a duration or a CPU mask — leaves that command in command position (`timeout 5 ghost …`, `timeout -k 5 10 ghost …`). On codex the same rule decides the moment an action counts as wired — `codexIsGhostHookAction` is the shared `ghostHookTail` read — but a wrapped action is COUNTED and left byte-identical rather than REWRITTEN: only a leading-token ghost action is eligible for the in-place repair, and `ghost mcp status --client codex` asks the same rule before it reports a hook missing, so the diagnostic and the merge agree on the same file.
