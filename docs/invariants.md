# Ghost invariants

The package map and the load-bearing design invariants: what each package owns, and the rules a change must not break. Moved verbatim from `CLAUDE.md` so that file stays short; the full design narrative is `docs/architecture.md`. The PR reviewer workflow reads this file from the base ref as part of its conventions.

## Stack
- Go 1.26+ CLI application
- SQLite with FTS5 for memory persistence (modernc.org/sqlite — pure Go, no CGO)
- CLI harness callers (claude/opencode/codex/goose subprocesses) — used by reflection, resolve, and supersede. Each harness owns its authentication and billing; Ghost does not add a direct API client. The prompt is written to the child's stdin and no positional message is passed: the kernel caps one argv element at 32 pages (128 KiB on a 4 KiB-page x86, 512 KiB on a 16 KiB-page one) and a reflect prompt reaches megabytes, so an argv prompt failed the spawn with E2BIG instead of answering. `claude -p` and `opencode run` read the message from a pipe when none is given; codex gets `exec -` and goose `run -i -`. `claude --system-prompt` stays an argument — small, fixed, and never confusable with user content. `cli.model_reflect` / `model_resolve` / `model_supersede` pin the opencode harness model per phase (each phase is its own process; ignored by claude/codex/goose which have no model flag). Empty = any inherited `GHOST_OPENCODE_MODEL`, else Ghost's explicit `opencode/big-pickle` default; a configured pin overrides an inherited env pin for that phase.
- MCP server via modelcontextprotocol/go-sdk (stdio transport)

## Package map
- `cmd/ghost/main.go` — CLI entrypoint; subcommands: mcp, hook, reflect, resolve, supersede, prune, lifecycle, project, obsidian, opencode, bench, backup, export, import, history, maintenance, upgrade, context, version, help. `runCLI` answers `-h`/`--help` (`cmd/ghost/help.go`, one usage table) before the dispatch, so a help request has no side effect. A command line the dispatch cannot route — an unknown command, a missing or unknown subcommand, no command at all — is `usageError` on stderr (the diagnostic, then that level's own usage) and exit `2`, the conventional usage-error code, kept distinct from the `1` every command uses for a run that started and failed (#691; bare `ghost mcp` still starts the server, the one group with a default action). Only the groups in `commandGroups` dispatch on a subcommand word: a word after a command that takes an OPERAND (`ghost history <memory-id>`, `ghost reflect <project>`) is data and its parser's business, and an unknown FLAG is that parser's too — exit `1` where it rejects one (`ghost reflect` still ignores it, as it always has)
- `internal/adversarial/` — Test-only support: the shared hostile-input corpus (prompt injection, secret shapes, invisible-character tricks, path shapes) and the shared inert-content invariant the three untrusted parse surfaces assert against (#585). Nothing under `cmd/` may import it; it exists to be called from `_test.go` files. The invariant in one sentence: a value parsed from an untrusted surface is data — stored exactly as parsed, naming at most one path component inside the directory its surface owns, and never deciding the parse. `internal/mcpserver/adversarial_test.go` (#538) proves the same invariant one layer out, over the wire
- `internal/ai/` — CLI-harness providers (`CLIClient`/`OpenCodeClient`/`SourceProvider`) used by reflection + resolve + supersede — no Anthropic HTTP API client. Every child is spawned through the one `harnessCommand` funnel, which applies the `harnessEnv` allowlist and confines the working directory and temp variables to an invocation-owned scratch dir. The backend is part of the policy, so each harness keeps only its own auth/config root (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, the safe `GOOSE_*` set, `OPENCODE_API_KEY`). Two harnesses additionally get an isolated config tree because their plugin/MCP discovery would otherwise find Ghost's own registration: opencode gets a fresh home plus an `mcp: {}`/`plugin: []` config, and goose gets an empty invocation-owned `HOME` (its plugin root is home-relative by specification, so `XDG_CONFIG_HOME` alone cannot move it). The goose home carries the config rather than restating where it lives — the inherited `XDG_CONFIG_HOME` when set, otherwise reproducing each home-relative root goose may resolve (`.config/goose`, `Library/Application Support/goose`; Windows uses `%APPDATA%`, which the allowlist already passes through) — so goose's own per-platform resolution is untouched and authentication still works. `GOOSE_PATH_ROOT` is the exception: goose consults it before any home variable (plugins resolve to `$GOOSE_PATH_ROOT/.agents/plugins`), so it is repointed at a root inside the isolated tree with the real `config/` carried into it, and a relative value is left alone because goose ignores one. Where a symlink is refused (Windows without Developer Mode) the files are copied instead. If the home cannot be established, the call fails rather than running with the real home. Codex needs no tree — `--ignore-user-config` already covers it. OpenCode's tree also owns a DATA root (`XDG_DATA_HOME`), which is what keeps a lifecycle run out of the user's session list (#588): `opencode run` has no flag to skip saving a session, so the store's location is the only control, and OpenCode resolves its session database from that variable (verified on v2.0.15 with `opencode debug paths`). V2 needs `--standalone` for this to hold — without it `run` attaches to the user's shared background service, and the server holding the user's data dir is what creates the session. No `session delete` follows a run: the store sits in the invocation-owned directory whose deferred cleanup removes it, so a session cannot outlive its call, and a delete would cost a second OpenCode process per harness call (hundreds per lifecycle) to erase a row from a directory about to be deleted. The pre-isolation backlog is `ghost opencode cleanup-sessions`. A child gets a minimal environment AND NO TOOL SURFACE — see “No harness child gets a tool” below for the per-harness mechanism, the argv goldens, the codex probe, the residuals and the live tests.
- `internal/memory/` — SQLite CRUD, FTS5 search, vector search, time-decay scoring, and the retriever contract behind the assembler (`Store.Candidates`: one read snapshot, widened untrimmed rows with their scoring facts, leg/edge statuses). `Store.CreateWithID` is the only writer that takes a primary key THE CALLER COMPUTED for a row Ghost is creating fresh: Create's write — same transaction, same history and evidence rows, same checks — plus a named key, and an empty one is refused rather than falling back to the column default. The other two writers that write a caller's id preserve an id Ghost already held rather than being handed a new one, and that is the whole difference: `ImportMemory` writes the id an artifact carries (so an unchanged store re-exports byte-identically, and id-only dedup means the destination's own copy is never overwritten), and `RestoreSnapshot` brings back rows under the id they had, so everything still pointing at them resolves again. `CreateWithID` is the inverse — nothing Ghost holds names the row otherwise, which is exactly what a reproducible measurement needs, and the only caller is the benchmark: a store's ids are part of what a measurement of that store means (the ranking breaks tied fused scores by id, and re-sorts the window by a decay factor built from `created_at`), so `internal/bench` seeds a corpus under ids derived from its keys and one `created_at` per pass rather than from `hex(randomblob(16))` and `datetime('now')` (#708). The benchmark calls `CreateWithIDFromCorpus` rather than `CreateWithID`, which is the same write with the record bit OFF, and the distinction is the corpus rule and not tidiness: a dataset's `verified_at` is the DATASET's claim, so the column keeps it verbatim and no `verified` record is appended — a record's stamp is the store's clock by design, so one for a claim the dataset dated to a year earlier would assert a check that happened now. `CreateWithIDFromCorpus` keeps the credential guard, which `CreateFromCorpus` waives for downloaded public eval corpora; the benchmark's own fixtures are committed and a review has read them, so it gets the rule without giving up the guard. Nothing here is on `provider.MemoryStore` or in the MCP surface, and `Create` still mints every id a live save gets — production rows are unaffected.
- `internal/assemble/` — context assembly: `assemble.Run` is the one entry point (one `[]stage` in `pipeline.go`), owning selection, validity, category/scope predicates before window closure, provenance (pinned at 1.0), budget closure, the outcome, the `response_fit` post-pass, the always-recorded trace and the shared `Item.Line()` renderer. Depends on one method, `Candidates`; `internal/memory` never imports it. `ScopeLabel` is the scope label `Item.Line()` embeds and the session-start block prints, so no surface re-derives it; `ScopeContradicts` is the named negation of `memory.ScopeMatches` rather than a second copy of the rule. The session-start loaders are callers of those two but not yet of `Run` — passive retrieval is not served by the seam
- `internal/mcpserver/` — MCP server: 22 tools + 4 resources + 2 prompts (`recall_project`, `record_decision`)
- `internal/hostevent/` — Normalized host-event contract (v1) and the transcript scanners; every parse or validation failure is an error the caller turns into "allow the stop", and a payload past `maxPayloadBytes` is one of them (nothing else on the path bounded it — the hook read stdin with an unbounded `io.ReadAll`, and `Parse` retains the payload decoded and again verbatim in `Raw`). The hook now reads through `hostevent.ReadPayload`, which stops one byte past the ceiling, so the bound limits the allocation and not only the parse. Field values are text the host did not write, so only the contract's own fields decide the envelope: an unknown field cannot become a known one, an instruction-shaped `hook_event_name` normalizes to nothing, and the goose native aliases (`event`, `working_dir`) bind only for `--source goose` and only per field where the dialect field is absent. `GhostSaves` counts STRUCTURE, never prose — a save tool named inside a text part, a shell command or an opencode Code Mode `execute` body is not a save, because that count is the save-nudge's evidence
- `internal/mcpinit/` — `ghost mcp init`, `ghost mcp status`, `ghost hook <event> --source <host>` (contract-v1 lifecycle dispatch; installers: claude-code, opencode plugin, codex TOML+hooks.json, goose Agent-Plugins package; goose field aliasing lives in hostevent.Parse). Every write to a file the user owns — settings.json, codex config.toml and hooks.json, the opencode plugin, the goose package, the MEMORY.md redirect — goes through `writeFileAtomic`/`writeFileAtomicPrivate` in settings.go, never a bare os.WriteFile: temp file in the same dir, flushed (data and mode) with `f.Sync()`, then rename, then the parent directory flushed, so an interrupted write cannot truncate a config, a reader holding it open still sees a whole document, and a power cut can leave neither an empty config nor a missing one. A temp-file flush failure stops the write and is reported; a directory-flush failure is not (the rename already landed, and Windows has no directory flush at all). The rename carries the permission bits across and nothing else — not the owner, POSIX ACLs, xattrs or hardlinks, so a hardlinked config in a dotfiles repo silently diverges from its repo copy. `writeFileAtomicPrivate` additionally clamps the mode to 0600 and is used only by settings.json, because that is the ceiling every pre-refactor save enforced; the other files keep whatever mode the user chose, even where a codex `[mcp_servers.ghost.env]` sub-table can hold a credential. Ghost's own marker/scratch files are exempt. Two files get a one-time `.bak` through `writeBackupOnce`: settings.json on its first save, and codex `config.toml` the first time Ghost writes to it — the first init, which appends the table to a file the user already had, so the copy is the pre-ghost file (a repair-only backup could never be, since a repair can only find a table that is already there). Neither is ever rolled forward, so a later run cannot overwrite the only pristine copy with Ghost's own output, and a 0-byte config.toml is skipped rather than copied — an empty backup would stand forever and block the real one.
- `internal/claudeimport/` — One-time import of Claude Code auto-memory on first contact. The files are written by a session that read a checkout Ghost never chose, so the parse layer is an untrusted surface: a front-matter line gets its own bound (`maxFrontmatterLine`) because `bufio.Scanner`'s 64 KiB default stops the scan on a long description and the block's loss is silent (the type, and with it the category, went with it), a block that could not be read whole is imported as body text rather than half-parsed, and a file past `maxMemoryFileBytes` is skipped. The import writes nothing to disk at all — a fixture asserts the tree is byte-identical afterwards — and it never promotes: `categoryMap` is the only thing that picks a category, so a planted `source: manual`, `pinned: true` or `type: _global` reaches none of the fields consolidation filters on
- `internal/embedding/` — Ollama async vectorization worker; every vector is stamped with the identity of the space that produced it (`<model>[:<dimensions>][+prefix]`, `embedding.VectorIdentity`) and nomic-embed-text is embedded with its `search_document: `/`search_query: ` task prefixes. A LIVENESS PROBE MISSING ITS DEADLINE IS NOT AN OUTAGE, which is why the probe is three-valued rather than a bool: `Client.Probe` answers `Reachable`, `Unreachable` (a non-200, or a refused connection — an ANSWER, so nothing is listening), or `Inconclusive` (the probe's own 2s deadline expired, so we learned nothing), and `Worker.checkAlive` returns that verdict while maintaining the `ollama-down-since` marker (`ghost mcp status` reads it for outage duration). The two errors are NOT symmetric, and every call site says which one it is making, which means the two gates DISAGREE on purpose: `EmbedPending` PROCEEDS on `Inconclusive` (its callers — a one-shot `ghost supersede` and a save-driven `processProject` — have no second chance, and skipping is what made #736 report a clean `0 candidate pairs`), while `SweepOnce` skips on anything but `Reachable`, because the daemon retries in one interval and a lenient gate there walks a HUNG endpoint through every project at `2 + 2·P + 32·P_pending` seconds, blocking `Worker.Run`'s select loop and dropping save notifications past `projectCh`'s 16-deep non-blocking buffer. `EmbedPending`'s in-batch re-probe after a failed embed stops on anything but `Reachable` (a part-done batch gains nothing from another 30s request), and it RETURNS the verdict `SweepOnce` may ACT ON — the re-probe's own where a batch attempted work, a CONCLUSIVE refusal otherwise, and an `Inconclusive` over no work collapsed to "nothing to act on" — so the sweep reuses one probe and a busy machine cannot end a tick over a project with no work. Reading a timeout as "down" cost a busy machine the whole index: both the daemon's sweep AND `ghost supersede`'s own pre-scan fill (`embedSupersedeCorpus`, #716) gate on this probe, so one slow round trip left the candidate scan with no vectors to score, `Result.Unscored` holding the entire corpus, and a clean-looking `0 candidate pairs` at exit 0 for a pair the operator could see (#736). The marker answers the OPPOSITE question, because a duration is only worth having for an outage that is real: written on a conclusive `Unreachable` at once and never re-written (so a still-down endpoint does not reset its own clock) — reachable only inside the DAEMON, which is the sole caller that builds a Worker with a data dir (`embedSupersedeCorpus` passes "" on purpose: the marker is the daemon's outage bookkeeping) — AND on `Inconclusive` after `inconclusiveStampsAfter` CONSECUTIVE unanswered SWEEP TICKS — a tick counts whether or not the strict gate let the sweep past it, so a hung endpoint that skips every project still keeps the clock running (three ticks is about six minutes at the daemon's 2-minute interval) — and one slow probe is a busy machine far more often than a dead endpoint, and a marker written on one is reported for as long as the machine stays busy, while the endpoints a refusal never describes (a wedged accept loop, a remote URL behind a dropping firewall) need that duration precisely because they never produce a refusal. The streak is counted PER SWEEP TICK (`SweepOnce` -> `noteSweep`) and NEVER per probe, because `checkAlive` is called more than once per tick — `EmbedPending` re-probes after every failed embed — so a per-probe count reaches its threshold inside ONE tick and stamps the marker on exactly the busy machine the streak exists to protect against. Any answered sweep SPENDS the streak, so a stall spread over minutes cannot accumulate into an outage that was never established; a stall never *clears* a real one, and an inconclusive probe never removes the marker at all. `Client.Alive` remains the two-valued form for the two callers that only warn a human (`mcpinit`'s init preflight, `ghost_health`); a caller that gates WORK on the answer uses `Probe`, because only there does a false "down" cost a skipped corpus rather than a conservative warning
- `internal/linking/` — Background worker linking similar memories into a graph
- `internal/resolve/` — `ghost resolve`: LLM-classified de-weighting of resolved-evidence memories (drops from ranked injection, stays searchable); classifies via CLI harness (see Classifier backend below)
- `internal/memref/` — the ONE ref-resolution implementation, now for every surface that takes a memory by name, not only the ones that CHANGE a row: `ghost supersede --withdraw`, `ghost resolve --mark` / `ghost_resolve_mark`, and `ghost history` (#720), which only READS. Two entry points and ONE set of rules: `Resolve(ctx, store, projectID, which, ref)` scopes the read to a project (its callers are about to change what they name), and `ResolveIn(ids, which, ref)` applies the same rules to an id set the CALLER collected, which is what a store-wide reader needs. The difference is which ids, never how a ref is judged. `ResolveIn` names no project in its refusals because its set is not confined to one, and `FullIDLen` is only the boundary between two honest sentences about a miss, never a test of whether a ref is a whole id. `ErrNoMatch` distinguishes the refusal that says the set holds nothing from the ones that say it holds too much, and a caller branches on it rather than on the ref's length — which cannot tell them apart. The reasoning for all of it, and for why `resolveIn` applies the prefix match itself, is in [architecture.md](docs/architecture.md#memory-history). A ref is a full id, or a PREFIX of at least 8 CHARACTERS (a RUNE count, never a byte length — the id column is TEXT and SQLite's substr() slices by character, so a byte-counted floor on a multi-byte id refuses a prefix the store really has and accepts one that is a third of an identity; the two lengths agree for the hex ids Ghost mints, which is exactly why the bug survives a normal test). The floor applies to a PREFIX ALONE and is decided by COMPARING the match with the ref, never by inspecting the ref's characters — a full id is accepted whatever its shape, because `ghost import` writes an artifact's ids verbatim and nothing about the column says they are hex. A byte-exact match wins at any length (the id is a unique key, so the spelling the caller typed is decisive, which is what lets a short full id that also prefixes a longer one resolve), then a single case-folded one, then the prefix rules. AMBIGUITY IS A REFUSAL, never a choice, and it LISTS the matches up to `MaxMatches` — with ONE exception: a ref below the floor is refused WITHOUT the match list, because printing it would turn a refusal into a dump of the id set (a store-wide set is a LARGER thing to dump, not a smaller one). Two case-folded matches and no byte-exact one (a THIRD casing of ids differing only in case) is unaddressable by any spelling, so that refusal LISTS the two stored spellings instead of naming a remedy — the reader's next keystroke is a copy of one. The rules are shared rather than copied because two copies eventually disagree about which id one spelling addresses; a guess is worse on the history path than on the change paths, where it changes a row nobody named — there it also prints one memory's whole recorded TEXT as though it were another's. NOTE THE SCOPE, because the claim is not wider than it looks: `resolve --reassess --only` does NOT route here. `internal/resolve/scope.go`'s `Scope.Select` has its own rules, and it HAS to differ on one point — a selector matching nothing is a REPORTED MISS that lets the rest of the scope still be judged (#698's scoping judgement), where a change to a named row cannot be a miss at all, so a failed ref there is a refusal of the whole request. It also measures its 8-character floor in BYTES and truncates an ambiguity listing with `id[:8]`, both of which memref fixes, and unifying the two is a separate change worth doing on its own. It is worth knowing they are on the same round trip: `--mark`'s own follow-up hands the operator a `ghost resolve <project> --reassess --only <ids>` command
- `internal/supersede/` — `ghost supersede`: LLM-classified 'supersedes'/'causes' link creation over live memories, batched 8 candidate pairs per harness call with a content-keyed NEITHER cache (`supersede_checked`, schema v8, cascading FKs) so a converged project's fresh candidates make zero calls — except reversed ones, which are never cached and are re-asked every pass (live-link pairs are still validated each pass). A classify call that FAILS is re-issued ONCE, after `classifyRetryDelay` (2s, injectable through `SetRetryDelay`) and counted by `Retries()` — it is on both reports and the reassess summary log — because a real `opencode run` that exited 1 once cost a whole `ghost supersede` pass in #699's rehearsal, and the rerun a minute later answered normally. ONE retry, not a schedule, and it decides nothing: the second failure is returned unchanged so a genuinely dead harness is exactly as fatal as before, `Run` still aborts and writes nothing, an UNPARSEABLE reply is not a transport failure and is not retried, and the wait is context-bounded so a cancelled run does not spend a second spawn to be told the same thing. Pairs are oriented by `updated_at`, so the prompt also carries each note's `created_at` and offers a fourth verdict, `reversed`: a supersedes link only points newer→older, so a verdict saying the OLDER note is the current one is refused (never written, never cached) rather than written backwards (#641). The pass is KEEP-biased because the edge is not an annotation: the ranking guards demote its target and `ghost resolve`'s piggyback stamps `resolved_at` on it, so a wrong edge removes a live memory from every later session. Two rules decide that, both from #686's 43%-precision measurement (every wrong edge joined two notes that were BOTH still true). The rubric asks the falsity question — after the newer note, is the older note's claim false or no longer applicable, and two notes both still true are NEITHER even on the same topic — and a `supersedes` answer must name the claim in a `replaced:` field; missing/empty/placeholder reads NEITHER, which is a decision and therefore cacheable, and the NEITHER cache key prefix moves v2→v3 for it (a cache hit is a permanent skip for the life of that text). `replaced:` is the twin of resolve's `closed-by:` and is read by the SAME helpers (`resolve.ReasonedField`/`resolve.ReasonlessValue`), so a value that keeps a note in one pass's injection cannot bury it in the other's ranking; a synonym verdict is no way around the field. `VetoSupersede` is the free half, before any call: an older note stating an imperative that the newer note never names as retired or changed is settled as no-edge, and the imperative vocabulary is resolve's own (`VetoKeepImperative`, which `VetoKeep` also calls) rather than a copy, so one list protects a memory from being buried and from being demoted. Its error is in resolve's direction — a false veto leaves a stale note ranked, and #641's own "status-report-fix" fixture is what that costs, which the labeled regression set pins by name. A pair whose endpoints' scopes conflict is never classified: the scope reaches `SearchVectorScoped` so the neighbour budget counts only linkable rows, and `Run` re-checks the rule over every pair it is about to spend a call on — the reclassify path included, which is the only way a link written before the rule existed is reached at all. Beside it, at the same point and for the same reason, a pair with a KEEP-FOREVER endpoint (`retention`, see "Retention tiers") is dropped: `SelectCandidates` refuses such a pair on the fresh path, but the reclassify path re-proposes an EXISTING edge whenever an endpoint changed since the edge was written and never passes through it — so an edge written before the row was declared keep-forever would be billed a classify call and re-affirmed the first time that row was edited, which is the outcome the exemption exists to prevent. The edge is left alone: withdrawing it is `--reassess` / `ghost_link_withdraw`, and the creation pass is not where graph history is deleted. What the refusal stops is spending a call to keep it alive. The classifier is handed note text only, so it cannot see a `memories.scope` column; the guard is structural, not a rubric line. The reclassify half saves one call per endpoint edit rather than one per pass, because skip-if-unchanged already holds an untouched pair quiet. The scope refusal is not counted in `Result`: against the shipped store the query drops the conflicting rows before `SelectCandidates` sees them, so a count there would read as zero for work declined, while the veto IS counted (`Result.Vetoed`, printed) because a run that declined work it did not do must not report the same totals as one that found nothing to. An existing scope-conflicting edge is left in the graph and exempted at read time by `SupersedePenalties`, by `ghost resolve`'s supersedes piggyback, and by the two fold-target liveness checks — the piggyback is the one that would have been persistent, stamping `resolved_at` on the older endpoint. A vetoed pair's existing edge is left alone there — the creation pass is not where graph history is deleted — and `ghost supersede <project> --reassess [--apply]` (`internal/supersede/reassess.go`) is the repair path: it re-judges every live 'supersedes'/'llm' edge under the current rules and withdraws the ones that come back NEITHER, vetoed, CAUSES or REVERSED through `InvalidateLink` (which writes the `unsupersede` history row), printing each withdrawn edge with the rule that withdrew it, which half decided it (`veto, no harness call` vs `classifier`) and — because a withdrawal sweeps the pair's 'causes' edge as `Run` does on the same self-contradicting verdicts — how many `causes` rows that took (`WithdrawnEdge.CausesSwept` is the PREDICTION in a dry run and the OBSERVED count under `--apply` — a row never claims a deletion that did not happen, and a sweep that ERRORED sets `SweepFailed` and prints "unknown" instead of a count (`ReassessResult.CausesSweepFailed` counts those rows, separately from the swept ones, because "swept 0" and "could not tell" are different sentences); a `causes` VERDICT sweeps nothing, because it affirms that relation). The prediction is read through each pair's OWN endpoints (`GetLinks` on the older id), NOT through `LinksByRelationSource`: the sweep deletes by id with no project predicate, so a pair whose older note has been promoted to `_global` or moved by `ghost project merge` is still swept, and a project-scoped read (which joins on the edge's source, and a 'causes' edge's source is the OLDER note) cannot see it. A dry run reports the count it is about to print, not `Result.Withdrawn` (which is 0 by construction in a dry run — the same rule `reassessSummaryLine` follows on the resolve side), and a failed invalidation returns the edges that DID land with the error, because each is its own transaction and a later pass will not see them again. That 'causes' sweep is predicted by a read that ONLY a dry run makes: under `--apply` every row's count comes from the sweep itself, so the prediction is not read at all and a discarded read can never be the reason a repair failed (`TestReassessUnderApplyNeverReadsThePrediction`). A dry run whose prediction read fails marks the row's second deletion unknown (`WithdrawnEdge.PredictionUnknown`, counted as `CausesPredictionFailed`) instead of printing a count nobody looked for, and `SweepFailed` stays false — no write ran. A classify call that FAILED is not fatal to those rows either, and that is the direction of the fix (#699: one dead `opencode run` cost a real rehearsal every withdrawal, 76 of 87 edges waiting on a rerun, including the ones the veto had settled for free): the settled withdrawals apply, the pairs the classifier never answered move to `ReassessResult.Unjudged` with their edges LEFT ALIVE, and the pass still returns an error so the exit says "rerun me". Every open pair is unjudged, not the subset the harness named last — a call that failed answers nothing about anything it carried, and a verdict-count mismatch is the same state, so both take this path. Withdrawing is the safe direction and settling the veto needs no harness, which is what makes it the one case where a partial repair is still a repair. The withdrawal sweeps the other relation's edge too, as `Run` does on the same self-contradicting verdicts, but NOT under a CAUSES verdict: there the existing 'causes' edge may be saying something true. THIS IS THE ONE PLACE THE VETO'S ERROR ARGUMENT DOES NOT CARRY OVER: on the creation pass a false veto costs recall, here it deletes a correct edge, and since the veto is deterministic on the same two note bodies the ordinary pass re-fires it forever, so the pair cannot be re-linked until a note changes — which is why the report marks those rows. Withdrawing is only half the repair: the memory is still stamped `resolved_at`, and only `ghost resolve --reassess` can clear it, so the chain is pinned end to end in `TestReassessResolvesAChainIntoResolveReassess` `supersede.Withdraw` (`withdraw.go`) is the OTHER repair, for an edge those rules still accept: a pair that is wrong for a reason no rubric can see (the newer note is not a replacement of the older one at all) is confirmed by the classifier, so `--reassess` keeps the edge and only the caller's judgement can withdraw it. Nothing is judged there, so no harness is involved and nothing is billed — `ghost supersede <project> --withdraw <src> <tgt> [--apply]` and the MCP `ghost_link_withdraw` call the same core, through `linkCapableStore`, so an operator and an agent take one path. Its rules are the ones a delete needs: a ref is a full id or 8+ characters of one (every report abbreviates to eight, so requiring 32 would make it undrivable), matched as ONE literal, case-insensitive PREFIX query inside the project plus `_global` — which is what lets a full id of any shape resolve through the same call, and `ghost import` writes an artifact's ids verbatim, so a ref check that insisted on hex would make an imported endpoint unnameable; the 8-character floor applies to a PREFIX alone and is decided by comparing the match with the ref rather than by inspecting the ref's characters; an ambiguous ref is a refusal LISTING the matches, never a choice; a pair with no live edge is an error whose message names the target's live edges; and the WHOLE request is settled before any write, so one bad pair out of five withdraws none of them (`TestWithdrawChangesNothingWhenAnyPairIsWrong`). The edge is found through the project that owns its SOURCE (`SupersedesLinksInto`), like every other supersede reader, so no project can withdraw or even see another's edge. Under `--apply` it prints the follow-up through the SAME helpers `ghost supersede --reassess --apply` uses (`supersedeReassessFollowup` + `writeReassessTargets`, one formatter and one file writer for the two repairs, and the file's header names which command wrote it), so both name the SCOPED `ghost resolve <project> --reassess --only <the withdrawn edges' target ids> --apply` plus a `--only-file` beside it (both surfaces through `internal/followup.ResolveCommand`, which quotes a project name that needs it — there is no MCP tool for the repair, because `ghost_resolve` is the FORWARD pass and stamps `resolved_at`, so the MCP result names the CLI command and says so) — scoped because an unscoped repair re-judges every resolved memory in the project (#702 measured 143 rows proposed, ~35% stale). The list is deduplicated and holds only rows the call actually withdrew: a row it never reached has a live edge, so nothing was orphaned by it. The report itself carries no resolve hint and prints the target's own first line, so the reader can confirm the edge was the right one
- `internal/bench/` — `ghost bench`: retrieval-quality benchmark harness (graded dataset + sweep + staleness/recency/ranking-state/maintenance-state suites + the no-answer false-positive report, measured per condition BY the runner — `runCondition` does not skip a query with an empty rel, it measures it, and the deeper report reads that measurement rather than searching again). Each scenario/fixture asserts the SHAPE of what it can see, not today's numbers: `TestRecencyTrapAtDefault`/`TestDecayFrontier`/`TestSupersedeDemoteClearsFrontier` are scoped to the trap fixture's never-decay half (the invariance the frontier claims; the decaying half moves by design and is reported), the ranking-state suite asserts that decay and the demote are each non-inert, that they do NOT compose (the demote recovers none of the probes decay demotes, because the rows decay pushes down are the rows the demote promotes), while the headline corpus is still inert — asserted by TestDecayDoesNotPerturbGradedBench, which owns the 551-memory load and checks it in the two forms the property has: measured for decay, STRUCTURAL for the demote (no memory in that corpus declares an age_days or a supersedes edge). Do NOT re-seed or re-measure the headline corpus in the ranking-state test: this package was within ~10s of CI's 600s per-binary ceiling, and #677 added ONE more corpus-wide test — ~9s — which failed `build-and-test` at 600.038s. One corpus load is ~10s and #677's per-row validity and provenance writes are free, so the cost here is TESTS, not rows and not loads: it fits again only because TestBenchRegressionFloors, TestBenchDatasetReport, TestDecayDoesNotPerturbGradedBench, TestSweep and TestFalsePositiveReport now run CONCURRENTLY, so assume a new corpus-wide test costs ~10s of a shared CI budget and measure before you add one — `go test -race ./internal/bench -run '^Test[^L]' -count=1` reads 188s on a laptop, a different machine that flatters the answer, and `sweep_test.go` carries the measurement and the failed CI job. The fusion claim is a PAIRED 95% bootstrap interval whose lower edge has to clear -`fusionTolerance` (0.02 = 4.4 queries of NDCG at n=220) — not a comparison of two means, because the margin over the vector leg is 0.018 with an interval of [+0.003, +0.034]
- `internal/obsidian/` — One-way Markdown vault mirror (`ghost obsidian export|sync`). The store can hold ids, project names, tags and bodies Ghost never generated (`ghost import` writes an artifact's ids verbatim), so every name it builds is a name somebody else chose: `idToken` keeps the first 8 bytes of an id only when they name a single path component a person could type and hashes the id otherwise (a separator put the note outside the `Memories/` subtree prune manages and had it deleted; a tab or line break is a legal name nobody can open; a NUL failed the whole export with `EINVAL` on every run), `folderNames` replaces a folder over `maxFolderName` the same way it replaces one that would escape because `ENAMETOOLONG` failed the export just as permanently, and `hasGhostID` unquotes exactly what `yamlScalar` emits. What prune keys its RETENTION on is the note's vault-relative PATH (`keepSet`, keyed by `keepKey`), not the id read back out of the note and not the bare basename — the front matter still decides whether a file is Ghost's to touch at all, so the block is prune's ownership test, but the id inside it is not its key: `yamlScalar` flattens tab/CR/LF to a space so every key stays on one line, and that is lossy — three records can render one `ghost_id` line, and keyed on that line they would collide on it and two of the three would be deleted. A basename is not safe either, and for a different reason: the same slug occurs in two project folders, and a memory and a task with the same title produce the same name and can share an id fragment, so one live note anywhere in the vault would keep a stale copy alive everywhere. A key that decides what to keep should be one the system holds, not one parsed back out of a file written for a human. Every front-matter value still has to occupy exactly one line — that is what makes the note valid YAML and the ownership test's answer well-defined (it reads to the first `---` and takes the one `ghost_id:` line there) — but no value read out of front matter, forged or merely flattened, can now make prune drop a note it wrote
- `internal/portable/` — The portable JSONL artifact (`ghost export` / `ghost import`): one typed record per line behind a schema-version header, written projects-then-memories-then-tasks-then-decisions in id order so two exports of an unchanged store are byte-identical. It is a wire format, not a backup — `memory.Store.Backup` is the restorable copy. Import never overwrites an id that already exists, so re-running is always safe; a record it cannot import is rejected individually and the run continues, so one hand-edited line does not abandon the file. A dry run opens the store read-only, so the preview cannot migrate or seed what it previews — which means openReadOnlyTransferStore must also refuse a store whose PRAGMA user_version is behind or ahead (memory.DBUserVersion / memory.SchemaVersion), or the first query fails with SQLite's "no such column" instead of a version mismatch. The artifact deliberately omits Ghost's own _global builtin seeds: they are written per-install under hex(randomblob(16)), so every importer's id-only dedup would duplicate them permanently, and the destination already re-creates them by content. Imported memories are stamped `source = "onboarding"` and unpinned unless `ImportOptions.TrustProvenance` is set: an artifact is a file that arrived from somewhere, and on its own authority it must not be able to plant rows the store exempts from consolidation by name (`manual`, `builtin`) or by pin. Embeddings, memory links and the resolve KEEP cache are not in the artifact: all three are derived and rebuilt by their workers
- `internal/reflection/` — Memory consolidation: LlmConsolidator + SQLiteConsolidator. The LLM tier speaks per-id operations, not free text (see "Reflection operation contract"). `persistent`-tier rows are never its input or its output: `ReplaceNonManual` excludes them from the snapshot and the replaceable set, which is the only way "a consolidation never saw this text" is true (see "Retention tiers")
- `internal/followup/` — the one renderer for the command that completes a supersede repair (`ResolveCommand`: `ghost resolve <project> --reassess --only <the withdrawn edges' target ids> --apply`, full ids, the project quoted through `--project` unless it is one bare shell word, and the ids quoted too — `ghost import` writes an artifact's ids verbatim, so an id is caller-supplied text like a project name. It returns TWO further values: the ids it could not carry because they hold a comma (the `--only-file` beside it reads one id per line and never splits, so that surface reaches them) and the ids it could not carry because they hold a NEWLINE, which NO surface can (`--only` splits on commas, the file is one id per line, and a `#` in an `--only-file` line is a comment only when it FOLLOWS WHITESPACE so an annotated `<id>   # note` keeps working — a selector holding a trailing comment is not a prefix and would make the repair refuse the whole file — at the cost of truncating an id containing ' #') — a memory with such an id stays resolved until the row is rewritten, and every surface says so rather than claiming a repair; the id file is REFUSED outright when every id in the set is one of those, because a file naming nothing is a list `readRefSelectors` rejects (one reader for both `--only-file` and `--mark-file`, differing only in the flag it names in its errors — a second reader would be a second place for the two to disagree about which ids a file can name). The command is EMPTY when no id is carriable, and that is deliberate in the other direction too: printing the command without `--only` is the project-wide re-judge #698 measured, and both surfaces print what comes back here as THE repair. A comma therefore reaches the id file; a newline reaches nothing, and is named. It is its own package because THREE surfaces print that command and none may render it differently: the CLI under its per-edge list, the CLI under `resolve --mark`'s report (`resolveMarkReport`, whose follow-up lists only the rows THIS call stamped — a row already resolved before the run is not something the command would change), and the MCP tool `ghost_link_withdraw`, where it is a CLI command rather than a tool call because no MCP surface exposes the repair at all — `ghost_resolve` is the FORWARD pass and stamps `resolved_at`, so pointing an agent at it would bury more memories than it restores- `internal/secret/` — Credential-shape detection for stored text (`Detect`); shape-based, never keyword-based
- `internal/provider/` — Interface contracts: LLMProvider, MemoryStore
- `internal/config/` — Layered YAML + env config (koanf). `Load` returns an error for a config file that exists but does not parse, for a `GHOST_*` value that is not readable as its key's type, and warns on file keys no `Config` field binds (env names are not key-checked — most `GHOST_*` variables are not config keys); CLI subcommands call it and fail. `LoadForHook` is the host-session path (SessionStart/Stop hooks, obsidian auto-sync, routing, the scratch budget): it reports the same problem on stderr and returns `FallbackConfig` — the compiled defaults plus the `GHOST_*` environment, i.e. every layer that does not read a file — so a typo cannot fail someone's session and cannot undo an environment opt-out. `envOverrides` lists the `GHOST_*` names the generic `GHOST_` prefix + `_`→`.` transformer cannot map, each with the parser for its key's type. `SetWarningWriter` redirects the warning sink, which `runMCP` points at its log channel; the sink is atomic because harness spawns warn from goroutines.
- `internal/procstat/` — process identity for the two places Ghost must not trust a bare PID: `StartTime(pid)` returns an opaque creation-time token — per-platform, from the `linux`, `darwin` and `windows` files plus a `!windows && !linux && !darwin` stub that returns `("", false)` — and `IsAlive(pid, wantToken, haveToken)` reports liveness from two variants only, POSIX signal 0 and the Windows handle/exit-code form. The token is opaque — never interpreted as wall-clock time, never compared across platforms or machines, only tested for exact equality against a token obtained the same way — and the load-bearing rule is that liveness FAILS OPEN: when the token cannot be read (an unsupported OS, an unreadable proc entry, permission denied) `IsAlive` reports alive, so a transient token-read failure can never flap a live process to "dead" and let `Reap` or `claimPidFile` delete what it should not. Linux's raw source is boot-relative ticks, which is not reboot-safe on its own while `.pid` files and `.owner` markers outlive a reboot, so the machine's `boot_id` is prefixed into the token. Windows treats a handle that opens with an exit code other than `STILL_ACTIVE` as not alive, because `OpenProcess` succeeding does not mean the process is still running. Both consumers go through it and neither re-implements it: `internal/mcpinit` (a `.pid` file holds `pid:token`, or a bare pid when no token was available) and `internal/scratch` (the `.owner` marker's `start` line). The extraction was forced by the second: `scratch` needs the same token but `mcpinit` already imports `scratch`, so a shared package was the only way to reuse the implementation instead of duplicating it — `mcpinit` keeps two unexported wrappers so its own call sites and platform tests did not move
- `internal/repo/` — repository identity read out of the filesystem, one function: `DetectRemote(dir)` runs `git -C dir config --get remote.origin.url` under a 2s `detectTimeout`. It exists to keep process-spawning out of `internal/memory`, which is deliberately a pure storage layer that never spawns a process, while the only place that can say which repository a path belongs to is a caller willing to ask git — so the capability is INJECTED rather than called: `cmd/ghost/main.go` hands this function in through `memory.SetDetectRemote`, `nil` restores a no-op returning `""`, and a store built without one resolves exactly as it did before repository identity existed. The load-bearing rule is that every failure returns `""` rather than an error — not a repository, no `origin` remote, an unreadable directory, no `git` binary, a hung `git` — because detection runs on save paths and "no repository known" is a legitimate answer, not a reason to fail a memory write; the timeout is that same rule applied to a network-mounted worktree or an NFS-backed checkout, which must never stall a write. `-C` walks up to the enclosing repository, so a path pointing inside a checkout still reports that checkout's remote. `internal/mcpserver` calls the same detector, and only when a `project_id` contains a path separator — a project NAME says nothing about a repository, so an ordinary named save never crosses the boundary, which is what lets its tests replace the package var and prove it. `ghost project bind` passes the same function, so the remote recorded there is the one resolution later compares against rather than a second spelling of one repository
- `internal/selfupdate/` — `ghost upgrade` self-update from GitHub Releases

## Key patterns
- Memory categories: architecture, decision, pattern, convention, gotcha, dependency, preference, fact
- Untrusted parse surfaces (`claudeimport`, `hostevent`, `obsidian`): a value somebody else wrote is DATA. It is stored exactly as parsed, it names at most one path component inside the directory its surface owns, and it never decides the parse — the parser's own vocabulary does, and a payload that does not fit is rejected or mapped to the documented fallback, never obeyed. `internal/adversarial` states the invariant once and holds the corpus all three suites drive (#585). Two rules that look like filters and are not: a planted payload stays retrievable (hiding the tampering is worse than showing it; quoting into the data block happens on the way out), and every `hostevent` refusal fails open, because "allow the stop" is the only response the hook contract emits. Defects here were silent rather than loud — a front-matter line past `bufio.Scanner`'s default cost a memory its category, a separator in a record id cost it its note, a quoted `ghost_id` cost it a second prune pass — which is why each is a fixture and not a line of prose
- Backup and portable transfer: `ghost backup` is `Store.Backup` → `memory.vacuumInto` (SQLite `VACUUM INTO`, the same one implementation the pre-migration copy uses), so both claim the destination with `reserveBackupPath` (a `0600` `O_EXCL` create, before any byte is written) and both refuse an existing path. `VACUUM INTO` names no mode, so creating the file first is what keeps a full copy of the memory database out of a group-readable window on an `--out` outside the `0700` data directory. The write lock is held for the vacuum and nothing longer. It counts the snapshot by opening the written file read-only, never the live one — the counts a restore is checked against have to describe the file that was written. The portable artifact (`internal/portable`) is the other half: `memory.PortableProjects` / `PortableMemories` are separate reads because `ListProjects` has no `repo_remote` and an artifact needs the columns in an order it owns. (The other reason this line used to give — that the ordinary list readers drop the validity triple — stopped being true when `memory.Memory` gained `valid_from`/`valid_until`/`verified_at`: retrieval hydrates all three, and `PortableMemories` selects them for itself.), and `Import*` are separate writes because no existing writer can preserve an imported id, `created_at` or pin. Every `Import*` takes an `apply` flag, so a dry run runs the same validation as the run it previews
- Time-decay scoring: convention/preference/fact never decay; architecture/pattern 45-day; decision/gotcha/dependency 30-day
- Retention tiers (schema v19, #587): `memories.retention` is `session|project|persistent` with a CHECK, default `project`, and `memories.expires_at` is DERIVED for a session save (now+`SessionTTL`) and stated by nobody else — so no save can schedule the memory it just wrote for deletion, and a NULL expiry is the unprunable direction. `migrateV19` adds both columns and updates no row: a memory that persisted until somebody resolved it WAS a project memory, which is what every pre-v19 row reads as afterwards. `memory.retention` (the column, in Go) is not `Memory.Retention` (the field): the field normalizes an unset column to `project` in `scanMemories`, because one reader forgetting the column would otherwise hydrate a session row as "no tier stated" and a prune could not see it — which is why the six full-row readers share ONE list (`memoryColumns`, plus `memoryColumnsPrefixed` for the two FTS queries that alias `memories`). `DecayFactor(category, retention, pinned, ageDays)` is the Go mirror of `DecayRankingSQL` and both carry the bounded session decay (tau 7 days, floor 0.5, formatted from the same constants); a durable row's score is exactly what it was before tiers, which is the whole reason the multiplier is 1.0 there, and `explain` names it per row as `retention_factor`. `persistent` is the one tier a default may not take back, and the exemption is asked at every WRITE and every ranking consequence, not only where a pass selects inputs: `ReplaceNonManual` (snapshot, replaceable set, concurrent-save set, output delete), `RestoreSnapshot`'s UPDATE, `ResolveCandidates`/`ResolvedCandidates`/`SetResolved`, `supersede.SelectCandidates` (before the classify call, so the verdict is not paid for), `SupersedePenalties` and `DemotionPenalties`, which take the caller's PROTECTION map rather than a list of pins — because a stale `duplicate` or `supersedes` edge would otherwise sink a row every other pass spares, and because both lookups run on read-only handles (`GetTopMemories`, `explain`, the session-start loaders), where a statement naming the column fails in full. The two maps are NOT the same: `DemotionPenalties` (the near-duplicate demotion) protects a plain `pinned` row the way it always did before tiers and extends that to keep-forever rows, while `SupersedePenalties` protects ONLY the `persistent` tier — a `supersedes` edge asserts that one claim replaced another, and a pin keeps a row visible without declaring its claim current, so a pinned supersedes target sinks exactly as it did before #587 (the pin-sparing supersede variant is issue #739, kept out of the tier PR; `TestAPinDoesNotStopASupersedesEdge` and `TestASupersedesEdgeDoesNotSinkAPersistentRow` pin the boundary). EVERY caller builds the map from rows it has already read, and a caller handed ids it did not hydrate is a caller that cannot protect them (`TestTheDemotionLookupsDoNotNameTheTierColumn` drops both v19 columns and calls both). A fold RAISES the surviving row's tier and never lowers it (`mergeRetention`): a protection the caller asked for and did not get is a false report, while lowering would let a `session`-tier restatement schedule another memory's durable row for deletion. `ghost prune` is the ONLY thing that removes a `session` row, it is never run for you (no lifecycle phase, hook or scheduler calls it), the dry run is a read-only PREVIEW built from the same predicate, scope and order every apply batch re-derives (so it cannot describe rows the apply would not select), the apply deletes in bounded batches (500 rows per transaction, each batch with its own tombstones and its own rollback), and every removal appends a `delete` tombstone before the DELETE. Its activity term is `COALESCE(last_accessed, updated_at, created_at)` — nothing in production writes `last_accessed` (`Touch` has no caller), so the grace is measured from the row's last WRITE, and `retention` is NOT carried by the portable artifact, so an imported memory arrives as `project` (kept longer, never pruned)
- Empty-set guard: never replace all memories with empty reflection output, and a reflection response carrying no operations fails the LLM tier rather than relying on that guard alone
- The gate lives in `TieredConsolidator`, NOT in the LLM tier — so naming a backend bypasses it unless the tier is wrapped. `ghost reflect --tier cli` and `--tier opencode` used to hand the bare `LlmConsolidator` to the apply path and had no floor at all, while the default `auto` tier and the unattended path were bounded; `eval/cycle` measures with `--tier opencode --apply`, so the suite was grading an ungated consolidator against a gated production one. Both branches now go through `gatedLLMTier` (`cmd/ghost/lifecycle.go`), which calls `reflection.NewGatedConsolidator` — one tier, no fallback added, so "exactly this backend" still means that and a too-small answer is a failed run rather than a quiet drop to Jaccard. It is a named function because `runReflect` calls `os.Exit`, so the tier switch is unreachable from a test and the behaviour has to be pinned at the seam. The wrapper reports the tier's OWN name, not the `tiered:` prefix (`TieredConsolidator.gated`): `Consolidator: cli` must keep printing `cli`, because a script or saved log-grep keyed on that label breaks silently otherwise, and wrapping a tier changes how it is bounded, not which one runs. The prefix marks WHICH CONSTRUCTOR ran, not how many tiers were in the list — `auto --require-llm` is a one-tier list and still prints it, so do not read the prefix as a claim about fall-through
- Reflection reduction warning counts survivors, not one scope: `reportReductionWarning` (`cmd/ghost/lifecycle.go`) measures `reflectRetained`, which adds the cross-project candidates back in when promotion is off because `applyReflection` folds them into the project. Reading `len(projectMems)` understates retention by the whole candidate set and fired `>50% reduction` on rounds that lost nothing — a warning that cries wolf on the one path where nobody reads it is worse than none. The input side is `len(consolidatable)`, not a re-count of non-`manual` sources: `consolidatable` already dropped `manual`/`builtin`/`pinned`/`persistent`/resolved, so every row left is one `ReplaceNonManual` would delete. It fires on a dry run too (the call is above the `if !apply` return), which is deliberate — the preview reports the compression it would apply — and only from `reductionWarnMinInput` (6) up, which is where the quality gate stops judging and this becomes the only signal
- Validity and provenance are written by the tools, or by nothing: `ghost_memory_save`, `ghost_save_global` and `ghost_memory_update` share one `validityArgs` struct (`internal/mcpserver/validity.go`) and one resolver, so the six optional arguments mean the same thing in all three schemas. `valid_from`/`valid_until`/`verified_at` take RFC 3339 or a date and are stored in `memory.StoredStampLayout` (`verified: true` is the same field as "now", and `verified` together with `verified_at` is refused rather than resolved); a window that does not end after it starts, a `confidence` outside [0,1], an unreadable stamp and a `source_ref` over `MaxSourceRefLen` are tool errors, because stage 2 would otherwise read them as claims nobody meant. Nothing is invented: an omitted argument is absent, and absent is NULL, so a store can still tell "nobody said" from "said to be nothing" — which also means a stamp can be replaced but not removed. Only `ghost_memory_search` filters on a window: the browsing surfaces do not run the pipeline, so they render one marked `expired` instead (assemble.ValidityStateOf), while the session-start block renders its own rows and shows no marker at all. Saying otherwise in a tool description is a lie the next surface inherits — and a surface that renders its own rows does not get the shared renderer for free. `agent` comes from `provenanceFor` (client name, then process ancestry) and `session_id` from `req.Session.ID()`, which is "" on the stdio transport every Ghost host actually uses — NULL is the honest record there, and a made-up id would be indistinguishable from a real one. `memory.UpdateMemoryWithOptions` writes the columns with `COALESCE` (and `NULLIF` on the provenance strings) rather than a read-merge-write, so an omitted field is the stored value by construction and two concurrent edits cannot lose each other; `provider.MemoryStore` is not widened for it, so `mcpserver` reaches it through the `updateCapableStore` assertion. Stage 4's multiplier stays `1.0`: the renderer shows confidence and the writer records it, and nothing ranks on either
- Durable knowledge, not repository facts (#674): a memory is for knowledge that survives the conversation and is expensive to rediscover, and one rule is stated in five AGENT-FACING places that must be reworded together — the MCP server instructions, the `ghost_memory_save` and `ghost_save_global` descriptions, the reflect ops prompt, and the resolve classify rubric — plus the two docs that describe them (`docs/mcp.md` agent guidance, `docs/cli.md` resolve section), which go stale silently because no test reads them. "foo.go contains HandleFoo()" is the bad example (the repository is authoritative, so the note goes stale silently and is cheap to re-read); "Production schema changes require explicit approval." and "Deployment keeps database migrations separate from application rollout, on purpose." are good ones. The rule GUIDES and never refuses: the only deterministic half is `repoFactHint` (`internal/mcpserver/durable.go`), one advisory sentence appended to a response that ALREADY reports a stored id, on the three paths that write caller-supplied memory text and say so: `ghost_memory_save`, `ghost_save_global` (the instructions route the cross-project case there) and `ghost_memory_update`. NOT `ghost_decision_record`, whose companion memory's text is composed inside `memory.RecordDecision` — duplicating that format string in the MCP layer to judge it would let the two drift apart silently, and it needs both a reference token and a containment predicate in the SAME sentence — one without the other fires on exactly the durable notes the rule protects, since a note that cites a path and adds a reason is the case to leave alone. The equivalent reflection guidance is an obsolete-drop CANDIDATE only: the unattended path's answer to an unexplained drop is the verbatim re-add, so the new rule splices the mode-dependent `staleTail` and claims nothing the apply does not do under `--allow-drops`. Resolve gets RUBRIC text and no new veto, and NO new veto pattern: a veto is a second vocabulary for what a memory is for, `internal/supersede` reads the imperative half of the same list for the opposite decision, and `ghost resolve --reassess` runs that veto over already-resolved rows, where a false one un-hides a note permanently (#702). The predicate list is LOCATION verbs only for the same reason — a path-anchored behavioural claim ("`lifecycle.go` calls `os.Exit`, so the tier switch is unreachable from a test") is a reason, not a repository fact. The REFERENCE half is PATH-LIKE for the same reason: "it contains a dot" is not a property of code, and a bare `Capitalised.Name` fires on durable notes (an independent review measured five — `U.S. regulators`, `Bob.Smith`, `Node.js`, `Terraform.State`, `Jane.Doe`, every one carrying a real containment predicate), so a bare `Stem.ext` needs a LOWERCASE stem and a bare dotted identifier needs a Go shape (lowercase package qualifier, or a final segment with an internal capital). Measured residual: 0/612 on the committed bench corpora
- Save-time consolidation opt-out: `ghost_memory_save`'s `pin` maps to `UpsertOptions.Pin` and pins inside `Upsert`'s existing `BEGIN IMMEDIATE` transaction, so a memory can opt out of `ghost reflect` in the call that stores it rather than in a second `ghost_memory_pin` call — nothing an agent writes is excluded by `source`. A fold pins BOTH rows (the copy just stored and the existing row the text merged into, which is the one a later consolidation is most likely to absorb), so the save result says so rather than letting the caller infer the pin from the id it returned; `FoldOnly` stores no row, so the target is the only thing the request can mean. `pinMemoryTx` deliberately leaves `updated_at` alone: the row's age and timestamp are load-bearing for decay and the `--skip-unchanged` fingerprint
- Upsert dedup is one write transaction: `UpsertWithOptions` opens its `BEGIN IMMEDIATE` transaction BEFORE the FTS duplicate probe and commits the writes the probe decides on, because a probe outside it leaves a window another ghost process can use — a save that strengthened the same row in that window had its increment overwritten by arithmetic on a value read before the fact, and a row committed in that window was invisible to the probe, so two saves of one fact became two unlinked rows (both are cross-process; the per-`Store` `s.mu` cannot close either). The strengthen is therefore `SET importance = MIN(1.0, importance + ?)`: the value it adds to is the one the row holds when the statement runs. Never query the pool inside an open transaction on the same handle — `OpenDB` pins one connection, so it deadlocks; go through the `sql.Tx`. `FoldOnly`'s re-verify of its target happens in that same transaction, which makes it a statement about the probed row, not a race guard
- A newer schema is refused before it is written to: `memory.OpenDB` reads `PRAGMA user_version` and rejects a store from a newer Ghost BEFORE `initSQL` runs. `initSQL` is `CREATE … IF NOT EXISTS`, so on a store that merely has more than this build knows it is nearly a no-op — which is what hid the ordering — but an object the newer build renamed, replaced or dropped is recreated there, in a store the same call then declares unreadable. A leg that FAILED suppresses the floor outright (`retrieval_partial`); a result with no arm value at all is `no_floor_arm`; a leg that never ran changes neither — the keyword arm still judges keyword-only results, and the leg's state is on the line (`legs=`, `abstain_cosine=not_applied`), never in the reason. An outage is not evidence about the corpus. An empty result whose rows were FOUND and withheld says "no sufficiently trustworthy memory found" and names the cause; only `no_candidates` claims nothing matched, and only that reason is evidence about the store. A leg that never RAN and a leg that ran and FAILED are different facts with different next steps, and the empty branch keeps them apart the way the non-empty one does: the first is `vector_backend_unavailable` (the keyword leg was all that ran), the second is a tool error rather than a verdict (an incident — retry); `legNeverRan` covers both "no embedder" and "this query would not embed", because the tool swallows the embed error and the leg status cannot tell them apart
- Vector scan: both legs are brute force over the project's embeddings, and they run in two phases (`internal/memory/vector_scan.go`, #556). `snapshotVectors` copies every candidate row out of SQLite and returns, holding the store's read lock and its single connection for the copy only; `vectorRows.search` scores the copy afterwards, so the O(corpus × dims) cosine pass — which `ghost supersede` runs once per memory — no longer blocks writers for the length of the corpus. The copy keeps the stored bytes rather than decoding them and the score loop reads the little-endian float32s back out in place (`cosineFromBytes`, bit-identical to `cosineSimilarity` on a decoded vector), and the scope column is parsed only for a row that wins a slot; a `scopeProbe` decides per-row eligibility by checking whether the stored text can mention a requested key at all, which can only save a `json.Unmarshal` and never decides membership, since `ScopeMatches` only excludes a row that names a requested key and disagrees. Ranking keeps a bounded window instead of the corpus — a min-heap whose root is the worst row held, ordered once at the end over at most `limit` rows — and the order is total (cosine descending, exact ties broken by scan position) so the answer is a function of the stored data AND the order the scan yielded it in, not of the heap's internals; that is not independence from the scan order (the query has no ORDER BY, so a VACUUM or index rebuild can reorder a tie), and it does not claim to be — what it buys is that two searches over the same rows in the same order agree, which the unstable `sort.Slice` it replaced did not promise. `TestSearchVectorRankingMatchesTheCollectAndSortBaseline` pins the whole result against a transcription of the pre-#556 collect-and-sort search, and `TestVectorSearchCopiesTheCorpusUnderTheStoreReadLock` / `TestVectorSearchScoresWithTheStoreLockReleased` pin that the copy takes the read lock and the scoring pass does not. A writer is still kept out during the copy, and that is the connection rather than the mutex: OpenDB pins the pool at one, so no amount of lock work lets a write start while a query is streaming. The scratch is recycled through a `sync.Pool` on the store, and an oversized embedding buffer is dropped on return rather than retained. What a query still allocates is the driver: `modernc.org/sqlite` copies every BLOB and TEXT column into a fresh allocation per row, which is why the remaining cost is a decoded-vector cache keyed on `PRAGMA data_version` (and then an ANN index), not more work on the scoring loop
- Vector-space identity: a stored vector is only scored when `memory_embeddings.model` equals the identity this process embeds into (`Store.SetEmbeddingIdentity`, fed from `embedding.VectorIdentity`). A model, dimension or task-prefix change therefore retires the old vectors instead of comparing them with queries from the new space. The rule is read in four places, one per caller: `loadVectorRows` (may a vector enter a search), `GetEmbedding` returning nil (may a stored vector act as a QUERY vector — the link worker and `ghost supersede` both do), `UnscannedEmbeddedMemoryIDs` (may the linker compare this memory yet), `EmbeddingStats` (is it covered, which `ghost mcp status` and `ghost_health` report). A retired vector never hides its memory: the keyword leg still finds it. Two side effects of a rewrite ride along: `StoreEmbedding` clears the row's `link_scans` slot when the identity changes (so the linker re-scans it in the new space — the re-scan ADDs current-space `related` edges alongside the ones the retired space produced; nothing invalidates those old rows, and `CreateLink`'s `MAX(strength, excluded.strength)` upsert means an edge whose new-space similarity is lower keeps its old strength), and the foreign-vector warning in `loadVectorRows` is emitted once per retired identity (a second reconfiguration in the same process warns again). `EmbeddingStats` reports stale and unembedded rows separately so `ghost mcp status` can show both. The identity is opaque (compared, never parsed) and empty means "no model configured", which keeps the bench harness and tests unfiltered
- Memory history: `memory_history` (schema v17, #578) is the append-only CHANGE LOG of how a memory reached its current state — one row per write. The name `memory_provenance` went to a different and later concept (evidence records, several per memory, answering "who or what supports this memory" — see "Evidence provenance" below), so never rename this table to it, and do not treat the two as the same thing; and every writer appends one row in the SAME transaction as the write — `Create`, `Upsert` (insert and the fold's `merge`), `UpdateMemory`, `ReplaceNonManual` (rewrite, reuse, bulk delete), `SetResolved`/`ClearResolved`/`MarkResolved` (the last recording the OPERATOR as performer, and clearing the row's KEEP cache in the same statement as the stamp — the only `resolve` row that can say a person decided rather than a classifier judged), `CreateLink` for a `supersedes` edge and `InvalidateLink` for its withdrawal (`unsupersede` — a memory can be superseded, withdrawn and superseded again, and only the sequence says which claim is live), `RestoreSnapshot`, `ImportMemory`, `Delete`, `PruneSessionMemories` (a `session` row removed by `ghost prune` — the one writer whose row is gone by design, and the reason the audit has to be a tombstone), the decision companion memory and the shipped seeds. Each row is a VERSION, not a diff: the state the memory held once that write landed, so "what did Ghost know at T" is the newest row at or before T (#647) and the prior content is the previous row. `agent`/`session_id` are the PERFORMER (the save/merge/import paths carry a Provenance; the lifecycle passes do not, and an empty field is an admission, not a claim) — which is what makes the issue's "a row changed by two different agents" answerable. `memory_id` deliberately has NO foreign key so a hard delete leaves a tombstone carrying the text the row held; `project_id` does cascade. Growth is bounded in the appending transaction: newest 50 versions per memory, newest 20 000 rows per store (rowid window, since an implicit rowid is max(rowid)+1 and never reused). A write that changes none of a memory's own recorded columns appends nothing (`Touch`, `TogglePin`, the KEEP cache), and a write that moves a memory BETWEEN projects must also move its history rows' project_id or the project-delete cascade takes the past of a memory that survived: `MergeProject` and `PromoteToGlobal` both do (the merge list exists twice on main). A verbatim consolidation re-emission is a NO-OP and appends nothing (#727: it measured at 80% of `memory_history` on a real store, and the per-memory cap was days from evicting real events) — when content, category, importance, tags and scope are all unchanged it writes no row and leaves `updated_at` alone, because `ghost supersede` orients each candidate pair by `updated_at` and `--skip-unchanged`'s fingerprint carries it as a change proxy; a change to any of those five IS a real update and is recorded (`reuseChangesNothing` compares them by value, and an unreadable stored value counts as changed). TWO writers deliberately repeat the state instead, and neither is a licence to repeat: `ghost prune` appends one per removal and changes no other shape (the backup manifest counts the CORPUS, never the change log, so a tombstone cannot make a post-prune backup fail to verify), and a `supersedes` edge appends a `supersede` row when it BECOMES active, recording a claim about the target's standing rather than a state change. Both spend a slot under the cap, which is what bounds them. Two columns carry the event's other end: `related_id` (the id that replaced a deleted row, or the memory whose edge claims it) and `merged_content` (the text a FoldOnly fold dropped, which no row keeps). `ghost history purge <id>` and `ghost_memory_delete`'s `purge_history` delete a row AND its history in one transaction — the redaction path, because a plain delete keeps the text a memory used to hold — and `ghost_history_content` is the SQL seam where #656's `secret.Detect` will redact content on the way in. A purge reaches a memory that is ALREADY deleted through `Store.PurgeMemoryHistory` (history only, never the row), because the tombstone is the feature and a delete-time purge cannot cover it; the same operation is what frees an id for `ghost import`, which REFUSES an id that still has history rather than splicing two memories' records under it (ids are not reused by Ghost, but a portable artifact carries them verbatim). `migrateV17` backfills nothing, so a pre-v17 memory's first edit files a `baseline` row before it overwrites the text. Read it with `Store.MemoryHistory` (oldest first, rowid order) or `ghost history <memory-id>` `as_of` (RFC 3339) on `ghost_memory_search` / `ghost_project_context` and `--as-of` on `ghost context` is the OTHER reader, and it is the reason the rows are versions rather than diffs: `Store.MemoriesAsOf` takes each memory's newest row at or before T, drops the ones whose newest row is a `delete` tombstone or whose first row is after T, and returns the version's own `content`/`category`/`importance`/`resolved_at`/`source`/`project_id` — one statement, driven by `memory_history` rather than by `memories` (a deleted memory's tombstone is the only surviving record of it, so a read that started from the live tables would report "Ghost never knew this" for a memory it held for months), ranked `ROW_NUMBER() OVER (PARTITION BY memory_id ORDER BY recorded_at DESC, rowid DESC)` with `rowid` as the second key because `recorded_at` is second-precision. A pre-v17 memory with no row at or before T is UNKNOWN, never guessed: it is left out of the set and counted in `AsOfSet.Unknown`, because a shorter set that says nothing about the gap reads as the whole truth — and that "no row at or before T" is TWO time-bounded tests, not one, because an unbounded `NOT EXISTS` asks "does this memory have history at all" and a pre-v17 memory the lifecycle touched after the upgrade does (only `UpdateMemory` files a baseline; every other first write appends a row read out of the memories row in the same transaction, so its text is recorded anyway, and that is why no writer needs a baseline there). The gap half also reaches the TOMBSTONES, because a pre-v17 memory deleted after T has no live row either and its gap is otherwise invisible — and that half must do TWO things, or a memory is counted twice: exclude ids that are LIVE again (because `RestoreSnapshot` reinstates a row under the id it recorded, so "tombstoned" does not imply "not live"), AND rank per memory keeping its newest tombstone (a delete → restore → delete memory holds two delete rows, and `UNION ALL` does not dedup). `CreatedAt` — the field the decay measures an age from — is the row's own when that column can answer and the version's `recorded_at` when it cannot: the row is gone (every column NULL, and an empty `created_at` reads as ~56,000 days, so a memory deleted yesterday sat at the decay floor in every listing covering the past year), or the column is LATER than T (no writer produces that, and it is refused because `ageDays` clamps a negative age at 0, making a future-dated column the most favourable value a row could carry into a ranking of the past). Everything else in `AsOfRow` is the current row, including the validity triple: `valid_from`/`valid_until` in particular are the present's until #575's writers land, as are tags, scope, pin, access count and provenance, which were never versioned — `Retention` is the ONE exception and is always empty, because it postdates the change log and a version has no tier to carry (see "Retention tiers"); the statement does not even name the column, since `ghost context --as-of` opens the store read-only and cannot migrate a store that predates it. A promotion REWRITES the history rows' `project_id` (it has to, or the project-delete cascade takes a memory's past with it), so a pre-promotion instant reports a promoted memory under `_global`; that imprecision is pinned by a test rather than worked around. Nothing in the as_of path reads `memory_provenance` (v18, the EVIDENCE table): an evidence record is one OBSERVATION of a memory, not a version of it, so nothing there can be placed at an instant — a count taken now would be a present-day claim about a past memory. The counts therefore stay zero, and since a zero renders as "no recorded evidence", the as_of DISCLOSURE says they were not read rather than leaving that phrase to stand as a claim. Every statement in the read names `memory_history` or `memories` and nothing else, so a pre-v18 store answers an as_of read in full (`TestCandidatesAsOfDoesNotDependOnMemoryProvenance` drops the table and reads on). In the assembler `as_of` is a BINDING, not a filter: `Run` moves `Now` to it, so age, validity and the trace are all decided against T, and the store treats `AsOf` as authoritative over `Now` for the same reason. The retrieval is keyword-ONLY and says so in the answer, the trace and the leg status: `memories_fts` and every embedding describe CURRENT content, so an as_of search matches the query's terms against the versions' own text (through the same `ftsQueryTerms` extraction the FTS leg uses, phrase- and prefix-aware), ranks by matched terms then the same decay composite at T — not bm25, so not comparable with a current order — reports the vector leg as `not applicable` and REFUSES `vector_only` rather than downgrading it, and does not read `memory_links` at all (it records when an edge was invalidated, never the graph at T) so the supersede demotion comes from the recorded `supersede`/`unsupersede` sequence and the edge status is a fifth value, `not_applicable`, because "no edge joins two of these candidates" is a claim a retrieval that read no graph must not render. Those disclosures are `Result.Qualifiers`, not `Result.Notes`: a note list is bounded from the end and shown for the empty answer, where a qualifier is the first thing to go, and a block that is silently a past reading is read as a present one. `ghost context --as-of` runs NONE of that path's startup side effects (the Obsidian mirror, the session-count bump) — they exist because the command backs a session start, and counting a replay would move the present's session number to answer a question about the past. Restoring the store to a past state is not this; that is export/import (#586)
- Evidence provenance: `memory_provenance` (schema v18, #673) is the EVIDENCE table — SEVERAL rows per memory, one per observation, answering "who or what supports this memory", which the change log above cannot: a fact claude-code reported in one session, codex in another, and a human verified is three rows here and one row of mutable columns on `memories`, which can only remember the last. Three concepts stay distinct and are not interchangeable: SOURCE is how Ghost received a memory (`memories.source`: mcp, reflection, import, manual), AGENT is which agent produced or observed it (`agent`), PROVENANCE is the evidence records themselves. `memory_id` CASCADES (unlike the change log's deliberately FK-free `memory_id`) because "3 observations support this" is a claim about a memory, and once the memory is gone the claim is about nothing; a purge deletes these rows explicitly as well, because `PurgeMemoryHistory` leaves the memory in place and no cascade fires for a row that stays — and it deletes the `memory_snapshot_evidence` rows too, since a snapshot is the rollback point for a whole PROJECT, so its evidence would otherwise outlive the purge by however many reflects prune that snapshot Every value except `kind` is NULL when the host did not report it — a guessed agent or session is a provenance claim nobody made, and `observed_at` is NULL for the migration's seed because the seed can say what the columns hold now and not when the fact was first seen. Writers, each in the SAME transaction as the write, each ONE statement: `Create` and `Upsert`'s insert append `observed`; a near-duplicate FOLD appends the second report to the SURVIVING memory (the point of the issue — the folding agent used to be discarded with the incoming wording, and `FoldOnly` stores no row of its own so without this the report would leave no trace); `RecordDecision` appends `observed` for its companion memory (an ordinary memory search returns and a later save folds against), empty of provenance because the decision tool reports none; `ReplaceNonManual`'s FRESH INSERT carries its sources' records onto the new id with `carried_from` naming each source — a rewrite or a merge mints an id whose evidence the cascade would otherwise have just deleted, which would make every consolidated memory read "no recorded evidence" forever, so the emissions loop runs BEFORE the delete and a test fails if the two swap; the REUSE branch appends nothing because the row never changed identity; `ImportMemory` appends `imported` plus whatever records the artifact carried (and NOT `carried_from`, which names a memory this store has never heard of); `RestoreSnapshot` restores a re-created row's records from `memory_snapshot_evidence` (a table, because a memory has several records, pruned with the snapshots) and touches NOTHING for a row it updates in place — the snapshot holds an older copy of that row's evidence, and restoring it would drop every corroboration recorded since. `AppendVerifiedEvidenceTx` is the exported seam the validity writers (#677) own the reserved `verified` kind through, and they now CALL it. State the contract as an OUTCOME, because the mechanisms differ on purpose and a reader filtering by `kind` sees three shapes for one rule: every writer that stores a `verified_at` leaves a record carrying a verification stamp in the same transaction, and `EvidenceCounts.Verified` counts any record carrying one whatever its kind. The live callers are `insertMemory` (behind `Create`) and all three of `UpsertWithOptions`' branches plus `UpdateMemoryWithOptions`; each goes through `appendVerificationIfStatedTx`, which gates on the caller stating a verification IN THIS CALL and never on the column, because a partial update COALESCEs a `verified_at` an earlier save wrote and appending for that would record a check nobody made. Their stamp is the STORE's clock, not the caller's (a verifier must not be able to date its own check), so the column carries what was claimed and the record carries when Ghost heard; the two are different facts and both are kept. `UpdateMemoryWithOptions` appends the `verified` leg but NOT an `observed` one — an edit is a change to a fact already reported, not a new report of it, and widening #673's design from inside #575 would inflate the report count on every content edit. THREE more writers store a `verified_at` and are deliberately not callers, each for its own reason. `ImportMemory` is IN the set and not among the callers: the artifact carries an OBSERVATION, so a check happened and is attested, and it rides the import's own `imported` record instead of adding a `verified` one — same store-clock stamp, same count, no second statement. That arrival stamp is CONDITIONAL, and the condition is the round trip: it is skipped whenever ANY carried record already holds a stamp, kind-agnostically, because a record with a stamp says the check happened and stamping again would make a corpus that crosses a machine boundary N times report N+1 verifications of one check. Kind-agnostic rather than `verified`-only because the second hop's artifact carries the FIRST hop's `imported` arrival, and that is the only stamped record it may hold — a kind-specific guard re-inflates on every hop after the first. The condition is a NON-EMPTY value, since a hand-edited artifact can carry `"verified_at": ""` and every reader treats that as no claim. `CreateFromCorpus` leaves NO record carrying a stamp — but it still records, because `insertMemory` appends the ingestion's `observed` row on that route unconditionally, and "no verified record" is the whole of it; a third-party dataset's `verified_at` is a value in a column with no observation behind it, so there is no event and the only stamp a record could carry would manufacture one. It opts out through `insertOptions.recordVerification` because it shares `insertMemory` with `Create`, which is why it needed a PARAMETER and not a comment — and the column keeps the dataset's value either way, since losing the dataset's own data would be the opposite defect. `RestoreSnapshot` writes it in pure SQL from the snapshot table, and a restore is a faithful copy of a corpus whose evidence rows travel with it, so appending per restored row would double-count every check the snapshot holds. That enumeration has been wrong three times — `CreateFromCorpus`, then `ImportMemory`, then by over-claiming what its own enforcement could see — every time because prose is not checkable, so it is ALSO two tests that answer different questions. `TestEveryVerifiedAtWriterIsEnumerated` asserts the OUTCOME each writer leaves: whether a record carries a stamp, and of what kind. `TestEveryVerifiedAtMentionIsClassified` walks `internal/memory` with `go/parser` and requires every function naming `verified_at` IN ITS OWN BODY to be in one of FOUR classifications (writes a memory row, touches a snapshot or evidence side, is a migration or reader, or genuinely SPANS two of those surfaces — `ReplaceNonManual` does, since its fresh-insert path now writes the memory row's validity and provenance as well as the snapshot tables), so a new one cannot be added without being placed; it found four mentions a hand-written list had missed on its first run, all scanners, and caught two of this PR's own new functions when they landed. The limit of that one is part of the claim: it does not resolve the column out of a package-level literal, so `migrateV10` — the migration that ADDS the column, naming it only through `phase1aProvenanceColumns` — is invisible to it, and `TestColumnListWritersAreClassified` closes that one indirection by requiring every function iterating that list to be classified. `AppendVerifiedEvidenceTx` is placed explicitly too, since the writers reach the column THROUGH it and its own body names no column. A function reaching the column by some other indirection is still invisible, and that is the honest edge of the guarantee. There is no growth prune, deliberately: it would be a second statement inside the write transaction, which is what took `TestMultiProcessSharedDatabase` to SQLITE_BUSY for the change log's prune, and the cascade keeps deleted memories from contributing. `migrateV18` REFUSES a database whose `memory_provenance` is not the EVIDENCE table (a pre-rename #664 dev build used the reserved name for the change log) rather than converting or dropping it, naming `sqlite3 <db> 'DROP TABLE memory_provenance'`, and `OpenDB` runs the same check BEFORE the pre-migration backup so a refusal costs no copy and its same-second retry reports the real error — the check tests for `id`/`memory_id`/`kind` ONLY, so it is an identity test and not a version test: a future column here must not make it refuse a legitimate store with a remedy that DROPs its evidence — initSQL's CREATE INDEX cannot catch that one, because the change log has a `memory_id` too, and a warning nobody sees leaves every writer failing on the same missing column. Otherwise it seeds one `legacy` row per memory that recorded at least one of agent/session_id/source_ref/confidence, and NONE for a memory that recorded nothing — an evidence row with nothing in it still says "this was observed", and a row per memory would make every store report one observation, the same fabrication as inventing a session id. Read it with `Store.MemoryProvenance` (oldest first, rowid) and `Store.MemoryEvidenceCounts`, whose `Label()` renders "supported by 2 observations, 1 verified"; the assembler records the counts in stage 4's trace (`Signals.Evidence`, carried on `memory.Candidate` because that is the only read the assembler has) and NOTHING RANKS ON THEM — the stage's multiplier stays 1.0 until a measured change justifies one. The portable artifact (v2) carries the records, nested under the memory they support because a bare evidence line cannot be attributed; the Obsidian mirror does not — it is a human-readable mirror, not a transfer format
- Memory links: `memory_links` edge table auto-populated by cosine similarity (internal/linking worker); links cascade-delete with memories and self-heal after reflection. A graph-expansion ranking bonus was evaluated and removed — dominated by a deeper vector-k (links and the vector leg are both cosine); the link graph is retained for Obsidian export and supersedes ranking (see `docs/superpowers/specs/2026-07-20-graph-expansion-stays-off-design.md`). No edge may join a scope-conflicting pair: every writer refuses one (`Upsert`'s dedup probes, the linker's `related` edge, `ghost supersede`'s candidates) and every reader ignores one already stored — the two ranking guards (`DemotionPenalties`, `SupersedePenalties`), `Store.SupersedesWithin`, `ghost resolve`'s supersedes piggyback and the repair pass's matching floor (`scopeCompatibleSupersedes`, which needed `GetByIDs` on `resolveStore`/`reassessStore`/`resolveCapableStore` for the link endpoints' scopes), and the two fold-target liveness checks (`foldTargetStillLive` + the cross-category probe). - Resolution classifier: `ghost resolve` runs a keyword prefilter, then a deterministic KEEP veto, then batches up to 8 notes per KEEP-biased CLI-harness classify call (`claude`/`opencode`/`codex`/`goose` subprocess, numbered `N: RESOLVED | closed-by: <fact>|KEEP` reply judged by a strict first-field line parser) to mark `resolved_at`, dropping resolved-evidence memories (changelogs, cost estimates, closed experiment notes) from ranked injection while keeping them searchable. KEEP-biased in code, not prose (#640: an independent judge found ~1 resolve in 3 on a real DB had buried durable knowledge): `resolve.VetoKeep` settles a candidate KEEP with no harness call when its text carries an imperative (`never|do not|don't|must|always|required`) or an open marker (`not yet|outstanding|still pending|still open|still stale|unresolved|todo`), all case-insensitive and word-bounded; the rubric asks the fresh-session question (would an agent starting fresh make a mistake, repeat work, or break a rule without this?) and says dates, PR numbers, commit hashes and "fixed in" do not resolve a note; a RESOLVED must carry a non-empty `closed-by:` or the parser reads it as KEEP. The veto guards the classifier only — the supersedes-edge piggyback and correction pairing still demote. Only explicit KEEP verdicts are cached by content hash in `memories.resolve_kept_hash` (schema v7; the v3 hash prefix invalidates the v1 implicit-KEEP and v2 explicit-KEEP caches, so #640's re-judged rules are re-asked); UNKNOWN parse failures remain uncached and are retried, so a converged project makes no calls only after explicit KEEPs. Dry-run writes nothing, `--apply` writes resolved_at and explicit KEEP cache entries; transport or verdict-count failures fail fatally rather than applying incomplete results, while UNKNOWN lines remain eligible for a later pass. `ghost resolve <project> --reassess` is the repair path for the resolutions the pass already got wrong: it re-runs the vetoes and the classifier (no keyword prefilter) over memories that are ALREADY resolved, prints the ones that now come back KEEP, and with `--apply` clears their `resolved_at` via `memory.ClearResolved` and caches the classifier's KEEP verdicts; SCOPE THAT REPAIR with `--only <id>[,<id>...]` (full ids or 8+ character hex prefixes) or `--only-file <path>` (one per line, `#` comments allowed; both may be given, the list is the union) — both are refused without `--reassess`, because the ordinary pass has no resolved pool to narrow, and a scoped report says how much of the project it read ("3 of 143 already resolved judged") instead of describing a pool it never looked at. Scoping narrows WHICH rows are judged and nothing else: every floor below still holds a judged row back. A selector that names nothing (mistyped, another project, or already cleared by an earlier repair) is reported and skipped, never an error for the run; an ambiguous prefix IS an error, because nothing can be said about which rows were meant. #698 measured why: an unscoped repair over a real store proposed un-hiding 143 memories and an independent judge sampling 40 found ~35% stale (completed changelogs, PR/host snapshots, notes a newer memory had superseded, a retired code path). `ghost supersede --reassess --apply` therefore prints its own follow-up — the exact `ghost resolve <project> --reassess --only <ids> --apply` over the withdrawn edges' targets — and writes the same id list under the data dir's scratch (`scratch.Root()`, `supersede-reassess-<project>-<ts>.ids`) for `--only-file`; a dry run prints neither, because it withdrew nothing and resolve would refuse the command while the edges are live. The repair path is also the only place `VetoKeep` does not settle KEEP by itself: when the same project holds a NEWER unresolved memory sharing >=2 of the note's key identifiers — a backticked span, an `#NNN` reference, a file name, a host name (`resolve.keyIdentifiers`, `subjectIndex.shadowing`; NOT a bare number or a version, which are what changes when a note goes stale) — the note goes to the classifier instead, because a veto protects a phrase and not a claim. The pool is `ResolveCandidates` for the correction floor's reason: a memory that is itself resolved is a row the next ordinary pass will not see. `Run`'s veto is unchanged, and the asymmetry is why: there a false veto keeps a note OUT of the resolution (one noisy memory, a later pass can still bury it), here it un-hides one permanently; a failed clear is fatal, a failed cache write only warns; `memory.ClearResolved` runs every batch in one transaction so "a failed clear repaired nothing" is literally true. It honours Run's two free demotions as a floor — a row a live `supersedes` edge still asserts, or an older row a NEWER *unresolved* correction pairs with (the same pool Run searches, via `correctionPairTargetsFrom`), is counted as `Demoted` and left resolved, because Run fires both before the veto and the KEEP cache, so clearing it would report a repair the next pass undoes. The pairing is re-checked after the re-KEEP set is known (`holdBack`), because a correction that is itself repaired leaves the resolved pool and would re-assert its pairing; both the floor and the hold-back pair only Run's keyword-prefiltered subset, since a keyword-free row is never a pairing target and holding it would be a permanent, mislabelled hold no later pass could undo. THE RE-CHECK READS THE POOL THE NEXT ORDINARY PASS WILL READ — the unresolved pool PLUS the rows this run clears — and uses it for BOTH the frequency count and the correction search, the two jobs `Run` gives its own `ResolveCandidates` pool (#712). Counted over the live pool alone, a row this run clears is missing from the count, so its subject tokens look rarer than the next pass will find them and a pairing the next pass will NOT make holds a row back for a second, identical pass to release. So the re-check ITERATES, bounded at `maxHoldBackRounds` (8): holding a row takes it back out of that pool, which lowers the frequency of the tokens it carries, which can turn a token rare that was not and reveal a pairing the previous round was blind to. WHAT TERMINATES THE LOOP IS NOT THE PAIRINGS, and the difference matters: a held-back row leaves the pool the re-check reads, and that pool is BOTH the frequency pool and the correction pool, so dropping a row does two OPPOSITE things — it lowers the document frequency of the tokens the row carries, which can reveal a pairing the round before was blind to, AND, when the row is correction-marked, it removes every pairing that row was asserting. A later round can therefore report FEWER pairings than the round before it (`TestHoldBackPairingsAreNotMonotoneAcrossRounds` is the case that does), and the ONLY termination invariant is that every round which finds anything removes at least one row from the repair set, which bounds the loop by `len(repair)` however the pairings move. So `maxHoldBackRounds` caps the WORK ONE RUN DOES, not safety: with it and without it the re-check ends, and what changes is whether one run reaches its fixed point or leaves work for the next. Dropping is ONE-WAY — a row held is never re-added, and a held-back correction therefore cannot free its row again — precisely because the pairings can retreat, and without that rule the answer would depend on how they moved between rounds and the LAST round would win rather than the union. A bound reached WITH a row still changing is a finding and not a truncation: `ReassessResult.Rounds`/`BoundHit` carry it and `reassessRoundsLine` prints its own sentence (“a further pass may clear more”), because a run that iterated is reporting an answer no single re-check would have given. Printed ONLY when there is something to say — more than one round, or the bound reached — since a line an operator learns to skip is a line that stops being read when it matters. No round re-asks the harness: the iteration is over the hold-back decision alone, on verdicts the run already holds, because a re-ask is billed work for an answer in hand. THE FLOOR DELIBERATELY STAYS THE CONSERVATIVE ONE, drawing its corrections only from the live pool, so it may over-hold a row the re-check releases — the right way round, because an over-held row is left resolved and REPORTED with a reason an operator can check, while an under-held one is cleared and immediately re-stamped by the pass that follows. EVERY HELD ROW IS NAMED, not counted: `ReassessResult.Held` (one entry per row, in pool order) is printed by `reassessHeldLines` as `held by supersedes <source-id>` or `held by correction <id>`, because the two reasons need different remedies — a live edge is undone by `ghost supersede --withdraw`, a correction pairing is undone by nothing and can only be READ — and `Demoted` is `len(Held)`, so the summary count and the list under it cannot disagree. EVERY HOLDER IS NAMED, never just one: a note two newer notes both supersede is held by both and withdrawing one of the two releases nothing, so naming one would send the operator to undo an edge whose undo changes nothing; `HeldMemory.Reason` sorts on a copy (supersedes first, then corrections, each by id) so two runs are comparable. A pairing therefore carries its correction now — `correctionPairingsFrom` returns one entry per (correction, target) pair and `correctionPairTargetsFrom` deduplicates the targets on top of it — so there is still ONE implementation of the rare-token rule and `Run`'s demoted-row order is byte-for-byte what it was. Those ids print WHOLE, unlike every other id on a Ghost report, because here they are OPERANDS rather than references: the source is what `--withdraw` takes, the held row's own id is what a scoped repair names, the correction's id is a note somebody has to go and read, and an eight-character abbreviation of any of them turns a repair already in hand into a second lookup. `Held` and `Rounds` are properties of the DECISION and not of what was written, so a dry run reports the same fixed point `--apply` reaches and writes nothing: a preview reporting a smaller repair than the run would reach is a preview an operator cannot plan from. A reasonless `closed-by` is not a reason: a bare mention of the key without its colon ("no closed-by available") and a placeholder value (`none`, `n/a`, `tbd`, …) are both KEEP — and so is a value whose FIRST WORD declines to name one ("not applicable", "no decision", "cannot name it", "unclear"), because a refusal is a phrase far more often than it is one of the nine placeholder keywords. That grammar is `resolve.ReasonedField`/`resolve.ReasonlessValue` and it is NOT resolve's alone: internal/supersede's `replaced:` field is the same contract for a supersedes verdict (#686), so one list decides both and a value that keeps a note here cannot bury it there. `VetoKeep` is likewise split — `VetoKeepImperative` is the imperative half, exported because internal/supersede's `VetoSupersede` reads the same words for the opposite decision (a rule is not a fact that goes out of date), while the open markers stay resolve's. The repair pass treats a live 'supersedes' edge as a floor, which is why `ghost supersede <project> --reassess --apply` has to run FIRST: withdrawing the edge is what makes the `resolved_at` it justified clearable, `TestReassessResolvesAChainIntoResolveReassess` runs that chain against a real store, and the e2e suite runs it against the built binary end to end (`TestCLISupersedeReassessFeedsResolveReassess` — write the edge, resolve stamps the target, withdraw it, then the printed `--only-file` clears that one memory and leaves another resolved memory in the same project resolved). That floor is counted per EDGE, not per note: a note two newer notes both supersede is held by either one, so withdrawing one of the two does NOT release it (`Demoted`, nothing cleared, no harness call) and only the last withdrawal does. A withdrawal wider than the edge it names would otherwise hand the note back to injection, where the very next ordinary pass re-stamps it from the surviving edge and no edge ever changes again (`TestReassessHoldsTheNoteWhileAnySupersedesEdgeSurvives`). `resolve.Mark` (`mark.go`) is the OTHER repair, and the only one that goes the other way from a caller's judgement: `ghost resolve <project> --mark <ids>|--mark-file <path> [--apply]` stamps `resolved_at` on the memories a caller NAMES, dry-run by default. It exists because NO pass reaches the case it serves — the ordinary pass only proposes a memory carrying a resolution keyword, and even where it does, a KEEP-biased classifier asked about THAT NOTE is not asked whether another memory in the project supersedes it, so a note a newer note says was fixed is routinely invisible to every pass (`--reassess` cannot help either: it judges what is ALREADY resolved, and this row is not). Like `supersede.Withdraw` it judges NOTHING, so no harness is involved and nothing is billed, and a machine that cannot spawn one can still repair its corpus. The refs are internal/memref's, not a second copy, so a ref means here exactly what it means to `--withdraw`. A request is settled before anything is written and a refusal writes NOTHING, not even the refs that were fine (`TestMarkRefusesAnAmbiguousPrefix` marks neither of two refs when one is ambiguous), and the per-row outcomes are three SEPARATE states rather than one "not marked" — `AlreadyResolved` (the issue's no-op: a memory the previous pass already buried, on which nothing is written including NO history row, because a history row records a write), `Pinned` and `ExemptCategory` (the store's guard, whose refusals have different remedies) — each counted on `MarkResult` off the same rows the report prints, so a count and a list cannot disagree. Only rows IN THE PROJECT may be marked, and that is checked on the READ that can see `project_id`, before any write, because `MemoryIDsByIDPrefix` reaches `_global` for the supersede endpoints' sake and a row every project shares is not one a project asked to bury; the store binds the project AGAIN in the same statement as the stamp, so a caller reaching the store directly cannot cross it either, AND refuses the `_global` SENTINEL beside the empty-project refusal — the binding does not catch it (a promoted row's own project_id IS `_global`, so naming `_global` satisfies every predicate MarkResolved has), and it is refused at the STORE layer rather than re-derived per caller, like every other `_global` refusal here. The report's per-row marker defaults to the NEGATIVE claim under `--apply`, never the success, because the eligibility guard is re-checked WHERE THE WRITE HAPPENS and a row pinned or recategorized between the read and the write is declined SILENTLY (another process's decision, not a failure) — a state the result says nothing about, so a default of `marked` would report a change that did not happen. `MarkedMemory.Declined` names it, `MarkResult.Declined` counts it, and both the CLI report and the MCP result fall through to `not marked` for any state they do not recognise, so a state added tomorrow reads as unwritten rather than written.  `Store.MarkResolved` is a separate method rather than a `SetResolved` wrapper for two reasons: it BINDS the project (the pass's ids are already project-scoped by the selection it made), and it RECORDS the performer, so the `resolve` history row it writes is the only resolve row that can say a PERSON decided rather than a classifier judged — which is the whole reason this is a command and not SQL, since the SQL route bypasses `memory_history` entirely and leaves the record showing a memory resolved with nothing saying who said so. It also drops `resolve_kept_hash` in the SAME statement as the stamp, or a later pass would skip the row as `N KEEP cached` and a memory buried on purpose would return the moment anything rewrote its text (#714's second effect). Unlike `supersede.Withdraw` there is NO partial outcome to report: the stamp, the cache clear and the history row are ONE transaction (`TestMarkHistoryAndStampLandInOneTransaction` drops `memory_history` and requires that `resolved_at` not survive), so an error returns NO ids — returning the ones it had collected would claim a stamp the rollback undid. Its inverse is `--reassess --only`, and every applied run prints that command through internal/followup, scoped to the ids it stamped and never to the project. The MCP `ghost_resolve_mark` calls the same core through a `markCapableStore` separate from `resolveCapableStore` — that one must never be able to reach the other direction — and its result names the inverse as a CLI COMMAND, because there is no MCP surface for CLEARING a resolved_at (`ghost_resolve` is the forward pass) and an agent with no shell should be told so rather than pointed at the tool that would bury more memories. Never invoked from the stop hook's synchronous path (that path forbids DB access); the stop hook's detached `ghost lifecycle` spawn (whose resolve phase runs `--apply`, never `--reassess`) and the standalone batch command are the only callers. See `docs/superpowers/specs/2026-07-26-resolution-classifier-design.md`.
- Classifier backend: `resolve`/`supersede` classify via the calling session's own CLI harness — the backend is picked from the MCP client's reported identity (an opencode session uses the opencode binary, claude uses claude, etc.) via `ai.SourceProvider`, or — on the headless CLI path — from `--source`, else `ai.DetectSource()` (env markers plus process ancestors); if no calling harness can be determined it fails fast with an actionable error. There is no claude-first cascade: `NewSourceProviderForSource("")` is unavailable, and `ai.CLIProvider` is an availability probe only. MCP sampling was retired from this path per SEP-2577 — see `docs/superpowers/specs/2026-08-24-resolve-sampling-path-design.md`.
- Lifecycle spawn guards: the stop hook spawns the reflect→resolve→supersede chain behind TWO independent per-project guards. `AcquireLifecycleLock`'s PID file says "a run is not already in progress"; `lifecycle.min_interval` (default 30m, `0` to disable) says "a run did not start too recently". The second is the mtime of `lifecycle-<project>.last` in the data dir — a file, not a row, because the stop hook's synchronous path forbids DB access. Only the `ghost lifecycle` process writes it (`mcpinit.TouchLifecycleStart`), and only once it has passed every precondition that can exit non-zero, so a run that dies before doing any work does not burn a window. Most unknowns read as "run" (no stamp, unreadable, non-regular) so that a bookkeeping problem cannot silently stop maintenance; a stamp dated in the FUTURE is the deliberate exception and reads as INSIDE the window, because a future date is not evidence the window expired. `config.LifecycleConfig.MinIntervalDuration` resolves an unreadable value to the default rather than `0`, because `0` means the cooldown is off.
## Key pattern: no harness child gets a tool

A harness child is given a **minimal environment AND no tool surface**, because
its prompt is memory text and memory text routinely carries third-party content.
The environment half is `harnessEnv`'s explicit allowlist; this is the tool half.
The rule is per-harness because the mechanism is, and the mechanism is whatever
that harness's own CLI documents — never a guessed flag.

**Every harness argv is a WHOLE-SLICE GOLDEN**, not a per-flag grep. A grep passes
when the flags it checks are present and says nothing about a flag that was never
added, which is exactly how goose shipped with an entire tool surface unchecked.
Each argv is built by a named function (`claudeInvocationArgs`,
`codexInvocationArgs`, `gooseInvocationArgs`, `openCodeInvocationArgs`,
`openCodePolicyFor`) so the whole slice is assertable;
`TestHarnessInvocationArgsAreGoldens` covers all four harnesses including both
opencode major versions, because V1 is the only shape that takes `--pure` and the
only one eligible for the deny policy.

A golden cannot check a flag against its upstream, so the shell-fake
harness-policy tests re-check what actually reaches the child, and two of them
cannot be checked by a fake at all. A fake that reads `$GOOSE_MODE` out of its own
environment proves only that Ghost WRITES the string — not that the harness accepts
the value, ranks it above its own config file, or acts on it. So the two upstream
facts this policy rests on have `GHOST_LIVE_TESTS=1`-gated tests that run the real
binary, pick a command that makes no LLM call, and report rather than assert where
the honest answer is "cannot settle".

**claude** is the only harness whose CLI can remove tools outright.
`claudeInvocationArgs` requires five capabilities probed from the INSTALLED
binary's own `--help` (`--tools`, `--disallowedTools`, `--safe-mode`,
`--restricted`, `--strict-mcp-config`) and REFUSES to run without them — a claude
that lacks one gets an error naming the upgrade, never a silently weaker policy.
`--tools ""` is the restriction (claude's own "disable all tools" spelling, which
unlike a list of names covers a tool shipped later). The child test walks its own
argv to assert the value is EMPTY, because `"$*"` renders a missing value and an
empty one identically — and a tool name there is both a grep hit and an open tool.

**codex has NO "no tools" flag.** `--sandbox read-only` bounds what a tool may do,
not which tools exist, so the policy is a list. Both exec tools are named
(`features.shell_tool` AND `features.unified_exec`) because codex registers either
the unified PTY-backed tool or the one-shot exec, and disabling one leaves the
other. `view_image` is named because it is a plain local file read the sandbox's
write policy does not cover. The plugin and connector group (`apps`, `plugins`,
`tool_suggest`, `skill_mcp_dependency_install`) goes together because each
contributes a tool of its own and installing an MCP server on demand RUNS A
COMMAND. `agents.enabled` and the top-level `web_search="disabled"` are not
feature keys, so `features list` says nothing about them and they are never
filtered.

**The codex list is filtered against the installed binary and NEVER refuses.**
`codexFeaturesFor` probes with `codex features list`, keyed on path/size/mtime by
a `sync.Map` exactly as claude's capability probe is, and caches the result. The
negative verdict is cached too, for `codexFeatureRetry` (5 minutes), and that
asymmetry is the point rather than an oversight: an unanswering codex is the
OLD-codex install this design exists to support, so probing it per call would add
a process to each of a lifecycle's hundreds of calls — the doubling the cache
exists to prevent, for the whole run. Caching the negative for the life of the
process is the opposite failure, because a codex upgraded in place under a
long-lived MCP server would never be noticed. A positive answer does not expire at
all.

**Both capability probes are SINGLE-FLIGHTED on a cold cache.** `codexFeaturesFor`
and `claudeCapabilitiesFor` each pair their per-identity `sync.Map` with a
`singleflight.Group` keyed on the SAME identity (`codexBinaryID`/`claudeBinaryID`
`probeKey`, built from the same three fields the cache key compares), so N
concurrent first-callers run ONE child process and all receive that probe's answer.
The cache alone cannot do this — it is check-then-probe, so every caller arriving
before the first one stores ran its own (measured: 50 spawns for 50 callers). A
`singleflight.Group` rather than a per-key mutex map because the two differ on the
FAILURE path, which is the whole difference: a mutex map serializes the burst, and
since a failed claude probe is deliberately NOT cached, each follower would take
the lock, find the cache still empty, and probe again — N processes, the bug rather
than a fix for it. The group shares the concurrent call's outcome whether it
succeeded or not, and retains NOTHING of its own, so the caches above keep owning
retention exactly as documented: a positive is kept for the life of the process, a
negative expires at `codexFeatureRetry`, a failure is never stored, and the
warn-once latches are untouched. The freshness test for codex therefore lives in
`codexCachedSupport` rather than at the lookup, because it is now read from two
places and a check-then-probe pair with that test in only one of them is how a
long-lived parent stops noticing a codex upgraded in place. The mutex-map argument
is CLAUDE'S, and codex is the case that would survive without the group:
the flight caches a verdict the probe could not REACH, so a per-key lock would
leave each follower a fresh negative to return. (A verdict reached under a DEAD
context is the one that is not cached — a cancellation, not an answer — which does
not change this.) Both use the same mechanism, chosen once, rather than a claim each
probe needs a guarantee it lacks.

**A caller's own context still governs its own call.** `Do` blocks on the leader's
flight and never consults the follower, so both probes use `DoChan` and `select` on
`ctx.Done()`: a caller whose context is dead reports its own error instead of waiting
out a verdict it cannot use — and on claude that error REFUSES the whole harness
call. The other half is that a leader whose context dies must not fail the followers
whose contexts are fine, or hand them its negative: in the long-lived `ghost mcp`
server one disconnected client would fail every concurrent turn in the burst. The
follower cannot tell those cases apart, because `exec.CommandContext` kills the child
and `Wait` reports `signal: killed`, never the context error — so the leader MARKS its
own failure (`probeContextError`, `internal/ai/probe.go`) and a live follower goes round
AGAIN, re-entering the same `singleflight.Group` under its own context. Re-entering the
group is load-bearing on the retry: a direct re-probe would restore the #741 burst (one
child per follower) on the rare path out of a common one, and re-reading the cache would
not do it either, because the followers all arrive within microseconds of each other and
would all miss it. Each round consumes one more cancellation, so rounds are bounded by
the callers sharing the key, and a caller whose OWN context is dead leaves without looping
— `isSharedProbeCancellation` requires a live `ctx`, and both arms of the select check it.
The converse is not treated as shared — a leader sees the same marker, and a dead caller
must not start a fresh attempt under a dead context, which is why
`isSharedProbeCancellation` requires a LIVE `ctx` as well as the marker.

**A cancelled caller leaves NOTHING behind.** The negative a killed probe produces says
more about the caller's connection than about the codex, so the flight inside
`codexFeaturesFor` stores the verdict of `probeCodexFeatures` only while THAT caller's
context is alive, and marks the flight instead when it is not. The store lives in the
flight rather than in the probe because the decision needs both facts at once — is the
answer worth keeping, and was the caller that produced it still alive — and a
check-then-act split across two functions disagrees with itself in the window between
them. It is measured on the CALLER's context and not on `probeCtx`: a probe that hit
its own 10s cap also knows nothing, and that one IS cached, for `codexFeatureRetry`,
because an unanswering codex is the install this design supports. Nothing was cached by
the round that died, so the next round's re-read misses and a live caller really does
re-probe rather than inherit the negative. For the same reason a caller that stopped
waiting gets no `warnOnWeakerCodexPolicy` at all (`CodexClient.run` checks `ctx.Err()`
first): nothing was learned about the codex, so the placeholder it was handed is not a
probe result, and reporting it would fire the `unverified` WARN and CONSUME its
once-per-process latch — silencing the real diagnostic for the rest of a long-lived
server, over the one turn that lost the most information.

**Both arms of the probe's `select` check the caller's own context.** When a caller's
context is already done AND the flight channel already holds a result, both `select` cases
are ready and Go picks between them at random, so a dead caller leaves by the flight arm
about half the time. The flight arm therefore re-checks `ctx.Err()` before it treats a
result as this caller's answer, rather than leaving the outcome to a coin — otherwise a
caller whose context died while the probe was running would report the leader's success
(or its kill) as its own, which is the one outcome the `ctx.Done()` arm exists to prevent.

The filter matters because codex **silently IGNORES** a `-c` key it does not know
(the fail-OPEN direction): `-c` overrides are applied onto the config tree without
a `deny_unknown_fields` check, so a key renamed upstream leaves the tool on and
the call still succeeds. `--strict-config` is the strict reading, it is opt-in, and
Ghost does not pass it, so `TestLiveCodexDeclaresTheNoToolFeatureKeys` provokes an
unknown key and reports which way the installed codex actually goes.

Probe output is validated by SHAPE before it is believed: one line must parse as
`<key> <known codex stage> <bool>`. A positive verdict is cached for the life of
the process, so a header row, a footer count or a single stray token read as an
answer would strip all ten overrides permanently and the only signal would be one
WARN. The test is deliberately NOT an overlap check against the policy's own key
list: a real codex older than this policy answers with a full table naming
features Ghost has never heard of and none of the ten it disables, and that is a
genuine weaker policy rather than an unreadable answer, so the two need different
warnings and only one of them means a tool is on.

`warnOnWeakerCodexPolicy` fires ONCE PER PROCESS **PER VERDICT** — two latches,
not one, because the two messages are not interchangeable and the suppressed one
is the more informative. The reachable order is a long-lived MCP server whose
first probe fails while the binary is mid-upgrade (unverified), after which the
`codexFeatureRetry` re-ask returns a real answer naming the missing keys; a shared
latch would drop the second, and that is the one which says which surfaces are on.
A probe that cannot answer says "unverified" rather than accusing the codex of
lacking features it was never asked about. The refusal is the part deliberately
absent, and the reason is which failure is larger: codex is selected with **no
version floor anywhere** — `CLIProvider` picks it by `exec.LookPath` below claude
and opencode, and a session-routed client names it as its backend with nothing
checked at all — so refusing would fail that session's reflect, resolve and
supersede calls on a working install over a surface that may not exist. The
failure the policy prevents is a tool that is already absent; the failure a refusal
creates is a lifecycle that does not run at all. An older codex therefore gets the
keys it understands, a weaker policy than a current one, and a warning that says
so.

The cache key is `{path, size, modTime}`, not the path alone, and an independent
review deleting the other two components passed the whole suite — so
`TestCodexProbeIsRekeyedWhenTheBinaryChanges` now rewrites a real executable in
place and requires a second probe. The limitation that test does NOT solve: codex
is commonly an **npm shim**, and the identity observed is the shim's, not the
vendor binary's. A real binary replaced behind a byte-identical, mtime-stable shim
is invisible to this key, and to every one like it in this package.

**opencode has no disabling flag either** — `run`'s only permission flag is
`--auto`, which moves in the WRONG direction and is never passed. The policy is a
permission deny/ask in the isolated config Ghost already writes, and the WILDCARD
is what makes it total: opencode defaults every unset permission to `allow`, so a
name it adds later is covered by `*` on the day it ships rather than the day
someone remembers it. V2 must use `ask` (a non-interactive `run` auto-declines
each ask) because a deny rule or a disabled tool strips tools from the request and
the free tier answers that with 403 `provider.auth`; V1 keeps `deny` since its
non-interactive ask behaviour is unverified.

**goose has NO flag for this at all** (its extension options only ADD extensions;
`--no-profile` governs the profile, not plugin discovery), so the restriction is
the `GOOSE_MODE=chat` environment variable goose's own reference documents as
"chat only, no tool calls", against a default of `auto` (approves tool calls). It
is SET rather than inherited, and `GOOSE_MODE` is deliberately absent from the
goose allowlist, because an inherited value could only weaken it while dropping it
returns the child to goose's autonomous default.

**Residuals, named rather than papered over.** codex's `apply_patch` has no
disabling flag or key (its registry entry is gated on the model catalog, and
`apply_patch_freeform` is marked Removed), so the read-only sandbox is its boundary
and a write attempt is refused rather than the tool withheld; the same holds for
codex's skills-extension read/list tools, which are off unless a skill exists and
the child's working directory is a neutral scratch dir holding none.

On the goose side two questions are open, and they are different in kind. Whether
`chat` mode SUPPRESSES EXTENSIONS in a given build is a property of the binary
that no configuration-printing command reports, so it is documented as unverified
rather than claimed as tested. Whether `chat` mode is COMPATIBLE WITH A HEADLESS
`goose run` is the question that decides whether this policy breaks the goose
backend at all, and `TestLiveGooseRunsATurnInChatMode` runs the production argv
under the production environment to answer it — behind `GHOST_LIVE_TESTS=1`,
because a real turn costs a model call. So the mode is confirmed end-to-end only
where goose is installed and a provider is configured, and not in CI.
