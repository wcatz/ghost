- Evidence provenance: `memory_provenance` (schema v18, #673) is the EVIDENCE table — SEVERAL rows per memory, one per observation, answering "who or what supports this memory", which the change log above cannot: a fact claude-code reported in one session, codex in another, and a human verified is three rows here and one row of mutable columns on `memories`, which can only remember the last. Three concepts stay distinct and are not interchangeable: SOURCE is how Ghost received a memory (`memories.source`: mcp, reflection, import, manual), AGENT is which agent produced or observed it (`agent`), PROVENANCE is the evidence records themselves. `memory_id` CASCADES (unlike the change log's deliberately FK-free `memory_id`) because "3 observations support this" is a claim about a memory, and once the memory is gone the claim is about nothing; a purge deletes these rows explicitly as well, because `PurgeMemoryHistory` leaves the memory in place and no cascade fires for a row that stays — and it deletes the `memory_snapshot_evidence` rows too, since a snapshot is the rollback point for a whole PROJECT, so its evidence would otherwise outlive the purge by however many reflects prune that snapshot Every value except `kind` is NULL when the host did not report it — a guessed agent or session is a provenance claim nobody made, and `observed_at` is NULL for the migration's seed because the seed can say what the columns hold now and not when the fact was first seen. Writers, each in the SAME transaction as the write, each ONE statement: `Create` and `Upsert`'s insert append `observed`; a near-duplicate FOLD appends the second report to the SURVIVING memory (the point of the issue — the folding agent used to be discarded with the incoming wording, and `FoldOnly` stores no row of its own so without this the report would leave no trace); `RecordDecision` appends `observed` for its companion memory (an ordinary memory search returns and a later save folds against), empty of provenance because the decision tool reports none; `ReplaceNonManual`'s FRESH INSERT carries its sources' records onto the new id with `carried_from` naming each source — a rewrite or a merge mints an id whose evidence the cascade would otherwise have just deleted, which would make every consolidated memory read "no recorded evidence" forever, so the emissions loop runs BEFORE the delete and a test fails if the two swap; the REUSE branch appends nothing for the reused row itself, which never changed identity, but when the emission's `ReplacesIDs` names OTHER sources beside it (a merge whose text is byte-identical to one source) those rows are deleted into it exactly as a fresh insert's sources are, so it carries their records with `carried_from` too and fills the reused row's UNSET claims from them (`fillReusedClaimsTx`: the reused row is the first source and its own values win — except that the decision links the absorbed sources carried are APPENDED to its own `source_ref` (`boundedDecisionRefs`), because a link is a list and keeping the row's value whole left an absorbed decision with no companion (#1206) — the window is filled only when the row states neither boundary, and no `updated_at` or history row is written since `memory_history` records none of those columns) — before #1207 a reuse-branch merge dropped the absorbed rows' evidence and claims, a decision companion's link among them; `ImportMemory` appends `imported` plus whatever records the artifact carried (and NOT `carried_from`, which names a memory this store has never heard of); `RestoreSnapshot` restores a re-created row's records from `memory_snapshot_evidence` (a table, because a memory has several records, pruned with the snapshots — by `ReplaceNonManual`'s prune and by `DeleteProject`'s own, since a project delete also takes its snapshots through the projects cascade —) and touches NOTHING for a row it updates in place — the snapshot holds an older copy of that row's evidence, and restoring it would drop every corroboration recorded since — with ONE exception: the records a merge carried onto an in-place row from a row this snapshot brings back (`carried_from` naming a snapshot row: ReplaceNonManual's reuse-branch merge and FoldRows' survivor) are removed (`uncarryRestoredSourcesTx`), because the absorbed row returns with its own records and a left-behind copy would count each of them twice beside a restored `verified_at` that no longer states them. `AppendVerifiedEvidenceTx` is the exported seam the validity writers (#677) own the reserved `verified` kind through, and they now CALL it. State the contract as an OUTCOME, because the mechanisms differ on purpose and a reader filtering by `kind` sees three shapes for one rule: every writer that stores a `verified_at` leaves a record carrying a verification stamp in the same transaction, and `EvidenceCounts.Verified` counts any record carrying one whatever its kind. The live callers are `insertMemory` (behind `Create`) and all three of `UpsertWithOptions`' branches plus `UpdateMemoryWithOptions`; each goes through `appendVerificationIfStatedTx`, which gates on the caller stating a verification IN THIS CALL and never on the column, because a partial update COALESCEs a `verified_at` an earlier save wrote and appending for that would record a check nobody made. Their stamp is the STORE's clock, not the caller's (a verifier must not be able to date its own check), so the column carries what was claimed and the record carries when Ghost heard; the two are different facts and both are kept. `UpdateMemoryWithOptions` appends the `verified` leg but NOT an `observed` one — an edit is a change to a fact already reported, not a new report of it, and widening #673's design from inside #575 would inflate the report count on every content edit. THREE more writers store a `verified_at` and are deliberately not callers, each for its own reason. `ImportMemory` is IN the set and not among the callers: the artifact carries an OBSERVATION, so a check happened and is attested, and it rides the import's own `imported` record instead of adding a `verified` one — same store-clock stamp, same count, no second statement. That arrival stamp is CONDITIONAL, and the condition is the round trip: it is skipped whenever ANY carried record already holds a stamp, kind-agnostically, because a record with a stamp says the check happened and stamping again would make a corpus that crosses a machine boundary N times report N+1 verifications of one check. Kind-agnostic rather than `verified`-only because the second hop's artifact carries the FIRST hop's `imported` arrival, and that is the only stamped record it may hold — a kind-specific guard re-inflates on every hop after the first. The condition is a NON-EMPTY value, since a hand-edited artifact can carry `"verified_at": ""` and every reader treats that as no claim. `CreateFromCorpus` leaves NO record carrying a stamp — but it still records, because `insertMemory` appends the ingestion's `observed` row on that route unconditionally, and "no verified record" is the whole of it; a third-party dataset's `verified_at` is a value in a column with no observation behind it, so there is no event and the only stamp a record could carry would manufacture one. It opts out through `insertOptions.recordVerification` because it shares `insertMemory` with `Create`, which is why it needed a PARAMETER and not a comment — and the column keeps the dataset's value either way, since losing the dataset's own data would be the opposite defect. `RestoreSnapshot` writes it in pure SQL from the snapshot table, and a restore is a faithful copy of a corpus whose evidence rows travel with it, so appending per restored row would double-count every check the snapshot holds. That enumeration has been wrong three times — `CreateFromCorpus`, then `ImportMemory`, then by over-claiming what its own enforcement could see — every time because prose is not checkable, so it is ALSO two tests that answer different questions. `TestEveryVerifiedAtWriterIsEnumerated` asserts the OUTCOME each writer leaves: whether a record carries a stamp, and of what kind. `TestEveryVerifiedAtMentionIsClassified` walks `internal/memory` with `go/parser` and requires every function naming `verified_at` IN ITS OWN BODY to be in one of FOUR classifications (writes a memory row, touches a snapshot or evidence side, is a migration or reader, or genuinely SPANS two of those surfaces — `ReplaceNonManual` does, since its fresh-insert path now writes the memory row's validity and provenance as well as the snapshot tables), so a new one cannot be added without being placed; it found four mentions a hand-written list had missed on its first run, all scanners, and caught two of this PR's own new functions when they landed. The limit of that one is part of the claim: it does not resolve the column out of a package-level literal, so `migrateV10` — the migration that ADDS the column, naming it only through `phase1aProvenanceColumns` — is invisible to it, and `TestColumnListWritersAreClassified` closes that one indirection by requiring every function iterating that list to be classified. `AppendVerifiedEvidenceTx` is placed explicitly too, since the writers reach the column THROUGH it and its own body names no column. A function reaching the column by some other indirection is still invisible, and that is the honest edge of the guarantee. There is no growth prune, deliberately: it would be a second statement inside the write transaction, which is what took `TestMultiProcessSharedDatabase` to SQLITE_BUSY for the change log's prune, and the cascade keeps deleted memories from contributing. `migrateV18` REFUSES a database whose `memory_provenance` is not the EVIDENCE table (a pre-rename #664 dev build used the reserved name for the change log) rather than converting or dropping it, naming `sqlite3 <db> 'DROP TABLE memory_provenance'`, and `OpenDB` runs the same check BEFORE the pre-migration backup so a refusal costs no copy and its same-second retry reports the real error — the check tests for `id`/`memory_id`/`kind` ONLY, so it is an identity test and not a version test: a future column here must not make it refuse a legitimate store with a remedy that DROPs its evidence — initSQL's CREATE INDEX cannot catch that one, because the change log has a `memory_id` too, and a warning nobody sees leaves every writer failing on the same missing column. Otherwise it seeds one `legacy` row per memory that recorded at least one of agent/session_id/source_ref/confidence, and NONE for a memory that recorded nothing — an evidence row with nothing in it still says "this was observed", and a row per memory would make every store report one observation, the same fabrication as inventing a session id. Read it with `Store.MemoryProvenance` (oldest first, rowid) and `Store.MemoryEvidenceCounts`, whose `Label()` renders "supported by 2 observations, 1 verified"; the assembler records the counts in stage 4's trace (`Signals.Evidence`, carried on `memory.Candidate` because that is the only read the assembler has) and NOTHING RANKS ON THEM — the stage's multiplier stays 1.0 until a measured change justifies one. The portable artifact (v2) carries the records, nested under the memory they support because a bare evidence line cannot be attributed; the Obsidian mirror does not — it is a human-readable mirror, not a transfer format

- Memory links: `memory_links` edge table auto-populated by cosine similarity (internal/linking worker); links cascade-delete with memories and self-heal after reflection. A graph-expansion ranking bonus was evaluated and removed — dominated by a deeper vector-k (links and the vector leg are both cosine); the link graph is retained for Obsidian export and supersedes ranking (see `docs/superpowers/specs/2026-07-20-graph-expansion-stays-off-design.md`). No edge may join a scope-conflicting pair: every writer refuses one (`Upsert`'s dedup probes, the linker's `related` edge, `ghost supersede`'s candidates) and every reader ignores one already stored — the two ranking guards (`DemotionPenalties`, `SupersedePenalties`), `Store.SupersedesWithin`, `ghost resolve`'s supersedes piggyback and the repair pass's matching floor (`scopeCompatibleSupersedes`, which needed `GetByIDs` on `resolveStore`/`reassessStore`/`resolveCapableStore` for the link endpoints' scopes), and the two fold-target liveness checks (`foldTargetStillLive` + the cross-category probe). Scope exempts a pair from ranking and folding; it never deletes a `memory_links` row. Where the exemption is decided: inside the candidate query, always, because the same `LIMIT` picks the candidates — a scope check applied after the cut spends the budget on rows the caller may not use and misses a compatible one ranked just below (#665). So the two cosine writers narrow before their window (`SearchVectorScoped`, in Go over the scan, so its top-k is the limit and there is no statement to fold the rule into) so their neighbour budgets count only linkable rows, and `Upsert`'s two dedup probes carry the rule inside their own `LIMIT 15` for exactly that reason. `foldTargetStillLive` is the one statement that carries it without a window to protect (it names one row by id) and for a different reason: a scope-conflicting `supersedes` edge is not a verdict that row may be acted on. Both are one rule in two forms, `scopesConflictSQL` in `internal/memory/scope.go`, held to `ScopesConflict` by `TestScopesConflictSQLAgreesWithScopesConflict`
