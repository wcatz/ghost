# Ghost invariants

The package map and the load-bearing design invariants: what each package owns, and the rules a change must not break. Moved verbatim from `CLAUDE.md` so that file stays short; the full design narrative is `docs/architecture.md`. The PR reviewer workflow reads this file from the base ref as part of its conventions.

## Stack
- Go 1.26+ CLI application
- SQLite with FTS5 for memory persistence (modernc.org/sqlite — pure Go, no CGO)
- CLI harness callers (claude/opencode/codex/goose subprocesses) — used by reflection, resolve, and supersede. Each harness owns its authentication and billing; Ghost does not add a direct API client. The prompt is written to the child's stdin and no positional message is passed: the kernel caps one argv element at 32 pages (128 KiB on a 4 KiB-page x86, 512 KiB on a 16 KiB-page one) and a reflect prompt reaches megabytes, so an argv prompt failed the spawn with E2BIG instead of answering. `claude -p` and `opencode run` read the message from a pipe when none is given; codex gets `exec -` and goose `run -i -`. `claude --system-prompt` stays an argument — small, fixed, and never confusable with user content. `cli.model_reflect` / `model_resolve` / `model_supersede` pin the opencode harness model per phase (each phase is its own process; ignored by claude/codex/goose which have no model flag). Empty = any inherited `GHOST_OPENCODE_MODEL`, else Ghost's explicit `opencode/big-pickle` default; a configured pin overrides an inherited env pin for that phase.
- MCP server via modelcontextprotocol/go-sdk (stdio transport)

## Package map
- `cmd/ghost/main.go` — CLI entrypoint; subcommands: mcp, hook, reflect, resolve, supersede, prune, lifecycle, project, obsidian, opencode, bench, backup, export, import, history, maintenance, upgrade, context, version, help. `runCLI` answers `-h`/`--help` (`cmd/ghost/help.go`, one usage table) before the dispatch, so a help request has no side effect. A command line the dispatch cannot route — an unknown command, a missing or unknown subcommand, no command at all — is `usageError` on stderr (the diagnostic, then that level's own usage) and exit `2`, the conventional usage-error code, kept distinct from the `1` every command uses for a run that started and failed (#691; bare `ghost mcp` still starts the server, the one group with a default action). Only the groups in `commandGroups` dispatch on a subcommand word: a word after a command that takes an OPERAND (`ghost history <memory-id>`, `ghost reflect <project>`) is data and its parser's business, and an unknown FLAG is that parser's too — exit `1` where it rejects one (`ghost reflect` still ignores it, as it always has)
- `internal/adversarial/` — Test-only support: the shared hostile-input corpus (prompt injection, secret shapes, invisible-character tricks, path shapes) and the shared inert-content invariant the three untrusted parse surfaces assert against (#585). Nothing under `cmd/` may import it; it exists to be called from `_test.go` files. The invariant in one sentence: a value parsed from an untrusted surface is data — stored exactly as parsed, naming at most one path component inside the directory its surface owns, and never deciding the parse. `internal/mcpserver/adversarial_test.go` (#538) proves the same invariant one layer out, over the wire
- `internal/ai/` — CLI-harness providers (`CLIClient`/`OpenCodeClient`/`SourceProvider`) used by reflection + resolve + supersede — no Anthropic HTTP API client. Every child is spawned through the one `harnessCommand` funnel, which applies the `harnessEnv` allowlist and confines the working directory and temp variables to an invocation-owned scratch dir. Confinement is not conditional on that scratch dir: when it cannot be created the funnel confines the child in its own invocation-owned `MkdirTemp` tree instead, under the same rewrite, and when even that is impossible it returns an error and the call fails — no backend can run a child unconfined (#751). The backend is part of the policy, so each harness keeps only its own auth/config root (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, the safe `GOOSE_*` set, `OPENCODE_API_KEY`). Two harnesses additionally get an isolated config tree because their plugin/MCP discovery would otherwise find Ghost's own registration: opencode gets a fresh home plus an `mcp: {}`/`plugin: []` config, and goose gets an empty invocation-owned `HOME` (its plugin root is home-relative by specification, so `XDG_CONFIG_HOME` alone cannot move it). The goose home carries the config rather than restating where it lives — the inherited `XDG_CONFIG_HOME` when set, otherwise reproducing each home-relative root goose may resolve (`.config/goose`, `Library/Application Support/goose`; Windows uses `%APPDATA%`, which the allowlist already passes through) — so goose's own per-platform resolution is untouched and authentication still works. `GOOSE_PATH_ROOT` is the exception: goose consults it before any home variable (plugins resolve to `$GOOSE_PATH_ROOT/.agents/plugins`), so it is repointed at a root inside the isolated tree with the real `config/` carried into it, and a relative value is left alone because goose ignores one. Where a symlink is refused (Windows without Developer Mode) the files are copied instead. If the home cannot be established, the call fails rather than running with the real home. Codex needs no tree — `--ignore-user-config` already covers it. OpenCode's tree also owns a DATA root (`XDG_DATA_HOME`), which is what keeps a lifecycle run out of the user's session list (#588): `opencode run` has no flag to skip saving a session, so the store's location is the only control, and OpenCode resolves its session database from that variable (verified on v2.0.15 with `opencode debug paths`). V2 needs `--standalone` for this to hold — without it `run` attaches to the user's shared background service, and the server holding the user's data dir is what creates the session. No `session delete` follows a run: the store sits in the invocation-owned directory whose deferred cleanup removes it, so a session cannot outlive its call, and a delete would cost a second OpenCode process per harness call (hundreds per lifecycle) to erase a row from a directory about to be deleted. The pre-isolation backlog is `ghost opencode cleanup-sessions`. A child gets a minimal environment AND NO TOOL SURFACE — see “No harness child gets a tool” below for the per-harness mechanism, the argv goldens, the codex probe, the residuals and the live tests.
- `internal/memory/` — SQLite CRUD, FTS5 search, vector search, time-decay scoring, and the retriever contract behind the assembler (`Store.Candidates`: one read snapshot, widened untrimmed rows with their scoring facts, leg/edge statuses). It is also the seam's second shape: a request with no query and a non-empty `Passive` list is a PASSIVE retrieval, one `[]SlicePolicy` per bucket, one policy per bucket BECAUSE the buckets genuinely disagree (order, over-fetch, two-pass selection, near-duplicate policy: the `_global` policy DROPS its losers, the project policy only reorders and leaves the drop to the cap), where the policy states the ORDER (`decay`, or `pinned_importance_updated` for `_global`), the over-fetch, the two-pass selection, the near-duplicate threshold and whether its losers are dropped — and where `SlicePolicy.Bucket` IS the project predicate, because `passiveFetchSQL` binds it as the `WHERE` clause and does not consult `CandidateRequest.Mode` at all. The decay order binds the caller's instant (`decayRankingSQLAt` derives the expression AND its bindings from one count of the constant's `julianday('now')` occurrences, round-tripped in a test) rather than `julianday('now')`, so the window, the Go-side decay score and the row ages the trace reports cannot straddle a second boundary. Passive rows carry the **-1 leg-rank sentinels**, not 0: rank 0 is a real first place, and a passive row reading 0 would clear the keyword floor arm on a rank nobody produced. Every bucket window is bounded, because this path runs at every session start and a passive window is read, ordered and demoted IN FULL — there is no leg to fuse and nothing to discard behind it — so a policy stating no `OverFetch` is refused (its window would be the whole store) and one above `maxPassiveOverFetch` (200) is refused rather than CLAMPED: a caller that states 5000 and is silently given 200 has been answered a different question. A policy naming no bucket, and two policies naming one bucket, are both refused — the first reads as an empty bucket and the second returns every row twice. A passive request cannot also be a HISTORICAL read: `AsOf` and `Passive` are mutually exclusive, checked in `Candidates` before the passive branch because the bench harness and the tests call it without going through the assembler. Routing it to the historical path would silently discard the policies and answer with `Fetch.Limit` while the caller believed its per-bucket over-fetches were in force; the two select over different things (live rows vs recorded versions) and there is no combination of the two here yet. A passive read is the first whole-`Memory` read this package makes through a NON-MIGRATING handle — every store Ghost opens itself migrates on the way in, and the session-start block it serves reads through `OpenReadDB`, which runs no DDL — so the fetch SELECTs `memoryColumnNames` with a column the store may lack replaced by a literal **of the shape `scanMemories` expects**: `retention` becomes `'' AS retention` and NOT NULL, because the scanner binds that one into a plain `string` and resolves `""` to `project` itself ("a row whose tier reads empty is a row a query did not select, not a fourth tier"), so a NULL there is a `Scan` error — "converting NULL to string is unsupported" — rather than a label; `scope` and `expires_at` take NULL precisely because they ARE bound as `sql.NullString` and NULL is the honest value for "no scope stated" and "no expiry claimed". The version is probed through the SNAPSHOT (`s.queryDB()`), never the pool: the read transaction already holds the only connection at `MaxOpenConns(1)`, so a PRAGMA on the pool is a deadlock rather than an error. An UNREADABLE version is treated as the FLOOR, not as "current" — a store whose version cannot be read is read without the columns that might not be there, which loses a label rather than failing the read, where returning an error would turn a transient PRAGMA failure into no session context at all. That leaves the evidence table (`memory_provenance`, v18) with a THREE-WAY decision rather than a boolean (`evidenceReadMode`), because substituting for a column that might exist is the safe direction while SKIPPING a read that might have succeeded is not: **read** (version read and at/above the floor), **report zero** (version read and below it, so the table was never created), and **read, tolerating ONLY a missing table** (version unreadable, so existence is unknown — skipping would report "no recorded evidence" as a fact about support, and a zero on a store that HAS the table would be a false claim that no memory is supported; anything but a missing table stays a real error). An unstated `DemotionThreshold` falls back to the store's configured one rather than to 0.0, which `nearDuplicatePenaltyRows` binds as `l.strength >= ?` — so 0.0 makes EVERY `related` edge a near-duplicate and a `DropDemotedLosers` bucket then DELETES a memory over a 0.1-similarity edge. `DemoteOnlyWhenOverCap` skips the near-duplicate demotion when the selected set fits entirely under the bucket's cap, because a demotion is a REORDER and on such a set it can only shuffle rows the answer shows in full — which is what both shipped readers do: the session block's project bucket states it, and the tool surface has no cap to be over. Near-duplicate protection is `Pinned || RetentionExempt(m)`, the same map every other caller passes: a pin-only map would penalise an unpinned `persistent` row on the losing end of a pair here and spare it everywhere else, and on a bucket that DROPS losers penalised means REMOVED from the block. `Store.CreateWithID` is the only writer that takes a primary key THE CALLER COMPUTED for a row Ghost is creating fresh: Create's write — same transaction, same history and evidence rows, same checks — plus a named key, and an empty one is refused rather than falling back to the column default. The other two writers that write a caller's id preserve an id Ghost already held rather than being handed a new one, and that is the whole difference: `ImportMemory` writes the id an artifact carries (so an unchanged store re-exports byte-identically, and id-only dedup means the destination's own copy is never overwritten), and `RestoreSnapshot` brings back rows under the id they had, so everything still pointing at them resolves again. `CreateWithID` is the inverse — nothing Ghost holds names the row otherwise, which is exactly what a reproducible measurement needs, and the only caller is the benchmark: a store's ids are part of what a measurement of that store means (the ranking breaks tied fused scores by id, and re-sorts the window by a decay factor built from `created_at`), so `internal/bench` seeds a corpus under ids derived from its keys and one `created_at` per pass rather than from `hex(randomblob(16))` and `datetime('now')` (#708). The benchmark calls `CreateWithIDFromCorpus` rather than `CreateWithID`, which is the same write with the record bit OFF, and the distinction is the corpus rule and not tidiness: a dataset's `verified_at` is the DATASET's claim, so the column keeps it verbatim and no `verified` record is appended — a record's stamp is the store's clock by design, so one for a claim the dataset dated to a year earlier would assert a check that happened now. `CreateWithIDFromCorpus` keeps the credential guard, which `CreateFromCorpus` waives for downloaded public eval corpora; the benchmark's own fixtures are committed and a review has read them, so it gets the rule without giving up the guard. Nothing here is on `provider.MemoryStore` or in the MCP surface, and `Create` still mints every id a live save gets — production rows are unaffected.
- `internal/assemble/` — context assembly: `assemble.Run` is the one entry point (one `[]stage` in `pipeline.go`), owning selection, validity, category/scope predicates before window closure, provenance (pinned at 1.0), budget closure, the outcome, the `response_fit` post-pass, the always-recorded trace and the shared `Item.Line()` renderer. Depends on one method, `Candidates`; `internal/memory` never imports it. `ScopeLabel` is the scope label `Item.Line()` embeds and the session-start block prints, so no surface re-derives it; `ScopeContradicts` is the named negation of `memory.ScopeMatches` rather than a second copy of the rule. `Result.Leaks()` and `Trace.TrimmedByBudget()` are the ONLY way a consumer learns which rows it should not have carried and what the budget cut, and both READ the verdicts the stages recorded (`Trace.Signals[id]`: `ValidityState`, `ScopeMatched`, `ProjectMatch`, plus the row's `resolved_at`) rather than re-deciding them — a second classifier anywhere, and the benchmark is the surface that wants one, is a second implementation of the same rules free to drift until a leak is reported as clean by the only component whose job is to say otherwise. `LeakArms` is the fixed report order with zeros included, and a consumer meeting an arm it has no row for refuses rather than counting that row clean. The session-start block is a caller of `Run` (`loadSessionPassive`, `internal/mcpinit/session_passive.go`), and it is the reason the golden block is byte-identical for every branch its fixture exercises: the block's rows are chosen by ONE `assemble.Run` with two bucket policies, where before they were chosen by two private queries with two private over-fetches, two private two-pass selections and two private near-duplicate passes, so the assembler's stages ran over rows a second implementation of the same rules had already picked. A `SourceSessionStart` with an empty `Query` is a PASSIVE request, and `Store.Candidates` serves it from `CandidateRequest.Passive`; a source alone is not what makes it passive, which is why the empty `Query` is load-bearing rather than decorative. The golden's byte-identity is scoped rather than absolute, and the exception is the `_global` bucket's SUPERSEDE demotion: `loadGlobalMemories` ran only the near-duplicate lookup over global rows, while the assembler's passive demotion runs `SupersedePenalties` for every bucket with no field to decline it, so a `supersedes` edge between two `_global` rows now pushes the replaced row out of a bucket capped at 8 — a membership change, not a reorder. It is kept, because that bucket already DROPS its near-duplicate losers on the stated ground that a superseded preference is not worth one of eight cross-project slots, and an explicit edge is a stronger signal than a cosine neighbour. `TestTheGlobalBucketNowDemotesSupersededRows` states it, and the golden cannot: its one `supersedes` edge joins two project rows. PASSIVE is keyed on the ABSENCE OF A QUERY (`assemble.Passive`), not on `Source`, because the consequences follow from the absence: no leg ran, so no FTS rank and no cosine exist to compare, a passive block is NEVER `weak` (it is `answerable`/`not_applicable` — `weak` would be a relevance verdict about a question the surface was never asked), and an empty passive window is `no_memories` rather than `no_candidates` because the passive path never counts the corpus. Both wordings are refusals in the other direction and each is a different lie: `no matching memories found` claims a census that was never taken, and `no sufficiently trustworthy memory found` claims rows were found and rejected when the window came back empty. A window that came back NON-empty and was then emptied by a stage IS an exclusion and says so in the shared wording. TWO passive requests are REFUSED rather than served, both because the seam cannot honour what they ask and would answer a confident false negative instead. One: a slice's bucket must be the requested project or `_global` (`validatePassiveBudget`). The bucket IS the project predicate — the store binds `SlicePolicy.Bucket` as the `WHERE` clause and never consults `Mode` — so a mismatched bucket would READ AND INJECT a project the request never named, and stage 3 only RECORDS that as `Signals[id].ProjectMatch=false`, which nothing refuses; the same decision `sliceBuckets` makes for a repeated bucket, one named bucket per slice, and it has to be a bucket this request is about. Two: a passive request cannot carry a `Category` or `Retention` filter. `passiveFetchSQL` binds no category and no tier in its SQL at all, while the query path WIDENS the window when either is set (`predicateFetchWiden`, what closed #573) precisely so a matching row below the cut stays reachable — and the passive branch of `retrievalWindow` returns before that widening, because the window there is the policies' own over-fetches. So the filter never applied at all: stage 3 drops every non-matching row out of a window nothing widened, and the caller gets `all_out_of_category` while the store holds the rows it asked for just below the cut. That is the damage, and it is why this is a refusal and not a widened fetch: a window is a bound, and an over-reported one costs a field's honesty, but a filter decides MEMBERSHIP, and a caller told its category is absent from the project will not widen anything. `abstain_cosine` therefore reports `not_applied` for a passive block rather than `off`: `off` is a configuration a reader can change, and the session-start surface has no vector arm to configure, whatever `context.abstain_cosine` is set to. The budget is what carries the bucket policies — `Slice` gains `OverFetch`/`Order`/`TwoPass`/`BehaviorFloor`/`BehaviorCategories`/`CategoryWeights`/`CategoryCaps`/`DemotionThreshold`/`DemoteOnlyWhenOverCap` — because a passive retrieval has no query to shape it, and a passive slice stating neither an over-fetch nor a cap is REFUSED at both seams: passive runs at every session start, and an unbounded fetch is a store scan. `Slice.MaxItems`/`MaxBytes` still bound membership, and `Budget.MaxItems`/`MaxBytes` stay 0 for session-start because `Budget.MaxBytes` bounds the complete rendered RESPONSE, which is the search framing a differently-framed surface must not spend (see `Result`)
- `internal/mcpserver/` — MCP server: 22 tools + 4 resources + 2 prompts (`recall_project`, `record_decision`). `ghost_health` leads with a store-version line (#746) that appears ONLY when the store on disk is newer than this build writes, naming both versions and saying reads still work; it is a report and not a check, so it deliberately does not go through the write path's refusal, because a server that cannot search and cannot say why is worse than one that can only save nothing. It renders nothing on a healthy store, and an unreadable version as `could not read` rather than as silence, so a server that cannot answer is never mistaken for one that answered "fine". The same sentence reaches the agent through the tools' own errors, which is asserted through a real `ghost_memory_save` call rather than by inspecting the error type — a handler that wraps or replaces an error is an ordinary thing to write, and only the tool call proves the wording survives. A browse that resolves a project NAME that matches no `projects` row is answered with the not-registered sentence and reads NOTHING: `ResolveProject` answers an unknown name with `("", "", nil)`, so the handler keeps the RAW name for the message (formatting the resolved id produced `Project "" is not registered`, naming nothing the caller can act on) and SKIPS the `ListMemories` call. Skipping it is not tidiness — `ListMemories` widens to `(project_id = ? OR project_id = '_global')` whenever a category or retention filter is present, so a FILTERED browse of a project Ghost has never heard of returned the `_global` rows, and the not-registered sentence was unreachable for that call because the answer was never empty. The bound is exactly the cross-project rows: the widened clause binds `project_id = ''` — `ResolveProject` answers an unknown name with the EMPTY string — so only the `_global` disjunct can match, and a named project's own rows are never in the answer (an UNFILTERED read does not widen, which is why only the filtered case leaked). An unresolved project browses NOTHING rather than showing the cross-project rows, and that is a deliberate difference from `ghost_project_context`, which DOES append them for the same unresolved name: a browse is "this project's memories, optionally filtered" and a project with none has an empty answer, while a context block is what the SessionStart instructions send an agent to precisely when the directory matched nothing. Whether `ListMemories` should widen at all is a question about its own scope and is not settled here.
- `internal/hostevent/` — Normalized host-event contract (v1) and the transcript scanners; every parse or validation failure is an error the caller turns into "allow the stop", and a payload past `maxPayloadBytes` is one of them (nothing else on the path bounded it — the hook read stdin with an unbounded `io.ReadAll`, and `Parse` retains the payload decoded and again verbatim in `Raw`). The hook now reads through `hostevent.ReadPayload`, which stops one byte past the ceiling, so the bound limits the allocation and not only the parse. Field values are text the host did not write, so only the contract's own fields decide the envelope: an unknown field cannot become a known one, an instruction-shaped `hook_event_name` normalizes to nothing, and the goose native aliases (`event`, `working_dir`) bind only for `--source goose` and only per field where the dialect field is absent. `GhostSaves` counts STRUCTURE, never prose — a save tool named inside a text part, a shell command or an opencode Code Mode `execute` body is not a save, because that count is the save-nudge's evidence
- `internal/mcpinit/` — `ghost mcp init`, `ghost mcp status`, `ghost hook <event> --source <host>` (contract-v1 lifecycle dispatch; the session-start block's MEMORY ROWS are `assemble.Run`'s (`loadSessionPassive`, `session_passive.go`) and its bucket policies are ONE statement, `sessionPassiveBudget`, because the project bucket and `_global` genuinely disagree and two copies of a policy is how they drifted; the project slice is CONDITIONAL on a project matching and the global slice is not, which is the case the old shape got for free — the global loader ran above the project resolution, so an unrecognised directory still rendered a Global section. Everything else the digest carries — the learned summary, the open tasks, the active decisions, the interaction count and the two totals — is still a direct read, because the assembler's `Item` has no field for any of it. The per-item PREVIEW budget stays with the renderer rather than riding on `Slice.ClampBytes`: a preview has to SAY it was cut, `ClampBytes` cannot append an ellipsis, and a caller cannot tell a clamped row from one that happened to be exactly its budget, which is the distinction the ellipsis needs; the stored row is untouched either way. Every query this package still issues against `memories` is a `COUNT(*)`, asserted by a source scan — a count names no row, while a row projection is a choice about which memories a session is shown, and a choice made here is a second implementation of the assembler's stages (the scope and tier schema-version probes that lived here for two releases are gone with the fetch they guarded, because `internal/memory` owns those substitutions in `passiveColumnsFor` and the store reads the version through its read SNAPSHOT); installers: claude-code, opencode plugin, codex TOML+hooks.json, goose Agent-Plugins package; goose field aliasing lives in hostevent.Parse). Every write to a file the user owns — settings.json, codex config.toml and hooks.json, the opencode plugin, the goose package, the MEMORY.md redirect — goes through `writeFileAtomic`/`writeFileAtomicPrivate` in settings.go, never a bare os.WriteFile: temp file in the same dir, flushed (data and mode) with `f.Sync()`, then rename, then the parent directory flushed, so an interrupted write cannot truncate a config, a reader holding it open still sees a whole document, and a power cut can leave neither an empty config nor a missing one. A temp-file flush failure stops the write and is reported; a directory-flush failure is not (the rename already landed, and Windows has no directory flush at all). The rename carries the permission bits across and nothing else — not the owner, POSIX ACLs, xattrs or hardlinks, so a hardlinked config in a dotfiles repo silently diverges from its repo copy. `writeFileAtomicPrivate` additionally clamps the mode to 0600 and is used only by settings.json, because that is the ceiling every pre-refactor save enforced; the other files keep whatever mode the user chose, even where a codex `[mcp_servers.ghost.env]` sub-table can hold a credential. Ghost's own marker/scratch files are exempt. Two files get a one-time `.bak` through `writeBackupOnce`: settings.json on its first save, and codex `config.toml` the first time Ghost writes to it — the first init, which appends the table to a file the user already had, so the copy is the pre-ghost file (a repair-only backup could never be, since a repair can only find a table that is already there). Neither is ever rolled forward, so a later run cannot overwrite the only pristine copy with Ghost's own output, and a 0-byte config.toml is skipped rather than copied — an empty backup would stand forever and block the real one. It also owns the read-only stale-server scan (`ReportStaleServers`, #746), which reports running `ghost mcp` processes whose executable is unlinked or is not the binary this command is, so `ghost mcp status` and `ghost upgrade` can name the clients to restart. The session hook's `bumpSessionCount` is the ONE write into a memory store that does not go through `internal/memory`'s guarded seams — the structural test behind those seams walks that package, and this one opens its own `sql.Open` handle — so it reads `PRAGMA user_version` itself and skips the write when the store has moved past this build. It is checked before the write rather than inside a transaction with it because there is no transaction: the counter is best-effort by design, its failure path is `return 0`, and wrapping a row that records something about this process in a guarded transaction would change what the hook is. The skip is silent, because a line printed on every session start lands in front of an agent on every start, and `ghost_health` plus `ghost mcp status` already say it where a human is looking. Four properties are load-bearing. It NEVER signals, kills or restarts anything, because only the operator knows which client is safe to interrupt. It detects by EXECUTABLE IDENTITY (the kernel's own `(deleted)` marker on `/proc/<pid>/exe`, then `os.SameFile`) and not by a version string, because a running process's version is text inside a binary this code must not execute, and the installed path plus the deletion marker are facts the kernel already keeps. It reports a THIRD state, "could not answer", as silence on a non-Linux platform and as `checked=false`, so an unreadable tree is never rendered as an empty list that reads as "nothing is stale" — and UNKNOWN is kept distinct from a FINDING at the per-process level too: `sameFile` is three-valued, because a two-valued one cannot say "could not read", and a `ghost mcp` running from a root-owned `/opt/ghost` at 0700 has an `/proc/<pid>/exe` this user cannot stat. Rendering that as "a different binary" would tell an operator to restart a healthy client, so the process is skipped: unreported is a small loss, wrongly reported costs a session. And its WORDING is derived from the evidence each finding carries, because `installed` is `os.Executable()` — the binary running this command — and not a discovered installation, so a `go run` build, a `make build` output and a `~/bin` copy are all ordinary ways to invoke the command and all have current clients. Only `ExeDeleted` is a fact about the world and is reported as "replaced"; a plain mismatch says "a different ghost binary than this one", and nothing anywhere claims a binary "is no longer installed", which asserts an installation this code never looked for. `ghost upgrade` compares against the path it just replaced, not `os.Executable()`, which is the old image this process is still running. Its consequence is hedged ("writes may be refused") because the scan never opens the store and so cannot assert the refusal happened; `ghost_health` is where that is actually reported.
- `internal/claudeimport/` — One-time import of Claude Code auto-memory on first contact. The files are written by a session that read a checkout Ghost never chose, so the parse layer is an untrusted surface: a front-matter line gets its own bound (`maxFrontmatterLine`) because `bufio.Scanner`'s 64 KiB default stops the scan on a long description and the block's loss is silent (the type, and with it the category, went with it), a block that could not be read whole is imported as body text rather than half-parsed, and a file past `maxMemoryFileBytes` is skipped. The import writes nothing to disk at all — a fixture asserts the tree is byte-identical afterwards — and it never promotes: `categoryMap` is the only thing that picks a category, so a planted `source: manual`, `pinned: true` or `type: _global` reaches none of the fields consolidation filters on
- `internal/embedding/` — Ollama async vectorization worker; every vector is stamped with the identity of the space that produced it (`<model>[:<dimensions>][+prefix]`, `embedding.VectorIdentity`) and nomic-embed-text is embedded with its `search_document: `/`search_query: ` task prefixes. A LIVENESS PROBE MISSING ITS DEADLINE IS NOT AN OUTAGE, which is why the probe is three-valued rather than a bool: `Client.Probe` answers `Reachable`, `Unreachable` (a non-200, or a refused connection — an ANSWER, so nothing is listening), or `Inconclusive` (the probe's own 2s deadline expired, so we learned nothing), and `Worker.checkAlive` returns that verdict while maintaining the `ollama-down-since` marker (`ghost mcp status` reads it for outage duration). The two errors are NOT symmetric, and every call site says which one it is making, which means the two gates DISAGREE on purpose: `EmbedPending` PROCEEDS on `Inconclusive` (its callers — a one-shot `ghost supersede` and a save-driven `processProject` — have no second chance, and skipping is what made #736 report a clean `0 candidate pairs`), while `SweepOnce` skips on anything but `Reachable`, because the daemon retries in one interval and a lenient gate there walks a HUNG endpoint through every project at `2 + 2·P + 32·P_pending` seconds, blocking `Worker.Run`'s select loop and dropping save notifications past `projectCh`'s 16-deep non-blocking buffer. `EmbedPending`'s in-batch re-probe after a failed embed stops on anything but `Reachable` (a part-done batch gains nothing from another 30s request), and it RETURNS the verdict `SweepOnce` may ACT ON — the re-probe's own where a batch attempted work, a CONCLUSIVE refusal otherwise, and an `Inconclusive` over no work collapsed to "nothing to act on" — so the sweep reuses one probe and a busy machine cannot end a tick over a project with no work. Reading a timeout as "down" cost a busy machine the whole index: both the daemon's sweep AND `ghost supersede`'s own pre-scan fill (`embedSupersedeCorpus`, #716) gate on this probe, so one slow round trip left the candidate scan with no vectors to score, `Result.Unscored` holding the entire corpus, and a clean-looking `0 candidate pairs` at exit 0 for a pair the operator could see (#736). The marker answers the OPPOSITE question, because a duration is only worth having for an outage that is real: written on a conclusive `Unreachable` at once and never re-written (so a still-down endpoint does not reset its own clock) — reachable only inside the DAEMON, which is the sole caller that builds a Worker with a data dir (`embedSupersedeCorpus` passes "" on purpose: the marker is the daemon's outage bookkeeping) — AND on `Inconclusive` after `inconclusiveStampsAfter` CONSECUTIVE unanswered SWEEP TICKS — a tick counts whether or not the strict gate let the sweep past it, so a hung endpoint that skips every project still keeps the clock running (three ticks is about six minutes at the daemon's 2-minute interval) — and one slow probe is a busy machine far more often than a dead endpoint, and a marker written on one is reported for as long as the machine stays busy, while the endpoints a refusal never describes (a wedged accept loop, a remote URL behind a dropping firewall) need that duration precisely because they never produce a refusal. The streak is counted PER SWEEP TICK (`SweepOnce` -> `noteSweep`) and NEVER per probe, because `checkAlive` is called more than once per tick — `EmbedPending` re-probes after every failed embed — so a per-probe count reaches its threshold inside ONE tick and stamps the marker on exactly the busy machine the streak exists to protect against. Any answered sweep SPENDS the streak, so a stall spread over minutes cannot accumulate into an outage that was never established; a stall never *clears* a real one, and an inconclusive probe never removes the marker at all. `Client.Alive` remains the two-valued form for the two callers that only warn a human (`mcpinit`'s init preflight, `ghost_health`); a caller that gates WORK on the answer uses `Probe`, because only there does a false "down" cost a skipped corpus rather than a conservative warning

- `internal/memref/` — the ONE ref-resolution implementation, now for every surface that takes a memory by name, not only the ones that CHANGE a row: `ghost supersede --withdraw`, `ghost resolve --mark` / `ghost_resolve_mark`, and `ghost history` (#720), which only READS. Two entry points and ONE set of rules: `Resolve(ctx, store, projectID, which, ref)` scopes the read to a project (its callers are about to change what they name), and `ResolveIn(ids, which, ref)` applies the same rules to an id set the CALLER collected, which is what a store-wide reader needs. The difference is which ids, never how a ref is judged. `ResolveIn` names no project in its refusals because its set is not confined to one, and `FullIDLen` is only the boundary between two honest sentences about a miss, never a test of whether a ref is a whole id. `ErrNoMatch` distinguishes the refusal that says the set holds nothing from the ones that say it holds too much, and a caller branches on it rather than on the ref's length — which cannot tell them apart. The reasoning for all of it, and for why `resolveIn` applies the prefix match itself, is in [architecture.md](docs/architecture.md#memory-history). A ref is a full id, or a PREFIX of at least 8 CHARACTERS (a RUNE count, never a byte length — the id column is TEXT and SQLite's substr() slices by character, so a byte-counted floor on a multi-byte id refuses a prefix the store really has and accepts one that is a third of an identity; the two lengths agree for the hex ids Ghost mints, which is exactly why the bug survives a normal test). The floor applies to a PREFIX ALONE and is decided by COMPARING the match with the ref, never by inspecting the ref's characters — a full id is accepted whatever its shape, because `ghost import` writes an artifact's ids verbatim and nothing about the column says they are hex. A byte-exact match wins at any length (the id is a unique key, so the spelling the caller typed is decisive, which is what lets a short full id that also prefixes a longer one resolve), then a single case-folded one, then the prefix rules. AMBIGUITY IS A REFUSAL, never a choice, and it LISTS the matches up to `MaxMatches` — with ONE exception: a ref below the floor is refused WITHOUT the match list, because printing it would turn a refusal into a dump of the id set (a store-wide set is a LARGER thing to dump, not a smaller one). Two case-folded matches and no byte-exact one (a THIRD casing of ids differing only in case) is unaddressable by any spelling, so that refusal LISTS the two stored spellings instead of naming a remedy — the reader's next keystroke is a copy of one. The rules are shared rather than copied because two copies eventually disagree about which id one spelling addresses; a guess is worse on the history path than on the change paths, where it changes a row nobody named — there it also prints one memory's whole recorded TEXT as though it were another's. NOTE THE SCOPE, because the claim is not wider than it looks: `resolve --reassess --only` does NOT route here. `internal/resolve/scope.go`'s `Scope.Select` has its own rules, and it HAS to differ on one point — a selector matching nothing is a REPORTED MISS that lets the rest of the scope still be judged (#698's scoping judgement), where a change to a named row cannot be a miss at all, so a failed ref there is a refusal of the whole request. It also measures its 8-character floor in BYTES and truncates an ambiguity listing with `id[:8]`, both of which memref fixes, and unifying the two is a separate change worth doing on its own. It is worth knowing they are on the same round trip: `--mark`'s own follow-up hands the operator a `ghost resolve <project> --reassess --only <ids>` command
- `internal/supersede/` — `ghost supersede`: LLM-classified 'supersedes'/'causes' link creation over live memories, batched 8 candidate pairs per harness call with a content-keyed NEITHER cache (`supersede_checked`, schema v8, cascading FKs) so a converged project's fresh candidates make zero calls — except reversed ones, which are never cached and are re-asked every pass (live-link pairs are still validated each pass). A classify call that FAILS is re-issued ONCE, after `classifyRetryDelay` (2s, injectable through `SetRetryDelay`) and counted by `Retries()` — it is on both reports and the reassess summary log — because a real `opencode run` that exited 1 once cost a whole `ghost supersede` pass in #699's rehearsal, and the rerun a minute later answered normally. ONE retry, not a schedule, and it decides nothing: the second failure is returned unchanged so a genuinely dead harness is exactly as fatal as before, `Run` still aborts and writes nothing, an UNPARSEABLE reply is not a transport failure and is not retried, and the wait is context-bounded so a cancelled run does not spend a second spawn to be told the same thing. Pairs are oriented by `updated_at`, so the prompt also carries each note's `created_at` and offers a fourth verdict, `reversed`: a supersedes link only points newer→older, so a verdict saying the OLDER note is the current one is refused (never written, never cached) rather than written backwards (#641). The pass is KEEP-biased because the edge is not an annotation: the ranking guards demote its target and `ghost resolve`'s piggyback stamps `resolved_at` on it, so a wrong edge removes a live memory from every later session. Two rules decide that, both from #686's 43%-precision measurement (every wrong edge joined two notes that were BOTH still true). The rubric asks the falsity question — after the newer note, is the older note's claim false or no longer applicable, and two notes both still true are NEITHER even on the same topic — and a `supersedes` answer must name the claim in a `replaced:` field; missing/empty/placeholder reads NEITHER, which is a decision and therefore cacheable, and the NEITHER cache key prefix moves v2→v3 for it (a cache hit is a permanent skip for the life of that text). `replaced:` is the twin of resolve's `closed-by:` and is read by the SAME helpers (`resolve.ReasonedField`/`resolve.ReasonlessValue`), so a value that keeps a note in one pass's injection cannot bury it in the other's ranking; a synonym verdict is no way around the field. `VetoSupersede` is the free half, before any call: an older note stating an imperative that the newer note never names as retired or changed is settled as no-edge, and the imperative vocabulary is resolve's own (`VetoKeepImperative`, which `VetoKeep` also calls) rather than a copy, so one list protects a memory from being buried and from being demoted. Its error is in resolve's direction — a false veto leaves a stale note ranked, and #641's own "status-report-fix" fixture is what that costs, which the labeled regression set pins by name. A pair whose endpoints' scopes conflict is never classified: the scope reaches `SearchVectorScoped` so the neighbour budget counts only linkable rows, and `Run` re-checks the rule over every pair it is about to spend a call on — the reclassify path included, which is the only way a link written before the rule existed is reached at all. Beside it, at the same point and for the same reason, a pair with a KEEP-FOREVER endpoint (`retention`, see "Retention tiers") is dropped: `SelectCandidates` refuses such a pair on the fresh path, but the reclassify path re-proposes an EXISTING edge whenever an endpoint changed since the edge was written and never passes through it — so an edge written before the row was declared keep-forever would be billed a classify call and re-affirmed the first time that row was edited, which is the outcome the exemption exists to prevent. The edge is left alone: withdrawing it is `--reassess` / `ghost_link_withdraw`, and the creation pass is not where graph history is deleted. What the refusal stops is spending a call to keep it alive. The classifier is handed note text only, so it cannot see a `memories.scope` column; the guard is structural, not a rubric line. The reclassify half saves one call per endpoint edit rather than one per pass, because skip-if-unchanged already holds an untouched pair quiet. The scope refusal is not counted in `Result`: against the shipped store the query drops the conflicting rows before `SelectCandidates` sees them, so a count there would read as zero for work declined, while the veto IS counted (`Result.Vetoed`, printed) because a run that declined work it did not do must not report the same totals as one that found nothing to. An existing scope-conflicting edge is left in the graph and exempted at read time by `SupersedePenalties`, by `ghost resolve`'s supersedes piggyback, and by the two fold-target liveness checks — the piggyback is the one that would have been persistent, stamping `resolved_at` on the older endpoint. A vetoed pair's existing edge is left alone there — the creation pass is not where graph history is deleted — and `ghost supersede <project> --reassess [--apply]` (`internal/supersede/reassess.go`) is the repair path: it re-judges every live 'supersedes'/'llm' edge under the current rules and withdraws the ones that come back NEITHER, vetoed, CAUSES or REVERSED through `InvalidateLink` (which writes the `unsupersede` history row), printing each withdrawn edge with the rule that withdrew it, which half decided it (`veto, no harness call` vs `classifier`) and — because a withdrawal sweeps the pair's 'causes' edge as `Run` does on the same self-contradicting verdicts — how many `causes` rows that took (`WithdrawnEdge.CausesSwept` is the PREDICTION in a dry run and the OBSERVED count under `--apply` — a row never claims a deletion that did not happen, and a sweep that ERRORED sets `SweepFailed` and prints "unknown" instead of a count (`ReassessResult.CausesSweepFailed` counts those rows, separately from the swept ones, because "swept 0" and "could not tell" are different sentences); a `causes` VERDICT sweeps nothing, because it affirms that relation). The prediction is read through each pair's OWN endpoints (`GetLinks` on the older id), NOT through `LinksByRelationSource`: the sweep deletes by id with no project predicate, so a pair whose older note has been promoted to `_global` or moved by `ghost project merge` is still swept, and a project-scoped read (which joins on the edge's source, and a 'causes' edge's source is the OLDER note) cannot see it. A dry run reports the count it is about to print, not `Result.Withdrawn` (which is 0 by construction in a dry run — the same rule `reassessSummaryLine` follows on the resolve side), and a failed invalidation returns the edges that DID land with the error, because each is its own transaction and a later pass will not see them again. That 'causes' sweep is predicted by a read that ONLY a dry run makes: under `--apply` every row's count comes from the sweep itself, so the prediction is not read at all and a discarded read can never be the reason a repair failed (`TestReassessUnderApplyNeverReadsThePrediction`). A dry run whose prediction read fails marks the row's second deletion unknown (`WithdrawnEdge.PredictionUnknown`, counted as `CausesPredictionFailed`) instead of printing a count nobody looked for, and `SweepFailed` stays false — no write ran. A classify call that FAILED is not fatal to those rows either, and that is the direction of the fix (#699: one dead `opencode run` cost a real rehearsal every withdrawal, 76 of 87 edges waiting on a rerun, including the ones the veto had settled for free): the settled withdrawals apply, the pairs the classifier never answered move to `ReassessResult.Unjudged` with their edges LEFT ALIVE, and the pass still returns an error so the exit says "rerun me". Every open pair is unjudged, not the subset the harness named last — a call that failed answers nothing about anything it carried, and a verdict-count mismatch is the same state, so both take this path. Withdrawing is the safe direction and settling the veto needs no harness, which is what makes it the one case where a partial repair is still a repair. The withdrawal sweeps the other relation's edge too, as `Run` does on the same self-contradicting verdicts, but NOT under a CAUSES verdict: there the existing 'causes' edge may be saying something true. THIS IS THE ONE PLACE THE VETO'S ERROR ARGUMENT DOES NOT CARRY OVER: on the creation pass a false veto costs recall, here it deletes a correct edge, and since the veto is deterministic on the same two note bodies the ordinary pass re-fires it forever, so the pair cannot be re-linked until a note changes — which is why the report marks those rows. Withdrawing is only half the repair: the memory is still stamped `resolved_at`, and only `ghost resolve --reassess` can clear it, so the chain is pinned end to end in `TestReassessResolvesAChainIntoResolveReassess` `supersede.Withdraw` (`withdraw.go`) is the OTHER repair, for an edge those rules still accept: a pair that is wrong for a reason no rubric can see (the newer note is not a replacement of the older one at all) is confirmed by the classifier, so `--reassess` keeps the edge and only the caller's judgement can withdraw it. Nothing is judged there, so no harness is involved and nothing is billed — `ghost supersede <project> --withdraw <src> <tgt> [--apply]` and the MCP `ghost_link_withdraw` call the same core, through `linkCapableStore`, so an operator and an agent take one path. Its rules are the ones a delete needs: a ref is a full id or 8+ characters of one (every report abbreviates to eight, so requiring 32 would make it undrivable), matched as ONE literal, case-insensitive PREFIX query inside the project plus `_global` — which is what lets a full id of any shape resolve through the same call, and `ghost import` writes an artifact's ids verbatim, so a ref check that insisted on hex would make an imported endpoint unnameable; the 8-character floor applies to a PREFIX alone and is decided by comparing the match with the ref rather than by inspecting the ref's characters; an ambiguous ref is a refusal LISTING the matches, never a choice; a pair with no live edge is an error whose message names the target's live edges; and the WHOLE request is settled before any write, so one bad pair out of five withdraws none of them (`TestWithdrawChangesNothingWhenAnyPairIsWrong`). The edge is found through the project that owns its SOURCE (`SupersedesLinksInto`), like every other supersede reader, so no project can withdraw or even see another's edge. Under `--apply` it prints the follow-up through the SAME helpers `ghost supersede --reassess --apply` uses (`supersedeReassessFollowup` + `writeReassessTargets`, one formatter and one file writer for the two repairs, and the file's header names which command wrote it), so both name the SCOPED `ghost resolve <project> --reassess --only <the withdrawn edges' target ids> --apply` plus a `--only-file` beside it (both surfaces through `internal/followup.ResolveCommand`, which quotes a project name that needs it — there is no MCP tool for the repair, because `ghost_resolve` is the FORWARD pass and stamps `resolved_at`, so the MCP result names the CLI command and says so) — scoped because an unscoped repair re-judges every resolved memory in the project (#702 measured 143 rows proposed, ~35% stale). The list is deduplicated and holds only rows the call actually withdrew: a row it never reached has a live edge, so nothing was orphaned by it. The report itself carries no resolve hint and prints the target's own first line, so the reader can confirm the edge was the right one

- `internal/obsidian/` — One-way Markdown vault mirror (`ghost obsidian export|sync`). The store can hold ids, project names, tags and bodies Ghost never generated (`ghost import` writes an artifact's ids verbatim), so every name it builds is a name somebody else chose: `idToken` keeps the first 8 bytes of an id only when they name a single path component a person could type and hashes the id otherwise (a separator put the note outside the `Memories/` subtree prune manages and had it deleted; a tab or line break is a legal name nobody can open; a NUL failed the whole export with `EINVAL` on every run), `folderNames` replaces a folder over `maxFolderName` the same way it replaces one that would escape because `ENAMETOOLONG` failed the export just as permanently, and `hasGhostID` unquotes exactly what `yamlScalar` emits. A basename is not safe either, and for a different reason: the same slug occurs in two project folders, and a memory and a task with the same title produce the same name and can share an id fragment, so one live note anywhere in the vault would keep a stale copy alive everywhere. A key that decides what to keep should be one the system holds, not one parsed back out of a file written for a human. Every front-matter value still has to occupy exactly one line — that is what makes the note valid YAML and the ownership test's answer well-defined (it reads to the first `---` and takes the one `ghost_id:` line there) — but no value read out of front matter, forged or merely flattened, can now make prune drop a note it wrote

- `internal/reflection/` — Memory consolidation: LlmConsolidator + SQLiteConsolidator. - `internal/followup/` — the one renderer for the command that completes a supersede repair (`ResolveCommand`: `ghost resolve <project> --reassess --only <the withdrawn edges' target ids> --apply`, full ids, the project quoted through `--project` unless it is one bare shell word, and the ids quoted too — `ghost import` writes an artifact's ids verbatim, so an id is caller-supplied text like a project name. It returns TWO further values: the ids it could not carry because they hold a comma (the `--only-file` beside it reads one id per line and never splits, so that surface reaches them) and the ids it could not carry because they hold a NEWLINE, which NO surface can (`--only` splits on commas, the file is one id per line, and a `#` in an `--only-file` line is a comment only when it FOLLOWS WHITESPACE so an annotated `<id>   # note` keeps working — a selector holding a trailing comment is not a prefix and would make the repair refuse the whole file — at the cost of truncating an id containing ' #') — a memory with such an id stays resolved until the row is rewritten, and every surface says so rather than claiming a repair; the id file is REFUSED outright when every id in the set is one of those, because a file naming nothing is a list `readRefSelectors` rejects (one reader for both `--only-file` and `--mark-file`, differing only in the flag it names in its errors — a second reader would be a second place for the two to disagree about which ids a file can name). The command is EMPTY when no id is carriable, and that is deliberate in the other direction too: printing the command without `--only` is the project-wide re-judge #698 measured, and both surfaces print what comes back here as THE repair. A comma therefore reaches the id file; a newline reaches nothing, and is named. It is its own package because THREE surfaces print that command and none may render it differently: the CLI under its per-edge list, the CLI under `resolve --mark`'s report (`resolveMarkReport`, whose follow-up lists only the rows THIS call stamped — a row already resolved before the run is not something the command would change), and the MCP tool `ghost_link_withdraw`, where it is a CLI command rather than a tool call because no MCP surface exposes the repair at all — `ghost_resolve` is the FORWARD pass and stamps `resolved_at`, so pointing an agent at it would bury more memories than it restores- `internal/secret/` — Credential-shape detection for stored text (`Detect`); shape-based, never keyword-based
- `internal/provider/` — Interface contracts: LLMProvider, MemoryStore
- `internal/config/` — Layered YAML + env config (koanf). `Load` returns an error for a config file that exists but does not parse, for a `GHOST_*` value that is not readable as its key's type, and warns on file keys no `Config` field binds (env names are not key-checked — most `GHOST_*` variables are not config keys); CLI subcommands call it and fail. `LoadForHook` is the host-session path (SessionStart/Stop hooks, obsidian auto-sync, routing, the scratch budget): it reports the same problem on stderr and returns `FallbackConfig` — the compiled defaults plus the `GHOST_*` environment, i.e. every layer that does not read a file — so a typo cannot fail someone's session and cannot undo an environment opt-out. `envOverrides` lists the `GHOST_*` names the generic `GHOST_` prefix + `_`→`.` transformer cannot map, each with the parser for its key's type. `SetWarningWriter` redirects the warning sink, which `runMCP` points at its log channel; the sink is atomic because harness spawns warn from goroutines.
- `internal/procstat/` — process identity for the two places Ghost must not trust a bare PID: `StartTime(pid)` returns an opaque creation-time token — per-platform, from the `linux`, `darwin` and `windows` files plus a `!windows && !linux && !darwin` stub that returns `("", false)` — and `IsAlive(pid, wantToken, haveToken)` reports liveness from two variants only, POSIX signal 0 and the Windows handle/exit-code form. The token is opaque — never interpreted as wall-clock time, never compared across platforms or machines, only tested for exact equality against a token obtained the same way — and the load-bearing rule is that liveness FAILS OPEN: when the token cannot be read (an unsupported OS, an unreadable proc entry, permission denied) `IsAlive` reports alive, so a transient token-read failure can never flap a live process to "dead" and let `Reap` or `claimPidFile` delete what it should not. Linux's raw source is boot-relative ticks, which is not reboot-safe on its own while `.pid` files and `.owner` markers outlive a reboot, so the machine's `boot_id` is prefixed into the token. Windows treats a handle that opens with an exit code other than `STILL_ACTIVE` as not alive, because `OpenProcess` succeeding does not mean the process is still running. Both consumers go through it and neither re-implements it: `internal/mcpinit` (a `.pid` file holds `pid:token`, or a bare pid when no token was available) and `internal/scratch` (the `.owner` marker's `start` line). The extraction was forced by the second: `scratch` needs the same token but `mcpinit` already imports `scratch`, so a shared package was the only way to reuse the implementation instead of duplicating it — `mcpinit` keeps two unexported wrappers so its own call sites and platform tests did not move
- `internal/scratch/` — the temp space Ghost's LLM-harness children are confined to. The root is `<dataDir>/scratch`, or `$GHOST_SCRATCH_DIR` when set and NON-EMPTY (a blank override is treated as unset, so an exported empty variable cannot silently move the root to the process's own working directory), created 0700 explicitly because `MkdirAll` leaves an existing directory's mode alone and the override may name a pre-existing shared dir. It is under the data dir rather than the shared system temp because opencode writes a hidden ~4.7 MiB JIT-cache shared object into its temp dir on EVERY spawn and one consolidation lifecycle spawns hundreds of harness processes: left in the system temp those droppings accumulate until the filesystem fills, at which point every LLM-backed phase fails at once. `Root` resolves the data dir through `config.DataDir`, whose #721 `GHOST_DEV_FORBID_DATA_DIR` refusal sits in `config.DataDirPath`, so that refusal reaches this root too and the scratch dir cannot be planted where the store is forbidden. `Open` mints one `<pid>-<16 hex>` directory and writes a `.owner` marker (`pid=`, `token=`, `start=`); `Release` is best-effort, idempotent and nil-safe, because it also runs on early returns and on paths `Reap` may have already collected. WHICH variables a child gets is the spawn site's business — `internal/ai` pins TMPDIR/TMP/TEMP — and nothing here reads or writes the inherited temp dir, because this package must keep working when the system temp is full or absent, which is the situation it exists to survive. `Reap(maxAge)` (once per lifecycle in `cmd/ghost`, and from `ghost mcp init`'s `ensureScratchSpace`, both with a 24h age) scans the root's DIRECT entries and never the root: only entries provably created by Ghost are eligible — a readable marker, or a markerless name of exactly `Open`'s shape, and a markerless one only once its mtime is past `maxAge`, which is what protects an entry whose marker is being written right now — and anything else is left alone, because the override may point at a directory shared with somebody else. A SYMLINK is never followed, because the root is Ghost-owned but a link can point anywhere. A marked entry is owned-and-live only when its pid is alive AND, where the marker carries one, its `start=` creation-time token still matches the live process's (the same pid-reuse token `internal/mcpinit`'s `.pid` files hold); a dead pid, or a live one whose token differs, is abandoned and removed regardless of age. A `start=none` sentinel says the platform cannot supply tokens at all, so liveness alone shields it and that shield is UNCONDITIONAL — no age ceiling, no mtime consultation — because a phase timeout can be configured to 0 (unbounded) and any ceiling could delete a live invocation's scratch. Only a marker with NO start line at all predates tokens, and only that form falls back to the age backstop. `EnforceBudget()` runs before each spawn (`internal/ai`'s `harnessCommand` is its one call site) in a fixed order: measure, and only if already over `scratch.max_bytes` reap, re-measure, then warn LOUDLY through slog naming the root and the bytes-over, and record the bytes and reap count to `maintenance_runs` when the check fired at all. Every failure path warns and RETURNS: enforcement must never BLOCK a spawn (maintenance is not stopped by its own hygiene) but must never be quiet either. `scratch.max_bytes <= 0` disables the check; an unset key is the compiled 512 MiB default (`config.DefaultScratchMaxBytes`)
- `internal/secret/` — credential-shape detection for text Ghost is about to store, and the only place that answers "does this value look like a secret". It answers from the SHAPE of the value and never from the words around it, because a memory store is prose ABOUT credentials ("rotate the deployment password quarterly", "the tokenizer keeps a 30k vocabulary" are ordinary knowledge) and a keyword heuristic refuses all of them — `internal/reflection`'s `looksLikeSecret` asks the different question (is this text safe to replay into every project) and must never reject a save, only narrow a scope. So every rule needs a value: a fixed provider prefix at a realistic length, a complete PEM block, a labelled Cardano key field, an unbroken credential-length hex or base64 run, a whole word sequence from the embedded BIP-39 list, or a credential-shaped NAME assigned to a value that could not have been written by someone documenting the setting — every length floor chosen against the longest innocent value of the same shape (`longHexFloor` 128, so a 32-byte Cardano public key, a payment credential and a stake credential all stay storable; `mnemonicWords` 24, not 12, and the cost is a documented false negative). A `Finding` names the format and NOTHING ELSE — never the matched text, because a Finding reaches the log file, the saving agent's context and a third-party model's prompt, so quoting the value relocates the secret instead of containing it — and the rules are ordered so the first match wins and a specific format must precede a general one. Precision is not optional: the refusal is loud and blocking, so a false positive trains a user to route around the control within a week. The performance shape is measured and pinned rather than assumed (no keyword prefilter, because `LiteralPrefix` returns empty for a pattern starting with a word boundary, so a derived prefilter would be useless and a hand-written one a silent false negative — wrong in the strict direction, and a rule that never fires in this control is indistinguishable from a rule that does not exist; `TestDetectIsLinearInLineLength` and `TestDetectDoesNotRescanTheLinePerAssignment` hold the line there). The writers that reach it are named at each call site rather than being all of them
- `internal/repo/` — repository identity read out of the filesystem, one function: `DetectRemote(dir)` runs `git -C dir config --get remote.origin.url` under a 2s `detectTimeout`. It exists to keep process-spawning out of `internal/memory`, which is deliberately a pure storage layer that never spawns a process, while the only place that can say which repository a path belongs to is a caller willing to ask git — so the capability is INJECTED rather than called: `cmd/ghost/main.go` hands this function in through `memory.SetDetectRemote`, `nil` restores a no-op returning `""`, and a store built without one resolves exactly as it did before repository identity existed. The load-bearing rule is that every failure returns `""` rather than an error — not a repository, no `origin` remote, an unreadable directory, no `git` binary, a hung `git` — because detection runs on save paths and "no repository known" is a legitimate answer, not a reason to fail a memory write; the timeout is that same rule applied to a network-mounted worktree or an NFS-backed checkout, which must never stall a write. `-C` walks up to the enclosing repository, so a path pointing inside a checkout still reports that checkout's remote. `internal/mcpserver` calls the same detector, and only when a `project_id` contains a path separator — a project NAME says nothing about a repository, so an ordinary named save never crosses the boundary, which is what lets its tests replace the package var and prove it. `ghost project bind` passes the same function, so the remote recorded there is the one resolution later compares against rather than a second spelling of one repository
- `internal/selfupdate/` — `ghost upgrade` self-update from GitHub Releases. The PRODUCER side of release authenticity (#694) is asserted from here, not from the workflow: every asset `.goreleaser.yml` publishes and every zip the `plugin` job uploads carries a GitHub artifact attestation minted by `actions/attest-build-provenance`, and that action is pinned by full commit SHA because it is the one release step whose output clients are told to trust (`TestReleaseJobAttestsExactlyWhatGoReleaserPublishes` DERIVES the expected subject paths from `.goreleaser.yml` rather than transcribing them, in both directions, so a new archive format or a renamed checksum file cannot merge as an unattested gap; `TestPluginJobAttestsExactlyWhatItUploads` reads the `gh release upload` step and compares; the two attestation scopes are job-scoped, never workflow-scoped, or the `docker` job inherits an OIDC token). The plugin attestation runs BEFORE `gh release edit --draft=false`, so a failure leaves an unpublished draft a re-run completes rather than a public release whose zips have no provenance — that ordering is asserted too, because it is the difference between a recoverable and an unrecoverable release. A DERIVATION only catches what it derives independently: an extra file's path is taken verbatim from `release.extra_files` because GoReleaser resolves that glob from the project root and never copies it into `dist/`, `TestEveryLiteralAttestationSubjectExists` then asks of every literal subject path whether it names a file that will exist at attest time (a repository file, the checksum file, or one this job's own steps build), and `TestTheReleaseTimeGuardFailsOnASingleZeroMatchPattern` EXECUTES the workflow's guard step so a guard that never fails is not mistaken for a guard. That last pair exists because `actions/attest-build-provenance` only errors when the COMBINED glob result is empty, so a single wrong path is dropped silently and the release ships an asset nobody attested. The CONSUMER side lives in the same package (`attestation.go`) and has three load-bearing rules, all of them about which states may be collapsed into which. (1) Nothing is hand-rolled: the bundle is parsed and the certificate checked by sigstore-go, and the trust root comes from that library's TUF client — a hand-written chain check is exactly the thing that is subtly wrong in ways no test here would catch, and the whole value of an attestation is that it is a signature nobody in this repository made. (2) The three failures are NOT one failure, and the boundary between them runs through the HTTP status code, not through the call site. `ErrNoAttestation` (the service holds none) is distinct from a 500, an unparseable response, a 404 on a presigned `bundle_url` and a trust root that would not fetch, because only the first is a fact about the release and only the first is something a user can permanently do anything about; the verifier reports the first as `AttestationAbsent` and everything else as `AttestationUnreachable`, and a client that collapsed them would turn a Sigstore outage into a permanent belief about a release. `attestationGet` takes `absenceOn404` for exactly this reason: ONLY the index's 404 is the answer to "does this release have an attestation", so a blob 404 must not be — and it is a parameter rather than a convention because a blob's presigned lifetime has nothing to do with whether the release is attested. A member that cannot be read is collected as a reason instead of aborting the lookup, so a release with several attestations and one dead blob link still yields the bundles the others carried; the reverse would let anyone who can publish one extra unreadable attestation make a release uninstallable. `AttestationUnverifiable` — a bundle exists and did not verify — is fatal whatever flags exist, because a loud override that can wave through a failed verification hands the feature to anyone who can mint one bundle of their own. (3) A refusal never quotes the identity that was REJECTED. A certificate SAN is attacker-supplied text and sigstore-go's own mismatch error prints the value it got, so `classifyAttestationFailure` reduces every failure to this package's own words and the required identity is named instead. The same rule reaches the reason strings: a blob 404 must not leak the absence wording into a message a user reads, because a correct state classification with a misleading sentence is the same defect told differently. The cutover constant `FirstAttestedVersion` is applied inside `AttestationVerifier.Check` rather than by its callers, so no call site can forget it, and an unorderable version counts as REQUIRING an attestation — "cannot tell" must never read as "old enough to skip". The trust root is fetched only once a bundle is in hand, from a data-directory resolver rather than a path, so a pre-cutover upgrade pays neither a TUF round trip nor the data-directory guard — and it is fetched under its own `attestationTimeout` rather than the caller's, because the caller in production is the whole 12-minute run budget, which is both a long wait and the wrong explanation for a stalled Sigstore endpoint.
- `eval/storyline/` — LOCAL-ONLY multi-session storyline runner (#339), reusing `eval/cycle`'s substrate (scratch XDG roots, seeded opencode auth, the built `cmd/ghost` binary, the embedding drain, the chronology restamp) rather than extracting it: the duplication is deliberate, a refactor would not have fit the diff, and a shared helper that both runners depend on is a follow-up, not a prerequisite. Five rules are load-bearing. (1) **The grade reads STORE STATE, never CLI stdout** — `memory_links` rows and `memories` stamps; stdout is kept in the report because a warning is evidence, but a phase that prints a verdict it did not write cannot pass a check. (2) **The block is rendered BEFORE that stage's own records are seeded**, so what a session received is exactly what sessions 1..N-1 left behind; seeding first hands every session its own answer and makes `carry-forward` pass for the wrong reason. (3) **A supersedes edge's DIRECTION is read from the store's `created_at` stamps, not from the ids' order** — and a pair whose chronology cannot be read FAILS rather than passes, because the arc's direction is the one thing a direction-blind check would hide. (4) **Every id the grade resolves came off the `Result`, the OPENING records' included** — they are saved before any session and belong to none, and `Validate` lets a storyline reverse one (`stageOf` answers -1 for an opening record, so the "must be a later stage" rule passes). An id held only in a local slice makes `supersede-edge` fail on a store that got the edge perfectly right, which is a runner defect wearing a finding's clothes. (5) **The model is resolved ONCE, in `resolveModel`, rather than at each use** — `internal/ai` reads `GHOST_OPENCODE_MODEL` out of the RUNNER's own environment when the pin is empty, and `scratchEnv` rewrites only the CHILD processes' environment, so a stale export would decide the sessions while the phases used the default and the report named a third model. Beyond those five, two limits bound what a passing run can claim: the `stale-original` match is deliberately narrow (the record's own verbatim text) and the opt-in `-judge` covers paraphrase; the arc's lifecycle runs AFTER the last session by construction, so the runner shows what the block does with a reversal already stored, not what a supersede caught mid-arc would have changed. Nothing here is wired into CI (#338), and a non-zero exit is a finding about Ghost, not a runner bug

## Key patterns
- Memory categories: architecture, decision, pattern, convention, gotcha, dependency, preference, fact
- Untrusted parse surfaces (`claudeimport`, `hostevent`, `obsidian`): a value somebody else wrote is DATA. It is stored exactly as parsed, it names at most one path component inside the directory its surface owns, and it never decides the parse — the parser's own vocabulary does, and a payload that does not fit is rejected or mapped to the documented fallback, never obeyed. `internal/adversarial` states the invariant once and holds the corpus all three suites drive (#585). Two rules that look like filters and are not: a planted payload stays retrievable (hiding the tampering is worse than showing it; quoting into the data block happens on the way out), and every `hostevent` refusal fails open, because "allow the stop" is the only response the hook contract emits. Defects here were silent rather than loud — a front-matter line past `bufio.Scanner`'s default cost a memory its category, a separator in a record id cost it its note, a quoted `ghost_id` cost it a second prune pass — which is why each is a fixture and not a line of prose
- Backup and portable transfer: `ghost backup` is `Store.Backup` → `memory.vacuumInto` (SQLite `VACUUM INTO`, the same one implementation the pre-migration copy uses), so both claim the destination with `reserveBackupPath` (a `0600` `O_EXCL` create, before any byte is written) and both refuse an existing path. `VACUUM INTO` names no mode, so creating the file first is what keeps a full copy of the memory database out of a group-readable window on an `--out` outside the `0700` data directory. The write lock is held for the vacuum and nothing longer. It counts the snapshot by opening the written file read-only, never the live one — the counts a restore is checked against have to describe the file that was written. The portable artifact (`internal/portable`) is the other half: `memory.PortableProjects` / `PortableMemories` are separate reads because `ListProjects` has no `repo_remote` and an artifact needs the columns in an order it owns. (The other reason this line used to give — that the ordinary list readers drop the validity triple — stopped being true when `memory.Memory` gained `valid_from`/`valid_until`/`verified_at`: retrieval hydrates all three, and `PortableMemories` selects them for itself.), and `Import*` are separate writes because no existing writer can preserve an imported id, `created_at` or pin. Every `Import*` takes an `apply` flag, so a dry run runs the same validation as the run it previews
- Time-decay scoring: convention/preference/fact never decay; architecture/pattern 45-day; decision/gotcha/dependency 30-day
- Retention tiers (schema v19, #587): `memories.retention` is `session|project|persistent` with a CHECK, default `project`, and `memories.expires_at` is DERIVED for a session save (now+`SessionTTL`) and stated by nobody else — so no save can schedule the memory it just wrote for deletion, and a NULL expiry is the unprunable direction. `migrateV19` adds both columns and updates no row: a memory that persisted until somebody resolved it WAS a project memory, which is what every pre-v19 row reads as afterwards. `memory.retention` (the column, in Go) is not `Memory.Retention` (the field): the field normalizes an unset column to `project` in `scanMemories`, because one reader forgetting the column would otherwise hydrate a session row as "no tier stated" and a prune could not see it — which is why the six full-row readers share ONE list (`memoryColumns`, plus `memoryColumnsPrefixed` for the two FTS queries that alias `memories`). `DecayFactor(category, retention, pinned, ageDays)` is the Go mirror of `DecayRankingSQL` and both carry the bounded session decay (tau 7 days, floor 0.5, formatted from the same constants); a durable row's score is exactly what it was before tiers, which is the whole reason the multiplier is 1.0 there, and `explain` names it per row as `retention_factor`. `persistent` is the one tier a default may not take back, and the exemption is asked at every WRITE and every ranking consequence, not only where a pass selects inputs: `ReplaceNonManual` (snapshot, replaceable set, concurrent-save set, output delete) — and a consolidation's fresh INSERT INHERITS its tier, `mergeRetention` over the `ReplacesIDs` sources' current tiers with `expires_at` from the same `sessionExpiry` rule (#773), beside `inheritedClaims` and for the same reason: an emission inherits rather than invents, and reflection never states a tier, so a merge of two `session` memories used to come out `project` with no expiry and nothing would ever prune it (#587's tier, defeated by consolidation). The fold runs over the SOURCES alone — the emission's own `Retention` is only the fallback for an emission with none, because `NormalizeRetention("")` is `project` and folding that in would raise every merge — and a `persistent` source is in no replaceable set but CAN be named in `ReplacesIDs`, so reading the sources is what keeps the successor from being shorter-lived than the one row nobody was allowed to consolidate. A REUSED row keeps its own tier only while the emission re-states that row ALONE, and RAISES it the moment `ReplacesIDs` names a source beside it (`raiseReusedRetentionTx`, #773) — those rows are merged into this one, so a session row absorbing a project one would otherwise take the project's knowledge to its own expiry. The raise is its own statement and runs for all three reuse branches INCLUDING `reuseChangesNothing`, which writes nothing else: a verbatim re-emission is the commonest case and the one that leaked. It clears `expires_at` on leaving the tier and NEVER renews one that stays, because a reflect run re-stating a row is not a new assertion of the fact by anybody — refreshing there would make one applied reflect per day a way to keep a conversation-scoped memory forever. That is the deliberate difference from a FOLD, which is a new assertion and does refresh (#772), and the reuse raise is skipped entirely when the set names no other source rather than falling back to the emission's silence, which would read as the project default and make every session memory durable, `RestoreSnapshot`'s UPDATE, `ResolveCandidates`/`ResolvedCandidates`/`SetResolved`, `supersede.SelectCandidates` (before the classify call, so the verdict is not paid for), `SupersedePenalties` and `DemotionPenalties`, which take the caller's PROTECTION map rather than a list of pins — because a stale `duplicate` or `supersedes` edge would otherwise sink a row every other pass spares, and because both lookups run on read-only handles (`GetTopMemories`, `explain`, and the assembler's near-duplicate stage over a passive bucket), where a statement naming the column fails in full. The two maps are NOT the same: `DemotionPenalties` (the near-duplicate demotion) protects a plain `pinned` row the way it always did before tiers and extends that to keep-forever rows, while `SupersedePenalties` protects ONLY the `persistent` tier — a `supersedes` edge asserts that one claim replaced another, and a pin keeps a row visible without declaring its claim current, so a pinned supersedes target sinks exactly as it did before #587 (the pin-sparing supersede variant is issue #739, kept out of the tier PR; `TestAPinDoesNotStopASupersedesEdge` and `TestASupersedesEdgeDoesNotSinkAPersistentRow` pin the boundary). EVERY caller builds the map from rows it has already read, and a caller handed ids it did not hydrate is a caller that cannot protect them (`TestTheDemotionLookupsDoNotNameTheTierColumn` drops both v19 columns and calls both). A fold RAISES the surviving row's tier and never lowers it (`mergeRetention`): a protection the caller asked for and did not get is a false report, while lowering would let a `session`-tier restatement schedule another memory's durable row for deletion. A fold also REFRESHES the expiry whenever the row's RESULTING tier is `session` — on the ordinary path and the `FoldOnly` path, and whether or not the tier moved, because a session→session fold is what “the same fact restated” looks like and `raiseRetentionTx` returns early on an unchanged tier (#772). Nothing else moves with it: `updated_at` and `last_accessed` are load-bearing for the decay recency and the `--skip-unchanged` fingerprint, and a fold is not a re-save (the same reason `pinMemoryTx` leaves them alone), and a durable row is never HANDED an expiry in either direction (`TestAFoldTouchesTheExpiryOnlyWhileTheRowIsStillSession`; a multi-row prune fixture therefore has to age every row AFTER every save, because the next save's dedup probe folds into the previous row and refreshes it). `ghost prune` is the ONLY thing that removes a `session` row, it is never run for you (no lifecycle phase, hook or scheduler calls it), the dry run is a read-only PREVIEW built from the same predicate, scope and order every apply batch re-derives (so it cannot describe rows the apply would not select), an APPLIED report is counted and listed from `RemovedIDs` rather than from the candidate list — every batch re-derives the predicate under the write lock, so a row a save pinned, re-tiered or re-saved between the preview and its own batch is correctly spared and is STILL in `Candidates` (`TestPruneSparesARowThatStoppedMatchingMidRun` puts such a write in that window through a tombstone trigger, because the `pruneBeforeDelete` seam cannot: it runs inside the batch transaction, which both holds the write lock and has already chosen the batch's ids), the rows it did not take are NAMED as spared and the line names the change rather than the outcome (a write that removed the row outright leaves nothing behind), the apply deletes in bounded batches (500 rows per transaction, each batch with its own tombstones and its own rollback), and every removal appends a `delete` tombstone before the DELETE. The grace is measured from ONE expression, `pruneActivitySQL` = `COALESCE(last_accessed, max(updated_at, created_at, expires_at))`, shared by the predicate, the candidate's `GraceFrom` and the removal order so the three cannot describe different runs (#772) — the report's OTHER stamp, `ActivityAt`, is a deliberately NARROWER term, `COALESCE(last_accessed, updated_at, created_at)` with no expiry, and the divergence is the point rather than a second spelling to reconcile. A recorded access is still preferred when it exists, but nothing in production writes `last_accessed` (`Touch` has no caller), so in practice the grace is measured from the row's last WRITE **or the expiry that write refreshed** — `max` rather than a fourth `COALESCE` term because `created_at` is `NOT NULL` and a trailing term is unreachable, and a row reinforced an hour ago whose `updated_at` is a month old is inside the grace rather than prunable the moment its fresh expiry arrived (`TestPruneMeasuresTheGraceFromAnExpiryAFoldRefreshed`). The report carries the two readings as SEPARATE fields, `PruneCandidate.ActivityAt` and `PruneCandidate.GraceFrom`, and `printPruneRow` labels them separately, because one field cannot honestly carry both: the basis includes an expiry, which is a value derived FORWARD at save, so projecting it under the name "last touched" would claim the row was touched at the instant it stopped being wanted — and on a row never written to since its save that instant IS the expiry, so the line would print one timestamp twice under two labels. The basis is omitted when it repeats the expiry, which is the ordinary case (`TestPruneReportsTheGraceBasisSeparatelyFromActivity`, `TestPrintPruneNamesTheGraceBasisWithoutClaimingItWasATouch`). The consequence is a tier EFFECTIVE LIFE of `SessionTTL` + grace rather than grace — an untouched session memory saved at T is removed at T + 24h + 7d, not T + 7d — which is the safe direction and is the point: the row is wanted until its expiry, and only then does the week start. Every statement of the term carries the expression, and a rule that changes ships in all of them (#772): `pruneActivitySQL` in `internal/memory/prune.go`, this bullet, `DefaultSessionGrace`'s doc in `internal/memory/retention.go`, `docs/cli.md` and `docs/architecture.md`. - A RUNNING server re-checks that on EVERY write, because the open-time check answers a question that a later migration invalidates (#746): a `ghost mcp` opened the store hours before a newer binary migrated it underneath, and kept writing for ~40 hours with no history row, no version for an edit, and no tombstone for a delete. There are TWO seams, because a check that only guards a transaction misses every write that never opened one: `memory.beginGuardedWrite` for a write TRANSACTION (what `beginWrite` delegates to) and `memory.execGuardedWrite` for a single AUTOCOMMIT statement. The second is not a nicety — the issue's own reproduction is a save, and a lone `Exec` on the pool is how a lone statement reaches SQLite; a version that was cached "somewhere per write" and a statement that never asked are the same hole. `TestEveryWriteRefusesANewerStore` walks the package with go/parser and requires every write to be one of the two or to carry a recorded reason, so a new write path cannot opt out by accident. Classifying writes by METHOD NAME alone is not enough to earn that claim, and the first version of this test was wrong in exactly that way: `CreateTask` (behind the `ghost_task_create` tool) and `IncrementInteraction` both wrote through `QueryRowContext` — a `RETURNING` clause, which is a write the method name denies and the SQL admits — and both succeeded against a store a newer Ghost owned while the scan passed. So the scan now reads the STATEMENT for a `Query*`: a leading word on a small read-only allow-list (`SELECT`, `PRAGMA`, `EXPLAIN`, `VALUES`) is a read, and everything else — every write keyword, `WITH` (which reads like an opener and can introduce an INSERT), and any statement text the scan cannot resolve at all — is a write needing a seam. Resolvable means a literal, the format string of an `fmt.Sprintf`, a concatenation rooted in either, or a name bound to one, read from its FIRST binding only because `+=` cannot change the leading word; a variable assembled anywhere else is unresolvable and therefore a write. `TestTheScanCatchesTheWriteShapesItWasBlindTo` pins each of those shapes against synthetic source, `TestTheScanStillCallsAReadARead` pins the other direction so the holes cannot be closed by calling everything a write, and `TestOnlyTheMigrationIsExemptByFile` keeps the whole-file exemption a single named decision rather than a shape that spreads. The scan also unwraps a parenthesised receiver and follows a bound method value (`f := s.db.ExecContext`), both of which reached SQLite with no selector at the call site; it tells a transaction from a statement the other way round, following `*sql.Tx` parameters, the values a tx-returning function hands back, and the executors and prepared statements derived from one, and it treats anything it cannot PROVE is a transaction as a write — the bias is deliberate, because the cost of guessing wrong is a failure naming a line and the cost of guessing the other way is a silent hole. Exemption keys are receiver-qualified, because this package declares a free function and a method with the same bare name and a key that named both would exempt both. `pinMemoryTx` therefore takes a `*sql.Tx` rather than the `sqlExecutor` interface that also admits a handle. The check runs AFTER `BeginTx` and THROUGH the transaction, which is what makes it race-free rather than merely likely: the DSN asks for BEGIN IMMEDIATE, so the write lock is already held, and a migration is itself a write that needs the same lock — the window is closed, not small. It is not a property a test can pin, and the variant that looks equivalent is wrong twice over: a pre-BEGIN read leaves the gap (and on this `MaxOpenConns(1)` pool it DEADLOCKS rather than racing, since the open transaction holds the only connection the probe would need). READS keep working, because refusing them would turn "restart your client" into "you cannot search"; a `ReadOnly` transaction is exempt for the same reason and the scan says so explicitly. The cost is one `PRAGMA user_version` per write and THERE IS NO CACHE, which is a decision rather than an omission: the pragma that looks like a change counter, `PRAGMA data_version`, is a per-CONNECTION counter rather than a property of the file, so on a connection the pool replaced underneath a long-lived server it can carry the value the previous one had (measured: two handles on one file both report 2, and a brand-new database also reports 2), and a cache keyed on it answers "unchanged" for exactly the stale write it was meant to prevent. What it saved was a memory read of a page the open transaction already holds. A probe that FAILS refuses the write and says which probe failed: an unreadable version is not a licence to write, and not a licence to claim the store is newer either, since that claim sends an operator hunting for a build that may not exist. `ErrStoreNewer` names both versions and says to restart the CLIENT rather than to upgrade, because the binary on disk may already be current and the running process is the stale half — an operator told to upgrade runs `ghost upgrade`, watches it report "already up to date", and learns nothing

An operation id may echo the prompt's own `id:` label, which is stripped rather than failing the pass. Everything else is strict, because a partially-understood operation list is a corpus rewritten as if the model had said something else: an unreadable line, an id Ghost did not feed the model (compared case-insensitively, never by prefix), an id claimed twice, a supersession whose target the same response does not carry forward, or a response with no `ops` array at all each fail the whole response so the tiered consolidator falls through to SQLite. A rejection costs ONE extra call, not the pass: the LLM tier re-reads the same prompt once with the reader's own complaint attached, and the second answer is read under the same strict rules — a re-read, not a repair, so there is still no fuzzy id matching, no prefix completion and no application of the answer just rejected (the pass-through above is what makes discarding it lossless). Two rejections fail the run with the SECOND complaint; a transport failure is not a rejection and is never retried here; the first complaint is logged at WARN and the turn is reported as `repair: 1` on the `Result:` line, which IS the append-only lifecycle.log on the unattended path, so a benchmark counts the token once — against the `Result:` lines, with the WARN line the record for a run that repaired and then failed outright (#689). The complaint has TWO renderings because the line it quotes is model prose over stored memory: `Error()` carries the clipped operation line for the person and the repair prompt, `opRefusal.Safe()` withholds it for the log and keeps the reason and the id — the same reason the three other lines the tier writes go through `previewContent`. TWO log sites use it: the tier's own WARN (`readerComplaintForLog`, fail-closed) and the tiered wrapper's `consolidator failed, trying next tier` (`safeTierError`, which redacts a refusal but passes a HARNESS failure through unchanged, because "signal: killed" is worth telling apart from a refused answer) — and on a manual `auto` run that wrapper's line lands in the log with no failure anywhere to explain it. TWO things are deliberately NOT redacted, and do not read the seam as a guarantee: a harness failure is not value-free either (internal/ai builds it from the child's own output, and opencode's stdout stream carries the model's `text` events — pre-existing and #540's deliberate trade, since the child's explanation is what made those failures diagnosable), and `runReflect` still prints the full refusal on its `error: consolidation failed:` line, which on the unattended path is lifecycle.log, the phase tail and the next session's maintenance alert (300 bytes of it). Every model-supplied fragment interpolated into a complaint is clipped at that point (`clipOpText`), or a `drop <id> reason: <a paragraph>` puts a paragraph into a prompt, a log and an error message — and THAT CLIP IS ALSO WHERE THE VALUE GATE RUNS: SIX reasons quote a model fragment (parseOpLine's unreadable drop tail and unknown verb; executeOps' unknown id, unknown superseded-by target, doubly-claimed id, and not-carried-forward supersession), all six routed through `clipOpText` at six call sites and eight invocations, enumerated in the source so the list can be audited against the code. That gate probes ALL THREE SPELLINGS (as written, lower-cased, upper-cased), and the two folds are what cover the case-SENSITIVE rules, which split by literal case — `gh[pousr]_` is lower, `AKIA|ASIA|ABIA|ACCA`+16 and `AGE-SECRET-KEY-1…` are upper. All three are reachable and each hides a token from the others: the parser upper-cases a supersession target (hiding a `ghp_…` from an as-written-only probe) while the free-form drop tail is probed in the model's own spelling (hiding a lower-cased `AKIA…` from a lower-fold-only probe, and folding that down is a no-op). The as-written probe is not redundant either — it is the ONLY one that reaches the mixed-case literals below, which is why `parseOpLine` keeps a raw copy of the verb instead of gating the folded one: lower-casing a token before the gate sees it turns a mixed-case literal into a shape no probe recognises. A stored id is safe here for two separate reasons, both from the detector's own constants: 32 hex characters is under the two bare-hex floors (`cardanoKeyMinRun` 68, `longHexFloor` 132) though above `assignedSecretFloor` (20), and it carries no provider prefix and no `key: value` assignment, which is what every remaining rule needs. `TestClipOpTextStillGatesARealId` pins that. KNOWN RESIDUAL, not closed: the MIXED-case literals (google-api-key `AIza…`, pypi `pypi-AgEIcHlwaS5vcmc…`, JWT `eyJ…`, PuTTY `PuTTY-User-Key-File-`) match ONLY the as-written probe, so a re-spelled one (`aizasyd-…`) is caught by no fold — closing THAT would mean lower-casing the rules in internal/secret, which changes what they match everywhere including the write boundary, so it is a change to that package, not to this probe set. Each of the three probes has a test that fails when it is removed, and `TestReaderComplaintGatesAMixedCaseLiteral` covers the as-written probe and the raw verb together rather than describing one, and a `drop <id> reason: <credential>` is refused BECAUSE the tail is free-form, so the value is in the reason. `clipOpText` therefore applies the same `secret.Detect` gate `previewContent` does, before the clip; a stored id is 32 chars (`hex(randomblob(16))`) so 60 never truncates a real one. A rewrite fixture cannot catch this class — its replacement text is inside the line that IS withheld. `ReflectionResult.RepairTurns` is per RUN, not per tier: `TieredConsolidator.Consolidate` carries a discarded tier's repair turns onto whichever result survives, so a run that repairs and then falls through to SQLite is still visible. The grounding check (`internal/reflection/grounding.go`) is the other half: a merge or rewrite that introduces a path, hash, version, hostname or number found in none of its source ids is REJECTED and its sources are emitted unchanged — the output is never repaired, because Ghost cannot know which side of a corrupted identifier (`2.BeXIAhbj.js` vs `2.BeXIAhbq.js`) is true, and a wrong specific is stored as fact forever. That is also why a `rewrite` fixes a CLAIM and never a specific: the corrected value would be an identifier the source does not contain, so the prompt asks for `keep` (or `drop`) instead and the check is never asked a question it must refuse. Ordinary prose is not an identifier: a merge that needs a new connective word is a legitimate merge, and a bare proper noun the model misspells is outside these classes
- Reflection input accounting: `ghost reflect` prints a section after the result list that accounts for EVERY input id (#684), identical for a dry run and for `--apply` and printed BEFORE the write so a dry run previews it exactly. The invariant is a partition: each input id appears in exactly one line or one count and EVERY count is a count of ids — a merge names any number of sources, so `Merges (3)` over one three-source merge is right and the count of operations is not — so an operator (or an independent judge) can add the numbers up to the input total, and the test asserts the quoted ids plus the two counts ARE the input set with no id twice AND that the section's own headers sum to the input total. The one place a line quotes an id it does not account for is a `superseded by` reason, which names the successor that replaced the row: that successor is accounted for by its own bucket, so the accounting is per input id and not per mention. It exists because the report used to list only what the corpus BECAME — an input a merge consumed vanished from it, so a merge and a loss printed identically, and the applied run recorded the answer in `memory_history` while the preview showed none of it. The truth lives in `reflection.AccountInputs` (`internal/reflection/accounting.go`), a PURE function of the result, because the records about a round belong beside the round; `reportInputAccounting` (`cmd/ghost/reflect_accounting.go`) only formats, and is a named function because `runReflect` calls `os.Exit`. A merge prints `new <- <ids> (<bytes> B from <bytes> B)` and NOT a successor id: the row does not exist until the apply writes it, and `memory_history`'s `related_id` is where the identity becomes visible, so the section cannot name an id that is not knowable yet and a dry run is still an exact preview. The buckets are the result's OWN records, which is why three of them had to be added: `Kept` (an explicit `keep`, otherwise indistinguishable from the pass-through), `Drops` (every explicit drop with its reason — an `obsolete` drop names no successor, so before this the result said NOTHING about the id it disposed of) and `Refusals` (a grounding-check rejection with the ids it kept and the identifiers that caused it, which used to be a log line inside the tier). Like `Replacements`, all three are RECORDS: nothing acts on them, and the drop guard still audits every disposed row on its own evidence. The sixth bucket, **deleted**, is the set of rows an apply REMOVES, one line each with its reason, and it is counted by the replace's own reuse pass rather than by whether the row's text is still in the result. `ReplaceNonManual` reuses stored rows by byte-identical content and claims ONE per emission — the row in the same category, else the oldest, which is why the claim is re-implemented in `claimedRows` over `(created_at, id)` — and deletes every candidate left in the bucket, so two inputs holding the same bytes both have their text in the result and only one is still there afterwards. Keying on the text called BOTH of them carried, which is this report's own defect pointed the other way (#684 review, a blocker). The two reasons are different outcomes: a row nothing carries is a loss, a row whose identical twin was reused is a deduplication whose knowledge is still in the project, and collapsing them is the confusion the section exists to remove. Every id a line prints is the STORED spelling, resolved through the input map rather than echoed from the record: `memIDKey` compares case-insensitively so a response may spell an id any way, and the parser normalises only a drop's successor target (a stored id is `hex(randomblob(16))`, which SQLite renders UPPER-case — measured on a real store, not read off the schema). A guard verdict annotates the line that named the id, by COUNT rather than by id (the line already names them, and a second mention would break the one-account contract), and says `re-added` or `--allow-drops accepts the deletion` so a drop line cannot be read as a deletion that did not happen. `--full` removes the 120-byte preview everywhere in the report through one `reflectTextLimit` seam, is display-only, and is deliberately not on the unattended lifecycle path whose stdout is an append-only log
- Hybrid search: 70% vector (cosine, Ollama) + 30% FTS5, RRF fusion — window selection is `Store.fuseAndRank` delegating to `selectWindow` (scope narrowing, keyword reservation, final cut), which every production search reaches including the FTS-only degenerate path; `FuseAndSelectWindow` is the exported entry point over the same seam, called only from the fusion tests. Explain mode does not RE-DERIVE any of it: `SearchParams.trace` (an unexported `*searchTrace`, nil everywhere but `ExplainSearchScoped`) is written by the stages themselves — the leg ranks and the vector cosine in `fuseCandidatePool`, the scope verdict in `scopeEligiblePool` (for the DROPPED candidates too, which is the structural fix for #571: explain reports the decision window selection made, so the two cannot disagree), the fused base and the status factor in `demoteStatus`, the two sides of the one multiplication (the product is not recorded — it is exactly that product, and the payload note tells the reader to perform it), the reservation exchange in `selectWindow` (both the promoted row and the one whose slot it took), the decay factor and the CLOCK in `decayRank`, the floor verdict in `searchHybridLegs` where the floor is applied, and the penalty counts plus their attributed counterpart ids in `supersedeVerdicts`/`nearDuplicateVerdicts` — one edge read each, so the id explain names is the id the demotion chose. Every stage already received `p SearchParams`, which is why the trace rides on it rather than as a new argument: a separately threaded trace is one a future stage can forget to accept, and a stage that forgets is a stage whose decisions explain cannot report. `TestExplainScoreIsTheScoreTheRankingUsed` pins the property by comparing explain against `Store.Candidates`, the other entry point into the same seam. A signal the ranking does NOT apply is reported as not applied and never given a contribution to fill the field: `confidence_contribution`, `provenance_contribution` and `validity_penalty` are 0 and `provenance_weight` is `"off"`, with a note per payload saying so — a multiplier that does not exist reported as 1.0 would read as "provenance was weighed and found neutral". Validity is a reported state read through `memory.ValidityState`, the ONE rule the assembler's validity stage also delegates to (it used to hold a second copy, and two copies is two answers to "may this row be used"). The payload is bounded at 150 CANDIDATE rows (`explainMaxRows`), the tool's window ceiling being 100 and the answer never being part of the budget; the cut spends itself on excluded candidates and never on a returned row, and it is marked in a `truncation` FIELD rather than a note, because a note list is bounded from the end and a short list that looks complete is the failure the marker exists to prevent. Status demotion (`statusDemotionFactor` and the `resolvedDemotionFactor`/`globalDemotionFactor` constants in `internal/memory/demotion.go`) multiplies a resolved row's fused score — and a `_global` row's when a specific project is searched — by 0.5 inside `fuseCandidatePool`, before the cut, so it owns membership as well as order; it scales the score rather than dropping the row, so both stay searchable, and explain reports the same number as `status_factor`. With k=60 the factor effectively ranks a demoted row below every live candidate the legs fetched (a halved rank-1 two-leg score of ≈0.0082 sits under the 0.7/80≈0.0088 floor of the deepest vector row in a default window), but it only reorders what the legs fetched — each leg pulls limit*2 rows from the project plus `_global`, which counts against that budget, so a short project result set still fills with demoted `_global` rows. The keyword reservation skips rows whose status factor is below 1 (raw rank and the demoted score would otherwise disagree), and injection still never reaches FUSION on either path — `loadSessionPassive` (`internal/mcpinit/session_passive.go`) assembles the session-start digest, `Store.GetTopMemories` backs the MCP tool surface, both filter `resolved_at IS NULL` — so no factor reaches injection. It will not reach fusion when the digest moves onto the seam either, and that is deliberate: the status factors scale a FUSED score, and a passive retrieval has no fused score to scale. A passive bucket states its own order instead (`decay`, or `pinned_importance_updated` for `_global`), excludes `resolved_at IS NOT NULL` in SQL, and selects over a window rather than over a fusion — so the resolved/global demotion has nothing to demote and adding it there would be a second ranking nobody measured. What the digest does share with the tool surface is the scope rule and its label: the block prints it with `assemble.ScopeLabel` — the same label a search line carries, so the two cannot spell one scope differently — and its fetch is narrowed by `injection.session_scope` inside the store's passive statement, using `memory.ScopeMatchesSQL`, the SQL statement of `memory.ScopeMatches` that the assembler applies in Go, held to the Go form by a test that runs both over the same rows. It has to be decided in SQL for the reason `scopesConflictSQL` gives: a statement that chooses its own candidate set with a `LIMIT` cannot check scope after that cut, and a passive bucket's `OverFetch` IS its candidate set. Unset, the clause is absent and the block is byte-identical to the one that shipped. The formatted `ghost_memory_search` path does not read that window directly: it asks `Store.Candidates` for a widened untrimmed set and hands it to `assemble.Run`, so the caller's category and scope are applied before the window closes (the window itself is still chosen inside fusion, unchanged) — `internal/assemble` owns every decision after retrieval, and `internal/memory` never imports it. It also owns the RELEVANCE VERDICT (#580): every block is `answerable`, `weak` or `empty` with a reason from a closed set, and the search tool's last line is machine-readable (`[ghost:outcome=… reason=… floor_fts_rank=… abstain_cosine=… candidates=… admitted=… legs=… tokens_est=…]`) with a human abstention sentence for the two non-answerable cases. `weak` withholds nothing — it labels the rows so a caller treats them as leads; the ONLY thing that removes a row for a reason other than a stage is the `response_fit` post-pass, and that is bounded by `Budget.MaxBytes` against the COMPLETE response (`Slice.MaxBytes` is item content; one field cannot bound two units). Arm A (keyword rank 0-3) is on and arm B (a vector cosine) ships OFF, because the bench no-answer report shows the two cosine distributions overlap and no constant separates them — `context.abstain_cosine` is a user's decision, and `abstain_cosine=off` on the line is how a disabled threshold is told from a cosine of zero. An arm applies to a result when it holds a VALUE, not when its leg ran: a leg that answered can have retrieved nothing, leaving every row at the -1 sentinel. A leg that FAILED suppresses the floor outright (`retrieval_partial`); a result with no arm value at all is `no_floor_arm`; a leg that never ran changes neither — the keyword arm still judges keyword-only results, and the leg's state is on the line (`legs=`, `abstain_cosine=not_applied`), never in the reason. An outage is not evidence about the corpus. An empty result whose rows were FOUND and withheld says "no sufficiently trustworthy memory found" and names the cause; only `no_candidates` claims nothing matched, and only that reason is evidence about the store. A leg that never RAN and a leg that ran and FAILED are different facts with different next steps, and the empty branch keeps them apart the way the non-empty one does: the first is `vector_backend_unavailable` (the keyword leg was all that ran), the second is a tool error rather than a verdict (an incident — retry); `legNeverRan` covers both "no embedder" and "this query would not embed", because the tool swallows the embed error and the leg status cannot tell them apart
- Vector scan: both legs are brute force over the project's embeddings, and they run in two phases (`internal/memory/vector_scan.go`, #556). `snapshotVectors` copies every candidate row out of SQLite and returns, holding the store's read lock and its single connection for the copy only; `vectorRows.search` scores the copy afterwards, so the O(corpus × dims) cosine pass — which `ghost supersede` runs once per memory — no longer blocks writers for the length of the corpus. The copy keeps the stored bytes rather than decoding them and the score loop reads the little-endian float32s back out in place (`cosineFromBytes`, bit-identical to `cosineSimilarity` on a decoded vector), and the scope column is parsed only for a row that wins a slot; a `scopeProbe` decides per-row eligibility by checking whether the stored text can mention a requested key at all, which can only save a `json.Unmarshal` and never decides membership, since `ScopeMatches` only excludes a row that names a requested key and disagrees. Ranking keeps a bounded window instead of the corpus — a min-heap whose root is the worst row held, ordered once at the end over at most `limit` rows — and the order is total (cosine descending, exact ties broken by scan position) so the answer is a function of the stored data AND the order the scan yielded it in, not of the heap's internals; that is not independence from the scan order (the query has no ORDER BY, so a VACUUM or index rebuild can reorder a tie), and it does not claim to be — what it buys is that two searches over the same rows in the same order agree, which the unstable `sort.Slice` it replaced did not promise. `TestSearchVectorRankingMatchesTheCollectAndSortBaseline` pins the whole result against a transcription of the pre-#556 collect-and-sort search, and `TestVectorSearchCopiesTheCorpusUnderTheStoreReadLock` / `TestVectorSearchScoresWithTheStoreLockReleased` pin that the copy takes the read lock and the scoring pass does not. A writer is still kept out during the copy, and that is the connection rather than the mutex: OpenDB pins the pool at one, so no amount of lock work lets a write start while a query is streaming. The scratch is recycled through a `sync.Pool` on the store, and an oversized embedding buffer is dropped on return rather than retained. What a query still allocates is the driver: `modernc.org/sqlite` copies every BLOB and TEXT column into a fresh allocation per row, which is why the remaining cost is a decoded-vector cache keyed on `PRAGMA data_version` (and then an ANN index), not more work on the scoring loop
- Vector-space identity: a stored vector is only scored when `memory_embeddings.model` equals the identity this process embeds into (`Store.SetEmbeddingIdentity`, fed from `embedding.VectorIdentity`). A model, dimension or task-prefix change therefore retires the old vectors instead of comparing them with queries from the new space. The rule is read in four places, one per caller: `loadVectorRows` (may a vector enter a search), `GetEmbedding` returning nil (may a stored vector act as a QUERY vector — the link worker and `ghost supersede` both do), `UnscannedEmbeddedMemoryIDs` (may the linker compare this memory yet), `EmbeddingStats` (is it covered, which `ghost mcp status` and `ghost_health` report). A retired vector never hides its memory: the keyword leg still finds it. Two side effects of a rewrite ride along: `StoreEmbedding` clears the row's `link_scans` slot when the identity changes (so the linker re-scans it in the new space — the re-scan ADDs current-space `related` edges alongside the ones the retired space produced; nothing invalidates those old rows, and `CreateLink`'s `MAX(strength, excluded.strength)` upsert means an edge whose new-space similarity is lower keeps its old strength), and the foreign-vector warning in `loadVectorRows` is emitted once per retired identity (a second reconfiguration in the same process warns again). `EmbeddingStats` reports stale and unembedded rows separately so `ghost mcp status` can show both. The identity is opaque (compared, never parsed) and empty means "no model configured", which keeps the bench harness and tests unfiltered
- Memory history: `memory_history` (schema v17, #578) is the append-only CHANGE LOG of how a memory reached its current state — one row per write. The name `memory_provenance` went to a different and later concept (evidence records, several per memory, answering "who or what supports this memory" — see "Evidence provenance" below), so never rename this table to it, and do not treat the two as the same thing; and every writer appends one row in the SAME transaction as the write — `Create`, `Upsert` (insert and the fold's `merge`), `UpdateMemory`, `ReplaceNonManual` (rewrite, reuse, bulk delete), `SetResolved`/`ClearResolved`/`MarkResolved` (the last recording the OPERATOR as performer, and clearing the row's KEEP cache in the same statement as the stamp — the only `resolve` row that can say a person decided rather than a classifier judged), `CreateLink` for a `supersedes` edge and `InvalidateLink` for its withdrawal (`unsupersede` — a memory can be superseded, withdrawn and superseded again, and only the sequence says which claim is live), `RestoreSnapshot`, `ImportMemory`, `Delete`, `PruneSessionMemories` (a `session` row removed by `ghost prune` — the one writer whose row is gone by design, and the reason the audit has to be a tombstone), the decision companion memory and the shipped seeds. Each row is a VERSION, not a diff: the state the memory held once that write landed, so "what did Ghost know at T" is the newest row at or before T (#647) and the prior content is the previous row. `agent`/`session_id` are the PERFORMER (the save/merge/import paths carry a Provenance; the lifecycle passes do not, and an empty field is an admission, not a claim) — which is what makes the issue's "a row changed by two different agents" answerable. `memory_id` deliberately has NO foreign key so a hard delete leaves a tombstone carrying the text the row held; `project_id` does cascade. Growth is bounded in the appending transaction: newest 50 versions per memory, newest 20 000 rows per store (rowid window, since an implicit rowid is max(rowid)+1 and never reused). A write that changes none of a memory's own recorded columns appends nothing (`Touch`, `TogglePin`, the KEEP cache), and a write that moves a memory BETWEEN projects must also move its history rows' project_id or the project-delete cascade takes the past of a memory that survived: `MergeProject` and `PromoteToGlobal` both do (the merge list exists twice on main). A verbatim consolidation re-emission is a NO-OP and appends nothing (#727: it measured at 80% of `memory_history` on a real store, and the per-memory cap was days from evicting real events) — when content, category, importance, tags and scope are all unchanged it writes no row and leaves `updated_at` alone, because `ghost supersede` orients each candidate pair by `updated_at` and `--skip-unchanged`'s fingerprint carries it as a change proxy; a change to any of those five IS a real update and is recorded (`reuseChangesNothing` compares each field by the value the side that produced it carries, an unreadable stored value counts as changed, and importance is compared at the EMISSION's float32 precision (`float32(stored) == emitted.Importance`) because Upsert's strengthen adds in the column's own float64 (with the increment itself bound as a float32) and leaves a value float32 cannot name, so a full-width comparison reported a change on every verbatim keep of a strengthened row and reinstated the flood #727 removed (#750)). TWO writers deliberately repeat the state instead, and neither is a licence to repeat: `ghost prune` appends one per removal and changes no other shape (the backup manifest counts the CORPUS, never the change log, so a tombstone cannot make a post-prune backup fail to verify), and a `supersedes` edge appends a `supersede` row when it BECOMES active, recording a claim about the target's standing rather than a state change. Both spend a slot under the cap, which is what bounds them. Two columns carry the event's other end: `related_id` (the id that replaced a deleted row, or the memory whose edge claims it) and `merged_content` (the text a FoldOnly fold dropped, which no row keeps). `ghost history purge <id>` and `ghost_memory_delete`'s `purge_history` delete a row AND its history in one transaction — the redaction path, because a plain delete keeps the text a memory used to hold — and `ghost_history_content` is the SQL seam where #656's `secret.Detect` will redact content on the way in. A purge reaches a memory that is ALREADY deleted through `Store.PurgeMemoryHistory` (history only, never the row), because the tombstone is the feature and a delete-time purge cannot cover it; the same operation is what frees an id for `ghost import`, which REFUSES an id that still has history rather than splicing two memories' records under it (ids are not reused by Ghost, but a portable artifact carries them verbatim). `migrateV17` backfills nothing, so a pre-v17 memory's first edit files a `baseline` row before it overwrites the text. Read it with `Store.MemoryHistory` (oldest first, rowid order) or `ghost history <memory-id>` `as_of` (RFC 3339) on `ghost_memory_search` / `ghost_project_context` and `--as-of` on `ghost context` is the OTHER reader, and it is the reason the rows are versions rather than diffs: `Store.MemoriesAsOf` takes each memory's newest row at or before T, drops the ones whose newest row is a `delete` tombstone or whose first row is after T, and returns the version's own `content`/`category`/`importance`/`resolved_at`/`source`/`project_id` — one statement, driven by `memory_history` rather than by `memories` (a deleted memory's tombstone is the only surviving record of it, so a read that started from the live tables would report "Ghost never knew this" for a memory it held for months), ranked `ROW_NUMBER() OVER (PARTITION BY memory_id ORDER BY recorded_at DESC, rowid DESC)` with `rowid` as the second key because `recorded_at` is second-precision. A pre-v17 memory with no row at or before T is UNKNOWN, never guessed: it is left out of the set and counted in `AsOfSet.Unknown`, because a shorter set that says nothing about the gap reads as the whole truth — and that "no row at or before T" is TWO time-bounded tests, not one, because an unbounded `NOT EXISTS` asks "does this memory have history at all" and a pre-v17 memory the lifecycle touched after the upgrade does (only `UpdateMemory` files a baseline; every other first write appends a row read out of the memories row in the same transaction, so its text is recorded anyway, and that is why no writer needs a baseline there). The gap half also reaches the TOMBSTONES, because a pre-v17 memory deleted after T has no live row either and its gap is otherwise invisible — and that half must do TWO things, or a memory is counted twice: exclude ids that are LIVE again (because `RestoreSnapshot` reinstates a row under the id it recorded, so "tombstoned" does not imply "not live"), AND rank per memory keeping its newest tombstone (a delete → restore → delete memory holds two delete rows, and `UNION ALL` does not dedup). `CreatedAt` — the field the decay measures an age from — is the row's own when that column can answer and the version's `recorded_at` when it cannot: the row is gone (every column NULL, and an empty `created_at` reads as ~56,000 days, so a memory deleted yesterday sat at the decay floor in every listing covering the past year), or the column is LATER than T (no writer produces that, and it is refused because `ageDays` clamps a negative age at 0, making a future-dated column the most favourable value a row could carry into a ranking of the past). **`as_of` state survives `ghost history compact`, and two metadata fields do not.** For a memory that is still LIVE the answer is read from its `memories` row, so removing a redundant version changes nothing a historical read is *for* — the state columns, the supersede edges and `CreatedAt` all answer as before, and `TestCompactingRedundantVersionsLeavesTheAsOfStateAlone` compares them one at a time. Two fields do move, and only because they NAME which version answered: `VersionRecordedAt` and `VersionPhase` can describe an EARLIER version carrying the same state, so a memory that was resolved and unresolved — or folded — may read as merely saved for an instant whose reflect flood has since been compacted away. That is a documented consequence rather than an accident, and it is the price of removing the flood at all: those rows are exactly what made a past read name a reflect run as the last thing that happened to a memory. A DELETED memory is excluded from the repair instead (rule (6) above), so for one of those neither field moves and the age does not either — which is why that is a scope rule rather than a fourth retention rule. Everything else in `AsOfRow` is the current row, including the validity triple: `valid_from`/`valid_until` in particular are the present's until #575's writers land, as are tags, scope, pin, access count and provenance, which were never versioned — `Retention` is the ONE exception and is always empty, because it postdates the change log and a version has no tier to carry (see "Retention tiers"); the statement does not even name the column, since `ghost context --as-of` opens the store read-only and cannot migrate a store that predates it. **The anchor is the newest version this repair will NOT remove AND whose WRITER moved `updated_at` in the same statement that filed it** — that is, the newest KEPT row in `stampMovingPhases`. It is NOT the newest version that changed its recorded state, and the two are different questions: a `delete` or a state change records what the memory SAYS, and `stampMovingPhases` records what a writer did to the STAMP. The state-change half was this rule's first version and it was wrong in the permissive direction, which is the one that invents. `SetResolved` writes `resolved_at` and says in as many words that it leaves `updated_at` alone; `Upsert`'s unsaturated fold writes `importance` and moves nothing; `RestoreSnapshot` puts the snapshot's own text back. In SQL the anchor is `NOT removable-like AND phase IN stampMovingPhases`, and the parentheses around the first are load-bearing: `historyRemovableLikeSQL` opens with an `EXISTS`, so `NOT EXISTS (…) AND a.phase IN (…)` and `NOT EXISTS (…) a.phase IN (…)` are not the same query, and only one of them is the one anyone is reading. `TestCompactHistoryFixUpdatedAtRestoresTheLastStampWrite` catches it because every memory in it has both kinds of row. - Resolution classifier: `ghost resolve` runs a keyword prefilter, then a deterministic KEEP veto, then batches up to 8 notes per KEEP-biased CLI-harness classify call (`claude`/`opencode`/`codex`/`goose` subprocess, numbered `N: RESOLVED | closed-by: <fact>|KEEP` reply judged by a strict first-field line parser) to mark `resolved_at`, dropping resolved-evidence memories (changelogs, cost estimates, closed experiment notes) from ranked injection while keeping them searchable. KEEP-biased in code, not prose (#640: an independent judge found ~1 resolve in 3 on a real DB had buried durable knowledge): `resolve.VetoKeep` settles a candidate KEEP with no harness call when its text carries an imperative (`never|do not|don't|must|always|required`) or an open marker (`not yet|outstanding|still pending|still open|still stale|unresolved|todo`), all case-insensitive and word-bounded; the rubric asks the fresh-session question (would an agent starting fresh make a mistake, repeat work, or break a rule without this?) and says dates, PR numbers, commit hashes and "fixed in" do not resolve a note; a RESOLVED must carry a non-empty `closed-by:` or the parser reads it as KEEP. The veto guards the classifier only — the supersedes-edge piggyback and correction pairing still demote. Only explicit KEEP verdicts are cached by content hash in `memories.resolve_kept_hash` (schema v7; the v3 hash prefix invalidates the v1 implicit-KEEP and v2 explicit-KEEP caches, so #640's re-judged rules are re-asked); UNKNOWN parse failures remain uncached and are retried, so a converged project makes no calls only after explicit KEEPs. Dry-run writes nothing, `--apply` writes resolved_at and explicit KEEP cache entries; transport or verdict-count failures fail fatally rather than applying incomplete results, while UNKNOWN lines remain eligible for a later pass. `ghost resolve <project> --reassess` is the repair path for the resolutions the pass already got wrong: it re-runs the vetoes and the classifier (no keyword prefilter) over memories that are ALREADY resolved, prints the ones that now come back KEEP, and with `--apply` clears their `resolved_at` via `memory.ClearResolved` and caches the classifier's KEEP verdicts; SCOPE THAT REPAIR with `--only <id>[,<id>...]` (full ids or 8+ character hex prefixes) or `--only-file <path>` (one per line, `#` comments allowed; both may be given, the list is the union) — both are refused without `--reassess`, because the ordinary pass has no resolved pool to narrow, and a scoped report says how much of the project it read ("3 of 143 already resolved judged") instead of describing a pool it never looked at. Scoping narrows WHICH rows are judged and nothing else: every floor below still holds a judged row back. A selector that names nothing (mistyped, another project, or already cleared by an earlier repair) is reported and skipped, never an error for the run; an ambiguous prefix IS an error, because nothing can be said about which rows were meant. #698 measured why: an unscoped repair over a real store proposed un-hiding 143 memories and an independent judge sampling 40 found ~35% stale (completed changelogs, PR/host snapshots, notes a newer memory had superseded, a retired code path). `ghost supersede --reassess --apply` therefore prints its own follow-up — the exact `ghost resolve <project> --reassess --only <ids> --apply` over the withdrawn edges' targets — and writes the same id list under the data dir's scratch (`scratch.Root()`, `supersede-reassess-<project>-<ts>.ids`) for `--only-file`; a dry run prints neither, because it withdrew nothing and resolve would refuse the command while the edges are live. The repair path is also the only place `VetoKeep` does not settle KEEP by itself: when the same project holds a NEWER unresolved memory sharing >=2 of the note's key identifiers — a backticked span, an `#NNN` reference, a file name, a host name (`resolve.keyIdentifiers`, `subjectIndex.shadowing`; NOT a bare number or a version, which are what changes when a note goes stale) — the note goes to the classifier instead, because a veto protects a phrase and not a claim. The pool is `ResolveCandidates` for the correction floor's reason: a memory that is itself resolved is a row the next ordinary pass will not see. `Run`'s veto is unchanged, and the asymmetry is why: there a false veto keeps a note OUT of the resolution (one noisy memory, a later pass can still bury it), here it un-hides one permanently; a failed clear is fatal, a failed cache write only warns; `memory.ClearResolved` runs every batch in one transaction so "a failed clear repaired nothing" is literally true. It honours Run's two free demotions as a floor — a row a live `supersedes` edge still asserts, or an older row a NEWER *unresolved* correction pairs with (the same pool Run searches, via `correctionPairTargetsFrom`), is counted as `Demoted` and left resolved, because Run fires both before the veto and the KEEP cache, so clearing it would report a repair the next pass undoes. The pairing is re-checked after the re-KEEP set is known (`holdBack`), because a correction that is itself repaired leaves the resolved pool and would re-assert its pairing; both the floor and the hold-back pair only Run's keyword-prefiltered subset, since a keyword-free row is never a pairing target and holding it would be a permanent, mislabelled hold no later pass could undo. THE RE-CHECK READS THE POOL THE NEXT ORDINARY PASS WILL READ — the unresolved pool PLUS the rows this run clears — and uses it for BOTH the frequency count and the correction search, the two jobs `Run` gives its own `ResolveCandidates` pool (#712). Counted over the live pool alone, a row this run clears is missing from the count, so its subject tokens look rarer than the next pass will find them and a pairing the next pass will NOT make holds a row back for a second, identical pass to release. So the re-check ITERATES, bounded at `maxHoldBackRounds` (8): holding a row takes it back out of that pool, which lowers the frequency of the tokens it carries, which can turn a token rare that was not and reveal a pairing the previous round was blind to. WHAT TERMINATES THE LOOP IS NOT THE PAIRINGS, and the difference matters: a held-back row leaves the pool the re-check reads, and that pool is BOTH the frequency pool and the correction pool, so dropping a row does two OPPOSITE things — it lowers the document frequency of the tokens the row carries, which can reveal a pairing the round before was blind to, AND, when the row is correction-marked, it removes every pairing that row was asserting. A later round can therefore report FEWER pairings than the round before it (`TestHoldBackPairingsAreNotMonotoneAcrossRounds` is the case that does), and the ONLY termination invariant is that every round which finds anything removes at least one row from the repair set, which bounds the loop by `len(repair)` however the pairings move. So `maxHoldBackRounds` caps the WORK ONE RUN DOES, not safety: with it and without it the re-check ends, and what changes is whether one run reaches its fixed point or leaves work for the next. Dropping is ONE-WAY — a row held is never re-added, and a held-back correction therefore cannot free its row again — precisely because the pairings can retreat, and without that rule the answer would depend on how they moved between rounds and the LAST round would win rather than the union. A bound reached WITH a row still changing is a finding and not a truncation: `ReassessResult.Rounds`/`BoundHit` carry it and `reassessRoundsLine` prints its own sentence (“a further pass may clear more”), because a run that iterated is reporting an answer no single re-check would have given. Printed ONLY when there is something to say — more than one round, or the bound reached — since a line an operator learns to skip is a line that stops being read when it matters. No round re-asks the harness: the iteration is over the hold-back decision alone, on verdicts the run already holds, because a re-ask is billed work for an answer in hand. THE FLOOR DELIBERATELY STAYS THE CONSERVATIVE ONE, drawing its corrections only from the live pool, so it may over-hold a row the re-check releases — the right way round, because an over-held row is left resolved and REPORTED with a reason an operator can check, while an under-held one is cleared and immediately re-stamped by the pass that follows. EVERY HELD ROW IS NAMED, not counted: `ReassessResult.Held` (one entry per row, in pool order) is printed by `reassessHeldLines` as `held by supersedes <source-id>` or `held by correction <id>`, because the two reasons need different remedies — a live edge is undone by `ghost supersede --withdraw`, a correction pairing is undone by nothing and can only be READ — and `Demoted` is `len(Held)`, so the summary count and the list under it cannot disagree. A request is settled before anything is written and a refusal writes NOTHING, not even the refs that were fine (`TestMarkRefusesAnAmbiguousPrefix` marks neither of two refs when one is ambiguous), and the per-row outcomes are three SEPARATE states rather than one "not marked" — `AlreadyResolved` (the issue's no-op: a memory the previous pass already buried, on which nothing is written including NO history row, because a history row records a write), `Pinned` and `ExemptCategory` (the store's guard, whose refusals have different remedies) — each counted on `MarkResult` off the same rows the report prints, so a count and a list cannot disagree. Only rows IN THE PROJECT may be marked, and that is checked on the READ that can see `project_id`, before any write, because `MemoryIDsByIDPrefix` reaches `_global` for the supersede endpoints' sake and a row every project shares is not one a project asked to bury; the store binds the project AGAIN in the same statement as the stamp, so a caller reaching the store directly cannot cross it either, AND refuses the `_global` SENTINEL beside the empty-project refusal — the binding does not catch it (a promoted row's own project_id IS `_global`, so naming `_global` satisfies every predicate MarkResolved has), and it is refused at the STORE layer rather than re-derived per caller, like every other `_global` refusal here. The report's per-row marker defaults to the NEGATIVE claim under `--apply`, never the success, because the eligibility guard is re-checked WHERE THE WRITE HAPPENS and a row pinned or recategorized between the read and the write is declined SILENTLY (another process's decision, not a failure) — a state the result says nothing about, so a default of `marked` would report a change that did not happen. `MarkedMemory.Declined` names it, `MarkResult.Declined` counts it, and both the CLI report and the MCP result fall through to `not marked` for any state they do not recognise, so a state added tomorrow reads as unwritten rather than written.  `Store.MarkResolved` is a separate method rather than a `SetResolved` wrapper for two reasons: it BINDS the project (the pass's ids are already project-scoped by the selection it made), and it RECORDS the performer, so the `resolve` history row it writes is the only resolve row that can say a PERSON decided rather than a classifier judged — which is the whole reason this is a command and not SQL, since the SQL route bypasses `memory_history` entirely and leaves the record showing a memory resolved with nothing saying who said so. It also drops `resolve_kept_hash` in the SAME statement as the stamp, or a later pass would skip the row as `N KEEP cached` and a memory buried on purpose would return the moment anything rewrote its text (#714's second effect). Unlike `supersede.Withdraw` there is NO partial outcome to report: the stamp, the cache clear and the history row are ONE transaction (`TestMarkHistoryAndStampLandInOneTransaction` drops `memory_history` and requires that `resolved_at` not survive), so an error returns NO ids — returning the ones it had collected would claim a stamp the rollback undid. Its inverse is `--reassess --only`, and every applied run prints that command through internal/followup, scoped to the ids it stamped and never to the project. The MCP `ghost_resolve_mark` calls the same core through a `markCapableStore` separate from `resolveCapableStore` — that one must never be able to reach the other direction — and its result names the inverse as a CLI COMMAND, because there is no MCP surface for CLEARING a resolved_at (`ghost_resolve` is the forward pass) and an agent with no shell should be told so rather than pointed at the tool that would bury more memories. Never invoked from the stop hook's synchronous path (that path forbids DB access); the stop hook's detached `ghost lifecycle` spawn (whose resolve phase runs `--apply`, never `--reassess`) and the standalone batch command are the only callers. See `docs/superpowers/specs/2026-07-26-resolution-classifier-design.md`.
- Classifier backend: `resolve`/`supersede` classify via the calling session's own CLI harness — the backend is picked from the MCP client's reported identity (an opencode session uses the opencode binary, claude uses claude, etc.) via `ai.SourceProvider`, or — on the headless CLI path — from `--source`, else `ai.DetectSource()` (env markers plus process ancestors); if no calling harness can be determined it fails fast with an actionable error. There is no claude-first cascade: `NewSourceProviderForSource("")` is unavailable, and `ai.CLIProvider` is an availability probe only. MCP sampling was retired from this path per SEP-2577 — see `docs/superpowers/specs/2026-08-24-resolve-sampling-path-design.md`.
- Lifecycle spawn guards: the stop hook spawns the reflect→resolve→supersede chain behind TWO independent per-project guards. `AcquireLifecycleLock`'s PID file says "a run is not already in progress"; `lifecycle.min_interval` (default 30m, `0` to disable) says "a run did not start too recently". The second is the mtime of `lifecycle-<project>.last` in the data dir — a file, not a row, because the stop hook's synchronous path forbids DB access. Only the `ghost lifecycle` process writes it (`mcpinit.TouchLifecycleStart`), and only once it has passed every precondition that can exit non-zero, so a run that dies before doing any work does not burn a window. Most unknowns read as "run" (no stamp, unreadable, non-regular) so that a bookkeeping problem cannot silently stop maintenance; a stamp dated in the FUTURE is the deliberate exception and reads as INSIDE the window, because a future date is not evidence the window expired. `config.LifecycleConfig.MinIntervalDuration` resolves an unreadable value to the default rather than `0`, because `0` means the cooldown is off.
## Key pattern: no harness child gets a tool

A harness child is given a **minimal environment AND no tool surface**, because
its prompt is memory text and memory text routinely carries third-party content.
The environment half is `harnessEnv`'s explicit allowlist; this is the tool half.
The rule is per-harness because the mechanism is, and the mechanism is whatever
that harness's own CLI documents — never a guessed flag.

**Every harness argv is a WHOLE-SLICE GOLDEN**, not a per-flag grep. A grep passes
when the flags it checks are present and says nothing about a flag that was never
added, which is exactly how goose shipped with an entire tool surface unchecked.
Each argv is built by a named function (`claudeInvocationArgs`,
`codexInvocationArgs`, `gooseInvocationArgs`, `openCodeInvocationArgs`,
`openCodePolicyFor`) so the whole slice is assertable;
`TestHarnessInvocationArgsAreGoldens` covers all four harnesses including both
opencode major versions, because V1 is the only shape that takes `--pure` and the
only one eligible for the deny policy.

A golden cannot check a flag against its upstream, so the shell-fake
harness-policy tests re-check what actually reaches the child, and two of them
cannot be checked by a fake at all. A fake that reads `$GOOSE_MODE` out of its own
environment proves only that Ghost WRITES the string — not that the harness accepts
the value, ranks it above its own config file, or acts on it. So the two upstream
facts this policy rests on have `GHOST_LIVE_TESTS=1`-gated tests that run the real
binary, pick a command that makes no LLM call, and report rather than assert where
the honest answer is "cannot settle".

**claude** is the only harness whose CLI can remove tools outright.
`claudeInvocationArgs` requires five capabilities probed from the INSTALLED
binary's own `--help` (`--tools`, `--disallowedTools`, `--safe-mode`,
`--restricted`, `--strict-mcp-config`) and REFUSES to run without them — a claude
that lacks one gets an error naming the upgrade, never a silently weaker policy.
`--tools ""` is the restriction (claude's own "disable all tools" spelling, which
unlike a list of names covers a tool shipped later). The child test walks its own
argv to assert the value is EMPTY, because `"$*"` renders a missing value and an
empty one identically — and a tool name there is both a grep hit and an open tool.

**codex has NO "no tools" flag.** `--sandbox read-only` bounds what a tool may do,
not which tools exist, so the policy is a list. Both exec tools are named
(`features.shell_tool` AND `features.unified_exec`) because codex registers either
the unified PTY-backed tool or the one-shot exec, and disabling one leaves the
other. `view_image` is named because it is a plain local file read the sandbox's
write policy does not cover. The plugin and connector group (`apps`, `plugins`,
`tool_suggest`, `skill_mcp_dependency_install`) goes together because each
contributes a tool of its own and installing an MCP server on demand RUNS A
COMMAND. `agents.enabled` and the top-level `web_search="disabled"` are not
feature keys, so `features list` says nothing about them and they are never
filtered.

**The codex list is filtered against the installed binary and NEVER refuses.**
`codexFeaturesFor` probes with `codex features list`, keyed on path/size/mtime by
a `sync.Map` exactly as claude's capability probe is, and caches the result. The
negative verdict is cached too, for `codexFeatureRetry` (5 minutes), and that
asymmetry is the point rather than an oversight: an unanswering codex is the
OLD-codex install this design exists to support, so probing it per call would add
a process to each of a lifecycle's hundreds of calls — the doubling the cache
exists to prevent, for the whole run. Caching the negative for the life of the
process is the opposite failure, because a codex upgraded in place under a
long-lived MCP server would never be noticed. A positive answer does not expire at
all.

**Both capability probes are SINGLE-FLIGHTED on a cold cache.** `codexFeaturesFor`
and `claudeCapabilitiesFor` each pair their per-identity `sync.Map` with a
`singleflight.Group` keyed on the SAME identity (`codexBinaryID`/`claudeBinaryID`
`probeKey`, built from the same three fields the cache key compares), so N
concurrent first-callers run ONE child process and all receive that probe's answer.
The cache alone cannot do this — it is check-then-probe, so every caller arriving
before the first one stores ran its own (measured: 50 spawns for 50 callers). A
`singleflight.Group` rather than a per-key mutex map because the two differ on the
FAILURE path, which is the whole difference: a mutex map serializes the burst, and
since a failed claude probe is deliberately NOT cached, each follower would take
the lock, find the cache still empty, and probe again — N processes, the bug rather
than a fix for it. The group shares the concurrent call's outcome whether it
succeeded or not, and retains NOTHING of its own, so the caches above keep owning
retention exactly as documented: a positive is kept for the life of the process, a
negative expires at `codexFeatureRetry`, a failure is never stored, and the
warn-once latches are untouched. The freshness test for codex therefore lives in
`codexCachedSupport` rather than at the lookup, because it is now read from two
places and a check-then-probe pair with that test in only one of them is how a
long-lived parent stops noticing a codex upgraded in place. The mutex-map argument
is CLAUDE'S, and codex is the case that would survive without the group:
the flight caches a verdict the probe could not REACH, so a per-key lock would
leave each follower a fresh negative to return. (A verdict reached under a DEAD
context is the one that is not cached — a cancellation, not an answer — which does
not change this.) Both use the same mechanism, chosen once, rather than a claim each
probe needs a guarantee it lacks.

**A caller's own context still governs its own call.** `Do` blocks on the leader's
flight and never consults the follower, so both probes use `DoChan` and `select` on
`ctx.Done()`: a caller whose context is dead reports its own error instead of waiting
out a verdict it cannot use — and on claude that error REFUSES the whole harness
call. The other half is that a leader whose context dies must not fail the followers
whose contexts are fine, or hand them its negative: in the long-lived `ghost mcp`
server one disconnected client would fail every concurrent turn in the burst. The
follower cannot tell those cases apart, because `exec.CommandContext` kills the child
and `Wait` reports `signal: killed`, never the context error — so the leader MARKS its
own failure (`probeContextError`, `internal/ai/probe.go`) and a live follower goes round
AGAIN, re-entering the same `singleflight.Group` under its own context. Re-entering the
group is load-bearing on the retry: a direct re-probe would restore the #741 burst (one
child per follower) on the rare path out of a common one, and re-reading the cache would
not do it either, because the followers all arrive within microseconds of each other and
would all miss it. Each round consumes one more cancellation, so rounds are bounded by
the callers sharing the key, and a caller whose OWN context is dead leaves without looping
— `isSharedProbeCancellation` requires a live `ctx`, and both arms of the select check it.
The converse is not treated as shared — a leader sees the same marker, and a dead caller
must not start a fresh attempt under a dead context, which is why
`isSharedProbeCancellation` requires a LIVE `ctx` as well as the marker.

**A cancelled caller leaves NOTHING behind.** The negative a killed probe produces says
more about the caller's connection than about the codex, so the flight inside
`codexFeaturesFor` stores the verdict of `probeCodexFeatures` only while THAT caller's
context is alive, and marks the flight instead when it is not. The store lives in the
flight rather than in the probe because the decision needs both facts at once — is the
answer worth keeping, and was the caller that produced it still alive — and a
check-then-act split across two functions disagrees with itself in the window between
them. It is measured on the CALLER's context and not on `probeCtx`: a probe that hit
its own 10s cap also knows nothing, and that one IS cached, for `codexFeatureRetry`,
because an unanswering codex is the install this design supports. Nothing was cached by
the round that died, so the next round's re-read misses and a live caller really does
re-probe rather than inherit the negative. For the same reason a caller that stopped
waiting gets no `warnOnWeakerCodexPolicy` at all (`CodexClient.run` checks `ctx.Err()`
first): nothing was learned about the codex, so the placeholder it was handed is not a
probe result, and reporting it would fire the `unverified` WARN and CONSUME its
once-per-process latch — silencing the real diagnostic for the rest of a long-lived
server, over the one turn that lost the most information.

**Both arms of the probe's `select` check the caller's own context.** When a caller's
context is already done AND the flight channel already holds a result, both `select` cases
are ready and Go picks between them at random, so a dead caller leaves by the flight arm
about half the time. The flight arm therefore re-checks `ctx.Err()` before it treats a
result as this caller's answer, rather than leaving the outcome to a coin — otherwise a
caller whose context died while the probe was running would report the leader's success
(or its kill) as its own, which is the one outcome the `ctx.Done()` arm exists to prevent.

The filter matters because codex **silently IGNORES** a `-c` key it does not know
(the fail-OPEN direction): `-c` overrides are applied onto the config tree without
a `deny_unknown_fields` check, so a key renamed upstream leaves the tool on and
the call still succeeds. `--strict-config` is the strict reading, it is opt-in, and
Ghost does not pass it, so `TestLiveCodexDeclaresTheNoToolFeatureKeys` provokes an
unknown key and reports which way the installed codex actually goes.

Probe output is validated by SHAPE before it is believed: one line must parse as
`<key> <known codex stage> <bool>`. A positive verdict is cached for the life of
the process, so a header row, a footer count or a single stray token read as an
answer would strip all ten overrides permanently and the only signal would be one
WARN. The test is deliberately NOT an overlap check against the policy's own key
list: a real codex older than this policy answers with a full table naming
features Ghost has never heard of and none of the ten it disables, and that is a
genuine weaker policy rather than an unreadable answer, so the two need different
warnings and only one of them means a tool is on.

`warnOnWeakerCodexPolicy` fires ONCE PER PROCESS **PER VERDICT** — two latches,
not one, because the two messages are not interchangeable and the suppressed one
is the more informative. The reachable order is a long-lived MCP server whose
first probe fails while the binary is mid-upgrade (unverified), after which the
`codexFeatureRetry` re-ask returns a real answer naming the missing keys; a shared
latch would drop the second, and that is the one which says which surfaces are on.
A probe that cannot answer says "unverified" rather than accusing the codex of
lacking features it was never asked about. The refusal is the part deliberately
absent, and the reason is which failure is larger: codex is selected with **no
version floor anywhere** — `CLIProvider` picks it by `exec.LookPath` below claude
and opencode, and a session-routed client names it as its backend with nothing
checked at all — so refusing would fail that session's reflect, resolve and
supersede calls on a working install over a surface that may not exist. The
failure the policy prevents is a tool that is already absent; the failure a refusal
creates is a lifecycle that does not run at all. An older codex therefore gets the
keys it understands, a weaker policy than a current one, and a warning that says
so.

The cache key is `{path, size, modTime}`, not the path alone, and an independent
review deleting the other two components passed the whole suite — so
`TestCodexProbeIsRekeyedWhenTheBinaryChanges` now rewrites a real executable in
place and requires a second probe. The limitation that test does NOT solve: codex
is commonly an **npm shim**, and the identity observed is the shim's, not the
vendor binary's. A real binary replaced behind a byte-identical, mtime-stable shim
is invisible to this key, and to every one like it in this package.

**opencode has no disabling flag either** — `run`'s only permission flag is
`--auto`, which moves in the WRONG direction and is never passed. The policy is a
permission deny/ask in the isolated config Ghost already writes, and the WILDCARD
is what makes it total: opencode defaults every unset permission to `allow`, so a
name it adds later is covered by `*` on the day it ships rather than the day
someone remembers it. V2 must use `ask` (a non-interactive `run` auto-declines
each ask) because a deny rule or a disabled tool strips tools from the request and
the free tier answers that with 403 `provider.auth`; V1 keeps `deny` since its
non-interactive ask behaviour is unverified.

**goose has NO flag for this at all** (its extension options only ADD extensions;
`--no-profile` governs the profile, not plugin discovery), so the restriction is
the `GOOSE_MODE=chat` environment variable goose's own reference documents as
"chat only, no tool calls", against a default of `auto` (approves tool calls). It
is SET rather than inherited, and `GOOSE_MODE` is deliberately absent from the
goose allowlist, because an inherited value could only weaken it while dropping it
returns the child to goose's autonomous default.

**Residuals, named rather than papered over.** codex's `apply_patch` has no
disabling flag or key (its registry entry is gated on the model catalog, and
`apply_patch_freeform` is marked Removed), so the read-only sandbox is its boundary
and a write attempt is refused rather than the tool withheld; the same holds for
codex's skills-extension read/list tools, which are off unless a skill exists and
the child's working directory is a neutral scratch dir holding none.

On the goose side two questions are open, and they are different in kind. Whether
`chat` mode SUPPRESSES EXTENSIONS in a given build is a property of the binary
that no configuration-printing command reports, so it is documented as unverified
rather than claimed as tested. Whether `chat` mode is COMPATIBLE WITH A HEADLESS
`goose run` is the question that decides whether this policy breaks the goose
backend at all, and `TestLiveGooseRunsATurnInChatMode` runs the production argv
under the production environment to answer it — behind `GHOST_LIVE_TESTS=1`,
because a real turn costs a model call. So the mode is confirmed end-to-end only
where goose is installed and a provider is configured, and not in CI.
